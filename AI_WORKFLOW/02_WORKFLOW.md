# AI 协作工作流规范

> ⚠️ **重要提醒**：所有评审环节严禁跳过！即使功能简单，也必须完成正式评审。
>
> - 需求评审：必须有明确的通过/不通过结论
> - 设计评审：必须检查技术选型和实现计划
> - 代码评审：必须调用 `superpowers:requesting-code-review` 技能
> - 违者：代码回退 + 重新走评审流程

所有开发任务必须严格遵循以下工作流流程。

---

## 快速通道（适用于简单需求）

满足以下条件的简单需求，可跳过架构设计阶段：

- [ ] 仅涉及 1-2 个文件的修改
- [ ] 无数据库结构变更
- [ ] 无 API 接口设计
- [ ] 无多模块交互

**快速通道流程**：
```
需求启动 → 需求评审 → 计划制定 → 开发 → 代码评审 → 测试 → 重构验证
```

---

## 技能选择决策树

```
用户指令类型判断：

"继续执行" / "开始 Phase X" / "执行已有计划"
  → 直接进入【阶段三：开发与交付】
  → 调用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans`

"我们要做 X" / "我想实现 X" / "新需求" / "添加功能"
  → 进入【阶段一：需求与计划】
  → 调用 `superpowers:brainstorming`

"修复 Bug" / "排查问题"
  → 调用 `superpowers:systematic-debugging`

"代码审查" / "评审"
  → 调用 `superpowers:requesting-code-review`
```

**注意**：
- 严禁在已有设计/计划的情况下重复调用 brainstorming
- 简单需求走快速通道，但必须完成评审
- 复杂需求必须走完所有阶段

---

## 阶段一：需求与计划

### 1. 需求澄清

- 需求分析师调用 `/superpowers brainstorm` 明确需求边界
- 如果需求过于简单，可直接进入PRD编写

### 2. PRD编写

需求分析师在明确需求后，编写 PRD 文档：
- 存储位置：`docs/superpowers/specs/YYYY-MM-DD-<需求名称>.md`
- 必须包含：产品概述、核心功能列表、验收标准

### 3. 需求评审

管理者调度【需求评审员】审查 PRD：
- 如果评审不通过，打回给【需求分析师】修改，并附上评审意见
- 如果评审通过，在 PRD 顶部标记 `[REVIEWED: PASS]`，进入计划制定

### 4. 计划制定

需求分析师调用 `/superpowers:write-plan` 生成实现计划：
- 存储位置：`docs/superpowers/plans/YYYY-MM-DD-<需求名称>.md`
- 等待用户确认计划
- 计划中需明确是否需要 UI/UX 设计

---

## 阶段二：系统设计

本阶段包含两条并行流程：架构设计（必选）+ UI/UX 设计（可选）

### 5. 架构设计（必选）

#### 5.1 方案探索

管理者调度【架构师】。架构师**必须**先调用 `/superpowers:brainstorm` 技能：
- 探索至少 2 种技术方案
- 分析各方案的优缺点（性能、成本、扩展性）

#### 5.2 技术设计文档

方案确认后，架构师调用 `/superpowers:write-plan` 产出详细技术实施计划：
- 存储位置：`docs/TECH_DESIGN.md` 或 `docs/superpowers/plans/`

#### 5.3 设计评审

管理者调度【设计评审员】对技术设计文档进行严格审查：
- 评审重点：技术选型是否合理？数据库设计是否满足需求？接口设计是否完整？
- 如果评审不通过，打回给【架构师】重构设计
- 如果评审通过，在文档顶部标记 `[DESIGN_APPROVED]`

---

### 6. UI/UX 设计（可选，仅当计划阶段确定需要时执行）

#### 6.1 UI/UX 设计

管理者调度【UI/UX 设计师】。设计师调用对应技能，产出高保真 UI 设计规范和原型：
- 存储位置：`docs/UI_UX_DESIGN.md`

#### 6.2 UI 评审

管理者调度【UI 评审员】对 UI 设计稿进行严格审查：
- 评审重点：交互流程是否合理？视觉规范是否一致？用户体验是否达标？
- 如果评审不通过，打回给【UI/UX 设计师】重构设计
- 如果评审通过，在文档顶部标记 `[UI_APPROVED]`

---

**注意**：如果同时存在 UI/UX 设计和架构设计，需两者都通过评审后才能进入开发阶段。

---

## 阶段三：开发与交付

### 7. 前后端并行开发

- **前端开发**：基于通过评审的 UI 设计稿进行前端开发
- **后端开发**：基于通过评审的架构文档开发 API 接口

**前置条件**：
- 前端组需要 UI 设计稿通过评审后方可开始
- 后端组需要架构设计通过评审后方可开始
- 双方需协商确定 API 接口规范后再进行开发

### 8. 联调与测试

当前端和后端各自完成开发后，进行联调测试：
- 验证 API 接口与前端调用是否匹配
- 验证功能是否符合 PRD 需求
- 修复联调中发现的问题

### 9. 代码评审

联调测试通过后，管理者调度【代码评审员】。评审员调用 `superpowers:requesting-code-review` 技能进行审查（使用 `superpowers:code-reviewer` 子代理类型）：
- 如果发现严重问题，直接打回给相应开发组修复
- 审查通过后，标记 `[CODE_REVIEWED: PASS]`，进入自动化测试阶段

### 10. 自动化测试

代码评审通过后，管理者调度【自动化测试工程师】执行测试：
- 运行现有测试套件
- 针对新功能编写端到端测试
- 输出测试报告

如果测试失败：
- 阻塞发布，打回给开发组修复
- 修复后重新运行测试

测试通过后，进入重构验证阶段

---

## 阶段四：重构验证

### 11. 重构验证

代码变更或重构后，必须按照 `AI_WORKFLOW/04_REFACTOR_CHECKLIST.md` 进行验证：
- 页面加载验证
- 前后台导航验证
- 路径规范检查
- 验证通过后方可提交部署

---

## 阶段五：技术债务处理

### 12. 技术债务记录

在开发过程中发现的不在原始需求范围内的代码问题：
- 记录到 `docs/technical-debt.md`
- 包含：问题描述、发现位置、建议修复方案

### 13. 技术债务处理

定期（如每两周）批量处理技术债务：
- 评估影响范围
- 安排到迭代计划中
- 修复后从清单中移除

---

## 评审检查清单（强制）

每个开发任务必须完成以下评审方可进入下一阶段：


| 阶段 | 评审项 | 标记格式 | 负责人 |
|------|--------|----------|--------|
| 需求阶段 | 需求评审 | `[REVIEWED: PASS]` 或 `[REVIEWED: REJECTED]` | 需求分析师 |
| 设计阶段 | 设计评审 | `[DESIGN_APPROVED]` 或 `[DESIGN_REJECTED]` | 架构师 |
| 开发阶段 | 代码评审 | `[CODE_REVIEWED: PASS]` 或 `[CODE_REVIEWED: REJECTED]` | 代码评审员 |
| 测试阶段 | 测试评审 | `[TEST_PASSED]` 或 `[TEST_FAILED]` | 自动化测试工程师 |

**注意**：未完成评审标记的任务，禁止进入下一阶段！

## 附录：输出路径规范

| 文档类型 | 输出路径 | 命名格式 | 生成角色 |
|----------|---------|---------|---------|
| PRD 需求文档 | `docs/superpowers/specs/` | `YYYY-MM-DD-<需求名>-PRD.md` | prd_writer |
| 需求评审报告 | `docs/superpowers/specs/` | `*-review.md` | prd_reviewer |
| 技术设计文档 | `docs/superpowers/plans/` | `YYYY-MM-DD-<功能名>-design.md` | architect → writing-plans |
| 实施计划 | `docs/superpowers/plans/` | `YYYY-MM-DD-<功能名>-实施计划.md` | architect → writing-plans |
| 代码评审报告 | 项目根目录 `mupc/` | `PHASE<X>_CODE_REVIEW.md` | code_reviewer |
| 测试报告 | `docs/` | `*-test-report.md` | qa_engineer |
| UI/UX 设计 | `docs/` | `UI_UX_DESIGN.md` | ui_ux_designer |

**路径原则**：
- `specs/` = 需求相关文档（What）- PRD、需求评审
- `plans/` = 技术/实施相关文档（How）- 设计、实施计划
- 评审报告与被评审内容同目录
