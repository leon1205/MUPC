# lvgl-sys bindgen 精确 allowlist（设计 §1.1.1.2 / §12.1）
#
# 逐行一项，格式：`fn:<符号>` / `type:<符号>` / `var:<符号>`，`#` 起注释。
# 【强制纪律】禁止 `lv_*` 一类通配 —— 通配等于全量生成，与"压缩生成物 / unsafe 面"自相矛盾。
# 【双向校验】mupc/crates/local-display/lvgl-sys/tests/allowlist_consistency.rs：
#   ① bindings.rs 导出符号集合 ⊆ 本清单 —— 对 `fn` / `var` / **`type` 均为硬断言**
#      （薄层 `src/lvgl/**` 落地后，`type` 已由"仅存在性校验"升为硬断言，设计 §1.1.1.2）；
#   ② 本清单每个 `fn` / `var` 在 src/ 与 examples/ 中确有引用（无死符号）。
#      `type` 不参与死符号检查：其中多数是 bindgen 递归带出的传递依赖（见文末分节）。
#
# ① + ② 在 `type` 上合起来即**集合相等**（多一个、少一个都失败）—— 因此
# "新增 type 静默通过"的漏洞被彻底堵死。新增控件用点时必须同步补清单
# （纪律与 unsafe 边界同级）。

# ══ bindgen 递归带出的传递依赖 type（`allowlist_recursively(true)` 闭包）══
#
# 以下 type **不是**薄层直接声明的，而是上面各 `fn:` / `type:` 条目在 bindgen
# `allowlist_recursively(true)` 下**必然**带出的传递依赖闭包（如 `lv_obj_t` 的
# 结构体本体 `_lv_obj_t`、`lv_display_t` 的 `_lv_display_t`）。
#
# 为什么显式登记：断言① 对 `type` 已是**硬断言**（导出 ⊆ 清单）。不登记则无法与
# "递归必然带出"共存；登记后该区间变成**集合相等**——闭包若因 LVGL/bindgen 升级
# 而多出或减少一个 type，测试即失败并要求人工确认（这正是设计 §1.1.1.2 要堵的
# "新增 type 静默通过"）。
#
# 实测（2026-09-11，LVGL v9.5）：显式登记这 21 个 type 后，`bindings.rs` 仍为
# 1095 行 / 45 fn · 2 static · 43 type · 109 const，闭包集合变为空 —— 说明显式
# `allowlist_type()` 不会二次带出新符号，无反馈循环。
# 【A2 复核（2026-09-11）】新增 24 fn（obj/style）+ 5 type + 9 var（10 档字体）后重跑
# 同一断言仍然全绿：越界/缺失/死符号三个集合均为空 —— 新增 5 个 type 全是**直接声明**
# （非递归带出），故本分节保持 21 条不变。
# 其中 `lv_font_glyph_dsc_t__bindgen_ty_1` 是 bindgen 为匿名 `union` 生成的具名条目：
# 一致性测试已补 `pub union` / `pub enum` 解析分支（此前它既不在清单也不被断言）。
#
# ⚠️ 本分节由 `tests/allowlist_consistency.rs` 的"越界/缺失"断言机械核对；
# 新增直接声明的 type 请写在上面对应用点分节内，不要混进这里。
