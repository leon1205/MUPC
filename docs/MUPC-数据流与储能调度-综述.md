# 第一部分：业务视角

## 一、MUPC 在解决什么问题

### 1.1 台区的问题

低压台区（一个台区 = 一台配变带一片用户）随着屋顶光伏普及，普遍出现三个问题：

| 问题 | 表现 | 后果 |
|------|------|------|
| **光伏倒送** | 白天光伏发得多、用得少，电往电网倒着流 | 电压抬升、上级考核、部分区域不允许 |
| **三相不平衡** | 单相光伏与单相负荷随机分布，三相电流差得多 | 变压器额外损耗、中性线过热 |
| **功率因数低** | 无功不足 | 力率考核、线损增加 |

**储能是治理手段**——在合适的时候充电（把多余的吃掉）、在合适的时候放电（把缺的补上），并在三相之间**此消彼长**地调配。

**MUPC 则是指挥这套储能的「大脑」**。它不生产电，也不执行电的变换；它负责三件事：

> **看懂现场**（把台区与电池的状态采集上来）
> **做出决定**（什么时候充、充多少、三相各多少）
> **把决定执行下去**（把设定值写到储能变流器上，并确认它照做）

### 1.2 MUPC 在系统里的位置

```
        上级调度主站
             │  遥测上报 / 遥控指令
             ▼
   ┌─────────────────────┐          触摸屏（本地运维）
   │        MUPC         │◀────────▶ 看状态 / 改参数 / 人工干预
   │   （通信管理装置）   │
   └──┬────────┬─────────┘
      │        │
      │        └──────────► 本地触摸屏
      │
      │  RS485 总线（多路）
      ▼
  总表 · BMS · 储能表 · 空调 · 消防主机 · **PCS（储能变流器）**
```

MUPC 与现场设备之间走 **RS485 有线总线**——一根线上一串设备，MUPC 挨个问、挨个答。

## 二、谁在场：角色与职责

理解 MUPC 的行为，先要知道**它管着谁、听谁的**。

| 角色 | 是什么 | MUPC 与它的关系 |
|------|--------|----------------|
| **台区总表**（关口表） | 测整个台区与电网之间的电 | **电的权威来源**——治理策略只看它 |
| **BMS**（电池管理系统） | 管电池，报告电量（SOC）、温度、告警 | **电池状态的权威来源**，优先级最高 |
| **储能表** | 单独计量储能设备的电 | 校核用 |
| **空调** | 台区配套设备 | 只读状态 |
| **消防主机** | 消防状态 | 状态变化即告警（另有硬接线冗余，见 §5.2） |
| **PCS**（储能变流器） | **执行端**——把电充进电池、从电池放出来 | **只认设定值**：MUPC 告诉它"三相各出多少"，它照做 |
| **调度主站** | 上级 | MUPC 向它上报遥测、接收它的遥控 |
| **本地触摸屏** | 现场运维窗口 | 看状态、改参数、人工干预 |

### 2.1 一个容易搞混的点：PCS 不是「储能电池」，是「储能的大脑和执行器」

PCS 负责直流的电池与交流的电网之间的变换。它自己也有保护逻辑——**不完全听 MUPC 的**。这一点很重要，后面 §5.3 会讲 MUPC 怎么处理这种「下属有自己的主见」的情况。

### 2.2 权威来源为什么重要

同一个量可能有**多个设备**能测（比如电池电量，BMS 能报，PCS 那边也读得到）。若不做主次，两个数打架时策略就会抖。

MUPC 的做法是**指定权威源**：

- **电** ⇒ 一律以**总表**为准（哪怕别的设备也测得到）
- **电池电量** ⇒ 以 **BMS** 为准；**BMS 失联时**才退而用 PCS 那边的读数兜底

> 这条规则是**配置期强制校验**的——想配错都配不了。

## 三、MUPC 怎么看懂现场

### 3.1 看得全：多路总线并行

台区设备挂在不同物理总线上。MUPC 的硬件有**多路独立的 485 口**，**每一路自己跑一条线**——所以接在不同口上的设备**可以同时问**，同一口上的设备**排队问**。

这直接决定了**采集周期**：关键设备（如总表、BMS）独占一口、可以问得勤；次要设备（如空调）可以慢一些。

### 3.2 看得懂：点表 = 一本「翻译对照表」

设备里的数据是一堆编号的寄存器，比如「第 1010 号寄存器里是电池电量，单位是 0.1%」。**不同厂家的设备编号与换算方式都不同。**

MUPC 用一份**点表**把它们翻译成业务含义：这是电压、那是电流、那是功率因数、那是电池电量……

> 当前台账覆盖 **618 个数据点**（台区设备 546 个 + 储能设备 72 个）。

点表不只是「翻译」，它同时是**校验依据**——配置时拿它核对，防止把「电压」配到「电流」的位置上。

### 3.3 看得准：数据有「保质期」

采集是周期性的。如果某条线断了，MUPC 手里会留着**上一次**的读数——**看起来有数据，其实是陈旧的**。

所以每份数据都带一个**新鲜度判据**：**总表数据超过 5 秒没更新**，就认定「当前看到的台区状态不可信」。

> 这条判据是后面 §4.4「宁可不动」和 §6「数据断链怎么办」的触发条件。

### 3.4 MUPC 采集到三类数据

| 类别 | 内容 | 主要用途 |
|------|------|---------|
| **电** | 分相的电压、电流、有功、无功、功率因数 | 治理策略的**输入**——判断该不该充放电、三相差多少 |
| **电池** | 电量（SOC）、健康度、温度、告警 | **安全边界**——防止充爆/放空 |
| **状态** | 设备在线与否、运行状态、消防/故障告警 | 上报告警、联锁安全 |

## 四、MUPC 怎么决定充放电

### 4.1 治理目标

策略的目标就是 §1.1 那三个问题的反面：

1. **把倒送压住**（白天不让电往电网倒）
2. **把三相拉平**
3. **把功率因数提上去**

### 4.2 一天里的四种工况

储能的行为随负荷与光伏的节奏变化，分四种工况：

| 工况 | 什么时候 | 储能做什么 |
|------|---------|-----------|
| **光伏吸收期** | 白天光伏倒送 | **充电**——把多余的吃掉，倒送压到很低的目标值 |
| **平段** | 供需大致平衡 | 基本不动 |
| **高峰放电** | 负荷高 | **放电**——削峰 |
| **日终收尾** | 一天将尽 | 把电量拉回目标区间，为明天做准备 |

### 4.3 一个周期算出来的是「六个数字」

每个控制周期，策略产出的是：

> **A / B / C 三相各自的有功设定 + 三相各自的无功设定**

- **三相一起**的那部分出力，负责削峰填谷（共模）
- **三相之间有差**的那部分，负责拉平不平衡（差模，三相之和恒为零——不会因为治不平衡而额外多用电）

有功的方向有约定：**正 = 放电，负 = 充电**。

### 4.4 三道不可逾越的边界

储能是有物理极限的。策略在给出任何设定值之前，必须过三道关：

| 边界 | 规则 | 为什么要 |
|------|------|---------|
| **电池边界** | 电量接近满（约 90%）时停止充电，接近空（约 10%）时停止放电；临近边界时**逐步降额**而不是硬切 | 防止充爆 / 放空，也防止边界附近来回跳 |
| **设备容量边界** | 三相的功率受「单相电流上限 / 总容量 / 总有功」约束，超了就**迭代裁剪** | 不能给设备下超出它能力的指令 |
| **数据可信边界** | 数据不可信时**不动作**（见下） | 基于错误测量去治理，可能把问题搞得更糟 |

### 4.5 ⭐ 数据不可信时：**归零，不是「保持不动」**

这是整个设计里**最反直觉、也最容易做错**的一条。

直觉上，「数据不可信」时应该**什么都不做**最安全。但这里的设备不是这样工作的：

> 给储能变流器的设定值是**「保持在某个值」**，不是「执行一次」。
> 一旦设定为「放电 20 千瓦」，它会**一直放下去，直到有人改写或它自己触发保护**。

所以如果数据断了 MUPC「什么都不做」，实际效果是——

> **储能继续执行断链前的最后一条指令，可能持续几个小时。**

正确的做法是**主动下发「归零」**（三相充放电都设为 0），**明确地把指令收回来**。

MUPC 在两种情况下会这样做：

| 情况 | MUPC 的动作 |
|------|------------|
| 总表数据超过 5 秒未更新 | 下发归零 + 告警 |
| 电池电量完全不可得（BMS 失联且 PCS 也读不到） | 下发归零 + 告警 |

> **为什么不用一个「假设值」先顶着**（比如假设电量为 50%）？
> 因为电量是**保护边界的输入**。用一个假的电量去算边界，会把保护档位算到**错误的位置**——比如以为电池还有一半电而实际已接近空，就会**继续放电**。
> **拿假数据驱动保护，比不控制更危险。**

### 4.6 人在回路：调度可以随时接管

策略不是唯一的发言者。调度主站可以随时下发**有功功率设定**，优先级高于策略——**这条指令一到，储能就按调度说的做**（具体交互见 §5.4）。

## 五、决定怎么执行出去

### 5.1 一条指令的旅程

```
  ① MUPC 算出三相设定值
        ↓
  ② 先过三道守门（见 5.2 / 5.3 / 5.5）
        ↓
  ③ 写进 PCS 的对应位置
        ↓
  ④ 确认 PCS 收到并照做（读回校验）
        ↓
  ⑤ 记录这次决策（谁在什么时候下了什么）
```

### 5.2 第一道守门：**安全联锁**（最高优先）

有些**安全信号**不允许经过策略、不允许被算法否决。典型的是**急停**和**消防报警**——它们走**硬接线**（干接点）进 MUPC。

联锁触发后的行为：

1. **立即让储能停机**
2. **锁存**——不允许自动重启
3. **必须人工确认 + 人工授权**才能恢复（这是防止「自动重启把问题掩盖掉」）

> 联锁是**独立通道**：它不经过治理策略，也不等待策略的下一个周期。而且它和策略**互斥**——联锁期间策略的下发被抑制。

### 5.3 第二道守门：**开机前先问一句**

给储能「开机」这件事，MUPC 不是直接下指令，而是**先读一次它的运行状态**：

- 如果它**已经停了**，而 MUPC **没有**得到人工授权重启 ⇒ **拒绝开机**，并要求人工授权
- 拿到授权后，**再读一次联锁状态**，确认联锁在这期间没有被触发
- 才真正下发开机

> **为什么这么绕**：储能设备可能因为**自身保护**（过温、过压……）而停机——**它不听 MUPC 的**。
> 如果 MUPC 不知道这件事、直接下发开机，就等于**绕过了设备自己的保护**。
> 「先问一句」是为了尊重设备的主见。

### 5.4 第三道守门：**量程钳位**

不同的设定项有**各自的量程**。MUPC 在下发前会把超出量程的值**钳到边界内**并记录告警——**包括人工下发的值**。

> **为什么人工下发的也要钳**：人会写错、系统会算错。执行端**不能假设上游永远正确**。

### 5.5 一条要特别注意的交互：**两个开关抢一个位**

MUPC 有两条下发路径：

| 路径 | 谁用 | 让储能干什么 |
|------|------|-------------|
| **治理策略** | MUPC 自己 | 三相各自独立出力（治不平衡用） |
| **调度指令** | 上级调度 / 人工 | 统一有功功率（不管三相差异） |

这两条路径**在设备上共用一个「工作模式」开关，而且想要的模式不一样**。所以：

- 调度下发一次，储能会**切到调度模式**（并且**把无功清零**）
- 策略的下一个周期又会**切回治理模式**
- 调度再下发，又切走……

⇒ 两边交叉下发时，这个开关会**来回翻**，而且**每次调度下发都会清掉无功**。

> **这是既定行为**（调度指令的语义就是「接管」），不是缺陷。但**现场若看到「模式莫名被切走」或「无功莫名归零」，先查是不是有调度指令与治理策略在交叉下发。**

### 5.6 控制不是单向的

MUPC 不只往下发，也在往上看：

| 看什么 | 用途 |
|--------|------|
| 电池电量 | 作为 BMS 失联时的**兜底来源** |
| 运行 / 停机状态 | 联锁的**停机确认**（发了停机指令，要确认它真的停了） |
| 三相电流与功率 | 上屏显示 |
| 在线与否 | 判离线并告警（连续几次读不到才算离线，避免偶发误码就判死） |

## 六、出状况时怎么办

### 6.1 一张表说清

| 出什么状况 | MUPC 怎么反应 |
|-----------|--------------|
| **总表数据断链** | 认定台区状态不可信 ⇒ **下发归零** + 告警（§4.5） |
| **电池电量不可得** | 认定无法安全充放电 ⇒ **下发归零** + 告警（§4.5） |
| **急停 / 消防触发** | 立即停机 + **锁存**，需**人工确认 + 授权**才能恢复（§5.2） |
| **某台设备掉线** | 该设备标离线并告警；**不影响同一总线上其他设备**，也不影响其他总线 |
| **储能设备离线** | 仍会尝试下发（失败即告警）；一旦发失败，**下个周期会重发**（防止"以为发过了"而让设备停等） |
| **装置本身故障** | 由操作系统的服务管理器负责重启；装置内部另有子系统健康巡检，异常时告警 |
| **磁盘写满** | 按水位分级：先告警，再停止写入新数据（**避免把磁盘彻底写死**） |

### 6.2 三条贯穿全文的原则

1. **宁可不动，不可乱动**——数据不可信时不做治理决策
2. **但「不动」不等于「保持」**——对保持型设定，必须**主动归零**把指令收回来
3. **安全信号不经算法**——急停与消防走独立硬接线通道，最高优先，锁存后必须人工介入

## 七、常见误解

| 误解 | 实际 |
|------|------|
| 「MUPC 是个通信盒子，转转发」 | 它**做决策**——储能怎么充放电是它算的 |
| 「策略直接控制电池」 | 策略**只给设定值**，真正的变换由 PCS 执行；PCS 还有自己的保护 |
| 「数据不可信时停发最安全」 | **相反**。设定值是保持型的，停发 = 让储能**继续执行旧指令**；必须**归零** |
| 「BMS 和 PCS 都能报电量，随便用哪个」 | 有**权威源约定**：BMS 优先，PCS 只在 BMS 失联时兜底 |
| 「调度指令和策略是配合的」 | 它们在设备上**共用一个模式开关**、目标相反，会互相切（§5.5） |
| 「储能掉线 = MUPC 故障」 | 储能掉线是**现场事件**（设备/线路问题）；MUPC 的"故障"另有所指（内部子系统不工作） |

```
                       │  切模式 → 启停 → 写 1006-1011      │
                       └───────────────┬──────────────────┘
                                       ▼
                           RS485 / Modbus RTU → PCS → 电池
```

## 附录 B · 三条最容易困惑的实现事实

| # | 事实 | 说明 |
|---|------|------|
| 1 | **一个进程装下了几乎全部模块** | `mupcd` 这一个进程里，网关、数据处理、存储、策略、南向调度、系统监控**全是库**；只有本地屏 `mupc-local-display` 是第二个进程。⇒ 文档里若把 `gateway` / `intercore` 列成「进程」，是**过期表述** |
| 2 | **「最新值」只有一份，在内存里** | 上云、上屏、策略取数**共用同一份内存快照**，**不查历史数据库**。历史库只用于事后查询 |
| 3 | **PCS 是「从站」，MUPC 是「主站」** | PCS 挂 RS485 做 Modbus RTU 从站；MUPC 主动轮询、主动写。⇒ 是**轮询 + 写寄存器**模型，不是消息推送模型 |

## 附录 C · 采集与四条通路

南向有四条并列通路（共用同一套串口 / Modbus 栈）：

| 通路 | 干什么 | 设计章节 |
|------|--------|---------|
| 插件化单设备 | 一设备一个实例（TTU / 逆变器 / 充电桩 / 柔性负荷） | 02 设计 §2–§6 |
| **站级多从站调度** | **配置驱动**：一口一 master、口内多从站串行轮询 | 02 设计 **§10** |
| **PCS 通信与控制** | `PcsHandle`——PCS 的完整所有者 | 02 设计 **§13** |
| 数字 IO | sysfs 读写 GPIO（DI/DO） | — |

**站级调度的核心概念**：一个「站」由 `port` / `slave` / `interval_ms` / `regs`(点表) / **`role`** 描述，`role` 是语义标签（`meter_grid` 总表 / `meter_batt` 储能表 / `battery` BMS / `hvac` 空调 / `fire` 消防），**决定数据往哪去**。

**PCS 的采集是特殊一条**：不走站级调度器，而是**独占 ttyS0 的独立循环**，每 `interval_ms`（缺省 1000 ms）发一次 **FC04**，**一次读 3 区 76 个寄存器**（原分散成 4 次/秒，2026-09 合并为 1 次/秒），解出 SOC / 运行状态 / 三相量，存入 **`PcsSnapshot`（采集快照）**。连续 3 拍失败判离线。

> **为什么用快照**：控制周期（1 s）不慢于采集周期，若每次决策都现读会与采集循环抢串口。快照把读写解耦。

**点表规模**：618 点 = 站级 **546** + PCS **72**（`mupc-southd/src/point_table.rs` 的 `POINT_REGS`，静态 510 行按探测器模板展开）。

## 附录 D · 处理、存储、上云、上屏

**`SouthSink`（装配层总出口）四个方法的去向**：

| 方法 | 谁调 | 干什么 |
|------|------|--------|
| `on_grid_package` | **只有 `meter_grid`** | 推策略 + 喂总表聚合器 |
| `on_battery_soc` | **只有 `battery`** | 推 SOC 给策略（BMS 优先源） |
| `on_station_telemetry` | 其余全部 | 标记站活性 + 事件落 `events` + 普通点落 `telemetry` + **写内存最新值** |
| `on_station_offline` | 站判离线 | 标记离线 + 落事件 |

> ⚠️ `meter_batt` / `hvac` / `fire` / `pcs` 四类 role 的 `DataPackage` 是**空包**（设计使然，只走 telemetry）；调度器**有 role 守卫**，空包**不会污染策略输入**。

**内存最新值 `LatestValues`** 是实时链路的枢纽，三处共用：北向上送 / 本地显示外设段 / 控制台外设端点。**硬约束：上送不得查 `telemetry` 历史表。**

**落库**：`WriteBuffer` 缓冲批量——**满 1000 条 或 每 5000 ms**（先到先执行）触发 flush，独立后台任务做 DB 事务。SQLite **6 张表**：`telemetry` / `faults` / `decisions` / `events` / `assets` / `action_space_config`。总表另有 1 分钟聚合（均值 + 极值）。

> `telemetry` 目前**只写不读**（查询出口未实现，属已知设计余量）——不得据此认为「历史查询已可用」。

**上云**：

| 通道 | 分档 |
|------|------|
| **IEC 104** | A 档 周期 1000 ms / B 档 周期 5000 ms / C 档 **变化驱动**；组帧 `M_ME_TF_1`(TI 36) 与 `M_SP_TB_1`(TI 30)；支持总召 |
| **MQTT** | 周期 + 变化驱动；topic `mupc/north/telemetry/<站>`、`mupc/north/event/<站>`（事件固定 **QoS 2**）；发布失败进内存离线缓存、恢复后按序补送 |

**上屏**：`mupcd` 组 `DisplayFrame`（协议 v3，含 SOC / 运行状态 / 三相 / 装置信息 / 告警 / 联锁 / 外设段）存内存，屏经 TCP 回环 `GET /v1/display/latest` 拉，用 **LVGL** 渲染到 HDMI 触摸屏。写操作走 `POST /v1/console/*`，**须二次确认 + 记审计**。

## 附录 E · 策略与下发的实现细节

**策略输入**（`tai_storage.rs`）：

| 输入 | 来源 |
|------|------|
| 分相电气量 | **`meter_grid` 站**（唯一 phase 真源，配置期强校验） |
| SOC | ① BMS 站（优先）② 回落 **PCS 采集快照** |
| 新鲜度闸门 | `last_data_ts`，`DATA_STALE_AFTER` = 5000 ms（=`DATA_FRESHNESS_MS`） |

**四状态机**：`S1PvAbsorb`（光伏吸收）/ `S2Flat`（平段）/ `S3Peak`（高峰放电）/ `S4Clear`（日终清空）。

**三道保护**：`soc_protect` 剪带（充 ≥90% 剪 0 / 88–90% 线性降额；放 ≤10% 剪 0 / 10–12% 线性降额）；`arbitrate` 容量仲裁（单相电流 / 总视在 / 总有功 + 收敛步在环内、复检在收敛步之后 + `d_p` 零净重归一）；`failsafe`（分相测量缺 ⇒ 冻结积分、斜坡回归 0、复位 Q 积分）。

**数据不可信 ⇒ 归零**：`refuse_missing_soc`（SOC 全缺）与 `refuse_stale_data(stale_after)`（数据超期）**同款处置**——状态清零 + `zero_command`（分相 P/Q 全 0）+ **各自独立的 30 s 节流告警槽**；两者都**不更新 `last_control_ts`**（保护性拒绝不消耗控制周期）。

**下发链路逐跳**：

```
1 s 驱动循环 → AiIntegrator::dispatch_ai_decision → run_fallback_strategies
  ├─ 5 s 新鲜度闸门（超期 ⇒ 归零）
  ├─ SOC 双源裁决 → TaiStorageStrategy::evaluate → control
  └→ dispatch_phase_pq（去抖 → 发送 → 审计的唯一实现）
       └→ PcsHandle::send_tai_command
            ├─ check_latched        ← 联锁锁存中 ⇒ 拒绝
            ├─ ensure_mode(2)       ← 写 1000=2（分相）
            ├─ ensure_started       ← 见下 S-4
            └─ 逐相写 1006~1011      ← 每相 clamp ±25
                 └→ StationBus::write_single → Rs485Device::write_single_register_from（FC06）
```

**S-4 守卫**（`ensure_started`）：① latch 拒 ② `started` 缓存短路 ③ **FC04 读 `1013`**——读到 0 且未授权 ⇒ 拒发并要授权；已授权 ⇒ **消费**（一次性）④ **写前复查** latch ⑤ 才写 `500=1`。

**PCS 的四个写入口**（收敛，无第五个）：

| 入口 | 谁调 | 写什么 | 量程 |
|------|------|--------|------|
| `send_tai_command` | 治理策略 | `1000=2` + 逐相交错写 `1006/1009`·`1007/1010`·`1008/1011` | 每相 **±25** |
| `send_dual_param` | 调度 `p_set` / AI | `1000=0` + `1001`(P) `1002`(Q) | **±100** |
| `stop()` | 联锁 | `500=0` | — |
| `restore_interlock_latched(bool)` | 联锁 | C-1 唯一 latch 入口 | — |

> 两个量程**各自独立、不可互换**：±25 是单相量程，±100 是三相总量程；套用会把合法指令静默降额。

**模式字争用**（正文 §5.5）：`send_dual_param` 的 `ensure_mode(MODE_CONST_POWER=0)` 与 `send_tai_command` 的 `ensure_mode(MODE_PHASE_SPLIT=2)` **都写 `1000`**、目标相反、共享缓存 ⇒ 交叉调用时来回翻；且 `send_dual_param` 把 `REG_CONST_Q_SET` **硬编码 0.0** ⇒ 每次人工 `p_set` 都清无功。

**联锁**：`InterlockController::on_trigger` → `restore_latched(true)` → `stop_once` → `PcsHandle::stop`（写 `500=0`）；互斥经 `InterlockPort` 薄 trait；策略侧 latch 抑制在驱动循环内。
