## 0. 先记住三件事（否则后面会一直困惑）

| # | 事实 | 为什么重要 |
|---|------|-----------|
| **1** | **一个进程装下了几乎全部模块** | `mupcd` 这一个进程里，网关、数据处理、存储、策略、南向调度、系统监控……**全是库**，不是独立进程。只有本地屏 `mupc-local-display` 是第二个进程。⇒ 文档里若见到「关键进程列表」把 `gateway` / `intercore` 列成进程，那是**过期表述** |
| **2** | **「最新值」只有一份，在内存里** | 上云、上屏、策略取数**共用同一份内存快照**，不查历史数据库。⇒ 历史库只用于**事后查询**，不参与实时链路 |
| **3** | **PCS 是「从站」，策略是「主站」** | PCS（= 实时控制模块）挂在 RS485 上做 Modbus RTU **从站**；MUPC 主动轮询它、主动写它。⇒ 控制是**轮询 + 写寄存器**模型，不是「推送消息」模型 |

## 2. 数据从哪来：南向采集

### 2.1 硬件层：板载 8 路隔离 RS485

MUPC 跑在 **BECG-3568**（RK3568）上，板子自带 **8 路隔离 RS485**，**每一路是独立的 Modbus master**（这一点很关键：口内设备串行、**不同口之间并行**）。

端口分配（部署 YAML 里可配）：

| 端口 | 接什么 |
|------|--------|
| `ttyS0` | **PCS**（两级式储能，独占） |
| `ttyS2` | BMS（电池管理系统） |
| `ttyS3` | 空调 |
| `ttyS4` | **关口表 / 台区总表**（策略的关键输入） |
| `ttyS5` | 储能表 |
| `ttyS6` | 消防主机 |

串口打开与配置在 `mupc/crates/rs485-plugin/src/device.rs`：用 libc 直接 `open(2)`，然后配 termios（波特率 / 校验 / 停止位）并**切 raw 模式**（关掉内核的行规约，否则 `VMIN/VTIME` 不生效、含 `0x0A` 的报文会被改写）。

### 2.2 软件层：南向有四条通路

`mupc-southd` 不是一个模块，是**四条并列的通路**，共用同一套串口 / Modbus 栈：

| 通路 | 干什么 | 章节 |
|------|--------|------|
| **插件化单设备** | 一设备一个 `SouthDevice` 实例（TTU / 逆变器 / 充电桩 / 柔性负荷），协议处理器注入 | 02 设计 §2–§6 |
| **站级多从站调度** | **配置驱动**：一口一 master、口内多从站串行轮询 | 02 设计 **§10** |
| **PCS 通信与控制** | `PcsHandle` —— PCS 的**完整所有者** | 02 设计 **§13** |
| **数字 IO** | `mupc-io`，sysfs 读写 GPIO（DI/DO） | — |

对「台区储能」这条主线，真正相关的是 **站级调度** 与 **PCS** 两条。

### 2.3 站级调度：核心概念

```
配置里的一个「站」   Station
  ├── port        跑在哪一路 RS485（如 ttyS4）
  ├── slave       Modbus 从站号
  ├── interval_ms 轮询周期
  ├── regs        点表（读哪些寄存器、怎么解码）
  └── role        ★ 这个站「是什么」——决定数据往哪去
```

`role` 是**语义标签**，当前有：`meter_grid`（总表）、`meter_batt`（储能表）、`battery`（BMS）、`hvac`（空调）、`fire`（消防）。

调度器（`mupc-southd/src/scheduler.rs`）为**每个 port 起一条采集任务**，每拍：

1. 取该口**到点**的站（按各自 `interval_ms`）
2. 打开口，按点表**读寄存器**
3. 交给 `mapper` 解码 → 产出 `DataPackage`
4. **按 `role` 分流投递**（见 §3.1）

> **点表有多大**：618 个点 —— **546** 个站级点 + **72** 个 PCS 点。定义在 `mupc-southd/src/point_table.rs` 的 `POINT_REGS`（静态 510 行，按探测器模板 n=20 展开后 618 行）。点表同时充当**配置期校验的期望值来源**。

### 2.4 PCS 的采集：一条特殊通路

PCS 不走站级调度器 —— 它是**独占 ttyS0 的独立循环**（`mupc-southd/src/pcs/collect.rs`）：

- 每 `interval_ms`（缺省 **1000 ms**）发一次 **FC04**，**一次读 3 区 `1000..=1075` 共 76 个寄存器**（原来分散成 4 次/秒的读，2026-09 合并成 1 次/秒）
- 从这一块里解出：`SOC`(1010)、`RUN_STATE`(1013)、三相电流(1022-1024)、三相有功(1029-1031)、总有功(1032)
- 解出的值存进 **`PcsSnapshot`（采集快照）**——注意是**快照**，按需读取时读的是快照，**不是现场再发一次请求**
- 连续 **3 拍**失败判离线

> **为什么要快照**：控制周期（1 s）比采集周期（1 s）快不起来，若每次决策都现场读一次，会与采集循环抢串口。快照把读写解耦。

## 3. 数据怎么处理、怎么存

### 3.1 第一站：SouthSink（装配层的总出口）

所有采集结果都汇到 `mupc-core-bin/src/startup.rs` 的 **`SouthSink`**。它实现 `StationSink` trait，四个方法对应四类数据：

| 方法 | 谁调 | 干了什么 |
|------|------|---------|
| `on_grid_package` | **只有 `meter_grid` 站** | ① 推给策略（`set_latest_data`）② 喂总表聚合器 ③ 算聚合行 |
| `on_battery_soc` | **只有 `battery` 站** | 推 SOC 给策略（BMS 优先源） |
| `on_station_telemetry` | **其余全部** | ① 标记站活性 ② 事件点落 `events` ③ 普通点落 `telemetry` ④ **写入内存最新值** |
| `on_station_offline` | 站判离线时 | 标记离线 + 落一条事件 |

> ⚠️ **一个容易误读的点**：`meter_batt` / `hvac` / `fire` / `pcs` 四类 role 产出的 `DataPackage` 是**空包**（`mapper.rs`）。这是**设计使然**——它们的数据只走 `on_station_telemetry`。而且调度器**有 role 守卫**（`on_grid_package` 只在 `MeterGrid` 时调），**空包不会污染策略输入**。

### 3.2 内存里那一份：`LatestValues`

**这是整个实时链路的枢纽。** `LatestValues`（`mupc-data-processing/src/latest_values.rs`）是**唯一的「最新值」真源**，三处消费方共用它：

| 消费方 | 怎么用 |
|--------|--------|
| **北向上送**（IEC 104 / MQTT） | `all()` / `get()` / `is_fresh()` 取内存值组帧 |
| **本地显示**（外设段） | 对外设值做投影 |
| **控制台**（外设端点） | 同一份投影 |

> **硬约束**：上送 **不得查 `telemetry` 历史表**（`uplink.rs` 里有明文）。历史库是「事后查询」用的，不是实时源。

### 3.3 落库：`WriteBuffer` → SQLite

写入不是「来一条写一条」，而是**缓冲批量**：

- 采集结果 → `WriteBuffer::buffer_telemetry()`（同步、不 await）
- **两个触发条件**（先到先执行）：容量满（缺省 **1000** 条）或 间隔到（缺省 **5000 ms**）
- 独立 flush 任务在后台做真正的 DB 事务
- 另有**总表聚合**：`GridAggregator` 把总表采样聚成 1 分钟一行（均值 + 极值）

数据库是 **SQLite**，**6 张表**：`telemetry`（时序）/ `faults`（录波）/ `decisions`（控制决策审计）/ `events`（告警事件）/ `assets`（设备台账）/ `action_space_config`。

> **注意**：`telemetry` 目前**只写不读**（查询出口未实现，属已知设计余量），不要据此认为「历史查询已可用」。

### 3.4 上云：IEC 104 与 MQTT

两条北向通道，都从 `LatestValues` 取数：

**IEC 104**（`mupc-core-bin/src/uplink.rs`）分三档：

| 档 | 触发 | 说明 |
|----|------|------|
| A | 周期（缺省 **1 s**） | 主要遥测 |
| B | 周期（缺省 **5 s**） | 次要遥测 |
| C | **变化驱动**（COS） | 值变化即报 |

组帧成 IEC 104 的 **ASDU**（遥测用 `M_ME_TF_1`、遥信/单点用 `M_SP_TB_1`），经 `Iec104Server` 发出；另支持**总召**（主站问一遍全部点）。

**MQTT**：周期 + COS，topic 形如 `mupc/north/telemetry/<站id>`、`mupc/north/event/<站id>`（事件固定 **QoS 2**，不可丢）；发布失败会进**内存离线缓存**，恢复后按序补送。

### 3.5 上屏：`DisplayFrame` → 本地显示终端

- `mupcd` 侧把要显示的东西组一个 **`DisplayFrame`（协议 v3）**，包含：SOC / 运行状态 / 三相 P·I / 装置信息 / 告警列表 / 联锁状态 / **外设段**
- 存在内存里，屏通过 **TCP 回环** `GET /v1/display/latest` 拉
- 屏进程（`mupc-local-display`）用 **LVGL** 渲染到 HDMI 外接触摸屏

**写操作走另一条路**：屏上的「改配置 / 释放联锁 / 授权重启」经 `POST /v1/console/*` 回 `mupcd`，并且**必须二次确认 + 记审计**（无登录，物理在场即授权）。

## 4. 储能策略：怎么算、拿什么算

### 4.1 谁在下决策

> **2026-09-09 起：AI 引擎停用。**
> 本地策略「**台区储能治理**」（`TaiStorageStrategy`）是**唯一默认的下发引擎**，AI 框架保留但不参与控制。

台区储能治理要解决三件事：**降返送**（光伏倒送电网）、**降三相不平衡**、**提功率因数**。

### 4.2 它拿什么算（两个输入 + 一个闸门）

| 输入 | 来自哪 | 说明 |
|------|--------|------|
| **分相电气量**（P/Q/电压/电流/功率因数） | **`meter_grid` 站**（`ttyS4` 的总表） | 策略的**唯一 phase 真源**（配置期强校验，别的站不许接） |
| **SOC**（电池荷电状态） | ① **BMS 站**（`battery` role，优先）<br>② 回落 **PCS 采集快照** | 双源裁决：BMS 新鲜就用 BMS；BMS 超期就**无条件**读 PCS 快照 |
| **数据新鲜度闸门** | `last_data_ts` | 总表数据 **> 5 s** 未更新 ⇒ 判定「数据不可信」 |

### 4.3 四状态机

```
S1 光伏吸收   ── 白天光伏倒送 → 储能充电，把返送压到目标进口
S2 平段       ── 平衡负载 → 基本不动作
S3 高峰放电   ── 高负荷 → 储能放电削峰
S4 日终清空   ── 收尾，把 SOC 拉回目标带
```

在每个状态下，控制器算出一个**共模出力**（三相一起充/放）和一个**差模出力**（三相之间此消彼长，用来治不平衡）。最终产出**六个数字**：A/B/C 三相各自的有功设定 + 三相各自的无功设定。

### 4.4 三道保命机制（阅读代码时最容易忽略）

| 机制 | 作用 |
|------|------|
| **SOC 剪带** | 充电到 90% 剪 0、88%~90% 线性降额；放电到 10% 剪 0、10%~12% 线性降额。**绝不允许把电池充爆/放空** |
| **容量仲裁** | 三相 P/Q 受「单相电流上限 / 总视在 / 总有功」约束，超了要迭代裁剪（含**零净重归一**，保证差模不引入共模偏移） |
| **数据不可信 ⇒ 归零** | 见下 |

### 4.5 ⭐ 数据不可信时怎么办：**归零，不是停发**

这是本设计里**最反直觉**的一条：

| 场景 | 处置 |
|------|------|
| **SOC 全缺**（无新鲜源也无冻结值） | 下发 `zero_command`（分相 P/Q 全 0）+ 30 s 节流告警。**不得**用假值（如 50%）驱动保护——假 SOC 会把充放电剪带剪到**错误档位**，比不控制更危险 |
| **总表数据超期 > 5 s** | **同样下发归零**（与上一条同口径）+ 节流告警 |

> **为什么不能「停发」？**
> 因为分相 P/Q 写在 **FC06 保持寄存器**里——它是**设定值，不是脉冲**。
> **没人改写，PCS 就一直按最后那条指令跑**，可能持续几小时。
> 「停发」看似保守，实际是**把一条陈旧指令留在设备上执行**。

两条「数据不可信」路径的处置必须**一致**，否则同一语义会有两种相反行为。

## 5. 指令怎么下发到 PCS

### 5.1 完整链路（逐跳）

```
1 s 驱动循环（core-bin）
  └→ AiIntegrator::dispatch_ai_decision
       └→ run_fallback_strategies
            ├─ 5 s 新鲜度闸门（超期 ⇒ 归零，见 §4.5）
            ├─ SOC 双源裁决
            └→ TaiStorageStrategy::evaluate → control    ← 算出三相 P/Q
                 └→ dispatch_phase_pq（去抖 → 发送 → 审计）
                      └→ PcsHandle::send_tai_command
                           ├─ check_latched     ← 联锁锁存中 ⇒ 拒绝（下行中止）
                           ├─ ensure_mode       ← 写 1000=2（分相模式）
                           ├─ ensure_started    ← 见 §5.3
                           └─ 逐相写 1006~1011  ← 每相 clamp ±25
                                └→ StationBus::write_single
                                     └→ Rs485Device::write_single_register_from（FC06）
                                          └→ RS485 / ttyS0 → PCS
```

### 5.2 PCS 只有四个写入口（收敛设计）

| 入口 | 谁调 | 写什么 |
|------|------|--------|
| `send_tai_command(p, q, mode)` | **台区储能策略** | `1000=2` → 逐相交错写 `1006/1009`·`1007/1010`·`1008/1011`（每相 clamp **±25**） |
| `send_dual_param(...)` | 调度侧 `p_set`（IEC 104）/ AI | `1000=0` → `1001`(有功) `1002`(无功)，钳 **±100** |
| `stop()` | **联锁** | `500=0`（停机） |
| `restore_interlock_latched(bool)` | 联锁 | C-1 的**唯一** latch 入口 |

**没有第五个入口**，也**没有**「南向站直接写 PCS」这种路径。

### 5.3 控制序列里最关键的一步：S-4 守卫

`ensure_started()` 不是简单地写 `500=1`，而是：

1. 联锁锁存中？⇒ **拒绝**
2. 缓存说已启动？⇒ 短路（省一次总线往返）
3. **【S-4】** 先 **FC04 读 `1013`（运行状态）**：
   - 读到 **0（停机）** 且未获人工授权 ⇒ **拒发**，返回「需人工授权」（M1 守卫）
   - 已授权 ⇒ **消费掉这次授权**（一次性）
4. **写前复查**一次联锁锁存
5. 才写 `500=1`

> **为什么这么绕**：PCS 可能因为**自身保护**停机（而不是听 MUPC 的）。若 MUPC 不知道、直接写上电，就等于**绕过了 PCS 的保护**。S-4 是「先问一句再动手」。

### 5.4 两条旁路，以及它们和策略的关系

| 通道 | 触发 | 与策略的关系 |
|------|------|-------------|
| **联锁停机** | DI 干接点（急停等） | **独立且优先**。触发即 `500=0` 并**锁存禁启**；策略侧同时被抑制。这是**安全链**，不经策略校验 |
| **调度侧 `p_set`** | 主站经 IEC 104 下发 | 与策略**共享同一个模式字**——见下 |

### 5.5 ⚠️ 两条通道会「抢同一个开关」

`send_dual_param`（恒功率）与 `send_tai_command`（分相）的**第一条动作都写模式字 `1000`**，但**目标值相反**（`0` vs `2`）：

```
T0  策略下发     → 1000 = 2（分相）
T1  调度 p_set   → 1000 = 0（切走分相！）+ 1001=p + 1002=0（清无功）
T2  策略下一拍   → 1000 = 2（切回）
T3  调度再下发   → 1000 = 0 …
```

⇒ 两通道交叉时 `1000` **来回翻**，且每次 `p_set` 都会**清掉无功**。**这是既定行为**（`p_set` 即"接管为恒功率"），但**现场排查「模式被切走 / 无功莫名归零」时，先查是否有交叉下发**。

### 5.6 PCS 的状态怎么回到策略

控制不是单向的 —— MUPC 还要知道 PCS 现在什么状态：

| 读什么 | 来源 |
|--------|------|
| **SOC** | `PcsSnapshot`（采集快照，非现读）→ 作为 SOC 的**回落源** |
| **运行状态** | 快照 → 联锁的停机确认、状态展示 |
| **三相电流/有功** | 快照 → 上屏 |
| **在线态** | 连续 3 拍采集失败判离线 |

## 6. 几条「新人最容易误解」的地方

| 误解 | 实际 |
|------|------|
| 「gateway / 策略 / 存储 是独立进程」 | **全是 `mupcd` 内的库**。只有屏是第二个进程 |
| 「控制指令是推送出去的」 | PCS 是**从站**，MUPC 主动**写寄存器**；采集是主动**轮询** |
| 「历史库参与实时上云」 | 不。上云/上屏/策略都读**内存最新值** |
| 「数据不可信时停发最安全」 | **相反**。保持寄存器会**留住**陈旧指令 ⇒ 必须**归零** |
| 「PCS 掉线 = 服务故障」 | PCS 掉线是**现场事件**（有独立告警通道）；「服务故障」指**进程内子系统不转了**。混用会导致恒告警 |
| 「`send_dual_param` 可以随便传值」 | 两个入口**各自钳各自寄存器的量程**（分相 ±25 / 恒功率 ±100），不可互换 |
