# LSTM 模型 Rust 源码评审

## 总体评价

该代码实现了一个基于 RKNN 运行时（NPU 推理）的 LSTM 时序预测模型，结构清晰，异步接口设计合理，并尝试提供了分位数预测和置信度计算。但与之前讨论的设计文档和优化建议相比，存在若干关键差距和工程风险，主要集中在**分位数预测的实现方式、置信度计算的合理性、输入输出尺寸与实际部署的一致性**等方面。

---

## 主要优点

1. **模块化设计**：`LstmModel`封装了 `RknnRuntime`，易于测试和维护。
2. **异步推理**：`predict`和 `predict_quantiles`均为 `async`，不阻塞决策主循环。
3. **协变量调整逻辑**：`calculate_covariate_adjustment`考虑了温度、时段、日期类型、季节等多种因素，体现了领域知识。
4. **分位数预测接口**：提供了 `ProbabilisticLoadOutput`结构体，为后续 RL 提供不确定性信息。
5. **单元测试覆盖**：包含基本的创建和属性测试。

---

## 关键问题与改进建议（按优先级排列）

### 🔴 高优先级

#### 1. 分位数预测并非真正的分位数回归，而是启发式调整

**问题**：

`predict_multi_quantile`的实现是：先调用 `self.predict(input)`获得点预测，然后根据协变量对点预测进行乘性缩放得到 P10/P50/P90。这不是统计意义上的分位数回归，而是一种经验调整。

* 例如 `p50 = base * base_multiplier`，`p10 = p50 - (p50 - base) * spread_multiplier`，本质上只是把点预测上下拉伸。
* 这与之前建议的“统一使用分位数损失训练所有输出头”完全背离。训练阶段并未输出分位数，部署时的分位数是后处理的产物，缺乏模型支撑。

**影响**：

* 分位数区间宽度不反映真实的不确定性，可能误导 RL 策略。
* 当协变量组合超出训练分布时，调整因子可能放大误差。

**建议**：

* **短期修复**：删除 `predict_quantiles`方法，或者将其标记为实验性功能，并在文档中注明“非正式分位数预测”。
* **长期改进**：按照之前建议，在训练阶段使用 Quantile Loss，让模型直接输出多个分位数（例如 10%, 50%, 90%）。部署时，ONNX 模型应直接输出这些分位数，不再需要后处理调整。

#### 2. 置信度计算缺乏理论基础

**问题**：

`predict`中的置信度计算：

```
let variance = if predictions.len() > 1 {
    let mean = predictions.iter().sum::<f32>() / predictions.len() as f32;
    predictions.iter().map(|p| (p - mean).powi(2)).sum::<f32>() / predictions.len() as f32
} else { 0.0 };
let confidence = (1.0 - variance.min(1.0)).max(0.0);
```

* 这里的 `variance`是预测序列**不同时间步之间的方差**，而非预测的不确定性。例如，一个平稳的预测序列（所有值接近）方差小，置信度高；但实际可能预测完全错误（偏差大），却得到高置信度。
* 将方差直接映射到置信度（1 - variance）没有物理意义。

**影响**：

* 置信度不能反映预测的可靠性，RL 无法据此调整策略。
* 可能导致 RL 过度信任错误预测。

**建议**：

* **移除该置信度字段**，或将其定义为占位符（如固定 0.5）。
* **未来使用分位数预测的区间宽度作为置信度**：例如 `confidence = 1.0 - (P90 - P10) / (2 * P50)`，但前提是分位数预测准确。

#### 3. 输入输出尺寸假设与设计文档不一致

**问题**：

代码中硬编码 `input_size = input_window_secs / 60`，`output_size = output_horizon_secs / 60`，假定数据粒度为**每分钟一个点**。但设计文档中训练数据粒度为 **15 分钟**（每步 15 分钟），且 LSTM 输出 47 维（15 个未来步的 pv/load 等）。

* 如果实际部署也是 15 分钟粒度，则 `input_window_secs = 3600`意味着 240 个 15 分钟点（60 小时），而非 60 分钟。
* 输出 `output_horizon_secs = 900`意味着 60 个 15 分钟点（15 小时），而非 15 分钟。

**影响**：

* 输入长度验证失败，模型无法正常运行。
* 即使通过验证，输入的历史窗口和预测时长也与设计目标不符。

**建议**：

* **明确数据粒度**：在 `LstmConfig`中添加 `step_seconds: u64`字段（如 900 表示 15 分钟），统一使用 `input_window_secs / step_seconds`计算步数。
* **同步设计文档**：确保代码中的默认值与训练管线一致（例如 `input_window_secs = 21600`（6 小时）、`output_horizon_secs = 13500`（15 步 × 15 分钟））。

#### 4. 分位数预测仅对第一个时间步生效

**问题**：

`predict_multi_quantile`中：

```
let base = output.predictions.first().copied().unwrap_or(0.0);
```

* 只取了 `predictions`的第一个元素（即第一个未来时间步的预测值）来计算分位数。
* 但 `ProbabilisticLoadOutput`只有一个 `base_load`和一个 `shock_probability`，没有为每个未来时间步提供分位数。

**影响**：

* 无法提供未来多个时间步的概率分布，RL 只能看到单一时间步的不确定性，失去了多步预测的价值。
* 与设计文档中“15 个未来步的分位数”描述不符。

**建议**：

* **扩展 `ProbabilisticLoadOutput`**：增加 `quantiles_per_step: Vec<Vec<QuantilePrediction>>`，每个时间步对应一组分位数。
* **修改 `predict_multi_quantile`**：对 `predictions`中的每一个时间步分别计算分位数（使用相同的协变量调整因子，但基线不同）。

### 🟡 中优先级

#### 5. 协变量调整因子使用硬编码阈值，缺乏泛化能力

**问题**：

`calculate_covariate_adjustment`中大量使用固定阈值（如 35°C、25°C、7-22 小时等），这些值可能仅适用于特定地区（如亚热带气候）。

* 例如，北方冬季温度可能低于 -20°C，此时 `temp_factor`计算为 `1.0 - 0.01 * temp_diff`，但实际供暖负荷可能增加。

**影响**：

* 模型迁移到其他气候区时，调整因子可能产生相反效果。

**建议**：

* **参数化阈值**：将这些阈值放入 `LstmConfig`或单独的 `ClimateConfig`中，允许运维人员根据台区位置调整。
* **或使用学习到的调整**：在训练阶段，将协变量作为模型输入的一部分，让 LSTM 自己学习其对预测的影响，而非手动规则。

#### 6. 冲击概率计算的正态假设可能不成立

**问题**：

`calculate_shock_probability`假设负荷服从正态分布，并使用 `spread ≈ 1.28 * std`（P90 对应 1.28σ）。

* 实际负荷分布可能有偏（如夏季空调负荷尖峰），正态假设会导致概率低估或高估。
* 使用 `erfc`近似时，分母 `denom = PI * abs_x + sqrt(PI * x^2 + 4)`是 Abramowitz-Stegun 近似，但未检查精度。

**影响**：

* 冲击概率不准确，RL 可能忽略或过度反应。

**建议**：

* **改用非参数方法**：直接从历史数据中统计冲击负荷的发生频率，作为先验概率。
* **或使用分位数比值**：`shock_probability = (P90 - P50) / (P50)`，无需正态假设。

#### 7. `predict`与 `predict_quantiles`存在冗余推理

**问题**：

`predict_quantiles`内部调用了 `self.predict(input)`，而 `predict_multi_quantile`又调用了 `self.predict(input)`。实际上，一次推理即可获得点预测，分位数调整应在同一结果上进行。

* 当前设计导致每次分位数预测执行两次 NPU 推理，浪费算力。

**建议**：

* **重构**：将 `predict`的结果作为中间产物，`predict_quantiles`直接使用该结果进行后处理，不再重复推理。
* 或者合并为一个方法 `predict_with_uncertainty`。

---

### 🟢 低优先级

#### 8. 缺少对模型输出维度的校验

**问题**：

`predict`中 `let output = self.runtime.run(&input.history).await?;`后直接 `take(output_size)`，未校验 `output`的长度是否至少为 `output_size`。如果模型输出少于预期，会静默截断，可能丢失数据。

**建议**：

* 添加断言或错误返回：`if output.len() < output_size { return Err(...) }`。

#### 9. 测试覆盖率不足

**问题**：

现有测试仅测试了模型创建和属性获取，未测试预测逻辑（因为需要实际 RKNN 模型文件）。

* 缺少对协变量调整、冲击概率计算等关键函数的单元测试。

**建议**：

* 为 `calculate_covariate_adjustment`、`calculate_shock_probability`、`calculate_quantile_confidence`添加纯函数测试，使用模拟输入验证输出是否符合预期。

## 与之前建议的对照总结


| 之前建议                         | 代码现状                               | 结论                  |
| -------------------------------- | -------------------------------------- | --------------------- |
| 1. 输入特征增强（日历+历史同期） | 未体现，协变量仅用于后处理调整         | ❌ 需在模型输入侧实现 |
| 2. 统一分位数损失                | 未实现，仍为点预测+后处理              | ❌ 需重新训练模型     |
| 3. 评估多步误差并截断            | 未评估，输出长度由配置决定             | ⚠️ 需补充评估       |
| 4. 数据增强与领域随机化          | 未涉及                                 | ❌ 需在训练管线中实现 |
| 5. INT8 量化评估与 QAT           | 配置中有`quantization`字段，但未做 QAT | ⚠️ 需验证           |
| 6. 在线自适应校正                | 未实现                                 | ❌ 需后续开发         |

---

## 最终建议

1. **立即修复**：修正输入输出尺寸计算（使用 `step_seconds`），移除无效的置信度计算，避免冗余推理。
2. **短期改进**：将分位数预测标记为实验性，或改为基于历史统计的简单分位数（如直接使用过去同期的 P10/P90），而非当前启发式调整。
3. **中期规划**：按照之前建议，重新训练 LSTM 模型使其直接输出分位数（Quantile Loss），并导出 ONNX。届时此 Rust 代码需要配合新的模型输出结构进行重构。
4. **长期演进**：集成在线自适应校正机制，并补充数据增强和领域随机化。

该代码作为原型是可用的，但要达到生产级可靠性，还需在上述关键问题上进行实质性改进。
