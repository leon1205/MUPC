### 3.1 码表网的「真源同源」核实（任务书点名的疑点）

设计 §11.1 的原文基线与实现的**实际基线不同源**，此处逐条核实（**这是设计原文的过期描述，不是实现缺陷**）：

| | 设计 §11.1 原文 | 实现（现状） |
|---|---|---|
| 扫描面 | `ui/**` + `state.rs` | `ui/**`（13 文件）+ `src/state.rs`（本轮补上，此前只有 `ui/**`） |
| 基线文件 | `fonts/font_subset_charset.txt` | **`fonts/lv_font_cmap.txt`**（= 各档生成字体 cmap 的**交集**派生清单，324 码位）；若生成了 `.c` 产物则**以产物为准**并与该清单做**漂移检测** |

**为什么基线不能用 `font_subset_charset.txt`（实测，可复现）**：

```bash
python -c "..."   # 见下方结论；或直接比对两个文件的码位集合
```

- `font_subset_charset.txt` 实测 **326** 字符，`lv_font_cmap.txt` **324** 码位；
- 前者**多出 `U+2715(✕)` 与 `U+275A(❚)`** —— 这两个字符**列在 `--symbols` 里但被 `lv_font_conv` 丢弃**，
  生成的 cmap 里**没有**（用旧基线 ⇒ **假阴**：源码里写 `✕` 会被判"有字形"，真机出豆腐块）。

**与 `console_host` 侧那道网是否同源**：**是**（同一个文件）。核验：

- `local-display` 侧：`ui/tests.rs::load_font_cmap()` → 无 `.c` 产物时读 `fonts/lv_font_cmap.txt`（`CMAP_MANIFEST`）；
- `mupc-core-bin` 侧：`console_host.rs::tests::font_cmap()` = `include_str!("../../local-display/fonts/lv_font_cmap.txt")`
  （另有 `config_receipt_messages_use_only_font_cmap_glyphs`（单元 G）/ `interlock_receipt_messages_use_only_font_cmap_glyphs`（单元 J）
  两道回执文案网，以及 `log_service::truncation_marker_is_inside_the_generated_font_cmap`）；
- 两侧**同一文件、同一码位集合**，但**判据不同**（互补而非重复）：
  `local-display` 侧查的是**屏上字面量**，`core-bin` 侧查的是**后端生成的回执/文案串**（那些串不在 `ui/**` 源码里，本地网扫不到）。

#### 4.3.2 【口径订正】§11.1 的「滚动条带内起手 = 内容区起手，变化量**完全一致**」

（**订正（L 收尾，2026-09-18）**：本行原写 `15 + 1024×768×3 = 2 359 312` —— **该算式不成立**
（`15 + 2359296 = 2359311 ≠ 2359312`）。**实测头部为 16 字节**：P6 头 = `P6\n` (3) + `1024 768\n` (9)
+ `255\n` (4) = **16**；`2359296 + 16 = 2359312` ✅。**结果显示的字节数 2 359 312 本身是对的**，
错的只是算式里的加数。）

> ⚠️ **可复现性标注（L 收尾，2026-09-18）—— `blits` 与逐页 `active_px` 都不是稳定值**
>
> 上一行时序里的 **`blits`**、以及六条 `page=P*` 行里的 **`active_px`**，取决于**本次临时桩**
> 返回的载荷与合并窗口内的脏区归并时机，**都不是可复现的定值**：
> - `blits`：独立复核员 **7 次运行**得 **137 / 138** 两个值（**均未写死**：`offscreen_smoke`
>   只断 `blits > 0`）⇒ 上文摘录里的 `blits=138` 是**单次观测**，本量**实测区间 = 137–138**；
> - P3 的 `active_px`：本节记为 **118128**（本次桩的载荷），而独立复核员**同一命令 7 次稳定得
>   **118386** ⇒ **该页数值依赖桩载荷**（尤其日志页的桩行内容），**桩不同即不同**。故本节的
>   118128 只代表**本次那一份临时桩**；`118386` 是复核员桩下的实测值。
>
> 这套数字**本就不该当定值读**：本报告的 stub 是**临时脚本、不入库**（正文只给了调用命令行，
> 没给桩的实现），第三方**无法**复现逐页像素数。**权威的可复现门禁**是
> `tests/offscreen_smoke.rs::offscreen_smoke_renders_six_pages_and_exits_zero` —— 它**自带桩**、
> 只断「每页 `> 0`」「六页里至少 4 个互不相同」「PPM 字节 = `ppm_bytes(1024,768)`」，
> **不写死任何页面像素数**（写死会变成"改样式就红"的脆断言）。

**顺带取到一个此前未量化的数字（设计 §14 R-24 的"余量倍数未量化"）**：
`LV_MEM_SIZE = 1 MB` 的定容池，**6 页 + 外壳 + 整屏降级层全驻留时** `mem_max_used = 374 088 B ≈ 365 KB`（37 %），
`mem_free = 626 368 B`、碎片 3 % ⇒ **1 MB 的余量 ≈ 2.6×**（设计原文只敢写"1 MB 是实测通过值、非最小理论值"）。

> ⚠️ **如实标注**：本次桩服务端的**控制通道** DTO 载荷写得过于最小（`/v1/console/config` 等回 404 或字段不全），
> 故 stderr 出现 `控制通道回执解码失败：missing field groups` 等行 —— 那是**桩的问题**，不是产品问题；
> 控制通道的权威证据是 `tests/control_channel.rs`（6/6 绿，真进程 + 记账桩，含"未确认 ⇒ 零 POST"）。
