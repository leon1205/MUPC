# 可解释性增强：动作归因与奖励分解详细设计

## 一、背景与目标

当前MUPC AI引擎的决策过程对运维人员而言是一个黑盒：输入78维状态向量，输出2维动作（p_ref, k_droop）。当AI做出异常决策（如突然大功率放电）时，运维人员无法快速理解原因，增加了故障排查难度和信任成本。此外，奖励函数的5个子项（光伏消纳、电池损耗、变压器过载等）各自的贡献值也未直观呈现。

**目标**：
1. 对每个决策周期，为每个动作维度（p_ref, k_droop）提供**归因分析**，列出影响最大的Top-N个状态特征及其贡献度。
2. 对每个决策周期，展示**奖励分解**，显示各子项的即时值和累计贡献。
3. 在Web UI上以可视化图表呈现，支持按时间范围查询和历史对比。

---

## 二、技术选型

### 2.1 动作归因方法对比

| 方法 | 适用场景 | 计算开销 | 可解释性 | 推荐度 |
|------|----------|----------|----------|--------|
| **SHAP (Shapley Additive Explanations)** | 模型无关，适用于任何黑盒模型 | 较高（需多次推理） | 强，具有理论一致性 | ⭐⭐⭐ |
| **LIME (Local Interpretable Model-agnostic Explanations)** | 模型无关，局部近似 | 中等 | 较强，但稳定性略差 | ⭐⭐ |
| **Integrated Gradients** | 需要模型梯度 | 低（一次前向+一次反向） | 强，满足敏感性公理 | ⭐⭐⭐（若模型支持梯度） |
| **DeepLIFT** | 类似Integrated Gradients，但基于参考值 | 低 | 强 | ⭐⭐ |

**推荐方案**：**SHAP**作为主要方法，因其理论根基扎实，且支持所有模型类型（包括RKNN导出的黑盒模型）。考虑到NPU推理延迟预算（<100ms），SHAP的计算需要放在**离线或后台异步线程**中执行，不阻塞1Hz实时决策周期。

**折衷方案**：若实时性要求极高，可采用**Integrated Gradients**（需在训练时保留PyTorch模型副本，部署时通过ONNX Runtime CPU推理获取梯度），但会增加部署复杂度。

### 2.2 奖励分解方法

奖励分解是确定性的：每个子项（如R_pv_consumption、P_battery_degradation等）在`RewardCalculator.calculate()`中已分别计算。只需在计算时记录各子项值，并与决策结果一起存储即可。

### 3.2 SHAP Explainer设计

```rust
/// SHAP解释器（后台运行，不阻塞决策周期）
pub struct ShapExplainer {
    /// 参考数据集（background dataset），用于计算基值
    background_data: Arc<Vec<Vec<f32>>>,
    /// RL模型推理函数（用于多次调用以计算SHAP值）
    model_predict: Arc<dyn Fn(&[f32]) -> Vec<f32> + Send + Sync>,
    /// 特征名称列表（与78维输入向量对应）
    feature_names: Vec<String>,
    /// 动作维度名称
    action_names: Vec<String>,
}

impl ShapExplainer {
    /// 计算单步决策的SHAP归因
    ///
    /// 输入：当前78维状态向量
    /// 输出：每个动作维度下，每个特征的贡献值
    pub async fn explain(
        &self,
        state_vector: &[f32],
        num_samples: usize, // 默认100
    ) -> Result<ShapExplanation, AiEngineError> {
        // 1. 使用KernelSHAP（模型无关，适用于任意黑盒）
        // 2. 对每个动作维度分别计算
        // 3. 返回每个特征的SHAP值
        let mut explanations = Vec::new();
        for (action_idx, action_name) in self.action_names.iter().enumerate() {
            // 定义预测函数：输入状态 → 输出该动作维度的值
            let predict_fn = |x: &[f32]| -> f32 {
                let outputs = (self.model_predict)(x);
                outputs[action_idx]
            };
            
            // KernelSHAP核心计算
            let shap_values = kernel_shap(
                state_vector,
                &self.background_data,
                &predict_fn,
                num_samples,
            );
            
            explanations.push(ActionExplanation {
                action_name: action_name.clone(),
                base_value: shap_values.base_value,
                feature_contributions: shap_values.feature_contributions,
            });
        }
        
        Ok(ShapExplanation {
            timestamp: chrono::Utc::now().timestamp_millis(),
            explanations,
        })
    }
}
```

### 3.3 KernelSHAP核心算法（简化伪代码）

```rust
/// KernelSHAP实现（基于抽样近似）
fn kernel_shap(
    x: &[f32],                    // 当前样本
    background: &[Vec<f32>],      // 背景数据集（K个样本）
    predict_fn: &dyn Fn(&[f32]) -> f32,
    num_samples: usize,           // 抽样次数
) -> ShapValues {
    let m = x.len(); // 特征维度=78
    let mut phi = vec![0.0; m];  // SHAP值
    let mut w_sum = 0.0;
    
    for _ in 0..num_samples {
        // 1. 随机选择一个背景样本 z
        let z = &background[rand::thread_rng().gen_range(0..background.len())];
        
        // 2. 随机生成一个特征子集 S（二进制掩码）
        let mask: Vec<bool> = (0..m).map(|_| rand::random::<bool>()).collect();
        
        // 3. 构造两个合成样本：
        //    x_S: 在S中的特征用x的值，其余用z的值
        //    x_S∪{i}: 在S∪{i}中的特征用x的值，其余用z的值
        for i in 0..m {
            let mut x_with_i = x.to_vec();
            let mut x_without_i = x.to_vec();
            for j in 0..m {
                if j == i || mask[j] {
                    // 使用x的值（已在初始化中）
                } else {
                    x_with_i[j] = z[j];
                    x_without_i[j] = z[j];
                }
            }
            // 注意：上面的简化不对，正确的KernelSHAP需要对每个特征i和每个子集S进行加权求和
            // 实际实现应使用成熟的SHAP库（如Python shap库导出为ONNX模型）
        }
    }
    
    // 返回phi（此处省略加权平均细节）
    ShapValues { base_value: predict_fn(&mean_of_background), feature_contributions: phi }
}
```

> **实际建议**：鉴于Rust生态中尚无成熟的SHAP库，建议采用以下两种方式之一：
> 1. **Python sidecar**：在RK3588上运行一个轻量级Python进程（使用`shap`库），通过IPC（Unix socket或共享内存）接收状态向量和模型预测结果，返回SHAP值。该进程优先级低于Rust主进程，避免影响实时推理。
> 2. **预计算近似模型**：在离线训练阶段，使用XGBoost或LightGBM训练一个**模仿RL模型行为的代理模型**（surrogate model），然后利用树模型的SHAP快速计算方法。代理模型可以部署在Rust中（通过`tract`或`ort`推理），计算延迟<10ms。

**推荐方案2**：代理模型方式，因为无需依赖Python运行时，且计算速度快。

**代理模型训练流程**：
1. 收集过去1个月的所有决策数据（状态+动作），约260万条（1Hz × 30天 × 24h × 3600s）。
2. 从中随机抽取10万条作为训练集。
3. 训练两个LightGBM回归模型（目标分别为p_ref和k_droop），使用均方误差损失。
4. 验证集R² > 0.95（确保代理模型足够逼近原RL模型）。
5. 导出为ONNX，部署到RK3588。

**推理延迟**：树模型SHAP计算延迟约1~5ms（取决于树的数量），可在后台线程中每N个决策周期（如每10秒）触发一次，不影响主循环。

## 四、奖励分解实现方案

### 4.1 数据结构

```rust
/// 奖励分解记录
#[derive(Debug, Clone, Serialize)]
pub struct RewardBreakdown {
    pub timestamp: i64,
    pub mode: RunningMode,
    pub total_reward: f64,
    pub components: Vec<RewardComponent>,
}

#[derive(Debug, Clone, Serialize)]
pub struct RewardComponent {
    pub name: String,           // 如 "R_pv_consumption"
    pub display_name: String,   // 如 "光伏消纳奖励"
    pub value: f64,             // 原始值（未加权）
    pub weight: f64,            // 当前权重
    pub weighted_value: f64,    // value * weight
    pub unit: String,           // 如 "分", "kW", "%"
    pub direction: String,      // "正向" 或 "负向"
    pub percentage: f64,        // 占总奖励的百分比（绝对值占比）
}
```

### 4.2 在RewardCalculator中记录

修改`RewardCalculator.calculate()`，使其返回`RewardBreakdown`而非单一的`f64`：

```rust
impl RewardCalculator {
    /// 计算奖励并返回分解
    pub fn calculate_with_breakdown(
        &self,
        mode: RunningMode,
        action: &ActionOutput,
        state: &FusedSystemState,
    ) -> (f64, RewardBreakdown) {
        let mut components = Vec::new();
        let total: f64;
        
        match mode {
            RunningMode::SeasonalLoadManagement => {
                let (r_pv, p_deg, p_trafo, r_pq, r_ramp, r_v_slope, r_smooth, r_override) = 
                    self.calc_agri_components(state, action);
                
                let w = &self.weights.seasonal_load_management;
                let weighted = [
                    w[0]*r_pv, -w[1]*p_deg, -w[2]*p_trafo, w[3]*r_pq,
                    -w[4]*r_ramp, -w[5]*r_v_slope, -w[6]*r_smooth, -w[7]*r_override
                ];
                total = weighted.iter().sum();
                
                components = vec![
                    RewardComponent::new("R_pv", "光伏消纳奖励", r_pv, w[0], weighted[0], "分", "正向"),
                    RewardComponent::new("P_batt_deg", "电池损耗惩罚", p_deg, w[1], weighted[1], "分", "负向"),
                    // ... 其余子项
                ];
            }
            // ... 其他场景
        }
        
        // 计算各子项占总奖励绝对值比例
        let abs_total: f64 = components.iter().map(|c| c.weighted_value.abs()).sum();
        for comp in &mut components {
            comp.percentage = if abs_total > 0.0 {
                comp.weighted_value.abs() / abs_total * 100.0
            } else {
                0.0
            };
        }
        
        (total, RewardBreakdown {
            timestamp: chrono::Utc::now().timestamp_millis(),
            mode,
            total_reward: total,
            components,
        })
    }
}
```

### 4.3 存储策略

- **实时存储**：每个决策周期的`RewardBreakdown`写入环形缓冲区（内存中保留最近1小时），用于Web UI实时刷新。
- **持久化存储**：每5分钟批量写入本地SQLite或时序数据库（如InfluxDB），保留30天。
- **采样存储**：为节省存储空间，可对归因数据（SHAP值）进行降采样，每10个周期存储一条。

## 六、性能与资源考量

| 组件 | 计算频率 | 延迟预算 | 存储需求 |
|------|----------|----------|----------|
| 奖励分解 | 每个决策周期（1Hz） | <0.1ms（已在RewardCalculator中） | 约100字节/周期 → 8.6MB/天 |
| SHAP归因（代理模型） | 每10个周期（0.1Hz） | <10ms（后台线程） | 约2KB/次（78个特征×2个动作）→ 17MB/天（降采样后） |
| SHAP归因（Python sidecar） | 每30个周期（0.033Hz） | <100ms（IPC延迟） | 同上 |

**建议配置**：
- 代理模型方式：每10秒计算一次SHAP，存储在内存环形缓冲区（最近1000条），持久化到磁盘时每5分钟批量写入。
- 若使用Python sidecar，需确保其优先级低于Rust主进程，可使用`nice`命令降低CPU优先级。

## 九、总结

通过集成代理模型SHAP归因和奖励分解记录，MUPC AI引擎的可解释性将得到质的提升：

- **运维人员**可以快速理解AI为何做出特定决策，增强信任感。
- **故障排查**时，可追溯到具体哪个特征导致了异常动作。
- **模型调优**时，可根据特征重要性分布判断是否需要调整状态空间或奖励函数。
- **合规审计**时，可提供完整的决策日志和归因报告。

该方案在工程上可行，对实时性能影响极小（归因计算放在后台线程，不阻塞1Hz决策周期），且充分利用了已有的奖励计算逻辑。建议在Phase 3C结束后，作为Phase 4的增强功能纳入开发计划。
