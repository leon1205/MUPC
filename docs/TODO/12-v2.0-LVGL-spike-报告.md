### 1.4 踩到的坑（3 个，均为真实报错）

#### 坑 1（**Windows 专有，必改**）：`canonicalize()` 的 `\\?\` verbatim 前缀 → `cl.exe` C1083

```
c1: fatal error C1083: 无法打开源文件: "\\?\E:\MUPC2\mupc\vendor\lvgl\src\core\lv_group.c"
error occurred in cc-rs: command did not execute successfully (status code exit code: 2)
```

原因：`Path::canonicalize()` 在 Windows 返回 `\\?\E:\...`，`cl.exe` **不认**该前缀（include 路径同样受影响）。
处置：`build.rs` 加 `strip_verbatim()` 剥离前缀（含 `\\?\UNC\` 分支）。Linux 上是 no-op。

#### 坑 2（**架构级发现，必改**）：排除 `src/libs/**` → 链接期 `LNK2019: lv_bin_decoder_init`

```
liblvgl_sys-….rlib(lv_init.o) : error LNK2019: 无法解析的外部符号 lv_bin_decoder_init，函数 lv_init 中引用了该符号
```

原因：`src/lv_init.c:298` **无条件**调用 `lv_bin_decoder_init();`（**没有 `LV_USE_*` 守卫**），
而它定义在 `src/libs/bin_decoder/lv_bin_decoder.c`。
处置：`build.rs` 改为"跳过 `src/libs/**`，**但白名单 `bin_decoder` + `rle`** 两个子目录"（`rle` 是 bin_decoder 的依赖）。
> 设计文档与 §12.1 未提及此项，实施时必须带着这个白名单，否则任何"只编核心"的想法都会在链接期爆掉。

#### 坑 3（**非阻塞**）：bindgen / libclang

`export LIBCLANG_PATH='C:\Program Files\LLVM\bin'` 后 **bindgen 开箱即用**：
未出现设计 §12.1 预告的 `Unable to find libclang`，也**未出现 `stdarg.h` 找不到**，
**`BINDGEN_EXTRA_CLANG_ARGS` 全程未使用**（clang 23 自动定位到了 MSVC 的 UCRT/STL 头）。
> 即：设计 §12.1 的"Windows 前置清单"里，`BINDGEN_EXTRA_CLANG_ARGS` 这条是**有备无患的兜底，不是必经步骤**。

### 3.3 体积实测（**这是本 spike 对设计最重要的修正**）

| 口径 | 实测 | 说明 |
|------|------|------|
| `lv_font_noto_sc_32.c` 文本大小 | **830,590 B (811 KB)** | `ls -l` 看到的就是它 |
| **位图字节数（真实进二进制的量）** | **131,793 B (128.7 KB)** | `grep -o '0x…' \| wc -l` |
| **启用 RLE 压缩**（去掉 `--no-compress`） | `.c` 489,851 B / **位图 71,078 B (-46%)** | 一行开关 |
| 编译产物 `liblvgl_fonts.a` (release) | **136,892 B (134 KB)** | 1 档 32px、326 字符的完整落盘体积 |
| 设计 §1.1.2 预算 | 「单档 **20–80 KB**；5 档合计 **≤300 KB**」 | **超标 ≈1.6×（未压缩）/ 达标（压缩）** |

**两个必须澄清的口径问题**：

1. **`.c` 文本 ≠ 体积**：C 十六进制文本约为位图的 **6.3 倍**（131,793 → 830,590 B）。设计 §1.1.2 写的是
   "构建后 `ls -l` 复核"，若照此执行会**把 811 KB 当成本档体积**（误差 6 倍）。**应以位图字节数或 `.a` 落盘体积为准。**
2. **总预算 ≤300 KB 几乎肯定不可能**：位图体积随字号**平方增长**。以 32px 为 129 KB 外推，
   96px ≈ 129 KB × 9 ≈ **1.16 MB（未压缩）/ ~0.64 MB（压缩）**，5 档合计约 **2.0–2.5 MB**。
   处置建议（需产品侧拍板，见 §5）：启用 RLE（必做）＋ 缩减档位（如 4 档）＋ 大字号改用
   少量字符的专用子集（SOC 数值只需 `0-9 . %`），或把总预算改到 1–2 MB。

（S-2 里则是 4 个**完全一样的方框**），后 8 位 `SOC 92%` 为拉丁/数字。
**退出码 0**。

> **诚实标注**：`连通域数 ≥ 字数` 这条断言的**判别力有限**——缺字占位也是"每个字一个方框"，
> S-2 的 6 个连通域同样是方框连通块。**真正有判别力的是"前景像素量（×5.7）"与 ASCII 图**。
> 设计 §1.1.3 把"连通域数 ≈ 字数"当判据是**偏弱的**，建议正式测试改判"文本区墨量密度"或
> 逐字模板比对（见 §5 未决项 4）。

## 4. 三项风险的判断

### 4.1 R-19：自写绑定层的工作量（XL）—— **设计估算基本可信，略偏乐观**

**实测锚点**：35 条 allowlist（21 fn / 12 type / 2 var）→ 852 行 `bindings.rs`；
S-2 全过程（init/tick/display/双缓冲/flush/obj/label/style/font/render）**只用了 21 个 C 函数**。

**外推**：设计 §5.1 列的薄层共 8 个模块，用点约 20 个控件。按实测的"每控件 ≈ 1 构造 + 6–10 个 setter"
（每个 setter ≈ 8–15 行含文档注释），20 控件 ≈ 900–1500 行；再加
`display.rs`（PARTIAL 双缓冲 + flush 桥）、`indev.rs`（read_cb 桥）、`event.rs`（user_data 生命周期）、
`style.rs`（主题单一真源）、`font.rs` ≈ 400–700 行 → **合计约 1300–2200 行**。
⇒ 设计给的 **1000–1800 行** 与实测形态吻合，**略偏乐观但可排期**；
`build.rs + lv_conf.h + allowlist 维护` 的 150–300 行估算**准确**（本轮 build.rs 实测 ~190 行 + lv_conf 100 行 + allowlist 57 行 ≈ 347 行，其中注释占比高）。

**绑定层的实际形态**（示意，取自本轮验证过的调用姿势）：

```rust
// crates/local-display/src/lvgl/display.rs —— 唯一 unsafe 边界之一
use lvgl_sys as sys;

pub struct Display { raw: *mut sys::lv_display_t, _buf1: Vec<u8>, _buf2: Vec<u8> }

/// P-1：自研 lv_display + PARTIAL 双缓冲 + flush 桥（设计 §1.1.1.1）
pub fn create(w: i32, h: i32, sink: impl Fn(sys::lv_area_t, &[u8]) + 'static) -> Display {
    let buf_pixels = (w as usize * h as usize) / 10;      // §10 预算：2 × 1/10 屏
    let mut buf1 = vec![0u8; buf_pixels * 4];             // XRGB8888
    let mut buf2 = vec![0u8; buf_pixels * 4];
    unsafe {
        let raw = sys::lv_display_create(w, h);
        assert!(!raw.is_null());
        sys::lv_display_set_default(raw);
        sys::lv_display_set_buffers(
            raw, buf1.as_mut_ptr().cast(), buf2.as_mut_ptr().cast(),
            (buf_pixels * 4) as u32, sys::LV_DISPLAY_RENDER_MODE_PARTIAL,
        );
        // 回调桥：Box::into_raw 保管 closure，flush_cb 内经 user_data 取回（不 panic）
        let cb: Box<dyn Fn(sys::lv_area_t, &[u8])> = Box::new(sink);
        sys::lv_display_set_user_data(raw, Box::into_raw(cb).cast());  // 生产需补 Drop 侧 from_raw
        sys::lv_display_set_flush_cb(raw, Some(trampoline));
        Display { raw, _buf1: buf1, _buf2: buf2 }
    }
}

unsafe extern "C" fn trampoline(d: *mut sys::lv_display_t, area: *const sys::lv_area_t, px: *mut u8) {
    // 1) 取出 user_data closure；2) 按 (x2-x1+1)*(y2-y1+1)*4 构造 slice；3) 调 sink；4) flush_ready
    // 纪律：此处绝不 panic（跨 FFI 展开 = UB），一律走错误码/日志（设计 §1.1.1.2 纪律 3）
    unsafe { sys::lv_display_flush_ready(d) };
}
```

**结论**：绑定层确实是"机械但确定"的工作量，**不是研究风险**；风险集中在
`event.rs` 的 `user_data` 生命周期与 `indev.rs` 的 read_cb 桥（这两处最不机械）。

### 4.2 R-20：三平台 C 编译链 —— **Windows MSVC 走通；aarch64 交叉仅静态预判（未实测）**

**Windows（实测走通）**：`cc` 自动探测到 MSVC 19.33，`bindgen` + LLVM 23 开箱即用，
`BINDGEN_EXTRA_CLANG_ARGS` **未使用**。踩坑 3 处见 §1.4（其中"`\\?\` 前缀"与"`src/libs` 白名单"
是**必须写进 build.rs 的硬知识**，不是环境问题）。

**aarch64 交叉（本机无工具链，未实测，以下为静态预判）**：

| 环节 | 配置 | 风险 |
|------|------|------|
| C 编译 | `CC_aarch64_unknown_linux_gnu=aarch64-linux-gnu-gcc`（`cc` crate 原生认这个变量），链接器走既有的 `CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER`（`mupc/.cargo/config.toml` 已配） | 低。**无新增前置**（`gcc-aarch64-linux-gnu` 项目已有） |
| bindgen | 本 spike 的 `build.rs` 已实现：`TARGET != HOST` 时追加 `--target=$TARGET`。**风险点**：clang 需要目标的 libc 头（sysroot），否则 `stdint.h/stdarg.h` 找不到 | **中**。两个处置（建议实施时择一验证）：<br>① `BINDGEN_EXTRA_CLANG_ARGS="-isystem /usr/aarch64-linux-gnu/include"`（设计 §12.1 预告的坑）；<br>② **64 位宿主 → 64 位目标**时基本类型尺寸一致，可**不传 `--target`**（直接用宿主 triple 生成），彻底绕开 sysroot 依赖 |
| 路径 | `strip_verbatim()` 仅 Windows 生效，Linux 是 no-op | 无 |

> **建议**：实施阶段把"交叉 bindgen"作为**第一个要跑通的验证点**（一条 `cargo build --target aarch64-unknown-linux-gnu -p lvgl-sys` 即可暴露全部问题）。
> 另注意 `-fvisibility=hidden`（本 spike 在 linux target 下已加）。

### 4.3 R-01：CJK 字形链 —— **可行，字形可辨；但设计给的体积预算不可信**

- 可行性：**PASS**，一次成功、5.3 s、无报错，字形肉眼可辨（§3.4）。
- 体积：**单档 32px = 128.7 KB 位图（未压缩）/ 71.1 KB（RLE）** ——
  **设计"20–80 KB"只在启用 RLE 时才成立**；且 5 档合计 **≤300 KB 不可能**（外推 2.0–2.5 MB）。
  设计 §1.1.2 建议的 `--no-compress` **恰好是导致超标的那个开关**，与"降到 2bpp"并列的两个候选处置里，
  **"启用 RLE"应当优于"降到 2bpp"**（RLE 无损、不掉画质；2bpp 会牺牲 UI V-4 的密笔画可辨性）。
- 另：`.`c` 文本 811 KB × 5 档 ≈ 4 MB 若入库会污染仓库；建议
  **`fonts/*.otf` 与 `fonts/*.c` 都不入库**（`.gitignore`），只入库 `gen_fonts.sh` + `extract_charset.py`
  + `font_subset_charset.txt` + 许可文本，构建前跑一次生成（或纳入构建脚本）。
