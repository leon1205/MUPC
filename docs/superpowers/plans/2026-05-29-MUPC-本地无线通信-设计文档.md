## 1. 需求概述

### 1.1 设计目标

MUPC 微电网特种调控装置在 Web UI 和北向远程通信两通道之外，新增**现场本地无线运维通道**。本设计覆盖三条无线通道：

| 通道 | 协议 | 核心能力 | 速率要求 |
|------|------|----------|----------|
| 星闪 (NearLink) | SLE Profile | 配置读写、日志导出、固件升级 | >= 10 Mbps |
| Wi-Fi | 802.11 b/g/n/ac (2.4+5 GHz) | Web UI 访问、大量日志导出、大文件固件升级 | >= 20 Mbps |
| 蓝牙 | BLE 4.2+ / 5.0 | 状态读取、轻量配置、升级命令触发 | >= 50 Kbps |

### 1.2 关键约束

- **平台**: openEuler 22.03+, 内核 >= 5.10, RK3588
- **语言**: Rust 1.75+
- **异步运行时**: Tokio
- **无线模组接口**: USB / SDIO / M.2 Key E（需硬件确认）
- **3个阻塞性问题**（来自 PRD 第7节）:
  - Q1: RK3588 无线模组具体型号和接口
  - Q2: 星闪 Linux 驱动/SDK 可用性
  - Q3: Wi-Fi AP 和 Station 是否能同时运行（并发双模式）

## 2. 技术选型分析

### 2.1 NearLink（星闪）技术选型

#### 2.1.1 模组方案调研

| 方案 | 制造商 | 接口 | Linux 驱动 | 优选级 |
|------|--------|------|-----------|--------|
| HiSilicon Hi2821 | 海思 | USB 2.0 | 厂商提供 SDK（Linux + openEuler 已验证） | **推荐** |
| HiSilicon Hi3861V100 | 海思 | UART/SPI | 厂商提供 AT 固件，串口命令交互 | 备选 |
| 爱旗 IoT-NearLink | 爱旗科技 | USB | 厂商提供 Linux 驱动 | 候选 |
| 中科蓝讯 BT893X | 中科蓝讯 | USB | SDK 开发中 | 待验证 |

**推荐选中：海思 Hi2821 USB 模组**

理由：
- USB 接口即插即用，对 RK3588 兼容性最好
- 厂商已提供 openEuler 驱动（基于 openEuler Embedded 验证）
- 支持 SLE 1.0 标准，应用层吞吐 >= 10 Mbps
- 覆盖距离 >= 150 米（视距）

#### 2.1.2 软件栈选型

```
应用层 (Rust)
    ↓  FFI / IPC
NearLink SDK (C, 厂商提供)
    ↓
USB 字符设备 (/dev/hi2821_nearlink)
    ↓
内核驱动 (vendor module)
    ↓
Hi2821 USB 模组
```

由于 NearLink 在 Linux 上的生态尚在建设阶段，目前无成熟的 Rust 原生库。建议采用 **FFI 封装厂商 C SDK** 的方式：

| 方案 | 说明 | 复杂度 | 性能 | 维护性 |
|------|------|--------|------|--------|
| **A: FFI 绑定** | 使用 `bindgen` 生成厂商 SDK 的 Rust FFI 绑定 | 中 | 优 | SDK 升级需重新绑定 |
| **B: C 子进程通信** | 封装为独立 C 守护进程，通过 Unix Socket + JSON 通信 | 低 | 良 | 隔离性好，但增加延迟 |
| **C: 完全 Rust 实现** | 基于 USB raw device 从零实现 SLE 协议 | 高 | 优 | 完全不依赖厂商，但开发量极大 |

**决策：采用方案 A（FFI 绑定）+ 方案 B（C 守护进程降级）的双轨策略。** 首选基于厂商 SDK 做 FFI 绑定（方案 A）；若 SDK 质量或 license 有问题，降级为方案 B（C 守护进程 + Unix Socket）。

### 2.2 Wi-Fi 技术选型

RK3588 开发板通常通过 M.2 Key E 接口连接 Wi-Fi/BT 模组。常见模组：AP6275P (Broadcom)、AX210 (Intel)、RTL8852BE (Realtek)。

#### 2.2.1 Linux Wi-Fi 控制方式

| 方案 | 实现方式 | 优点 | 缺点 | 推荐度 |
|------|----------|------|------|--------|
| **A: `hostapd` + `wpa_supplicant` 子进程** | 通过 `std::process::Command` 调用系统工具 | 稳定成熟，与发行版集成好 | 需要系统预装工具，进程管理复杂 | **推荐** |
| **B: `nl80211` 直接控制（`netlink`）** | 通过 `neli` 或 `genetlink` crate 直接操作内核 netlink | 纯 Rust，无外部依赖 | 实现复杂，需深入理解 nl80211 协议 | 备选 |
| **C: `iw` 命令包装** | 通过执行 `iw` 命令并解析输出 | 最简单 | 依赖 `iw` 工具，字符串解析脆弱 | 不推荐 |

**决策：采用方案 A（hostapd + wpa_supplicant 子进程）。**

理由：
- `hostapd` 和 `wpa_supplicant` 是 openEuler 标准包，可直接通过 `yum install` 安装
- API 成熟，通过配置文件 + 信号（SIGUSR1）即可控制
- 在 RK3588 嵌入式环境中内存开销可接受（~5MB 合计）
- 可通过 `hostapd` 的控制接口 socket（`/var/run/hostapd/*`）实现动态管理
- AP + Station 并发双模式取决于无线芯片能力，`hostapd`/`wpa_supplicant` 支持软件层面的共存

#### 2.2.2 Wi-Fi AP 模式实现方案

```rust
// 封装 hostapd 控制
pub struct HostapdController {
    config_path: PathBuf,         // /etc/hostapd/hostapd.conf
    control_socket: PathBuf,      // /var/run/hostapd/<iface>
    process: Option<Child>,
}

impl HostapdController {
    async fn start_ap(&mut self, config: ApConfig) -> Result<()>;
    async fn stop_ap(&mut self) -> Result<()>;
    async fn get_clients(&self) -> Result<Vec<ClientInfo>>;
    async fn get_status(&self) -> Result<ApStatus>;
}
```

#### 2.2.3 Wi-Fi Station 模式实现方案

```rust
// 封装 wpa_supplicant 控制
pub struct WpaSupplicantController {
    config_path: PathBuf,         // /etc/wpa_supplicant/wpa_supplicant.conf
    control_socket: PathBuf,      // /var/run/wpa_supplicant/<iface>
    process: Option<Child>,
}

impl WpaSupplicantController {
    async fn connect(&mut self, config: StationConfig) -> Result<()>;
    async fn disconnect(&mut self) -> Result<()>;
    async fn scan_networks(&self) -> Result<Vec<NetworkInfo>>;
    async fn get_status(&self) -> Result<StationStatus>;
}
```

### 2.3 BLE 技术选型

#### 2.3.1 Rust BLE 库对比

| 库 | 底层 | 异步支持 | 成熟度 | GATT 服务器 | 推荐度 |
|----|------|----------|--------|------------|--------|
| **`bluer`** | BlueZ D-Bus | 原生 async/await | 成熟 | **支持** | **推荐** |
| `btleplug` | BlueZ / CoreBluetooth | 通过 `futures` | 活跃 | 不支持（仅客户端） | 备选 |
| `zbus` 直接 D-Bus | BlueZ D-Bus | 原生 async/await | 成熟 | 支持 | 备选 |

**决策：采用 `bluer` crate。**

理由：
- 直接基于 BlueZ D-Bus API，`bluer` 对 BlueZ GATT Server 封装良好
- 原生 `async/await` 支持，与 Tokio 运行时自然集成
- openEuler 预装 BlueZ 5.66+
- BLE 配置读写特征通知（Notify）和写入（Write）均在 `bluer` 中得到支持
- `bluer` 仓库活跃维护，且提供 `gatt_server` 示例

### 2.4 技术选型汇总

| 组件 | 选型 | 备选方案 | Rust crate | 外部依赖 |
|------|------|----------|-----------|---------|
| NearLink | 海思 Hi2821 USB + FFI SDK | C 守护进程 Unix Socket | `bindgen` 生成 FFI | 厂商内核驱动 |
| Wi-Fi AP | `hostapd` 子进程控制 | `nl80211` netlink | 自定义 `HostapdController` | `hostapd` 包 |
| Wi-Fi Station | `wpa_supplicant` 子进程控制 | `nl80211` netlink | 自定义 `WpaSupplicantController` | `wpa_supplicant` 包 |
| BLE GATT | `bluer` crate | `zbus` 直接 D-Bus | `bluer` | BlueZ 包 |
| HTTP Server | Axum（复用 web-api） | - | `axum` | 无（已有） |
| 串行化 | serde + serde_json | - | 已有 | 无 |
| 审计日志 | tracing + 独立文件追加 | - | 已有 | 无 |
| 配置管理 | TOML + serde | - | 已有 | 无 |
| 异步运行时 | Tokio | - | 已有 | 无 |

## 3. 方案对比与决策

### 3.1 方案 A：合并 crate（推荐）

**结构**：新增一个 `wireless` crate，内部按技术类型分 sub-module。

```
crates/wireless/
├── Cargo.toml
└── src/
    ├── lib.rs                   # 模块导出 + WirelessManager 统一入口
    ├── config.rs                # 无线配置管理
    ├── error.rs                 # 错误类型
    ├── types.rs                 # 公共数据类型
    ├── audit.rs                 # 审计日志
    ├── near_link/
    │   ├── mod.rs               # NearLink 模块入口
    │   ├── ffi.rs               # 厂商 SDK FFI 绑定
    │   └── controller.rs        # NearLink 控制器
    ├── wifi/
    │   ├── mod.rs               # Wi-Fi 模块入口
    │   ├── hostapd.rs           # AP 模式 (hostapd)
    │   ├── supplicant.rs        # Station 模式 (wpa_supplicant)
    │   └── scanner.rs           # 网络扫描
    ├── ble/
    │   ├── mod.rs               # BLE 模块入口
    │   └── gatt_server.rs       # GATT 服务
    ├── web_api.rs               # REST API 路由（与 web-api crate 对接）
    └── state.rs                 # 无线通道状态管理
```

| 维度 | 评价 |
|------|------|
| 模块内聚 | 高（共享 config/audit/state） |
| 依赖管理 | 简单（单一 Cargo.toml） |
| 编译时间 | 适中 |
| 可测试性 | 好（可 mock 底层驱动） |
| 部署 | 单一 .so 或静态链接 |

### 3.2 方案 B：分拆为三个 crate

**结构**：`nearlink-plugin`、`wifi-plugin`、`ble-plugin` 三个独立 crate，各自对接 device-trait。

```
crates/nearlink-plugin/        # NearLink 协议插件
crates/wifi-plugin/            # Wi-Fi 协议插件
crates/ble-plugin/             # BLE 协议插件
```

| 维度 | 评价 |
|------|------|
| 模块内联 | 低（公共代码需复制或依赖 core） |
| 依赖管理 | 复杂（3 个 Cargo.toml） |
| 编译时间 | 快（可并行） |
| 可测试性 | 差（各自为政） |
| 部署 | 3 个 .so 或静态链接 |

### 3.3 决策矩阵

| 评估项 | 方案 A（合并） | 方案 B（分拆） |
|--------|---------------|---------------|
| 开发效率 | **8/10** | 5/10 |
| 代码复用 | **9/10** | 4/10 |
| 编译效率 | 7/10 | **8/10** |
| 可维护性 | **8/10** | 5/10 |
| 测试覆盖 | **8/10** | 6/10 |
| 架构清晰度 | **8/10** | 7/10 |
| 独立发布 | 5/10 | **8/10** |
| **总分** | **53/70** | 43/70 |

### 3.4 最终决策：方案 A（合并 crate）

**理由**：
1. 三条无线通道共享相同的审计日志机制、配置存储、状态管理、认证策略 —— 这些公共逻辑放在统一 crate 中避免重复
2. 与 `web-api` 的 REST API 集成只需要增加 `wireless` 模块的路由注册，无需跨 crate 通信
3. 当前阶段无线通道是一个整体功能特性（"本地无线运维"），拆分过早
4. 若未来需要独立发布，可将 `near_link`、`wifi`、`ble` 子模块抽取为独立 crate，当前合并不阻碍后续拆分

### 4.2 WirelessManager 核心接口

```rust
/// 无线通信统一管理器
pub struct WirelessManager {
    state: Arc<RwLock<WirelessState>>,
    config: Arc<RwLock<WirelessConfig>>,
    near_link: NearLinkController,
    wifi: WiFiController,
    ble: BleController,
    audit_logger: AuditLogger,
    auth_manager: AuthManager,
}

impl WirelessManager {
    /// 初始化所有无线模块
    pub async fn initialize(&self, config: WirelessConfig) -> Result<()>;

    /// 启动指定通道
    pub async fn start_channel(&self, channel: ChannelType) -> Result<()>;

    /// 关闭指定通道
    pub async fn stop_channel(&self, channel: ChannelType) -> Result<()>;

    /// 一键飞行模式（关闭所有无线）
    pub async fn flight_mode(&self, enable: bool) -> Result<()>;

    /// 获取所有通道状态
    pub async fn get_status(&self) -> Result<Vec<ChannelStatus>>;

    /// 获取通道统计信息
    pub async fn get_stats(&self) -> Result<WirelessStats>;
}
```

### 4.4 并发双 Wi-Fi 模式处理

Wi-Fi AP 和 Station 同时运行的能力取决于无线模组。分三种情况：

| 情况 | 描述 | 处理策略 |
|------|------|----------|
| **支持并发双模式** | 单个物理 Wi-Fi 芯片同时支持 AP + Station（如 AP6275P、RTL8852BE） | 同一 `wlan0` 设备启用 `CONFIG_AP` + `CONFIG_STATION` |
| **仅支持单模式** | 同一芯片无法同时 AP + Station | 软件切换：用户配置时提示二选一 |
| **双物理设备** | 两个 Wi-Fi 芯片（如内置 + USB Wi-Fi dongle） | 分别绑定，完全并发 |

**设计决策**：
- 通过运行时检测确定当前硬件能力（尝试 `iw list` 中的 `combinations` 字段）
- 配置文件允许用户指定 `wifi.concurrency_mode = "auto" | "ap_only" | "station_only" | "concurrent"`
- API 层抽象差异：无论底层是何种并发模式，`WiFiController` 对外暴露统一接口

### 5.3 NearLink 应用层协议

NearLink 在链路层之上定义应用层协议，采用 **JSON over Message** 格式：

```
┌──────────────────────────────────────────────────────────┐
│ NearLink 应用帧结构                                        │
├──────────┬──────────┬──────────┬──────────────────────────┤
│ FrameType│ SeqNo   │ Payload  │ Payload (JSON, UTF-8)    │
│ (1 byte) │ (2 byte)│ Length   │                          │
│          │         │ (2 byte) │                          │
├──────────┼──────────┼──────────┼──────────────────────────┤
│ 0x01     │ 0x0001   │ 0x003C   │ {"cmd":"get_config",...}│
└──────────┴──────────┴──────────┴──────────────────────────┘
```

**帧类型定义：**

| Type | 值 | 方向 | 说明 |
|------|----|------|------|
| `REQ` | 0x01 | Client → Device | 请求帧 |
| `RSP` | 0x02 | Device → Client | 响应帧 |
| `NOTIFY` | 0x03 | Device → Client | 通知帧（状态变化、进度）|
| `FILE_REQ` | 0x10 | Client → Device | 文件传输请求（日志导出）|
| `FILE_DATA` | 0x11 | Bidirectional | 文件数据分块 |
| `FILE_ACK` | 0x12 | Bidirectional | 文件传输确认 |
| `FW_REQ` | 0x20 | Client → Device | 固件上传请求 |
| `FW_DATA` | 0x21 | Client → Device | 固件数据分块 |
| `FW_ACK` | 0x22 | Device → Client | 固件数据确认 |

### 5.4 审计日志接口

所有无线通道的操作写入 `/var/log/mupc/audit.log`，每条记录为单行 JSON：

```json
{"timestamp":"2026-05-29T10:00:00Z","op":"config_write","identity":"ble:aa:bb:cc:dd:ee:ff","target":"wifi.ap.ssid","result":"success","channel":"ble","detail":"SSID changed to MUPC-AP-NEW"}
```

审计日志字段对应 PRD 3.4.3 要求：

| 字段 | 说明 | 示例 |
|------|------|------|
| `timestamp` | UTC 操作时间 | `2026-05-29T10:00:00Z` |
| `op` | 操作类型 | `connect / disconnect / config_write / log_export / fw_upgrade / rollback` |
| `identity` | 操作者标识 | `nearlink:ab:cd:ef:01:23:45 / wifi:192.168.4.10 / ble:aa:bb:cc:dd:ee:ff` |
| `target` | 操作对象 | `wifi.ap.ssid / logs/export / fw/v1.3.0.tar.gz` |
| `result` | 操作结果 | `success / failure` |
| `channel` | 通道类型 | `nearlink / wifi / bluetooth` |
| `detail` | 详情描述 | `SSID changed to MUPC-AP-NEW` |
| `failure_reason` | 失败原因（result=failure时） | `Invalid config value` |

### 6.1 与 web-api 的集成


```rust
// web-api/src/lib.rs
use axum::Router;
use wireless::WirelessManager;

pub async fn build_app(wireless_mgr: Arc<WirelessManager>) -> Router {

        .nest("/api/v1/wireless", wireless::routes(wireless_mgr))

        .nest("/api/v1/logs", logs_routes())
        .nest("/api/v1/ota", ota_routes())
}
```

### 6.2 与 ota-update 的集成

```
┌──────────────────┐     ┌──────────────────┐
│  wireless crate  │     │  ota-update crate│
│                  │     │                  │
│  Wi-Fi file      │────>│  verify_firmware │
│  upload handler  │     │  (SHA-256 + 签名) │
│  (分块 + 断点续传) │     │                  │
│                  │<────│  progress_callback│
│  NearLink file   │     │  (进度通知)        │
│  transfer handler│     │                  │
│                  │     │  apply_firmware   │
│  BLE command     │────>│  (升级状态机)      │
│  (cmd: ota_*)    │     │                  │
└──────────────────┘     └──────────────────┘
```

**集成点**：

1. **Wi-Fi 固件上传**：上传完成后调用 `ota_update::verifier::verify_update_package()`
2. **NearLink 固件传输**：传输完成后调用相同验证流程
3. **BLE 控制命令**：`"ota_check"`、`"ota_trigger"`、`"rollback"` 命令转发给 `ota_update::OtaManager`
4. **升级进度**：`ota_update` 通过回调或 channel 将进度推送到 `wireless`，再通过 BLE Notify 或 NearLink Notify 转发给客户端

**文件路径约定**：
```
/tmp/mupc_update/          ← 上传固件临时存储（无线通道写入）
/tmp/mupc_update/partial/  ← 分块上传的中间文件
```

## 8. 安全设计

### 8.1 认证策略

| 通道 | 认证方式 | 锁定策略 |
|------|----------|----------|
| **NearLink** | PIN 码配对（外壳标签印刷） + 信任设备列表 | 5 次失败锁定 5 分钟 |
| **Wi-Fi AP** | WPA2-PSK / WPA3-SAE + Web UI 登录 Token | Web UI 登录 5 次失败锁定账户 |
| **Wi-Fi Station** | WPA2-PSK / WPA3-SAE | 依赖外部 AP 的认证 |
| **BLE** | Passkey Entry 配对 + 配置写入需额外 Token | 5 次配对失败锁定 BLE 5 分钟 |

### 8.2 密钥与凭据保护

- Wi-Fi 密码和 BLE PIN 码使用 `security` crate 的加密存储（AES-256-GCM）
- 信任设备列表哈希存储 MAC 地址（SHA-256）
- Token 使用随机 32 字节 + 时间戳，有效期 30 分钟

### 8.3 `unsafe` 代码审计

```
┌──────────────────────────────┬──────────┬──────────────┐
│ unsafe 代码位置               │ 行数     │ 说明           │
├──────────────────────────────┼──────────┼──────────────┤
│ near_link/ffi.rs             │ 10-30    │ FFI 调用厂商   │
│                              │          │ SDK (bindgen) │
├──────────────────────────────┼──────────┼──────────────┤
│ wifi/hostapd.rs              │ 0        │ 无 unsafe      │
├──────────────────────────────┼──────────┼──────────────┤
│ wifi/supplicant.rs            │ 0        │ 无 unsafe      │
├──────────────────────────────┼──────────┼──────────────┤
│ ble/gatt_server.rs           │ 0        │ 无 unsafe      │
│                              │          │ (bluer 封装)   │
├──────────────────────────────┼──────────┼──────────────┤
│ **总计**                      │ **~20**  │               │
└──────────────────────────────┴──────────┴──────────────┘
```

所有 unsafe 代码集中在 `near_link::ffi` 模块，其余模块零 unsafe。

### 8.4 审计日志保护

审计日志文件不可篡改保证：
- 日志文件以 `O_APPEND` 模式打开，仅可追加不可修改
- 日志文件权限设置为 `0600`（仅 root 可读写）
- 日志文件使用 `chattr +a`（如果文件系统支持）限制只可追加
- 每 24 小时强制轮转（logrotate），旧日志保留 180 天

### 8.5 端到端传输加密协议

PRD 3.4.2 要求配置数据传输使用端到端应用层加密。本设计基于 **ECDH (X25519) + AES-256-GCM** 实现所有无线通道的传输加密。

#### 8.5.1 密钥协商流程（ECDH X25519）

```
MUPC (Server)                          Client (App/Tool)
    │                                        │
    │  ── 广播自身公钥 PubKey_MUPC ────────►  │   (Advertising/Beacon中携带)
    │                                        │
    │  ◄── 客户端公钥 PubKey_Client ─────────  │   (连接建立后交换)
    │                                        │
    │  计算共享密钥:                          │   计算共享密钥:
    │  SharedSecret = X25519(               │   SharedSecret = X25519(
    │    PrivKey_MUPC, PubKey_Client         │     PrivKey_Client, PubKey_MUPC
    │  )                                     │   )
    │                                        │
    │  派生会话密钥 (HKDF-SHA256):            │   派生会话密钥 (HKDF-SHA256):
    │  salt = channel_id || session_id       │   salt = channel_id || session_id
    │  info = "mupc-wireless-aes-gcm"       │   info = "mupc-wireless-aes-gcm"
    │                                        │
    │  AES_Key    = HKDF-Expand(salt, info, 32)    │
    │  AES_Nonce_Base = HKDF-Expand(salt, info || 0x01, 12) │
    │                                        │
    │  ── Encrypted(测试帧) ────────────────►  │   解密测试帧成功
    │  ◄── Encrypted(测试帧确认) ─────────────  │
    │                                        │
    │  安全通道建立完成                        │   安全通道建立完成
    │                                        │
```

**密钥派生参数说明**：

| 参数 | 值 | 说明 |
|------|----|------|
| KEM | X25519 (Curve25519 ECDH) | 椭圆曲线密钥交换，RFC 7748 |
| KDF | HKDF-SHA256 | RFC 5869 密钥派生函数 |
| 加密算法 | AES-256-GCM | 认证加密 (AEAD)，NIST SP 800-38D |
| AES Key 长度 | 32 字节 (256-bit) | |
| Nonce 长度 | 12 字节 (96-bit) | 随机 per-message |
| Auth Tag 长度 | 16 字节 (128-bit) | GCM 认证标签 |
| 公钥长度 | 32 字节 (256-bit) | X25519 原始格式 |

#### 8.5.2 AES-256-GCM 加密帧格式

每条应用层消息在发送前进行加密封装：

```
┌──────────────────────────────────────────────────────────────────┐
│ Encrypted Application Frame                                       │
├─────────────┬─────────────┬──────────────┬──────────────────────┤
│ Frame Header│ Nonce       │ Ciphertext   │ GCM Auth Tag         │
│ (plaintext) │ (random)    │ (encrypted)  │ (integrity check)    │
├─────────────┼─────────────┼──────────────┼──────────────────────┤
│ 4 bytes     │ 12 bytes    │ variable     │ 16 bytes             │
├─────────────┼─────────────┼──────────────┼──────────────────────┤
│ Version(1B) │ Per-message │ AES-256-GCM  │ GCM authentication   │
│ FrameType   │ random      │ output       │ tag                  │
│ (1B)        │ nonce       │              │                      │
│ Reserved(2B)│             │              │                      │
└─────────────┴─────────────┴──────────────┴──────────────────────┘
```

**帧头定义（明文传输）：**

| 字段 | 长度 | 说明 |
|------|------|------|
| Version | 1 byte | 协议版本号，当前 `0x01` |
| FrameType | 1 byte | `0x01` 数据帧 / `0x02` 确认帧 / `0x03` 密钥协商帧 / `0x04` 密钥轮换帧 |
| Reserved | 2 bytes | 保留字段，填充 `0x0000` |

**加密流程**（发送端）：

```
1. 生成随机 Nonce (12 bytes)，使用加密安全随机数生成器
2. AES-256-GCM 加密: (ciphertext, auth_tag) = AES-256-GCM-Encrypt(key, nonce, plaintext, aad)
   aad = FrameHeader (4 bytes 明文)
3. 组装帧: FrameHeader || Nonce || Ciphertext || AuthTag
```

**解密流程**（接收端）：

```
1. 提取 FrameHeader, Nonce, Ciphertext, AuthTag
2. AES-256-GCM 解密: plaintext = AES-256-GCM-Decrypt(key, nonce, ciphertext, auth_tag, aad)
   aad = FrameHeader (4 bytes)
3. 验证 auth_tag: 若验证失败，丢弃该帧，记录告警并递增认证失败计数
```

**安全约束**：
- Nonce 必须随机生成（推荐使用 `getrandom` 或 `openssl` 安全随机数），禁止使用计数器模式
- 同一会话密钥下最多加密 2^32 条消息后必须轮换密钥（安全余量）
- AAD（附加认证数据）包含 FrameHeader，防止帧头被篡改

#### 8.5.3 Wi-Fi AP 通道加密传输流程

Wi-Fi 链路层已通过 WPA2/WPA3-SAE 提供链路加密，在此基础上叠加应用层加密实现"双保险"：

```
┌──────────────┐         Wi-Fi (WPA2/WPA3)       ┌──────────────┐
│   MUPC AP    │ ◄══════════════════════════════► │    Client    │
│              │   链路层加密 (CCMP/GCMP)         │              │
│  应用层加密   │   应用层加密 (AES-256-GCM)       │  应用层加密   │
│  (ECDH +     │                                  │  (ECDH +     │
│   AES-GCM)   │                                  │   AES-GCM)   │
└──────────────┘                                  └──────────────┘
```

**连接流程**：
1. Client 连接 Wi-Fi AP（WPA2-PSK / WPA3-SAE 链路层认证）
2. Client 访问 `http://192.168.4.1/` 获取 Web UI，登录获取会话 Token
3. 首次访问受保护 API 时触发密钥协商：
   a. Client 生成 X25519 密钥对，通过 REST API 发送公钥
   b. MUPC 返回自己的公钥，双方计算共享密钥
   c. 后续 API 请求使用自定义 Header `X-MUPC-Encrypted` 传输加密帧
4. **HTTPS 说明**：若部署 TLS 1.3 证书（需硬件确认是否支持），HTTPS 本身已提供传输层加密。应用层 AES-256-GCM 加密作为**补充层**，用于：
   - 无证书场景下的安全保障（自签名证书场景）
   - 与 BLE 通道统一加密协议栈，减少代码分支
   - 防御 TLS 中间人攻击（企业内部网场景）

**API 加密通信示例**：

```
// 步骤1: 密钥协商请求
POST /api/v1/wireless/key-exchange
Content-Type: application/json

{
  "pubkey": "base64-encoded-x25519-public-key",
  "algorithm": "X25519",
  "session_id": "uuid-session-identifier"
}

// 步骤2: 密钥协商响应
HTTP/1.1 200 OK
Content-Type: application/json

{
  "pubkey": "base64-encoded-x25519-public-key",
  "algorithm": "X25519",
  "session_id": "uuid-session-identifier",
  "encrypted_test": "base64-encoded-encrypted-test-message"
}

// 步骤3: 后续加密请求（所有 API 调用）
POST /api/v1/wireless/encrypted/config
Content-Type: application/octet-stream
X-MUPC-Session: uuid-session-identifier

[Encrypted Frame: Header(4B) + Nonce(12B) + Ciphertext + AuthTag(16B)]

// 步骤4: 加密响应
HTTP/1.1 200 OK
Content-Type: application/octet-stream
X-MUPC-Session: uuid-session-identifier

[Encrypted Frame: Header(4B) + Nonce(12B) + Ciphertext + AuthTag(16B)]
```

#### 8.5.4 BLE 通道加密传输流程

BLE 链路层加密（LESC/Passkey Entry）仅保护配对阶段，不保护配对完成后的 GATT 数据交换。所有 GATT Characteristic 的读写操作必须在应用层加密：

```
┌──────────────┐        BLE (LE Legacy/LESC)    ┌──────────────┐
│   MUPC BLE   │ ◄────────────────────────────► │  BLE Client  │
│   GATT Server│      链路层: 仅配对加密          │              │
│              │      应用层: AES-256-GCM        │              │
│  应用层加密   │ ◄═════════════════════════════► │  应用层加密   │
│  (ECDH +     │      在 GATT 特征中完成          │  (ECDH +     │
│   AES-GCM)   │      密钥协商                    │   AES-GCM)   │
└──────────────┘                                  └──────────────┘
```

**密钥协商特征**（在 `5.2.2` 表中已定义，UUID: `0000FAC0-0000-1000-8000-00805F9B34FB`）：

| 属性 | 说明 |
|------|------|
| Write | 客户端写入公钥 + session_id |
| Indicate | 服务端回复公钥 + 加密测试帧 |

**BLE 加密通信流程**：
1. **连接建立**：Client 通过 Passkey Entry 配对建立 BLE 连接
2. **密钥协商**：
   - Client 生成 X25519 密钥对，将公钥写入密钥协商特征
   - 写入数据格式：`session_id(16B UUID bytes) || pubkey(32B)`
   - MUPC 回复 Indicate：`session_id(16B) || pubkey(32B) || encrypted_test_frame`
3. **会话密钥派生**：双方计算 SharedSecret → HKDF → AES-256-GCM 会话密钥
4. **测试帧验证**：Client 解密 encrypted_test_frame，验证密钥正确性
5. **加密数据交换**：
   - **写入操作**：Client 构建加密帧 → 写入目标特征 → MUPC 解密执行
   - **通知/指示**：MUPC 构建加密帧 → 通过 Notify/Indicate 发送 → Client 解密
   - **读取操作**：Client 发送加密读取请求 → MUPC 返回加密响应

**Characteristic 加密行为变化**：
- 密钥协商完成前：所有特征返回操作拒绝（未加密状态）
- 密钥协商完成后：特征值自动进入加密模式，每次读写均使用 AES-256-GCM 封装
- 连接断开重连需重新执行密钥协商

#### 8.5.5 密钥轮换策略

| 轮换类型 | 触发条件 | 操作 | 影响 |
|---------|---------|------|------|
| **会话级** | 每次新连接建立 | 重新执行 ECDH 密钥协商 | 毫秒级重新握手 |
| **周期轮换** | 每 24 小时 或 每 1GB 加密数据量 | 重新密钥协商，更新会话密钥 | 现有连接中断 < 100ms，自动重连 |
| **事件驱动** | 检测到安全事件（非预期帧、认证失败过多） | 立即重新密钥协商 | 临时断开后自动恢复 |
| **客户端主动** | 客户端发起密钥更新请求 | 通过密钥协商特征重新写入新公钥 | 无中断（双缓冲切换） |

**密钥材料生命周期管理**：

```
┌─────────────────────────────────────────────────────────────────┐
│                   密钥材料生命周期                                │
├───────────────────┬───────────────────┬─────────────────────────┤
│ 长期密钥          │ 会话密钥           │ 临时密钥                │
│ (PrivKey_MUPC)    │ (Session Key)     │ (Per-message Nonce)    │
├───────────────────┼───────────────────┼─────────────────────────┤
│ 存储: security    │ 存储: 内存         │ 存储: 栈/寄存器         │
│ crate 加密存储    │ (mlock 锁定)       │ (不持久化)              │
├───────────────────┼───────────────────┼─────────────────────────┤
│ 生命周期: 设备寿命  │ 生命周期: 连接周期  │ 生命周期: 单条消息      │
├───────────────────┼───────────────────┼─────────────────────────┤
│ 轮换: 恢复出厂设置  │ 轮换: 24h/1GB     │ 轮换: 每条消息          │
│ 时更换              │ 或连接断开          │                        │
└───────────────────┴───────────────────┴─────────────────────────┘
```

**密钥清除协议**：
1. **连接断开/会话超时**：MUPC 立即清除内存中的会话密钥和派生密钥
2. **主动销毁**：通过控制命令 `cmd: "key_clear"` 清除所有会话状态
3. **恢复出厂**：配合 security crate 的清空流程，移除所有长期密钥材料
4. **内存保护**：会话密钥通过 `mlock()` 锁定在物理内存，禁止 swap 到磁盘

**安全通道状态模型**：

```
┌───────────┐
│  SECURE   │ ← 密钥协商完成，安全通道可用
└─────┬─────┘
      │
      ├── 密钥到期 / 安全事件 ──► ┌───────────┐
      │                          │ REKEYING  │ ← 正在重新协商密钥
      │                          └─────┬─────┘
      │                                │ 密钥协商完成
      │                                ▼
      │                          ┌───────────┐
      │                          │  SECURE   │
      │                          └───────────┘
      │
      ├── 连接断开 ──► ┌───────────┐
      │               │  CLOSED   │ ← 清除所有密钥材料
      │               └───────────┘
      │
      └── 认证失败超过阈值 ──► ┌───────────┐
                             │  LOCKED   │ ← 与 AuthManager 联动
                             └───────────┘
```

```rust
// wireless/src/auth.rs
pub struct AuthManager {
    lock_state: Arc<RwLock<HashMap<String, LockEntry>>>,
    config: AuthConfig,
}

impl AuthManager {
    /// 记录认证失败，如果达到阈值则锁定通道
    pub async fn record_auth_failure(&self, identity: &str, channel: ChannelType) -> Result<LockStatus> {
        let mut state = self.lock_state.write().await;
        let key = format!("{}:{}", channel, identity);
        let entry = state.entry(key.clone()).or_insert(LockEntry {
            fail_count: 0,
            locked_until: None,
        });

        entry.fail_count += 1;

        if entry.fail_count >= self.config.lock_threshold {
            let until = Instant::now() + Duration::from_secs(
                self.config.lock_duration_minutes as u64 * 60
            );
            entry.locked_until = Some(until);

            tracing::warn!(
                "通道 {} 已锁定 {} 秒: 身份 {} 认证失败 {} 次",
                channel, self.config.lock_duration_minutes * 60,
                identity, entry.fail_count
            );

            // 记录审计日志
            self.audit_logger.log(AuditEntry {
                op: "auth_lock",
                identity: identity.to_string(),
                target: channel.to_string(),
                result: "failure",
                channel,
                detail: format!("连续 {} 次认证失败", entry.fail_count),
            }).await;

            return Ok(LockStatus::Locked {
                remaining_seconds: self.config.lock_duration_minutes * 60,
            });
        }

        Ok(LockStatus::Permitted {
            remaining_attempts: self.config.lock_threshold - entry.fail_count,
        })
    }
}
```

```rust
impl BleGattServer {
    /// 监测 BLE 连接稳定性
    pub fn monitor_connection_stability(&self) {
        let mut disconnect_count = 0;
        let mut last_disconnect_time = Instant::now();

        // BLE 连接断开回调
        self.on_disconnect = Box::new(move || {

                }
            } else {
                disconnect_count = 0;
            }
            last_disconnect_time = now;
        });
```

### 11.3 与 PRD 阻塞性问题的对应关系

| PRD 阻塞问题 | 本方案的处理 |
|-------------|------------|
| Q1: 无线模组型号 | Wi-Fi/BLE 假定为 M.2 Key E 模组（AP6275P 类），NearLink 假定为 Hi2821 USB 模组。设计上通过 `detect_*_module()` 函数与具体硬件解耦，更换模组不影响上层逻辑。 |
| Q2: 星闪 Linux 驱动 | 采用双轨策略：首选 FFI 绑定厂商 SDK；若不可用降级为 C 守护进程 + Unix Socket。无论是哪种方式，`near_link::controller` 的对外接口不变。 |
| Q3: Wi-Fi AP+Station 并发 | 通过 `ConcurrencyDetector` 运行时检测硬件能力，配置 `concurrency_mode` 字段适应三种情形。即使硬件不支持并发，也保证 AP 和 Station 可单独运行。 |
