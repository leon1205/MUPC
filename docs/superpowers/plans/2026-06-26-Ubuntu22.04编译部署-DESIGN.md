## 1. 技术选型

### 1.1 构建工具

| 场景 | 工具 | 理由 |
|------|------|------|
| **CI 构建** | `cross` (cross-rs) | 在 x86_64 GitHub-hosted runner 上交叉编译至 ARM64，自动提供 Docker 化 sysroot (glibc 2.35)，免维护目标平台根文件系统 |
| **开发者本地构建** | `cargo` + 手动 sysroot | 开发者使用 `rustup target add aarch64-unknown-linux-gnu` + `apt install gcc-aarch64-linux-gnu`，从 Ubuntu 22.04 ARM64 Docker 镜像提取 sysroot。离线可用，无需 Docker daemon |
| **备用构建** | Dockerfile (skeleton) | `docker/Dockerfile.build` 作为离线备用方案，骨架代码占位（Phase 2+ 完善） |

**决策逻辑**：不采用 Windows/MSVC host 构建路径（用户明确声明开发环境只为 Linux x86_64）。不采用自托管 ARM64 physical runner（硬件未就绪）。

### 1.2 编译 Target

```
target: aarch64-unknown-linux-gnu
```

- **glibc 版本**: >= 2.35（对齐 Ubuntu 22.04 系统库）
- **linker**: `aarch64-linux-gnu-gcc` (gcc-aarch64-linux-gnu 包)
- **构建 host**: x86_64-unknown-linux-gnu

### 1.3 Feature 策略

| Feature | 归属 crate | 默认 | 状态 | 说明 |
|---------|-----------|------|------|------|
| `npu` | `mupc-ai-engine` | false | **新增** | 启用 RKNN Runtime FFI 链接。CI 构建时传 `--features npu`，开发/测试时不传 |
| `real_gmsm` | `mupc-security` | true (default) | 已有 | SM2/SM3/SM4 国密，依赖 gmsm crate。ARM64 交叉编译可用（纯 Rust） |
| `real_iec61850` | `mupc-iec61850-plugin` | false | 已有 | libIEC61850 FFI 接入，Phase 2+ 才启用 |
| `fake_iec61850` | `mupc-iec61850-plugin` | true (计划 default) | 已有 | 骨架占位实现，编译无外部依赖 |
| `ffi` | `hplc-plugin` | false | 已有（预留） | HPLC 芯片驱动 FFI，Phase 2+ 预留 |

### 1.4 编译优化参数

Workspace `Cargo.toml` 已配置 `[profile.release]`:

```toml
[profile.release]
opt-level = 3
lto = true
codegen-units = 1
strip = true
panic = "abort"   # 新增：减少 unwinding 代码体积
```

仅需新增 `panic = "abort"` 一行。

**`panic = "abort"` 对测试的影响说明**:

- `[profile.release]` 仅影响 release 构建（`cargo build --release`），不影响默认的 debug profile
- 标准 `cargo test` 使用 debug profile，**不受影响**：panic 仍会 unwind，`#[should_panic]` 和 `std::panic::catch_unwind()` 正常工作
- `cargo test --release`（极少使用）会受影响：panic 直接 abort 进程，`#[should_panic]` 测试可能失败（测试框架无法捕获 abort），`catch_unwind` 无效
- CI test job (Section 6.1) 使用 `cargo test --workspace`（debug profile），不受此变更影响
- 本项目的 `[profile.release]` 设置与 Rust 生态主流实践一致（嵌入式/系统守护进程常用 `panic = "abort"` 以减小 binary size 并避免 unwind 代码路径）

### 3.2 启动流程

`main.rs` 的顶层启动流程采用 phase-gate 模型：

```
main()
  │
  ├─ Phase 0: CLI 解析 + --version / --help 快速退出
  │
  ├─ Phase 1: 配置加载 (mupc_core_config.yaml, mupc_env_config.yaml)
  │     └─ --validate-config → 此处退出 (exit 0)
  │
  ├─ Phase 2: tracing 初始化 (JSON subscriber → file + stdout)
  │     └─ 失败 → FATAL 日志, exit 1
  │
  ├─ Phase 3: 子系统初始化 (见 3.3 节顺序)
  │     └─ 任一子系统初始化失败 → FATAL 日志, 已启动的子系统级联清理, exit 1
  │
  ├─ Phase 4: 注册信号处理 (SIGTERM / SIGINT)
  │
  ├─ Phase 5: 主循环 wait-for-shutdown
  │     └─ 收到 SIGTERM/SIGINT → 进入 Phase 6
  │
  └─ Phase 6: 优雅退出
        ├─ 子系统逆序停止 (LIFO: 最后启动的优先停止)
        ├─ 30s 超时保护 (超时则强制 exit 1)
        └─ tracing flush → exit 0
```

**初始化伪代码** (`startup.rs`):

```rust
pub async fn initialize_all(
    config: &CoreConfig,
    coord: &ServiceCoordinatorImpl,
) -> Result<StartupContext, MupcError> {
    // 1. 消息总线
    let message_bus = Arc::new(TokioMessageBus::new(256));
    coord.register("message_bus", ServiceStatus::Running);

    // 2. 安全模块
    let security = SecurityModule::load(&config.cert_dir)?;
    coord.register("security", ServiceStatus::Running);

    // 3. 持久化
    let storage = StorageService::connect(&config.data_dir).await?;
    coord.register("storage", ServiceStatus::Running);

    // 4. 核间通信
    let intercore = InterCoreClient::connect(&config.intercore).await?;
    coord.register("intercore", ServiceStatus::Running);

    // 5. 插件
    let plugin_loader = Arc::new(PluginLoaderImpl::new());
    load_plugins(&plugin_loader, &config.plugin_dir).await?;
    coord.register("plugin_loader", ServiceStatus::Running);

    // 6-14. 后续子系统...

    Ok(StartupContext {
        message_bus,
        security,
        storage,
        intercore,
        plugin_loader,
        // ...
    })
}
```

### 3.4 信号处理

`signal_handler.rs` 负责监听 SIGTERM 和 SIGINT，触发优雅退出：

```rust
use tokio::signal;

pub async fn wait_for_shutdown() {
    let ctrl_c = signal::ctrl_c();
    let terminate = async {
        signal::unix::signal(signal::unix::SignalKind::terminate())
            .expect("failed to install SIGTERM handler")
            .recv()
            .await;
    };

    tokio::select! {
        _ = ctrl_c => tracing::info!("收到 SIGINT，开始优雅退出..."),
        _ = terminate => tracing::info!("收到 SIGTERM，开始优雅退出..."),
    }
}
```

## 4. Feature gate 设计

### 4.1 问题分析

当前 `mupc-ai-engine` 没有 `npu` feature gate，`rknn_runtime_sys.rs` 中的 `#[link(name = "rknnrt")] extern "C"` 始终被编译，导致：

- Windows `cargo test` 链接失败 (找不到 `rknnrt.lib`)
- Linux 无 RkNN SDK 时 `cargo build` 链接失败
- 纯 CPU LSTM/RL 测试被阻塞

### 4.2 方案：`npu` feature + `cfg(feature = "npu")`

#### 4.2.1 `Cargo.toml` 变更

```toml
# ai-engine/Cargo.toml

[features]
default = []
npu = []
```

**`rknn_runtime.rs`** -- 全文件包裹：

```rust

```

**`lib.rs`** -- 条件 re-export：

        tracing::warn!("npu feature 未启用，RKNN 模型加载跳过。使用纯 CPU 推理。");
        Ok(())
    }

#### 4.2.4 build.rs

新建 `crates/ai-engine/build.rs`（在 workspace 根目录执行时路径相对于 `crates/ai-engine/`）：

```rust
use std::path::Path;

fn main() {
    // 仅在启用 npu feature 时生成链接指令
    let npu_enabled = std::env::var("CARGO_FEATURE_NPU").is_ok();

    if !npu_enabled {
        println!("cargo:warning=AI Engine: npu feature 未启用，跳过 RKNN FFI 链接");
        return;
    }

    // ── RKNN Vendor 目录 ──
    // 优先级: 环境变量 RKNN_VENDOR_DIR > 默认 vendor/rknn (workspace 根)
    let manifest_dir = std::env::var("CARGO_MANIFEST_DIR").unwrap();
    let default_vendor = Path::new(&manifest_dir)
        .parent().unwrap()  // crates/
        .parent().unwrap()  // mupc/
        .join("vendor").join("rknn");

    let vendor_dir = std::env::var("RKNN_VENDOR_DIR")
        .unwrap_or_else(|_| default_vendor.to_string_lossy().to_string());

    println!("cargo:rustc-link-search=native={}", vendor_dir);
    println!("cargo:rustc-link-lib=dylib=stdc++");
    // 注: #[link(name = "rknnrt")] 在 rknn_runtime_sys.rs 中声明，
    // build.rs 只提供 -L 搜索路径和间接依赖 stdc++

    // ── SHA256 完整性校验 ──
    let so_path = Path::new(&vendor_dir).join("librknnrt.so");
    if so_path.exists() {
        let hash_file = Path::new(&vendor_dir).join("librknnrt.so.sha256");
        if hash_file.exists() {
            let expected = std::fs::read_to_string(&hash_file)
                .expect("Failed to read SHA256 file");
            let expected = expected.split_whitespace().next()
                .expect("Invalid SHA256 file format");
            let actual = compute_sha256(
                &std::fs::read(&so_path).expect("Failed to read librknnrt.so")
            );
            assert_eq!(expected, actual,
                "librknnrt.so SHA256 mismatch!\n  Expected: {}\n  Got:      {}",
                expected, actual);
            println!("cargo:warning=librknnrt.so SHA256 校验通过");
        } else {
            // 首次导入：自动生成 .sha256 文件
            let actual = compute_sha256(
                &std::fs::read(&so_path).expect("Failed to read librknnrt.so")
            );
            std::fs::write(&hash_file, format!("{}  librknnrt.so\n", actual))
                .expect("Failed to write SHA256 file");
            println!("cargo:warning=已自动生成 librknnrt.so.sha256 校验文件");
        }
    } else {
        println!("cargo:warning=librknnrt.so 未找到，跳过 SHA256 校验");
    }
}

fn compute_sha256(data: &[u8]) -> String {
    use sha2::Digest;  // trait 导入，提供 .digest() 方法
    use std::fmt::Write;
    let hash = sha2::Sha256::digest(data);  // sha2 已是 ai-engine 的直接依赖
    let mut s = String::with_capacity(64);
    for byte in hash.iter() {
        write!(&mut s, "{:02x}", byte).unwrap();
    }
    s
}
```

**注意**：`build.rs` 中直接使用 `sha2` crate -- 需在 `ai-engine/Cargo.toml` 的 `[build-dependencies]` 中声明：

```toml
[build-dependencies]
sha2 = "0.10"
```

#### 4.2.5 Feature gate 传播

**关键问题**：MUPC 是虚拟 workspace（virtual manifest），无 root package。`cargo build --features npu` 在虚拟 workspace 中不生效 -- Cargo 要求 `--features` 必须配合 `-p <package>` 使用。

**方案**：`mupc-core-bin/Cargo.toml` 声明 `npu` feature 并转发至 `mupc-ai-engine`：

```toml
# crates/mupc-core-bin/Cargo.toml

[features]
default = []
npu = ["mupc-ai-engine/npu"]   # 转发 feature 到唯一需要 FFI 的 crate
```

下游 crate (`strategy-engine`, `web-api`) 不应在 `Cargo.toml` 中直接声明 `npu` feature 依赖：

```toml
# strategy-engine/Cargo.toml — 不做此方式（不推荐）
# mupc-ai-engine = { path = "../ai-engine", features = ["npu"] }

# 正确方式：mupc-core-bin 顶层控制 feature
# cargo build -p mupc-core-bin --features npu
#   → mupc-core-bin/npu 激活 → 转发 mupc-ai-engine/npu
# strategy-engine 中的 ai-engine 调用自动获得正确的 cfg 路径
```

这是因为 `mupc-ai-engine` 暴露的公共 API 对于 `npu`/`no-npu` 两种模式是一致的（`ModelManager::load_rknn_model` 两种实现签名相同），下游无需感知 feature 选择。

## 5. 插件 .so 编译方案

### 5.1 背景

当前 4 个插件 crate 均未显式声明 `crate-type`，Cargo 默认产出 `rlib`（Rust 静态库）。生产环境中 `plugin-loader` 通过 `libloading::Library::new()` 动态加载 `.so` 文件，因此需要插件 crate 同时产出 `cdylib`。

### 5.2 双 crate-type 策略

每个插件 crate 的 `Cargo.toml` 增加 `[lib]` 节，声明 `crate-type = ["rlib", "cdylib"]`：

| 插件 crate | Cargo.toml name | lib name | cdylib 产出 | rlib 产出 (依赖方) |
|-----------|----------------|----------|------------|-------------------|
| `rs485-plugin` | `rs485-plugin` | `rs485_plugin` | `librs485_plugin.so` | `rs485-plugin.rlib` (strategy-engine 依赖) |
| `hplc-plugin` | `hplc-plugin` | `hplc_plugin` | `libhplc_plugin.so` | `hplc-plugin.rlib` (无直接依赖方) |
| `mqtt-plugin` | `mupc-mqtt-plugin` | `mqtt_plugin` | `libmqtt_plugin.so` | `mupc-mqtt-plugin.rlib` (无直接依赖方) |
| `iec61850-plugin` | `mupc-iec61850-plugin` | `iec61850_plugin` | `libiec61850_plugin.so` | `mupc-iec61850-plugin.rlib` (无直接依赖方) |

**配置示例**（以 `rs485-plugin/Cargo.toml` 为例）：

```toml
[lib]
crate-type = ["rlib", "cdylib"]
name = "rs485_plugin"
path = "src/lib.rs"
```

**注意事项**：

1. `rlib` 保留给 workspace 内依赖方使用（如 `strategy-engine` 依赖 `rs485-plugin`），在 workspace 内构建时 Cargo 使用 rlib 路径
2. `cdylib` 产出 `.so`，供 `plugin-loader` 在运行时通过 `libloading` 动态加载
3. `mqtt-plugin` 的 `Cargo.toml name = "mupc-mqtt-plugin"`，因此 rlib 名为 `libmupc_mqtt_plugin.rlib`，cdylib 的 `lib.name` 必须明确设为 `mqtt_plugin` 以产出 `libmqtt_plugin.so`
4. 编译命令 `cargo build --release` 会同时产出 rlib 和 cdylib 两种 artifact

### 5.3 加载路径约定

```rust
// plugin-loader 搜索优先级:
// 1. 配置文件中指定的 plugin_dir (mupc_core_config.yaml: plugins.search_paths)
// 2. 环境变量 MUPC_PLUGIN_DIR
// 3. LD_LIBRARY_PATH 中的路径
// 4. 默认 /opt/mupc/lib/plugins/

// 部署目录:
/opt/mupc/lib/plugins/
├── librs485_plugin.so
├── libhplc_plugin.so
├── libmqtt_plugin.so
└── libiec61850_plugin.so
```

### 5.4 FFI 导出函数规范

每个插件 `.so` 必须导出两个 FFI 函数（已由 `plugin-loader/src/loader.rs` 约定）：

```rust
#[no_mangle]
pub unsafe extern "C" fn create_plugin() -> *mut dyn Plugin { ... }

#[no_mangle]
pub unsafe extern "C" fn plugin_meta() -> PluginMeta { ... }
```

当前 4 个插件 crate 均已实现这两个 FFI 导出函数，编译为 cdylib 无需额外修改 FFI 边界代码。

### 6.3 缓存策略

- **cargo registry**: 按 `Cargo.lock` hash 缓存
- **cross docker image**: `cross` 自动管理，首次拉取约 5 分钟
- **sccache**: 可选（后续优化，Phase 2）

### 6.4 RKNN SDK 管理

`librknnrt.so` 不纳入 Git LFS。CI 中通过以下机制获取：

1. **GitHub Repository Secrets**: 将 `librknnrt.so` 的 Base64 编码存放于 `secrets.RKNN_SO_B64`，CI 构建时解码到 `vendor/rknn/`
2. **自托管制品库**: 从内部 Nexus/Artifactory 通过 `curl` 下载
3. **fallback**: 若 RKNN SDK 不可用，跳过 `npu` feature，构建纯 CPU 版本（LSTM/RL 可用，RKNN Runtime 不可用）

```yaml
- name: Decode RKNN SDK from Secrets
  env:
    RKNN_B64: ${{ secrets.RKNN_SO_B64 }}
  run: |
    if [ -n "$RKNN_B64" ]; then
      echo "$RKNN_B64" | base64 -d > vendor/rknn/librknnrt.so
    fi
```

**启动流程集成**：在 Section 3.2 的 Phase 3（子系统初始化）中，`mupc-ai-engine` 初始化 Python 增加模型完整性校验步骤：

```
Phase 3: 子系统初始化
  ...
  7. mupc-ai-engine
     ├─ 解析 model_manifest.json，校验 manifest_version 格式
     ├─ 逐模型校验 sha256（文件实际 hash vs manifest 记录值）
     │   └─ 任一不匹配 → FATAL 日志 "Model integrity check FAILED: {filename}"
     │      expected={manifest_hash}, actual={file_hash}" → 阻止启动 (exit 1)
     ├─ 校验 version 字段与 mupc_env_config.yaml version.fingerprint 的对齐
     │   └─ 版本不兼容 → WARNING 日志（不阻塞，允许运维强制启动）
     └─ 模型加载至 NPU/CPU 推理管线
```

**校验函数接口**（在 `ai-engine/src/model_manager.rs` 中实现）：

```rust
/// 校验 models/ 目录下所有 .rknn 文件的完整性
/// 返回 Ok(manifest) 若全部通过；任一失败返回 Err(AiEngineError::ModelIntegrityError)
pub fn verify_model_integrity(manifest_path: &Path) -> Result<ModelManifest, AiEngineError> {
    let manifest_json = std::fs::read_to_string(manifest_path)?;
    let manifest: ModelManifest = serde_json::from_str(&manifest_json)?;

    for model in &manifest.models {
        let file_path = manifest_path.parent().unwrap().join(&model.filename);
        let file_data = std::fs::read(&file_path)
            .map_err(|e| AiEngineError::ModelIntegrityError(
                format!("Cannot read {}: {}", model.filename, e)))?;

        let actual_hash = compute_sha256(&file_data);
        if actual_hash != model.sha256 {
            return Err(AiEngineError::ModelIntegrityError(
                format!("SHA256 mismatch for {}: expected {}, got {}",
                    model.filename, model.sha256, actual_hash)));
        }
    }
    Ok(manifest)
}
```

## 9. 技术决策记录 ADR

### ADR-001: 构建工具选型 -- cross vs 本机构建 vs Docker 自建

**日期**: 2026-07-03
**状态**: 已决策

**上下文**:
MUPC workspace 需从 x86_64 Linux host 编译至 aarch64-unknown-linux-gnu target。有三种可选路径：
- A. 使用 `cross` 工具（cross-rs），在 Docker 容器内交叉编译
- B. 手动配置 sysroot + `aarch64-linux-gnu-gcc`，在 host 上直接交叉编译
- C. 自建 Dockerfile 含 ARM64 sysroot，`cargo build` 在容器内执行

**决策**:
选择 **A (CI) + B (开发者本地)** 双路径。CI 流水线使用 `cross`（免维护 sysroot，自动对齐 glibc 2.35），开发者本地使用方案 B（离线可用，不依赖 Docker daemon）。方案 C 的 Dockerfile 作为骨架占位，Phase 2+ 完善。

**理由**:
1. `cross` 自动拉取预构建 Docker 镜像含完整 sysroot，消除 "glibc 版本不对" 类问题
2. `cross` 社区活跃维护，与 rustup target 无缝集成
3. 开发者本地交叉编译无需 Docker（降低门槛），`apt install gcc-aarch64-linux-gnu` + 从 Ubuntu ARM64 镜像提取 sysroot 即可
4. 方案 C 的维护成本（需跟随 Rockchip SDK 更新、处理多架构冲突）在 Phase 1 不划算

**后果**:
- CI 首次运行需拉取 cross Docker 镜像（约 5 分钟），后续被 GitHub Actions cache
- 开发者需手动配置一次 sysroot（见附录 9.1 节操作步骤）
- `librknnrt.so` 交叉链接仍需验证（cross Docker 内 linker 为 aarch64-linux-gnu-gcc，可链接 ARM64 .so）

### ADR-002: Feature gate 边界 -- npu feature 在 workspace 中的传播策略

**日期**: 2026-07-03
**状态**: 已决策

**上下文**:
`mupc-ai-engine` 的 `rknn_runtime_sys.rs` 包含 `#[link(name = "rknnrt")]` FFI 声明。不加 feature gate 会导致所有测试和检查因链接失败而阻塞。需要决定 `npu` feature 的作用范围和传播策略。

**决策**:
`npu` feature 仅在 `mupc-ai-engine` 内部生效，**不向上游传播**。下游 crate (`strategy-engine`, `web-api`) 不声明 `mupc-ai-engine/npu`，不感知 feature 选择。`mupc-core-bin/Cargo.toml` 声明 `npu = ["mupc-ai-engine/npu"]` 作为 feature 转发点。构建时通过 `cargo build -p mupc-core-bin --features npu` 传播。这是因为虚拟 workspace 无 root package，`--features` 必须配合 `-p` 使用（详见 Section 4.2.5）。

**理由**:
1. `mupc-ai-engine` 暴露的公共 API 对于 `npu`/`no-npu` 两种模式是**签名一致的**（`ModelManager::load_rknn_model()` 在两种模式下均有实现，无非 NPU 时记录 warn 日志并返回 Ok），下游代码无需 `cfg` 判断
2. 避免 feature 污染 -- 若 `strategy-engine` 传播 `npu`，则所有依赖 `strategy-engine` 的 crate 都间接依赖 RKNN 链接
3. 统一入口控制 -- `mupc-core-bin` 是唯一的二进制构建目标，顶层 `-p mupc-core-bin --features npu` 通过 feature 转发链决定整个 workspace 的编译路径

**后果**:
- `cargo test --workspace` 始终可用（无 `--features npu`）
- 需确保 `model_manager.rs` 中两种 cfg 路径的 public API 签名严格一致
- 新增 RKNN 相关代码时需审查 cfg 边界是否正确

### ADR-003: 插件 crate 双 crate-type 策略

**日期**: 2026-07-03
**状态**: 已决策

**上下文**:
4 个插件 crate 既需要作为 rlib 被 workspace 内其他 crate 引用（`strategy-engine` 依赖 `rs485-plugin`），又需要产出 cdylib `.so` 文件供 `plugin-loader` 在运行时动态加载。需决定 crate-type 声明策略。

**决策**:
每个插件 crate 声明 `crate-type = ["rlib", "cdylib"]`，同时产出静态库和动态库。

**理由**:
1. `rlib` 路径保留 workspace 内编译期依赖（Cargo 自动选择 rlib 路径以保证编译优化）
2. `cdylib` 路径产出 `.so` 产 runtime 加载，与 `plugin-loader` 的 `libloading` 机制对齐
3. 不需要在 workspace 中维护独立的 "plugin-stub" crate 来替代 `strategy-engine` 的 `rs485-plugin` 依赖
4. `libloading` 在运行时调用 `Library::new("librs485_plugin.so")` 加载的是独立的动态库，与编译时 rlib 链接不冲突 (两个符号空间隔离)

**后果**:
- CI 构建时每个插件 crate 被编译两次 (rlib + cdylib)，增量约 1-2 分钟（4 crate 共 4-8 分钟），在 30 分钟 CI 预算内
- cdylib 的 `lib.name` 需与 rlib 的 crate name 一致或明确指定
- `mqtt-plugin` 因 `Cargo.toml name = "mupc-mqtt-plugin"` 与期望的 `libmqtt_plugin.so` 不一致，需在 `[lib]` 中显式指定 `name = "mqtt_plugin"`

**设计约束备注**:

1. **LTO 时间成本**: `lto = true` 显著增加链接时间（单 codegen-unit 约增加 2-3 分钟），但二进制体积减少 30-40%。考虑到部署带宽（OTA 增量更新 > 全量），体积优先于编译时间。
2. **panic = "abort" 的影响**: 见 Section 1.4 末尾说明，`panic = "abort"` 会改变 release test 的 panic 行为（详见该节）。
3. **存储增长预估**: `/opt/mupc/logs/mupc.log` 需配合 logrotate 限制大小（建议 100MB + 保留 7 天）；`/opt/mupc/data/mupc.db` 按每日 1000 条决策记录估算，年增长 ~50MB。
4. **sccache 阶段**: 当前 Phase 1 不强制要求 sccache，Phase 2 评估增量构建收益后决定是否集成（sccache 对 cross 的兼容性需额外验证）。
