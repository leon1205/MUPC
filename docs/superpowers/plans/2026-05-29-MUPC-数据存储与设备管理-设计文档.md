## 1. 技术选型

### 1.1 存储引擎对比

| 维度 | SQLite (WAL模式) | RocksDB | sled | redb |
|------|------------------|---------|------|------|
| **语言** | C (rusqlite绑定) | C++ (librocksdb-sys) | Rust原生 | Rust原生 |
| **交叉编译(RK3588)** | 易 (已有依赖) | 难 (需ARM SF) | 易 | 易 |
| **写吞吐(1000条/秒)** | 满足 (WAL+批量) | 优秀 | 良好 | 良好 |
| **ACID事务** | 完整支持 | 列族级 | 单键级 | 完整支持 |
| **SQL查询能力** | 完整SQL | 无SQL (API) | 无SQL | 无SQL |
| **时间范围查询** | 索引支持 | Key前缀扫描 | Key前缀扫描 | Key前缀扫描 |
| **数据库文件数** | 1个 | 多个(LSM文件) | 1个目录 | 1个文件 |
| **内存占用(Runtime)** | ~2MB | ~10MB+ | ~5MB | ~3MB |
| **现有依赖** | 已在data-processing使用 | 未使用 | 未使用 | 未使用 |
| **数据清理** | DELETE / DROP分区 | Compact + DeleteRange | DeleteRange | Delete |
| **社区成熟度** | 极成熟 | 极成熟 | 较成熟 | 仍在发展 |

### 1.2 决策依据

**结论：采用双引擎混合策略**

| 数据类型 | 选型 | 理由 |
|----------|------|------|
| 设备台账、铭牌、维护记录 | SQLite | 关系模型、事务完整性、已有依赖 |
| 告警日志、事件记录 | SQLite | 关系模型、多条件组合查询、事务完整性 |
| 遥测历史数据、电池数据 | SQLite (按月分区) | 避免引入新依赖；WAL模式+批量写入可满足1000条/秒吞吐；按月分区简化清理(直接DROP TABLE) |
| 故障录波波形数据 | 文件系统 | 大文件二进制存储(1-10MB/次)，沿用现有方案 |

**不选用RocksDB/sled的理由：**
- RK3588交叉编译RocksDB的C++依赖链复杂，会增加构建维护成本
- 新增sled/redb只是替换SQLite做KV存储，对遥测查询还需在应用层实现时间范围索引逻辑，收益有限
- SQLite按月分区 + 复合索引(device_id, timestamp) 在1000台设备/百万条记录规模下已可满足3秒查询限时
- 多引擎增加部署、监控、备份复杂度，在当前阶段得不偿失

### 1.3 关键技术决策

**SQLite配置：**
- `PRAGMA journal_mode=WAL` — 读写不互斥，并发性能提升5-10倍
- `PRAGMA synchronous=NORMAL` — 平衡安全性与写入性能
- `PRAGMA busy_timeout=5000` — 等待5秒后再返回忙错误
- `PRAGMA cache_size=-64000` — 使用64MB页缓存
- `PRAGMA temp_store=MEMORY` — 临时表存储在内存

**写入架构：**
- 异步通道缓冲 + 批量事务提交(每100ms或积累100条，取先到者)
- 写入协程与查询协程通过不同SQLite连接实例隔离(读写分离)
- 写入协程使用单个连接，串行化写入；查询协程使用独立连接池(最多4个连接)

**数据分区策略：**
- 遥测和电池表按月分区：`telemetry_202605`, `telemetry_202606` ...
- 分区表自动创建，应用层通过 `YYYYmm` 格式拼接表名
- 数据清理时直接 `DROP TABLE` 整表删除，避免大量DELETE产生WAL膨胀

## 3. 模块划分与crate设计

### 3.1 决策：新建 `mupc-storage` crate

**理由：**
1. storage 是一个独立的内聚模块，有自己清晰的职责边界
2. 被多个上层模块依赖(data-processing, web-api, gateway)，放在 data-processing 中会导致循环依赖
3. 独立的 crate 便于单测、维护、后续替换存储引擎
4. 遵循现有架构模式（每个功能域一个 crate）

### 3.4 核心接口定义

```rust
// lib.rs

/// 存储服务 - 所有存储操作的统一入口
pub struct StorageService {
    writer: Arc<WriteBuffer>,
    pool: DbPool,
}

impl StorageService {
    /// 初始化存储服务 (打开数据库、创建连接池、运行迁移)
    pub async fn init(config: StorageConfig) -> Result<Self, StorageError>;

    /// 获取设备台账服务
    pub fn asset_service(&self) -> AssetService<'_>;

    /// 获取遥测数据服务
    pub fn telemetry_service(&self) -> TelemetryService<'_>;

    /// 获取告警服务
    pub fn alarm_service(&self) -> AlarmService<'_>;

    /// 获取事件服务
    pub fn event_service(&self) -> EventService<'_>;

    /// 获取生命周期服务
    pub fn lifecycle_service(&self) -> LifecycleService<'_>;

    /// 获取导出服务
    pub fn export_service(&self) -> ExportService<'_>;

    /// 检查存储状态
    pub fn storage_status(&self) -> Result<StorageStatus, StorageError>;

    /// 关闭存储服务，释放资源
    pub async fn shutdown(self);
}

/// 写入缓冲 - 批量写入以提高吞吐
pub struct WriteBuffer {
    tx: mpsc::UnboundedSender<WriteCommand>,
}

impl WriteBuffer {
    /// 异步写入遥测数据
    pub async fn write_telemetry(&self, data: TelemetryRecord) -> Result<(), StorageError>;

    /// 异步写入电池数据
    pub async fn write_battery(&self, data: BatteryRecord) -> Result<(), StorageError>;

    /// 异步写入告警日志
    pub async fn write_alarm(&self, data: AlarmRecord) -> Result<(), StorageError>;

    /// 异步写入事件记录
    pub async fn write_event(&self, data: EventRecord) -> Result<(), StorageError>;
}
```

### 4.2 完整表结构

#### 表 4.2.1: device_asset (设备资产)

```sql
CREATE TABLE IF NOT EXISTS device_asset (
    device_id           TEXT PRIMARY KEY,           -- 设备唯一标识
    device_type         TEXT NOT NULL,              -- 枚举值: ttu/inverter/charger/flexible_load/fire_alarm/battery/grid_connection/other
    asset_number        TEXT,                       -- 资产编号
    manufacturer        TEXT NOT NULL,              -- 厂商
    model               TEXT NOT NULL,              -- 型号
    serial_number       TEXT NOT NULL,              -- 出厂序列号
    firmware_version    TEXT,                       -- 固件版本
    hardware_version    TEXT,                       -- 硬件版本
    device_alias        TEXT,                       -- 设备别名
    description         TEXT,                       -- 备注
    commissioning_date  TEXT NOT NULL,              -- 投运日期 (ISO 8601)
    last_maintenance_date TEXT,                     -- 最近维护日期
    decommissioning_date TEXT,                      -- 退役日期
    warranty_expiry_date TEXT,                      -- 质保到期日
    status              TEXT NOT NULL DEFAULT 'active',  -- active / decommissioned
    created_at          TEXT NOT NULL,              -- 创建时间
    updated_at          TEXT NOT NULL,              -- 更新时间
    deleted_at          TEXT                        -- 软删除时间
);
CREATE INDEX idx_device_asset_type ON device_asset(device_type);
CREATE INDEX idx_device_asset_status ON device_asset(status);
```

```sql
CREATE TABLE IF NOT EXISTS nameplate_change_log (
```

```rust
// data-processing 集成示例
impl DataCollectorImpl {
    pub fn with_storage(mut self, storage: Arc<StorageService>) -> Self {
        self.storage = Some(storage);
        self
    }

    async fn process_telemetry(&self, pkg: DataPackage) {
        if let Some(storage) = &self.storage {
            // 构造遥测记录并异步写入
            let record = TelemetryRecord {
                device_id: pkg.device_id,
                timestamp: pkg.timestamp,
                // ... 映射字段
            };
            if let Err(e) = storage.write_buffer().write_telemetry(record).await {
                tracing::error!("写入遥测数据失败: {}", e);
            }
        }
    }
}
```

## 7. 存储容量规划

### 7.1 容量估算 (基于PRD数据)

| 数据类型 | 记录日增量 | 存储90天 | 存储1年 | 存储默认保留期 |
|----------|-----------|----------|---------|---------------|
| 遥测数据(100台) | 28.8 MB | 2.59 GB | 10.5 GB | 2.59 GB (90天) |
| 电池数据(100台) | 21.6 MB | 1.94 GB | 7.9 GB | 1.94 GB (90天) |
| 告警日志 | 25 KB | 2.25 MB | 9 MB | 9 MB (365天) |
| 事件记录 | 200 KB | 18 MB | 73 MB | 146 MB (730天) |
| 故障录波 | 50 MB | 4.5 GB | 18 GB | 18 GB (365天) |
| **合计** | **~100.6 MB** | **~9.1 GB** | **~36.5 GB** | **~22.7 GB** |

### 7.2 存储分配方案

默认 64GB eMMC 分区规划：

| 分区 | 分配大小 | 说明 |
|------|---------|------|
| 系统分区 | 20 GB | openEuler + MUPC程序 |
| 数据分区 | 44 GB | 数据库 + 波形文件 + 导出目录 |
| ├─ 时序数据 | ~5 GB | 90天遥测+电池 (WAL模式额外+WAL文件) |
| ├─ 告警事件 | ~200 MB | 告警+事件 SQLite表 |
| ├─ 故障录波 | ~18 GB | 波形文件 (文件系统) |
| ├─ 导出目录 | ~5 GB | CSV 导出临时文件 |
| ├─ WAL文件 | ~512 MB | SQLite WAL 日志上限 |
| └─ 预留 | ~15 GB | 安全余量 |

### 7.3 存储告警阈值

| 磁盘使用率 | 告警级别 | 系统行为 |
|-----------|---------|---------|
| >= 85% | WARN日志 | 仅记录日志 |
| >= 90% | minor告警 | 通知运维人员，建议手动清理 |
| >= 95% | critical告警 | 自动紧急清理(删除最短保留期30天前的数据)，停止新的时序数据写入 |
| >= 98% | critical告警 | 停止所有数据写入，仅维持只读查询 |

### 7.4 WAL文件管理

```rust
// WAL 文件检查点策略
// 1. 每次自动清理完成后执行 checkpoint
// 2. 当 WAL 文件大小超过 256MB 时执行 checkpoint
// 3. 可通过 PRAGMA wal_checkpoint(TRUNCATE) 截断 WAL
fn manage_wal_checkpoint(conn: &Connection) -> Result<(), StorageError> {
    let wal_size: i64 = conn.query_row(
        "PRAGMA wal_checkpoint(TRUNCATE)", [], |row| row.get(0)
    )?;
    tracing::info!("WAL checkpoint 完成, 返回码: {}", wal_size);
    Ok(())
}
```

## 8. 关键业务流程

### 8.1 设备创建流程

```
1. 用户 POST /api/v1/devices
2. web-api 解析请求体 → DeviceAssetCreateRequest
3. 校验必填字段: device_id, device_type, manufacturer, model, serial_number, commissioning_date
4. 校验 device_id 唯一性 → 查询 device_asset 表
5. 如果重复 → 返回 409 DUPLICATE_DEVICE_ID
6. 插入 device_asset 表
7. 创建默认铭牌参数记录 (所有字段为 NULL)
8. 记录事件: event_type=device_operation, description="创建设备 INV-001"
9. 通知 gateway (标记台账已变更, 准备上送)
10. 返回 201 { device_id, created_at }
```

### 8.2 铭牌参数修改流程

```
1. 用户 PUT /api/v1/devices/{id}/nameplate
2. web-api 解析请求体 → NameplateUpdateRequest
3. 校验 device_id 存在 → 否则返回 404
4. 查询当前铭牌参数
5. 对比新旧值, 为每个变更字段生成 NameplateChangeLog 记录
6. UPDATE device_nameplate 表
7. 记录事件: event_type=device_operation
8. 通知 gateway
9. 返回 200
```

### 8.3 数据清理流程

```
每日 02:00 (可配置) 自动触发:

1. 读取 storage_config 中的保留策略
2. 根据保留策略计算各数据类型的截止时间戳
3. 对于遥测/电池分区表:
   a. 列出所有 telemetry_* / battery_* 表
   b. 计算哪些月份的分区已超出保留期限
   c. DROP TABLE telemetry_202501 (直接删除整表)
4. 对于告警/事件表:
   a. DELETE FROM alarm_log WHERE trigger_time < cutoff
   b. DELETE FROM event_log WHERE event_time < cutoff
5. 对于故障录波:
   a. 查询 fault_records 表中超期的记录
   b. 删除关联的波形文件
   c. DELETE FROM fault_records
6. 执行 PRAGMA wal_checkpoint(TRUNCATE) 截断 WAL
7. 记录清理日志: 清理数据类型、删除记录数、清理耗时、释放空间
```

### 8.4 磁盘空间紧急处理

```rust
// 存储空间检查 (每次写入前采样执行, 间隔5分钟)
async fn check_disk_space(status: &StorageStatus) -> Option<StorageAction> {
    let usage = status.disk.usage_percent;
    match usage {
        0.0..85.0 => None,                         // 正常
        85.0..90.0 => Some(StorageAction::LogWarn),
        90.0..95.0 => Some(StorageAction::TriggerMinorAlarm),
        95.0..98.0 => Some(StorageAction::EmergencyCleanup), // 删除30天前的数据
        _ => Some(StorageAction::StopWrites),       // 停止写入
    }
}
```

### 9.2 降级模式

| 故障场景 | 降级行为 | 恢复条件 |
|---------|---------|---------|
| 数据库文件损坏 | 停止时序写入, 资产只读, 告警事件内存缓存 | 修复成功或重新初始化 |
| 磁盘空间 > 95% | 停止时序写入, 其他功能正常 | 清理后空间 < 90% |
| 磁盘空间 > 98% | 停止所有写入 | 清理后空间 < 95% |
| 单次写入超时(>5s) | 放弃本次写入, 继续处理下一条 | 正常写入恢复 |
| 连续10次写入失败 | 触发告警, 每5分钟重试 | 重试成功 |

### 9.3 启动自检

```
StorageService::init() 启动时:

1. 打开 /var/mupc/data/mupc.db
2. PRAGMA integrity_check  → 校验数据库完整性
3. 如果完整性检查失败:
   a. 尝试 PRAGMA quick_check (轻量检查)
   b. 如果仍失败 → 触发 DatabaseCorrupted 告警 → 初始化降级存储
4. 如果完整性检查通过:
   a. PRAGMA journal_mode=WAL
   b. 运行迁移 (创建缺失的表和索引)
   c. 初始化连接池
5. 启动后台任务: 写入处理协程、磁盘空间监控、数据清理调度
```

```rust
// 写入流程: 批量事务 + 幂等设计
async fn flush_batch(writes: Vec<WriteCommand>, conn: &Connection) -> Result<(), StorageError> {
    conn.execute("BEGIN IMMEDIATE", [])?;

    for write in writes {
        match write {
            WriteCommand::Telemetry(record) => {
                // 使用 INSERT OR IGNORE 处理重复时间戳 (幂等)
                conn.execute("INSERT OR IGNORE INTO ...", params![...])?;
            }
            WriteCommand::Alarm(record) => {
                conn.execute("INSERT INTO alarm_log ...", params![...])?;
            }
            // ...
        }
    }

    conn.execute("COMMIT", [])?;
    Ok(())
}
```

## 10. 安全性设计

### 10.1 输入验证

- 所有 device_id 必须符合 `^[a-zA-Z0-9_-]{1,64}$` 格式
- 时间戳必须在合理范围内（不允许未来2小时后的时间戳）
- 字符串字段做长度截断（如 manufacturer 不超过 128 字符）
- 分页参数 page_size 限制最大值 1000，默认 20

### 10.2 SQL注入防护

- 所有 SQL 查询使用参数化查询（rusqlite 原生支持 `params![]`）
- 分区表名使用白名单验证：仅允许 `^telemetry_\d{6}$` 或 `^battery_\d{6}$`

### 10.3 文件路径安全

- 导出文件路径使用白名单验证
- 文件下载路由做路径遍历防护：`file_name` 必须是 `[a-zA-Z0-9_.-]+`
- 导出文件存放在固定目录 `/var/mupc/export/`，禁止符号链接
