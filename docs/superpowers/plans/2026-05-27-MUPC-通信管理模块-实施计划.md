## 1. 项目结构

```
mupc/
├── Cargo.toml              # Workspace 配置
├── crates/
│   ├── common/             # 公共库：日志、错误类型
│   ├── gateway/             # 北向通信网关（IEC 104）
│   ├── intercore/           # 核间通信（TCP/RJ45）
│   ├── data-processing/     # 数据处理（接口预留 Phase 1）
│   ├── strategy-engine/      # 本地策略引擎（接口预留 Phase 1）
│   └── web-ui/              # Web UI（Axum + 静态文件服务）
└── tests/                  # 集成测试
```

## 2. 模块依赖关系

```
common (基础层)
    ├── gateway ──────────────依赖 common
    ├── intercore ───────────依赖 common
    ├── data-processing ──────依赖 common
    ├── strategy-engine ──────依赖 common
    └── web-ui ───────────────依赖 common

gateway ──────────────────────可调用 intercore（转发指令）
intercore ────────────────────可调用 strategy-engine（数据上报）
data-processing ──────────────依赖 intercore（获取原始数据）
strategy-engine ─────────────依赖 data-processing（获取处理后数据）
```

## 3. 模块实施计划

### 3.1 common - 公共库

**第一步**：创建 `crates/common/Cargo.toml`，定义依赖

**第二步**：创建目录结构

```
crates/common/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   ├── error.rs         # MupcError 枚举
│   └── logging.rs       # tracing 封装
└── tests/
```

**第三步**：实现错误类型 `error.rs`

- 实现 `std::error::Error` trait
- 定义 `MupcError` 枚举，覆盖模块：
  - `Gateway(Iec104Error)`
  - `Intercore(IntercoreError)`
  - `DataProcessing(DataProcessingError)`
  - `StrategyEngine(StrategyEngineError)`
  - `WebUi(WebUiError)`
  - `Config(ConfigError)`
  - `Internal(InternalError)`
- 支持错误链（`error.source()`）

**第四步**：实现日志模块 `logging.rs`

- 基于 `tracing` + `tracing-appender`
- 日志格式：`{时间戳} [{级别}] [{模块名}] {消息}`
- 文件滚动：单文件 10MB，保留 10 个
- 日志路径：`/var/log/mupc/`

**关键决策点**：
- 日志库选型：`tracing` + `tracing-subscriber` + `tracing-appender`
- 错误库选型：直接使用 `thiserror` 简化错误定义

### 3.2 gateway - 北向通信网关（IEC 104）

**第一步**：创建 `crates/gateway/Cargo.toml`，依赖 common

**第二步**：创建目录结构

```
crates/gateway/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   ├── protocol/        # IEC 104 协议解析
│   │   ├── mod.rs
│   │   ├── frame.rs    # 帧解析（U/S/I帧）
│   │   └── asdu.rs     # ASDU 类型解析
│   ├── connection.rs    # 连接管理状态机
│   ├── session.rs       # 会话管理
│   └── handler.rs      # 数据处理 handler
└── tests/
```

**第三步**：实现 IEC 104 协议解析 `protocol/`

- U 帧：STARTDT、STOPDT、TESTFR
- S 帧：确认收到的 I 帧
- I 帧：应用数据（TypeID 解析）
- 支持的 TypeID：
  - M_SP_TA_1（单点遥信）
  - M_DP_TA_1（双点遥信）
  - M_ME_TA_1（测量值，归一化）
  - M_ME_TD_1（测量值，归一化，带时标）
  - C_SC_TA_1（单点遥控）
  - C_DC_TA_1（双点遥控）
  - C_SE_TA_1（调节命令）

**第四步**：实现连接管理 `connection.rs`

- 状态机：断开、连接中、已连接、等待激活
- 心跳间隔：可配置（默认 10s，范围 1s~60s）
- 连接超时：30s
- 自动重连：断连后 5s 开始，最多 10 次

**第五步**：实现数据收发 `handler.rs`

- 数据上行：周期性发送遥测（可配置周期，默认 1s）+ 告警立即上送
- 数据下行：遥控命令转发给 strategy-engine 校验

**关键决策点**：
- 网络框架：使用 tokio-net 构建 TCP 服务器
- Frame 编解码：自定义 `LengthDelimitedCodec` 适配 IEC 104 帧格式
- 并发连接：使用 `Arc<Mutex<>>` 管理多连接

### 3.3 intercore - 核间通信（TCP/RJ45）

**第一步**：创建 `crates/intercore/Cargo.toml`，依赖 common

**第二步**：创建目录结构

```
crates/intercore/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   ├── protocol.rs     # 自定义二进制协议（帧头 + 数据 + CRC16）
│   ├── client.rs       # TCP 客户端（主动连接实时控制模块）
│   ├── heartbeat.rs    # 心跳与看门狗
│   ├── command.rs      # 指令下发
│   └── data_reader.rs   # 数据读取
└── tests/
```

**第三步**：实现自定义二进制协议 `protocol.rs`

- 帧头格式：`0xAA 0x55 + 长度(2字节) + 类型(1字节) + 序号(2字节)`
- CRC16 校验
- 定义帧类型：
  - 心跳帧
  - 指令帧
  - 数据帧
  - 确认帧

**第四步**：实现心跳与看门狗 `heartbeat.rs`

- 心跳周期：1s
- 看门狗超时：10s（连续 10 次心跳无响应）
- 超时处理：触发告警、记录日志
- 心跳帧包含：状态码、CPU温度、内存使用率

**第五步**：实现指令下发 `command.rs`

- 支持指令类型：
  - 电池有功设定（P_batt_set）
  - 电池无功设定（Q_batt_set）
  - 分相补偿系数
  - 启停命令
- 指令下发延迟 ≤ 50ms
- 指令超时时间：5s
- 指令确认机制

**第六步**：实现数据读取 `data_reader.rs`

- 读取数据类型：
  - 电气量：U、I、P、Q、cosφ、频率
  - 电池数据：SOC、SOH、温度
  - 逆变器状态
  - 功率：光伏、负荷、充电桩
- 读取周期：≥ 1Hz（默认 1s）

**关键决策点**：
- TCP 客户端模式：主动连接实时控制模块（2501端口）
- 本地监听端口：2500
- 使用 `tokio::net::TcpStream` 异步 I/O

### 3.4 data-processing - 数据处理（接口预留 Phase 1）

**第一步**：创建 `crates/data-processing/Cargo.toml`，依赖 common、intercore

**第二步**：创建目录结构

```
crates/data-processing/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   ├── traits.rs       # 抽象接口定义
│   └── mock.rs         # Phase 1 mock 实现（可编译通过）
└── tests/
```

**第三步**：定义抽象接口 `traits.rs`

Phase 1 仅定义接口，暂不实现具体逻辑：

```rust
// 数据汇聚接口
pub trait DataCollector {
    fn collect(&self) -> DataPackage;
}

// 高频遥测接口
pub trait HighFrequencyTelemetry {
    fn start(&self, period_ms: u64);
    fn stop(&self);
}

// 数据上报接口
pub trait DataReporter {
    fn report(&self, data: &DataPackage) -> Result<()>;
}

// 故障录波接口
pub trait FaultRecorder {
    fn trigger(&self, condition: &FaultCondition);
    fn get_waveform(&self) -> WaveformData;
}
```

**第四步**：实现 mock 类型 `mock.rs`

- 实现所有 trait，但仅有占位逻辑
- 返回空数据或默认值
- 确保 Phase 1 可编译、可运行

**关键决策点**：
- Phase 1 不实现真实数据处理逻辑，仅定义接口 + mock
- Phase 2  реализация 时替换 mock 即可

### 3.5 strategy-engine - 本地策略引擎（接口预留 Phase 1）

**第一步**：创建 `crates/strategy-engine/Cargo.toml`，依赖 common、data-processing

**第二步**：创建目录结构

```
crates/strategy-engine/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   ├── traits.rs       # 抽象接口定义
│   ├── commands.rs     # 控制命令类型定义
│   └── mock.rs         # Phase 1 mock 实现
└── tests/
```

**第三步**：定义抽象接口 `traits.rs`

Phase 1 仅定义接口：

```rust
// 兜底策略接口
pub trait FallbackStrategy {
    fn evaluate(&self, data: &DataPackage) -> ControlCommand;
}

// AI 指令校验接口
pub trait AiCommandValidator {
    fn validate(&self, cmd: &AiCommand) -> ValidationResult;
}
```

**第四步**：定义控制命令类型 `commands.rs`

```rust
pub struct ControlCommand {
    pub p_batt_set: f64,        // 电池有功设定 (-1000kW ~ 1000kW)
    pub q_batt_set: f64,        // 电池无功设定 (-1000kVar ~ 1000kVar)
    pub phase_compensation: [f64; 3],  // 分相补偿系数
    pub start_stop: StartStop,  // 启停命令
}

pub struct ValidationResult {
    pub valid: bool,
    pub reason: Option<String>,
}
```

**第五步**：实现 mock 校验逻辑 `mock.rs`

- FallbackStrategy：返回默认控制命令
- AiCommandValidator：仅校验范围，不实现 AI 逻辑
  - 有功设定值：-1000kW ~ 1000kW
  - 无功设定值：-1000kVar ~ 1000kVar
  - 变化率限制：每周期不超过 10%

**关键决策点**：
- Phase 1 校验规则写死在 mock 中
- Phase 2 替换为真实 AI 引擎时，仅需改变 trait 实现

### 3.6 web-ui - 本地运维界面

**第一步**：创建 `crates/web-ui/Cargo.toml`，依赖 common、gateway、intercore

**第二步**：创建目录结构

```
crates/web-ui/
├── Cargo.toml
├── src/
│   ├── lib.rs
│   ├── main.rs          # 入口（可选，也可作为二进制）
│   ├── auth.rs          # HTTP Basic 认证
│   ├── routes/
│   │   ├── mod.rs
│   │   ├── config.rs    # 配置管理 API
│   │   ├── logs.rs      # 日志查看 API
│   │   ├── status.rs    # 状态查看 API
│   │   └── static_files.rs  # 静态文件服务
│   └── templates/       # HTML 模板（可选，也可用静态 HTML）
└── frontend/           # 前端静态文件
    ├── index.html
    ├── css/
    └── js/
```

**第三步**：实现 HTTP Basic 认证 `auth.rs`

- 默认用户：admin（密码可配置）
- 认证失败返回 401
- 敏感操作需要再次确认

**第四步**：实现配置管理 API `routes/config.rs`

- GET/PUT 配置项：
  - IEC 104 连接参数（IP、端口、心跳间隔 1s~60s）
  - intercore 通信参数（本地端口 2500、对端端口 2501）
  - 遥测上报周期
  - 日志级别
- 配置保存后自动生效

**第五步**：实现日志查看 API `routes/logs.rs`

- WebSocket 实时推送日志（ERROR、WARN、INFO 过滤）
- 按时间范围、关键字搜索
- 下载日志文件（.log 格式）
- 单次导出最大 10000 条

**第六步**：实现状态查看 API `routes/status.rs`

- 固件版本号、编译时间
- 运行时间（uptime）
- CPU 温度、内存使用率
- 各模块连接状态
- 页面自动刷新周期：5s

**第七步**：创建前端静态文件 `frontend/`

- 简化版单页应用（SPA）
- 使用原生 HTML/CSS/JS，无框架依赖
- 支持 Chrome 90+、Firefox 88+、Edge 90+

**关键决策点**：
- Web 框架选型：Axum（支持 WebSocket、路由简便）
- HTTP 服务独立运行，不影响核心通信
- 默认端口：8080
- 前端不引入框架，保持轻量（Phase 1 够用即可）

## 4. 关键路径分析

### 4.1 关键路径（必须按顺序执行）

```
1. common（基础层，所有模块依赖）
   ↓
2. intercore（依赖 common，需最早与实时控制模块对接）
   ↓
3. gateway（依赖 common，可独立开发）
   ↓
4. strategy-engine（依赖 common、data-processing）
   ↓
5. data-processing（依赖 common、intercore）
   ↓
6. web-ui（依赖 common、gateway、intercore）
```

### 4.2 可并行工作

| 并行组 | 模块 | 说明 |
|--------|------|------|
| 并行 1 | common | 独立开发，无依赖 |
| 并行 2 | gateway | 仅依赖 common |
| 并行 3 | intercore | 仅依赖 common |
| 并行 4 | data-processing + strategy-engine | 互相依赖，可同时定义接口 |
| 并行 5 | web-ui | 依赖 common、gateway、intercore |

### 4.3 第一步汇总

| 模块 | 第一步 |
|------|--------|
| common | 创建 `Cargo.toml`，定义 tracing + thiserror 依赖 |
| gateway | 创建 `Cargo.toml`，依赖 common |
| intercore | 创建 `Cargo.toml`，依赖 common |
| data-processing | 创建 `Cargo.toml`，定义 traits.rs 接口 |
| strategy-engine | 创建 `Cargo.toml`，定义 traits.rs 接口 |
| web-ui | 创建 `Cargo.toml`，依赖 common + Axum |

## 8. 技术决策记录

| 决策 | 选择 | 备选方案 | 决策理由 |
|------|------|----------|----------|
| 日志库 | tracing + tracing-subscriber + tracing-appender | log + env_logger | tracing 与 Tokio 集成更好，支持结构化日志 |
| 错误库 | thiserror | 自定义错误枚举 | 简化错误定义，自动实现 Error trait |
| Web 框架 | Axum | actix-web | 与 Tokio 兼容性更好，API 简洁 |
| 前端框架 | 原生 HTML/JS | React/Vue | Phase 1 够用，减少依赖复杂度 |
| 配置文件 | TOML | YAML/JSON | Rust 原生支持，配置简洁 |
| 协议编解码 | 手动实现 | protobuf/cbor | 二进制协议简单，自定义更灵活 |
