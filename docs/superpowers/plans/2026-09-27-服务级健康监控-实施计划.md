# 服务级健康监控 —— 实施计划

> **来源**：U-164（`docs/technical-debt.md` §6.19）裁定「口径改三层 + 服务级健康要真的实现」。
> 本计划为实施合同；**评审通过后**按下述 Task 顺序落地。

**目标**：① 把 07 号（OTA 与系统可靠性）的进程监控口径改为**三层分工**；② 实现 `mupcd` 内的**服务级健康巡检**。

**架构**：复用既有的 `ServiceCoordinator`（`mupc-core`）与 `AlertFeed`（`mupc-core-bin`），**不新建轮子**；巡检任务镜像 `storage_health.rs` 的形状（周期任务 + 纯函数判据 + 边沿触发）。

**关键前置事实**（均已实测）：

- `ServiceCoordinatorImpl` 的 `update_service_status` / `health_check` / `list_all_services` / `get_service_info` —— **全仓零调用点**（死代码）
- `startup.rs` 已注册 **14 个服务**，**注册后无人读**
- `security` / `ai_engine` / `ota_update` / `wireless` 注册时状态即 `Stopped`（停用/框架态）；`health_check()` **只把 `Failed` 算不健康** ⇒ `Stopped` 天然不告警
- 进程级存活/重启/上限 **systemd 已就位**（`Restart` / `RestartSec` / `StartLimitBurst` / `MemoryMax`）

---

## 一、三层分工（目标口径）

| 层 | 谁做 | 现状 |
|---|---|---|
| **进程级**（`mupcd` / `mupc-local-display`） | **systemd** | ✅ 已就位，不重复实现 |
| **服务级**（`mupcd` 内子系统） | **`ServiceCoordinator`** | 🟡 面已存在但为死代码 ⇒ 本计划落地 |
| **跨进程**（只对 display） | `mupcd` 经 display 通道观测 | 🟡 通道连接态可得 |

**为何 `system-monitor` 做不了进程级**：它是 `mupcd` **内部**的库，监控/重启 `mupcd` 自己会随之一同消失。⇒ §4.2.1 关键进程存活、§4.2.2 自动重启、§6.4「同时 3 个进程按优先级重启」是**结构性不可实现**，不是"没做"。

## 三、探针清单（判据来源）

> **⚠️ 本节已于实现时纠正（2026-09-27）** —— 初版探针表有三条**判据语义错误**，实现时剔除。详见下方「为什么剔除」。
> 纠正后的表即**落地形态**（`mupc-core-bin/src/service_health.rs` 的 `unhealthy_services` / `NOT_PROBED`）。

### 落地探针（只做**有可靠失败信号**的）

| 服务 | 判据来源 | 位置 |
|---|---|---|
| `pcs` | `pcs_collect_watch.{finished(), panicked()}` —— B-9 的 `TaskWatch`（采集 task 结束/panic） | `mupc-southd/src/task_watch.rs:42,47`；装配点 `startup.rs` 的 `pcs_collect_watch` |
| `storage` | `WriteGate::is_degraded()` —— DB 完整性失败或磁盘水位触发停写 | `storage/src/write_gate.rs:146` |

### 显式不做探针（登记于 `NOT_PROBED`，每条附理由）

| 服务 | 为什么没有探针 |
|---|---|
| `gateway` | ~~`connection_count()`~~ —— **0 连接是常态**（主站未连），不能当服务故障 |
| `hmi_backend` | ~~display 通道态~~ —— **屏可以关**，不能当服务故障 |
| `data_processing` | ~~`station_is_active`~~ —— 反映**现场设备**离线，是**外部事件**（已有独立告警通道） |
| `intercore` | 核间 TCP **生产路径无消费者**，无「可用/不可用」可言 |
| `security` / `ai_engine` / `ota_update` / `wireless` | 注册时即 `Stopped` ⇒ **天然不告警**（硬约束：不得当 `Failed`） |
| `message_bus` / `strategy_engine` / `plugin_loader` / `system_monitor` | 进程内组件，无独立失败面 |

### 为什么剔除那三条（本次实现的**关键取舍**）

初版把「外部设备/对端不在线」当成了「服务不健康」，而这三者在现场**绝大多数时间是常态**：

- `Iec104Server::connection_count() == 0` —— 主站没连就恒告警
- display 通道未连接 —— 屏没开就恒告警
- `LatestValues::station_is_active(..) == false` —— 现场设备离线就恒告警，且它**已有自己的告警通道**

⇒ 用它们当判据会造出**比"不实现"更坏**的形态（现场被恒告警淹没，真故障反而看不见）。
**本模块的判据只认「进程内这个子系统不转了」**，这条边界写在 `service_health.rs` 模块头第 2 条。

## 四、明确不做

- **不**在 `mupcd` 内实现进程级重启（systemd 的事）
- **不**实现「服务级自动重启」（单进程内没法重启单个服务，只**告警 + 降级**）
- **不**动 `system-monitor` 的自愈（U-131 已如实返 `success:false`）
- **不**重连 U-163（HIL 闭环已裁定不重建）
- **不**改 `ServiceCoordinator` trait 本身（面已够用）
