## 2. 固件 OTA 架构

### 2.1 A/B 双分区方案

#### 2.1.1 RK3588 分区布局

基于 RK3588 平台 eMMC 存储的物理分区规划（推荐 eMMC >= 32GB）：

```
eMMC 布局:
┌──────────────────────────────────────────────────────────────┐
│ 分区名称        | 大小    | 挂载点          | 文件系统 | 说明  │
├──────────────────────────────────────────────────────────────┤
│ bootloader      | 8MB     | -               | raw     | U-Boot│
│ env             | 8MB     | -               | raw     | U-Boot env (含 boot_partition) │
│ trust           | 8MB     | -               | raw     | OP-TEE │
│ boot            | 256MB   | /boot           | ext4    | 内核+DTB+initrd │
│ system-a        | 2GB     | /               | ext4    | 主系统分区 A │
│ system-b        | 2GB     | (备用)          | ext4    | 主系统分区 B │
│ data            | 剩余    | /data           | ext4    | 持久化数据 │
│ ota_scratch     | 512MB   | /ota            | ext4    | OTA 临时文件/差分包 │
│ models          | 1GB     | /models         | ext4    | AI 模型存储 │
│ logs            | 2GB     | /var/log        | ext4    | 系统日志 │
└──────────────────────────────────────────────────────────────┘
```

#### 2.1.2 Bootloader 分区选择逻辑

U-Boot 环境变量 `boot_partition` 控制从哪个分区启动：

```
启动决策树:
1. U-Boot 读取 env 分区中的 `boot_partition` 变量
   ├── "a" → 从 system-a 分区启动
   └── "b" → 从 system-b 分区启动
2. 如果 `boot_partition` 不存在或无效:
   └── 默认从 system-a 分区启动
3. 如果指定分区无法挂载 (e.g. ext4 fs 损坏):
   └── 回退到另一个分区并设置 `ota_status=rollback`
```

**env 分区关键变量定义：**

| 变量名 | 类型 | 说明 |
|--------|------|------|
| `boot_partition` | string | `"a"` 或 `"b"`，当前启动分区 |
| `boot_attempts` | u32 | 当前分区启动尝试次数 |
| `max_boot_attempts` | u32 | 最大启动尝试次数（默认 3） |
| `ota_status` | string | `"idle"`/`"updated"`/`"rollback"`/`"safe"` |

#### 2.1.3 分区切换原子性保证

```
升级切换流程:
1. ota-update 写入 system-b 完成
2. 计算 system-b 全分区 SHA-256 → 写入 /ota/b_checksum
3. 写入 env: boot_partition = "b" (带 fsync)
4. 写入 env: ota_status = "updated" (带 fsync)
5. 如果第 3 步失败 → 保持 "a"，上报 bootloader_update_failed
6. 如果第 4 步失败 → 不影响启动，只是丢失状态标记
```

**关键可靠性措施：**

- U-Boot env 写入后执行 `saveenv` + 等待存储写回确认
- env 分区使用双备份（主 env + 冗余 env），一个损坏时使用另一个
- `boot_partition` 写入前校验 system-b 分区的完整性

### 2.3 `.mupc` 固件包容器格式实现

```rust
/// .mupc 固件包容器格式
///
/// 二进制布局:
/// ┌─────────────────────────────────────────┐
/// │ Magic:         4B  "MUPC"               │
/// │ Version:       1B  容器格式版本 (0x01)   │
/// │ HeaderLen:     4B  LittleEndian u32     │
/// │ HeaderJSON:    N 字节 JSON 字符串        │
/// │ Padding:       变长 对齐到 4 字节        │
/// │ Signature:     64B SM2-with-SM3 签名    │
/// │ Payload:       N 字节 (tar.gz 或 bsdiff)│
/// └─────────────────────────────────────────┘

/// 头部 JSON 结构
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct MupcHeader {
    /// 包类型: "full" 或 "incremental"
    pub package_type: String,
    /// 目标固件版本 (semver)
    pub target_version: String,
    /// 基准版本 (增量包必填)
    #[serde(skip_serializing_if = "Option::is_none")]
    pub base_version: Option<String>,
    /// Payload SHA-256 校验和
    pub checksum: String,
    /// 文件清单
    pub file_list: Vec<FileEntry>,
    /// 时间戳 (Unix 毫秒)
    pub timestamp: u64,
    /// 目标平台
    pub target_platform: String,
    /// 最低 bootloader 版本
    pub min_bootloader_version: String,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct FileEntry {
    pub path: String,
    pub size: u64,
    pub mode: u32,       // Unix 文件权限
    pub checksum: String, // 单个文件 SHA-256
}
```

### 2.4 A/B 分区管理实现

```rust
/// 分区信息
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct PartitionInfo {
    pub name: String,        // "system-a" / "system-b"
    pub device: String,      // "/dev/mmcblk0p3" / "/dev/mmcblk0p4"
    pub mount_point: String, // "/" / "(备用)"
    pub is_active: bool,     // 当前是否激活
}

/// 分区管理器
pub struct PartitionManager {
    current: PartitionInfo,
    standby: PartitionInfo,
    env_device: String, // "/dev/mmcblk0p2" (env 分区)
}

impl PartitionManager {
    /// 检测当前和备用分区
    pub fn detect() -> Result<Self>;

    /// 挂载备用分区
    pub async fn mount_standby(&self) -> Result<MountGuard>;

    /// 写入备用分区
    pub async fn write_standby(&self, payload: &[u8], file_list: &[FileEntry]) -> Result<()>;

    /// 验证备用分区完整性
    pub async fn verify_standby_integrity(&self, expected_checksum: &str) -> Result<bool>;

    /// 切换 boot_partition 到备用分区
    pub async fn switch_to_standby(&self) -> Result<()>;

    /// 回滚到原分区
    pub async fn rollback_to_current(&self) -> Result<()>;

    /// 读取 U-Boot env 变量
    fn read_env_var(&self, name: &str) -> Result<Option<String>>;

    /// 写入 U-Boot env 变量 (带 fsync)
    fn write_env_var(&self, name: &str, value: &str) -> Result<()>;
}
```

**写入流程细节（关键路径）：**

```
write_standby():
1. 解析 file_list（有序，先创建目录）
2. 对每个文件条目:
   a. 在备用分区创建父目录 (mkdir -p)
   b. 写入文件内容 (write)
   c. 设置文件权限 (chmod)
   d. fsync 文件
3. 对备用分区根目录执行 fsync
4. 验证写入后文件数量与 file_list 匹配
```

### 2.5 Bootloader env 操作实现

```rust
/// Bootloader env 操作抽象
///
/// 通过 fw_setenv / fw_printenv 工具或直接操作 MTD 设备
pub struct BootloaderEnv {
    /// env 分区设备路径
    env_device: String,
    /// 是否使用 fw_setenv 工具
    use_tools: bool,
}

impl BootloaderEnv {
    /// 读取 env 变量
    pub fn read(&self, key: &str) -> Result<Option<String>>;

    /// 写入 env 变量 (自动执行 saveenv)
    pub fn write(&self, key: &str, value: &str) -> Result<()>;

    /// 批量写入（原子性，全部成功或全部回滚）
    pub fn batch_write(&self, pairs: &[(&str, &str)]) -> Result<()>;

    /// 读取当前启动分区
    pub fn current_boot_partition(&self) -> Result<String> {
        self.read("boot_partition")
            .map(|v| v.unwrap_or_else(|| "a".to_string()))
    }

    /// 切换启动分区（核心操作）
    pub fn set_boot_partition(&self, partition: &str) -> Result<()> {
        // 1. 先写入 boot_partition
        self.write("boot_partition", partition)?;
        // 2. 重置启动尝试计数
        self.write("boot_attempts", "0")?;
        // 3. 设置 ota_status
        self.write("ota_status", "updated")?;
        Ok(())
    }
}
```

## 3. 升级状态机设计

### 3.1 固件升级专用状态

```rust
/// 固件OTA状态 - 细化状态机，与模型OTA状态分离
#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub enum FwOtaState {
    /// 空闲
    Idle,
    /// 版本查询中
    Checking,
    /// 等待升级窗口
    WaitingWindow,
    /// 预检查中（包含与 intercore 的协同检查）
    PreCheck,
    /// 发送 ai_ready=false + strategy_mode=basic
    SendingDowngradeSignal,
    /// 等待实时控制模块确认
    WaitingControlConfirm,
    /// 下载中（带进度）
    Downloading { progress: u8 },
    /// 下载暂停（等待重试）
    DownloadPaused,
    /// 完整性验证中
    IntegrityCheck,
    /// 签名验证中
    SignatureVerify,
    /// 写入备用分区
    WritingPartition,
    /// 分区验证中
    PartitionVerify,
    /// 更新 Bootloader 配置
    UpdatingBootloader,
    /// 等待重启
    WaitingReboot,
    /// 重启后验证中
    PostVerify,
    /// 标记升级成功
    MarkingSuccess,
    /// 回滚中
    RollingBack,
    /// 发送 ai_ready=true 恢复信号
    SendingRestoreSignal,
    /// 升级成功完成
    Completed,
    /// 失败
    Failed { error: String, phase: String },
    /// 安全模式（连续3次失败）
    SafeMode,
}
```

### 3.3 核心状态机实现

```rust
/// 固件升级状态机
pub struct FwStateMachine {
    state: RwLock<FwOtaState>,
    config: FwOtaConfig,
    /// 连续失败计数器
    consecutive_failures: AtomicU32,
    /// 超时计时器
    timeout: RwLock<Option<Instant>>,
}

impl FwStateMachine {
    /// 尝试状态转换（含守卫检查）
    pub async fn transition(&self, target: FwOtaState) -> Result<(), OtaError> {
        let current = self.state.read().await;
        if !self.is_valid_transition(&current, &target) {
            return Err(OtaError::InvalidStateTransition {
                from: format!("{:?}", current),
                to: format!("{:?}", target),
            });
        }
        drop(current); // 释放读锁

        // 执行边界检查
        self.check_transition_guards(&target).await?;

        // 转换状态
        let mut state = self.state.write().await;
        *state = target;
        Ok(())
    }

    /// 有效转换检查
    fn is_valid_transition(&self, from: &FwOtaState, to: &FwOtaState) -> bool {
        match (from, to) {
            // Idle → Checking
            (FwOtaState::Idle, FwOtaState::Checking) => true,
            // Checking → WaitingWindow / PreCheck / Idle
            (FwOtaState::Checking, FwOtaState::WaitingWindow) => true,
            (FwOtaState::Checking, FwOtaState::PreCheck) => true,
            (FwOtaState::Checking, FwOtaState::Idle) => true,
            // WaitingWindow → PreCheck (窗口到达)
            (FwOtaState::WaitingWindow, FwOtaState::PreCheck) => true,
            // PreCheck → SendingDowngradeSignal
            (FwOtaState::PreCheck, FwOtaState::SendingDowngradeSignal) => true,
            // SendingDowngradeSignal → WaitingControlConfirm
            (FwOtaState::SendingDowngradeSignal, FwOtaState::WaitingControlConfirm) => true,
            // WaitingControlConfirm → Downloading
            (FwOtaState::WaitingControlConfirm, FwOtaState::Downloading { .. }) => true,
            // Downloading → IntegrityCheck / DownloadPaused
            (FwOtaState::Downloading { .. }, FwOtaState::IntegrityCheck) => true,
            (FwOtaState::Downloading { .. }, FwOtaState::DownloadPaused) => true,
            // DownloadPaused → Downloading (重试)
            (FwOtaState::DownloadPaused, FwOtaState::Downloading { .. }) => true,
            // IntegrityCheck → SignatureVerify
            (FwOtaState::IntegrityCheck, FwOtaState::SignatureVerify) => true,
            // SignatureVerify → WritingPartition
            (FwOtaState::SignatureVerify, FwOtaState::WritingPartition) => true,
            // WritingPartition → PartitionVerify
            (FwOtaState::WritingPartition, FwOtaState::PartitionVerify) => true,
            // PartitionVerify → UpdatingBootloader
            (FwOtaState::PartitionVerify, FwOtaState::UpdatingBootloader) => true,
            // UpdatingBootloader → WaitingReboot
            (FwOtaState::UpdatingBootloader, FwOtaState::WaitingReboot) => true,
            // WaitingReboot → PostVerify (系统重启后)
            (FwOtaState::WaitingReboot, FwOtaState::PostVerify) => true,
            // PostVerify → MarkingSuccess / RollingBack
            (FwOtaState::PostVerify, FwOtaState::MarkingSuccess) => true,
            (FwOtaState::PostVerify, FwOtaState::RollingBack) => true,
            // MarkingSuccess → SendingRestoreSignal
            (FwOtaState::MarkingSuccess, FwOtaState::SendingRestoreSignal) => true,
            // SendingRestoreSignal → Completed
            (FwOtaState::SendingRestoreSignal, FwOtaState::Completed) => true,
            // RollingBack → Idle / SafeMode
            (FwOtaState::RollingBack, FwOtaState::Idle) => true,
            (FwOtaState::RollingBack, FwOtaState::SafeMode) => true,
            // Failed → Idle / SafeMode
            (FwOtaState::Failed { .. }, FwOtaState::Idle) => true,
            (FwOtaState::Failed { .. }, FwOtaState::SafeMode) => true,
            // SafeMode → Idle (管理员手动恢复后)
            (FwOtaState::SafeMode, FwOtaState::Idle) => true,
            // 超时或失败分支：任意状态 → Failed
            (_, FwOtaState::Failed { .. }) => true,
            // 相同状态
            (s, t) if s == t => true,
            _ => false,
        }
    }

    /// 转换守卫检查（超时/失败计数）
    async fn check_transition_guards(&self, target: &FwOtaState) -> Result<()> {
        match target {
            FwOtaState::PreCheck => {
                // 检查连续失败次数
                if self.consecutive_failures.load(Ordering::Acquire) >= 3 {
                    return Err(OtaError::SafeModeEngaged);
                }
            }
            FwOtaState::Downloading { .. } => {
                // 检查下载窗口
                self.check_download_window().await?;
            }
            _ => {}
        }
        Ok(())
    }
}
```

## 4. 差分包与签名验证

### 4.1 差分算法选型

| 算法 | 压缩率 (patch版本) | 内存需求 | 速度 | Rust 生态 | 选择 |
|------|-------------------|---------|------|-----------|------|
| **bsdiff** | 基准 (patch包约全量30%) | 高 (需加载完整新旧文件) | 快 | `bsdiff-rs` / `bspatch` | **首选** |
| xdelta3 | 略低于 bsdiff | 中 | 中 | `xdelta3` | 备选 |
| rdedup | 适合固件有大量重复块 | 中 | 慢 | `rdedup` | 不选 |

**选型决定：bsdiff**

依据：
1. PRD 要求 patch 版本差分包不超过全量包 30% — bsdiff 在二进制差分上表现最优
2. 固件包大小上限 200MB，RK3588 有足够内存承载差分运算
3. Rust 生态存在 `bspatch` 库可集成（或用 C 绑定通过 FFI 调用）

**bsdiff 在固件 OTA 中的应用：**

```
OTA 服务器端 (生成差分包):
1. 获取基准固件包 (base_version) 和目标固件包 (target_version)
2. 调用 bsdiff 生成差分数据
3. 将差分数据打包为 incremental 类型 .mupc 包
4. 签名并发布

设备端 (应用差分包):
1. 下载 incremental .mupc 包
2. 从当前运行分区读取基准固件数据
3. 调用 bspatch 合并 → 得到完整固件数据
4. SHA-256 校验合并结果
5. 将完整固件写入备用分区
```

```rust
/// MTBF 计算结果
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct MtbfReport {
    /// 报告生成时间
    pub report_time: u64,
    /// 报告起止时间
    pub period_start: u64,
    pub period_end: u64,
    /// 总运行时间 (秒)
    pub total_running_duration: u64,
    /// 异常中断次数
    pub crash_count: u32,
    /// MTBF 计算值 (小时)
    pub mtbf_hours: f64,
    /// 各中断类型占比
    pub fault_distribution: HashMap<String, u32>,
    /// 当前 uptime (秒)
    pub current_uptime: u64,
    /// 当前状态
    pub status: MtbfStatus,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum MtbfStatus {
    Healthy,                    // MTBF >= 50,000
    Warning,                    // 10,000 < MTBF < 50,000
    Critical,                   // MTBF < 10,000
    InsufficientData,           // 数据不足
}

/// MTBF 计算器
pub struct MtbfCalculator {
    uptime_tracker: Arc<UptimeTracker>,
    fault_counter: Arc<FaultCounter>,
    /// 报告输出路径: /var/lib/mupc/systemd/mtbf.json
    report_path: PathBuf,
}

impl MtbfCalculator {
    /// 计算 MTBF (365 天滚动窗口)
    ///
    /// MTBF = sum(running_durations) / crash_count
    ///
    /// 其中:
    /// - running_durations: 365天内所有正常运行的时段总和
    /// - crash_count: 365天内异常中断的次数
    pub async fn calculate(&self) -> Result<MtbfReport> {
        let now = chrono::Utc::now().timestamp() as u64;
        let window_start = now - 365 * 24 * 3600;

        // 读取所有历史记录
        let history = self.uptime_tracker.read_history().await?;

        // 筛选窗口内的记录
        let windowed: Vec<&UptimeRecord> = history.iter()
            .filter(|r| r.boot_time >= window_start)
            .collect();

        // 计算总运行时间
        let total_running: u64 = windowed.iter()
            .filter_map(|r| r.running_duration)
            .sum();

        // 获取故障计数 (仅异常中断)
        let faults = self.fault_counter.query_recent_faults(365).await?;
        let crash_count = faults.len() as u32;

        // 计算 MTBF
        let mtbf_hours = if crash_count > 0 {
            total_running as f64 / crash_count as f64 / 3600.0
        } else {
            // 无故障时返回总运行时间作为 MTBF
            total_running as f64 / 3600.0
        };

        // 生成报告
        Ok(MtbfReport {
            report_time: now,
            period_start: window_start,
            period_end: now,
            total_running_duration: total_running,
            crash_count,
            mtbf_hours,
            fault_distribution: self.compute_distribution(&faults),
            current_uptime: self.get_current_uptime().await,
            status: Self::classify(mtbf_hours),
        })
    }

    /// MTBF 分类
    fn classify(mtbf_hours: f64) -> MtbfStatus {
        if mtbf_hours >= 50_000.0 {
            MtbfStatus::Healthy
        } else if mtbf_hours >= 10_000.0 {
            MtbfStatus::Warning
        } else if mtbf_hours > 0.0 {
            MtbfStatus::Critical
        } else {
            MtbfStatus::InsufficientData
        }
    }

    /// 定时计算 (每 24 小时)
    pub async fn scheduled_calculation(&self) {
        let mut interval = tokio::time::interval(Duration::from_secs(24 * 3600));
        loop {
            interval.tick().await;
            match self.calculate().await {
                Ok(report) => {
                    // 保存报告
                    self.save_report(&report).await?;
                    // 如果 MTBF < 10,000，分发告警
                    if matches!(report.status, MtbfStatus::Critical) {
                        alert_dispatcher.dispatch(/* MTBF 告警 */).await?;
                    }
                }
                Err(e) => tracing::error!("MTBF 计算失败: {}", e),
            }
        }
    }
}
```

```rust
impl UpgradeSignalManager {
    /// 发送降级信号 (升级前)
    ///
    /// 1. 发送 strategy_mode = "basic"   → 实时控制模块切换至兜底策略

        let cmd = IntercoreFrame::new(
            FrameType::ControlCmd,
            self.next_seq_no(),
            serde_json::to_vec(&serde_json::json!({
                "cmd": "set_strategy_mode",
                "mode": "basic"
            }))?,
        );
        self.intercore_client.send_frame(cmd).await?;

        // 发送 ai_ready
        let cmd = IntercoreFrame::new(
            FrameType::StatusReport,
            self.next_seq_no(),
            serde_json::to_vec(&serde_json::json!({
                "ai_ready": false
            }))?,
        );

    pub async fn send_restore_signals(&self) -> Result<()> {

                }
```

```rust
                Err(e) => {
                    return Err(OtaError::IntercoreReconnectFailed(format!(
                        "重连 {} 次后失败: {}",
                        retries, e
                    )));
                }
            }
        }
```

## 10. 与现有模块集成方案

### 10.1 与 security crate 集成

```rust
// update-engine 中通过 feature gate 复用 security 的 SM2 能力
// Cargo.toml:
// mupc-security = { path = "../security" }

// 使用方式:
use mupc_security::sm2_verify;

// 注意: security crate 的 sm2_verify 接受 &[u8] 数据 + &[u8] 签名
//      固件 OTA 需要传入 64 字节签名 + magic+header+payload 的完整哈希
```

### 10.2 与 intercore crate 集成

```rust
// update-engine 中通过 mupc-intercore 发送升级信号
// Cargo.toml:
// mupc-intercore = { path = "../intercore" }

// 在升级前:
use mupc_intercore::{IntercoreServer, IntercoreFrame, FrameType};

// UpgradeSignalManager 使用 IntercoreServer 发送:
// 1. strategy_mode = basic (FrameType::ControlCmd)
// 2. ai_ready = false (FrameType::StatusReport)

// system-monitor 中也引用 intercore 的 HeartbeatManager
// 用于监控核间通信延迟
```

### 10.3 与 web-api crate 集成

```rust
// system-monitor 对接 web-api 暴露 REST API:
// GET /api/v1/ota/firmware/status  → 升级状态
// GET /api/v1/ota/firmware/history → 升级历史
// GET /api/v1/system/resources      → 资源监控指标
// GET /api/v1/system/mtbf           → MTBF 报告

// system-monitor 实现 WebSocket 推送:
// 告警事件通过 web-api 的现有 WS 通道推送到前端

// 集成方式: system-monitor 不直接作为 web-api 的路由
// 而是通过 HTTP 或共享数据库向 web-api 提供数据
// 或 system-monitor 内部启动一个轻量级 HTTP 端点供 web-api 反代
```
