## 三、类别①：可立即做的 4 项

### 立项 B-1（G2 主体）｜`PcsHandle::send_dual_param` 补输入边界 ✅ **已执行（2026-09-29）**

- **改什么**：在 `send_dual_param` 写寄存器前对 `p_ref` 做**设备量程 clamp**（与分相通道 `clamp_phase ±25` 对称），越限时 `warn!` 记录原值与被 clamp 后的值。
- **为什么**：`PcsHandle` 是**安全链执行端**；两入口的边界防护应**对称**。当前唯一活调用者（IEC104）上游已 clamp（`startup.rs:270`），但这是"靠调用方自律"。
- **已做**（`5d77d37`）：`regs.rs` **+35** 新增 `CONST_POWER_LIMIT_KW = 100.0` + `clamp_const_power`；`pcs/mod.rs` **+71** 在 `send_dual_param` 接入（**签名未改**）。
- ⭐ **量程取值的证据与理由**（实施时自主判断，**经我复核协议原文确认**）：
  - **依据**：协议 V1.3 点表**逐行明写取值** —— 寄存器 `1001`「输出有功功率设置」`*1Kw` **−100~100**；`1002`「输出无功功率设置」`*1kvar` **−100~100**（`hw/_ref_pcs60_proto.txt:1262-1280`）
  - **不取额定 60 kW**：其权威源在**策略侧**（`p_cap`），在此复制即生**第二份真源**
  - **不可复用 ±25**：那是**单相**量程，会把 60 kW 的合法指令静默降到 25 ⇒ **功能回归**
  - ⇒ 各处各自钳**自己寄存器的声明量程**（分相 ±25 / 恒功率 ±100），语义对称且无第二真源
- **测试**：`send_dual_param_clamps_p_ref_to_device_range`（正负双侧）。
- **验证**：`cargo test -p mupc-southd` **303 passed / 0 failed**；**破坏性验证**（代理复做）：去掉 clamp ⇒ 红（`left 38400 / right 25600`）→ `cp` 还原 + `sha256sum` 一致。未越限入参**零行为变化**（现网合法值 ≤60，线上字节一字不变）。
- **路径**：**B**。

### 立项 B-3（Q-1 裁定）｜数据超期停发 ⇒ 改为**下发归零**

- **改什么**：`run_fallback_strategies` 的 `ts.elapsed() > DATA_STALE_AFTER` 分支（`ai_integration.rs:386-393`）——由「`warn!` + `return Ok(())`」改为「`warn!` + **下发 `zero_command`**（分相 P/Q = 0）+ **保持节流告警**」。
- **为什么**：裁定取 (b)，与 **D-2**（`refuse_missing_soc` → `zero_command`，`tai_storage.rs:477/446`）一致——**同一语义（驱动数据不可信）不应有两种相反的处置**。
- **复用现成件**：`zero_command` 与"30 s 节流告警"在 D-2 里**已实现**，本项是把它接到第二条触发条件上，**不新建机制**。
- **⚠️ 三项须一并处理，不得只加一行**：
  1. **归零本身是一次控制动作** —— 须确认不会与"去抖 `last_sent_tai`"互相干扰（归零值也要进缓存，否则恢复后可能被节流跳过）
  2. **幂等** —— 超期期间每拍都会走该分支；若每拍都下发归零，即为每拍一次 RS485 事务 ⇒ **须与 D-2 同款节流**（只在"首次进入降级"时下发一次，而非每拍）
  3. **恢复路径** —— 数据恢复后须能重新拉起（检查 `last_sent_tai` 是否因归零被占位而跳过真实指令）
- **范围**：`mupc/crates/strategy-engine/src/ai_integration.rs`（主）+ 可能的 `tai_storage.rs`；**3 条判别力测试**（首次进入降级下发一次归零 / 持续降级不重复下发 / 恢复后能正常拉起）。
- **路径**：**B**，但**属安全相关行为变更** ⇒ 设计口径须先写进 04 设计文档再改代码；代码评审与测试门禁**不可省**。
- ✅ **已执行（2026-09-29，`26b6dc6`）**：
  - `tai_storage.rs` **+64**：新增 `refuse_stale_data()`（与 `refuse_missing_soc` 对称：状态清零 + `zero_command` + 更新 `last_cmd` + **独立节流告警** `stale_warned`/`stale_warn_count`/`STALE_WARN_INTERVAL`）
  - `ai_integration.rs` **+286/−49**：抽出**私有 `dispatch_phase_pq`**（去抖→发送→审计的**唯一实现**），正常路径与归零路径**共用**——这正是"归零值也写入 `last_sent_tai`"的保证点；超期分支改为调 `refuse_stale_data()` + `dispatch_phase_pq`
  - **3 条测试**：`b3_stale_data_dispatches_zero_once` / `b3_stale_data_repeated_ticks_dispatch_once` / `b3_recovery_resends_real_command_after_zeroing`，每条注明"改什么即红"
  - **验证**：`cargo test -p mupc-strategy-engine` **87 passed / 0 failed**（基线 84）；**独立破坏性验证**（本人复做，非采信代理）：把超期分支改回"停发" ⇒ **3/3 红**（文案「归零须写满分相 P/Q 6 个寄存器，实得 []」）→ `cp` 还原 + `sha256sum` 一致 + 复跑全绿
  - **如实登记的局限**：① 告警文案把阈值**硬编码为 "5s"**（`DATA_STALE_AFTER` 为私有常量，改阈值须同步文案）；② `tai_storage` 未注入时，旧的无条件 `warn!` 降为 `debug!`（**观测性略降**，但不影响控制）；③ 恢复路径测试依赖"归零前后控制输出逐位相同"，若将来控制器引入"跨拒绝不清"的状态则该用例可能失效
