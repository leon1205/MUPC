## 1. 产品概述

### 1.1 产品定位

AI 优化引擎的动作空间（Action Space）是 RL 模型输出控制指令的接口定义，直接决定 AI 引擎对电网运行状态的干预方式。本次重构将 AI 引擎的动作空间从"单一有功功率绝对值输出"升级为"有功基准点（P_ref）+ 电压-有功下垂系数（k_droop）"双参数联合输出模式，实现 AI 全局优化与底层物理反馈的时间尺度解耦，构建通信中断场景下的本质安全兜底机制。

### 1.2 核心职责

| 职责 | 说明 |
|------|------|
| 双参数输出 | RL 模型同时输出 P_ref 和 k_droop 两个参数 |
| 下垂公式闭合 | 执行器侧根据公式 P = P_ref + k_droop × ΔV 计算实时功率 |
| 本质安全兜底 | k_droop 赋予执行器自主调节能力，通信中断时保持最后有效值继续控制 |
| 训练对齐 | 训练管线同步修改，ONNX 模型输出维度从 1 维变为 2 维 |

### 1.3 目标平台

| 项目 | 要求 |
|------|------|
| 硬件 | RK3588 (NPU: 6 TOPS) |
| 操作系统 | openEuler 22.03+ |
| 编程语言 | Rust >= 1.75 |
| 推理框架 | RKNN Runtime (INT8 量化) |
| 模型格式 | ONNX（训练）→ .rknn（部署） |

## 2. 变更背景与动因

### 2.1 原方案缺陷

原需求定义 AI 引擎直接输出有功功率绝对值（p_batt_set）。在农网台区实际部署与仿真验证中发现，该方式存在以下结构性缺陷：

| 缺陷类型 | 具体问题 | 影响 |
|----------|----------|------|
| 暂态响应盲区 | AI 推理周期（秒级/分钟级）无法覆盖电网毫秒级电压波动 | 调压滞后，电压质量无法保障 |
| 通信强依赖 | AI 与执行器之间为刚性指令链路，通信抖动或中断即导致系统失控或停机 | 系统可用性低，故障域大 |
| 安全裁剪破坏梯度 | AI 探索到的越限动作被外部裁剪器截断后，奖励函数梯度不连续 | 策略震荡、收敛困难 |
| Sim-to-Real 鸿沟大 | AI 被迫隐式学习电磁暂态特性，对仿真保真度要求极高 | 现场迁移成本高，调试周期长 |

### 2.2 变更目标

将 AI 引擎的动作空间从"单一有功功率输出"重构为"有功基准点（P_ref）+ 电压-有功下垂系数（k_droop）"的双参数输出模式：

1. **时间尺度解耦**：AI 负责稳态全局优化（P_ref），执行器负责毫秒级暂态调节（k_droop × ΔV）
2. **通信中断优雅降级**：通信中断时，执行器保持最后有效的 P_ref 和 k_droop，继续按下垂公式计算，保障基础安全不停机
3. **安全约束内嵌**：越限动作不再被外部裁剪，而是通过 k_droop 的物理特性自然消化
4. **降低 Sim-to-Real 鸿沟**：AI 学习的是稳态下垂系数而非暂态响应，对仿真暂态保真度要求降低

### 2.3 预期收益

| 收益 | 量化目标 | 测量方法 |
|------|----------|----------|
| 暂态电压调节响应时间 | 从秒级提升至毫秒级 | 执行器端示波器观测 |
| 通信中断场景系统可用性 | 保持最后有效下垂控制，保障基础安全不停机 | 断联测试 |
| AI 训练收敛速度 | 策略收敛速度提升（因梯度连续） | 训练日志对比 |
| 现场调试周期 | 缩短（因仿真保真度要求降低） | 现场调试报告 |

## 3. 核心功能需求

### 3.1 双参数输出接口

#### 3.1.1 动作空间定义

| 维度 | 字段名 | 数据类型 | 取值范围 | 单位 | 说明 |
|------|--------|----------|----------|------|------|
| A1 | p_ref | f64 | [-P_safe, +P_safe] | kW | 有功功率基准点（负值=充电，正值=放电）|
| A2 | k_droop | f64 | [k_min, k_max] | kW/V | 电压-有功下垂系数 |

**取值范围约束：**

- P_safe：由 `action_space.max_batt_charge_power` / `max_batt_discharge_power` 确定，为稳态安全域边界
- k_min / k_max：由实时控制模块提供（与下垂控制硬件能力相关），通过 intercore 获取

#### 3.1.2 数据结构

```rust
/// 动作输出结构体（重构后，双参数模式）
#[derive(Debug, Clone)]
pub struct ActionOutput {
    pub p_ref: f64,           // 有功功率基准点 (kW), 范围由 ActionSpaceConfig 确定
    pub k_droop: f64,         // 电压-有功下垂系数 (kW/V), 范围由实时控制模块提供
    pub confidence: f64,      // 决策置信度 (0.0 ~ 1.0)
}

/// 动作输出结构体（重构前，单参数模式，废弃）
#[derive(Debug, Clone)]
pub struct ActionOutputLegacy {
    pub p_batt_set: f64,      // 电池有功功率设定值 (kW), 废弃
    pub load_shedding: f64,   // 可中断负荷切除量 (kW), 保留
    pub pv_limit: f64,         // 光伏限功率比例, 保留
}
```

> **兼容性说明：** 原 `p_batt_set` 输出模式废弃，`load_shedding` 和 `pv_limit` 保留。系统启动时通过配置项 `action_space.mode` 选择 "dual"（新）或 "legacy"（旧）模式，默认 "dual"。

#### 3.1.3 接口约束规则

| 规则 ID | 约束条件 | 说明 |
|---------|----------|------|
| ACT-DUAL-01 | p_ref ∈ [-max_batt_charge_power, max_batt_discharge_power] | 充电/放电功率约束 |
| ACT-DUAL-02 | k_droop ∈ [k_droop_min, k_droop_max] | 下垂系数范围由实时控制模块提供 |
| ACT-DUAL-03 | Δp_ref 变化率 <= p_batt_ramp_limit_kw / 步 | 防止基准点突变 |
| ACT-DUAL-04 | 当 dispatch_p_set 有效时，p_ref 绝对值不得超过 dispatch_p_set 绝对值 | 调度指令权限约束 |

### 3.2 下垂控制逻辑

#### 3.2.1 下垂公式

```
P_output = P_ref + k_droop × ΔV
```

其中：
- P_output：执行器最终输出的有功功率设定值
- P_ref：AI 输出的有功基准点
- k_droop：AI 输出的下垂系数（电压-有功下垂系数）
- ΔV：电压偏差（V_actual - V_target），单位 V

#### 3.2.2 k_droop 物理含义

| 参数 | 量纲 | 说明 |
|------|------|------|
| k_droop | kW/V | 电压每升高 1V，输出功率增加 k_droop kW（充电方向）；电压每降低 1V，输出功率减少 k_droop kW（放电方向） |

#### 3.2.3 双参数下发时序

```
1. AI 引擎推理 → 输出 P_ref 和 k_droop
2. ActionValidator 校验 → 确认 P_ref 和 k_droop 在各自约束范围内
3. intercore 双参数下发 → TCP 帧同时携带 P_ref 和 k_droop
4. 实时控制模块接收 → 更新本地 P_ref 和 k_droop 状态
5. 执行器闭环计算 → P_output = P_ref + k_droop × ΔV（每个控制周期执行）
```

#### 3.2.4 k_droop 管理权

| 角色 | 权限 | 说明 |
|------|------|------|
| AI 引擎 | 输出 p_ref **和** k_droop | 不转交实时控制模块 |
| 实时控制模块 | 接收并使用 k_droop | 不得修改 k_droop |
| 兜底机制 | k_droop 保持最后有效值 | 通信中断时，执行器保持最后收到的 k_droop，不主动归零 |

### 3.3 异常处理

#### 3.3.1 异常场景与处理措施

| 异常场景 | 检测条件 | 处理措施 |
|----------|----------|----------|
| AI 推理失败 | 心跳超时或状态码异常 | 自动降级至本地策略引擎（strategy-engine），p_ref 使用兜底值 |
| 通信中断 | intercore TCP 断开检测 | 执行器保持最后收到的 P_ref 和 k_droop，继续按下垂公式计算 |
| k_droop 超范围 | k_droop < k_min 或 k_droop > k_max | clamp 至 [k_min, k_max]，记录 WARN 日志 |
| p_ref 超范围 | p_ref < -P_safe 或 p_ref > P_safe | clamp 至 [-P_safe, P_safe]，记录 WARN 日志 |
| 双参数缺失 | P_ref 和 k_droop 同时为 NaN | 触发 AI 降级，使用兜底策略 |
| 实时控制模块故障 | 执行器心跳丢失 | 触发系统告警，等待人工干预 |

#### 3.3.2 通信中断降级流程

```
通信中断检测（intercore TCP 断开）
    ↓
执行器收到通知（或检测到心跳超时）
    ↓
执行器保持最后收到的有效 P_ref 和 k_droop
    ↓
P_ref = 最后有效值（不主动归零）
    ↓
k_droop = 最后有效值（不主动归零）
    ↓
P_output = 最后 P_ref + 最后 k_droop × ΔV（保持控制能力）
    ↓
系统发出告警（AI通信中断，维持最后有效下垂控制）
    ↓
通信恢复后，自动切回 AI 双参数控制模式
```

#### 3.3.3 兜底策略说明

| 策略 | 说明 |
|------|------|
| P_ref 兜底 | 保持最后收到的有效值，不主动归零 |
| k_droop 兜底 | 保持最后收到的有效值，不主动归零 |
| 降级行为 | 维持最后有效下垂控制能力，保障基础安全不停机 |

> **说明：** 通信中断时执行器维持最后有效的 P_ref 和 k_droop，继续按照下垂公式 P = P_ref + k_droop × ΔV 计算输出。等待通信恢复后自动切回 AI 双参数控制模式。

## 4. 数据流设计

### 4.1 完整数据流

```
南向设备 ←→ RS485/HPLC ←→ intercore (实时控制模块)
                                    ↓
                        ┌─────────── TCP/RJ45 ────────────┐
                                    ↓                       ↑
AI 引擎（双参数推理）  →  ActionValidator (校验)  →  intercore (TCP帧扩展)
        ↓                                                    ↓
  P_ref + k_droop                                  TCP 帧携带双参数
        ↓                                                    ↓
  双参数下发                                        实时控制模块接收
                                                        ↓
                                              执行器闭环计算
                                                        ↓
                                         P_output = P_ref + k_droop × ΔV
                                                        ↓
                                              南向设备执行
```

### 4.2 核间 TCP 帧扩展

现有 TCP 帧结构扩展，新增两个字段：

| 字段 | 数据类型 | 单位 | 说明 |
|------|----------|------|------|
| p_ref | f64 | kW | 有功基准点 |
| k_droop | f64 | kW/V | 下垂系数 |

**TCP 帧版本号：** v2.0（全新协议格式，不兼容旧版 v1.x）

### 4.3 数据源映射

| 数据流 | 生产方 | 消费方 | 说明 |
|--------|--------|--------|------|
| RL 决策输出 | ai-engine (ModelManager) | intercore | P_ref 和 k_droop 双参数 |
| 下垂系数范围 | intercore (实时控制模块) | ai-engine (ActionValidator) | k_min / k_max 由实时控制模块提供 |
| 执行器最终输出 | intercore (执行器) | 南向设备 | P_output = P_ref + k_droop × ΔV |

### 4.4 消息总线 Topic 扩展

| Topic | 发布者 | 订阅者 | 数据格式 | 频率 |
|-------|--------|--------|----------|------|
| `ai/action_output` | ModelManager | strategy-engine, intercore | `ActionOutput` JSON (含 p_ref, k_droop) | 1Hz |
| `ai/droop_range` | intercore | ActionValidator | `{k_min: f64, k_max: f64}` JSON | 按需更新 |

## 5. 训练管线对齐要求

### 5.1 ONNX 模型输出维度变更

| 版本 | 模型输出维度 | 输出含义 |
|------|-------------|----------|
| 重构前 | 1 维 | p_batt_set（有功功率绝对值） |
| 重构后 | 2 维 | [P_ref, k_droop]（有功基准点 + 下垂系数） |

**影响范围：**
- LSTM 模型：无需修改（仅做时序预测）
- RL 模型（MADDPG/PPO）：输出层维度从 1 变为 2，输出激活函数需重新设计
- 奖励函数：需适配新的动作空间（P_ref 替代 p_batt_set）
- 训练环境（gym/simulator）：需实现下垂公式 P = P_ref + k_droop × ΔV

### 5.2 训练环境改造

#### 5.2.1 下垂公式集成

训练环境的执行器模型需实现下垂公式闭环：

```python
# 训练环境（伪代码）
class DroopControlEnv:
    def step(self, action):
        p_ref, k_droop = action
        delta_v = self.get_voltage_deviation()  # 获取当前电压偏差
        p_output = p_ref + k_droop * delta_v     # 下垂公式
        return self.execute(p_output)             # 执行并返回下一个状态
```

#### 5.2.2 奖励函数适配

原奖励函数中的 `p_batt_set` 替换为 `p_ref`：

| 场景 | 原表达式 | 新表达式 |
|------|----------|----------|
| SCENE-01 变化率惩罚 | λ × |ΔP_batt| / E_battery | λ × |ΔP_ref| / E_battery |
| SCENE-B1 电价差收益 | P_batt_set × Δt × (price_sell - price_buy) | P_ref × Δt × (price_sell - price_buy) |

### 5.3 模型版本管理

| 版本 | 文件名 | 说明 |
|------|--------|------|
| 重构前 | ` maddpg_v1.onnx` / ` maddpg_v1.rknn` | 单参数输出（p_batt_set） |
| 重构后 | ` maddpg_v2.onnx` / ` maddpg_v2.rknn` | 双参数输出（P_ref + k_droop） |

**兼容性要求：**
- v2 模型加载前验证输出维度是否为 2
- v1 模型拒绝加载（不兼容双参数模式）
- OTA 升级时自动同步模型版本号

### 5.4 训练管线验收标准

| ID | 标准 | 验证方法 |
|----|------|----------|
| TRAIN-01 | ONNX 模型输出维度为 2（P_ref + k_droop） | 模型文件验证（netron/onnx 检查） |
| TRAIN-02 | 下垂公式正确集成于训练环境 | 单元测试（固定 ΔV 和 k_droop，验证 P_output） |
| TRAIN-03 | 奖励函数正确使用 P_ref 替代 p_batt_set | 单元测试 |
| TRAIN-04 | v2 模型文件加载成功 | 集成测试 |
| TRAIN-05 | v1 模型文件加载失败并返回明确错误 | 集成测试 |
