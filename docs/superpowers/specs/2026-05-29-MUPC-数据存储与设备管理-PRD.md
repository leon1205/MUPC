## 1. 产品概述与核心价值

### 1.1 产品定位

MUPC 通信管理模块当前已完成故障录波数据的 SQLite 存储，但在以下两个关键领域存在功能缺口：

1. **设备台账管理**：无法管理和上送设备的资产信息、铭牌参数、投运日期、维护记录等台账数据，导致调度主站和运维人员无法获取管辖范围内设备的完整资产档案。
2. **通用历史数据存储**：缺乏统一的本地数据库存储周期性采集的电气量数据、电池运行数据、告警日志和事件记录。当前仅故障录波数据持久化，其余数据仅在内存中流转，掉电即丢失。

### 1.2 核心价值

| 价值 | 说明 |
|------|------|
| 设备全生命周期管理 | 从投运到退役，完整记录设备资产信息和维护历史，支撑运维决策 |
| 数据可追溯 | 历史运行数据、告警、事件持久化存储，满足事后分析和审计要求 |
| 离线自洽 | 网络中断时本地存储不丢失数据，恢复后自动同步 |
| 合规支撑 | 满足电力行业对数据留存和审计的合规要求 |

### 1.3 目标平台

| 项目 | 要求 |
|------|------|
| 操作系统 | Linux (openEuler) |
| 硬件 | RK3588，存储介质：eMMC（默认 64GB）+ TF 卡扩展槽 |
| 编程语言 | Rust |
| 异步运行时 | Tokio |

### 1.4 开发范围

本次开发覆盖 Section 3.4"数据存储与管理"的全部两项内容：

1. **设备台账管理**（M-02/高优先级）
2. **通用历史数据存储**（P-03/高优先级）

#### 不在本次范围内

- 云端数据同步服务（仅本地存储，上送功能依赖现有 gateway + MQTT-bridge）
- AI 模型训练数据的批量导出（由 AI 引擎独立处理）
- 实时控制模块自身的日志存储（由实时控制核心独立管理）

## 2. 目标用户角色

| 角色 | 描述 | 权限范围 | 优先级 |
|------|------|----------|--------|

| **系统管理员** | 配置数据保留策略、存储清理规则 | 数据生命周期配置、存储管理 | 高 |

## 3. 核心功能列表

### 3.1 设备台账管理

#### 功能 3.1.1：设备资产信息管理（CRUD）

**User Story：**
> 作为本地运维人员，我需要创建设备资产档案，记录每台设备的唯一标识、型号、厂商、出厂编号、资产编号等信息，以便在设备全生命周期中追踪每台设备的状态。

**验收标准：**

- 系统支持对以下资产信息字段进行创建、读取、更新、删除（CRUD）操作：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| device_id | 字符串 | 是 | 设备唯一标识，全局不可重复 |
| device_type | 枚举 | 是 | 可选值：ttu / inverter / charger / flexible_load / fire_alarm / battery / grid_connection / other |
| asset_number | 字符串 | 否 | 资产编号，企业资产管理系统的唯一编码 |
| manufacturer | 字符串 | 是 | 设备生产厂商全称 |
| model | 字符串 | 是 | 设备型号 |
| serial_number | 字符串 | 是 | 出厂序列号，设备出厂时唯一编号 |
| firmware_version | 字符串 | 否 | 当前固件版本号 |
| hardware_version | 字符串 | 否 | 硬件版本号 |
| device_alias | 字符串 | 否 | 设备别名/名称，用于界面显示 |
| description | 文本 | 否 | 设备备注说明 |

- 创建设备时，`device_id` 不能与已有记录重复，重复时返回明确错误提示
- 支持删除已废弃的设备，删除操作为软删除（标记 deleted 状态），保留历史记录
- 每次 CRUD 操作均记录操作时间和操作人

#### 功能 3.1.2：铭牌参数管理

**User Story：**
> 作为本地运维人员，我需要记录和管理每台设备的铭牌额定参数（额定功率、额定电压、额定电流、额定容量等），以便调度策略计算时查询设备能力边界。

**验收标准：**

- 系统支持对以下铭牌参数进行管理：

| 字段 | 类型 | 必填 | 适用设备类型 | 说明 |
|------|------|------|-------------|------|
| rated_power | 浮点数 | 否 | 全部 | 额定有功功率（kW） |
| rated_capacity | 浮点数 | 否 | battery | 额定容量（kWh） |
| rated_voltage | 浮点数 | 否 | 全部 | 额定电压（V） |
| rated_current | 浮点数 | 否 | 全部 | 额定电流（A） |
| max_charge_power | 浮点数 | 否 | battery/charger | 最大充电功率（kW） |
| max_discharge_power | 浮点数 | 否 | battery | 最大放电功率（kW） |
| charge_efficiency | 浮点数 | 否 | battery | 充电效率（%，0-100） |
| discharge_efficiency | 浮点数 | 否 | battery | 放电效率（%，0-100） |
| soc_min | 浮点数 | 否 | battery | SOC 下限（%，0-100） |
| soc_max | 浮点数 | 否 | battery | SOC 上限（%，0-100） |
| rated_reactive_power | 浮点数 | 否 | inverter | 额定无功功率（kVar） |
| protection_level | 字符串 | 否 | 全部 | 防护等级，如 IP65 |
| cooling_method | 字符串 | 否 | 全部 | 冷却方式，如自然冷却/强制风冷 |

- 铭牌参数与设备资产信息关联，一个设备对应一组铭牌参数
- 铭牌参数支持修改，每次修改记录变更历史（字段名、旧值、新值、修改时间、修改人）
- 铭牌参数查询响应时间不超过 500ms（1000 台设备规模）

#### 功能 3.1.3：投运日期管理

**User Story：**
> 作为本地运维人员，我需要记录每台设备的投运日期和退役日期，以便跟踪设备运行的时长和维护周期。

**验收标准：**

- 系统支持记录以下时间字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| commissioning_date | 日期时间 | 是 | 设备投运日期 |
| last_maintenance_date | 日期时间 | 否 | 最近一次维护日期 |
| decommissioning_date | 日期时间 | 否 | 设备退役日期，空表示仍在运行 |
| warranty_expiry_date | 日期时间 | 否 | 质保到期日期 |

- 投运日期在创建设备资产时必须填写
- 退役日期填写后，该设备在常规运行界面中不再显示，但数据仍可查询
- 系统自动计算设备已运行天数 = （当前时间 - commissioning_date）

#### 功能 3.1.4：维护记录管理

**User Story：**
> 作为本地运维人员，我需要记录每台设备的维护历史，包括维护时间、维护类型、维护内容和维护人员，以便追溯设备的维护履历。

**验收标准：**

- 系统支持对维护记录进行创建和查询操作，每条维护记录包含：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| record_id | 整数（自增） | 是 | 维护记录唯一标识 |
| device_id | 字符串 | 是 | 关联的设备 ID |
| maintenance_date | 日期时间 | 是 | 维护执行日期 |
| maintenance_type | 枚举 | 是 | 可选值：routine_inspection / fault_repair / firmware_upgrade / part_replacement / calibration / other |
| description | 文本 | 是 | 维护内容详细描述 |
| operator | 字符串 | 是 | 维护执行人员姓名或工号 |
| result | 枚举 | 是 | 可选值：success / failed / partial |
| next_maintenance_date | 日期时间 | 否 | 建议下次维护日期 |

- 支持按 device_id 查询该设备的所有维护记录，并按日期倒序排列
- 支持按 maintenance_type 过滤维护记录
- 支持按日期范围查询维护记录
- 单设备维护记录查询响应时间不超过 300ms

### 3.2 设备台账上送

#### 功能 3.2.1：台账数据北向上送

**User Story：**
> 作为调度主站运维人员，我需要远程获取 MUPC 管辖范围内所有设备的台账信息，以便在主站系统中统一管理资产档案，无需现场人工抄录。

**验收标准：**

- 系统支持通过北向协议（IEC 104 / MQTT）将设备台账数据上送至调度主站或物联平台
- 上送触发方式：

| 触发方式 | 说明 | 优先级 |
|----------|------|--------|
| 主动全量上送 | 设备台账发生变更（新增/修改/删除）后 30 秒内自动上送 | 高 |
| 定时全量上送 | 每日凌晨 3:00 定时上送一次全量台账（可配置） | 中 |
| 主站召唤上送 | 收到主站召唤指令后立即上送全量台账 | 高 |

- 上送数据格式应满足 IEC 104 标准的设备参数报文规范
- 上送过程不可阻塞主业务流程，数据序列化和网络发送应在异步任务中执行
- 上送失败时自动重试，最多重试 3 次，重试间隔分别为 10s、30s、60s
- 上送结果记录日志，包含：上送时间、数据条数、成功/失败状态、失败原因

### 3.3 历史运行数据存储

#### 功能 3.3.1：周期性电气量数据存储

**User Story：**
> 作为本地运维人员，我需要系统自动存储周期性采集的电气量数据（电压、电流、功率、频率等），以便事后查询设备的历史运行趋势和分析电能质量。

**验收标准：**

- 系统按可配置的存储周期（默认 1 分钟）将 data-processing 模块采集的电气量数据持久化存储
- 存储的电气量数据包含以下测量维度：

| 数据分类 | 包含字段 |
|----------|----------|
| 三相电压 | phase_a_voltage, phase_b_voltage, phase_c_voltage (V) |
| 三相电流 | phase_a_current, phase_b_current, phase_c_current (A) |
| 功率 | total_active_power, total_reactive_power, total_apparent_power (kW/kVar/kVA) |
| 功率因数 | power_factor (0-1) |
| 频率 | frequency (Hz) |
| 分相功率 | phase_a_power, phase_b_power, phase_c_power (kW) |
| 电能 | total_import_energy, total_export_energy (kWh) |

- 每条数据记录包含：设备 ID、时间戳（精确到毫秒）、各测量值、数据质量标记
- 数据存储为非阻塞写入，写入延迟不超过 10ms
- 支持按设备 ID + 时间范围查询历史数据
- 查询响应时间：单设备 24 小时数据量查询不超过 3 秒

#### 功能 3.3.2：电池运行数据存储

**User Story：**
> 作为本地运维人员，我需要系统自动存储电池系统的运行数据（SOC、SOH、温度、充放电状态等），以便分析电池的健康状态和衰减趋势。

**验收标准：**

- 系统按可配置的存储周期（默认 1 分钟）存储电池运行数据
- 存储的电池数据包含以下字段：

| 字段 | 单位 | 说明 |
|------|------|------|
| soc | % | 荷电状态（0-100） |
| soh | % | 健康状态（0-100） |
| battery_temperature | °C | 电池温度 |
| ambient_temperature | °C | 环境温度 |
| dc_voltage | V | 直流侧电压 |
| dc_current | A | 直流侧电流 |
| charge_power | kW | 充电功率 |
| discharge_power | kW | 放电功率 |
| charge_status | 枚举 | 可选值：charging / discharging / idle / fault |
| cycle_count | 整数 | 累计充放电循环次数 |
| cell_min_voltage | V | 单体最低电压 |
| cell_max_voltage | V | 单体最高电压 |
| cell_min_temperature | °C | 单体最低温度 |
| cell_max_temperature | °C | 单体最高温度 |

- 支持按时间范围查询电池运行数据，查询响应时间不超过 3 秒
- 支持查询 SOC/SOH 的变化趋势（按天/周/月聚合）

### 3.4 告警日志存储与查询

#### 功能 3.4.1：告警日志持久化

**User Story：**
> 作为运维人员，我需要系统自动记录所有告警事件并持久化存储，以便及时得知设备异常状态并进行排查处理。

**验收标准：**

- 系统自动记录所有产生的告警事件，每条告警记录包含：

| 字段 | 类型 | 说明 |
|------|------|------|
| alarm_id | 整数（自增） | 告警唯一标识 |
| device_id | 字符串 | 触发告警的设备 ID |
| alarm_type | 枚举 | 可选值：over_voltage / under_voltage / over_current / over_frequency / under_frequency / over_temperature / soc_low / soh_low / communication_loss / protection_action / hardware_fault / other |
| severity | 枚举 | 可选值：critical / major / minor / warning |
| description | 文本 | 告警描述 |
| trigger_time | 日期时间 | 告警触发时间 |
| acknowledge_time | 日期时间（可空） | 确认时间 |
| acknowledge_by | 字符串（可空） | 确认人 |
| clear_time | 日期时间（可空） | 告警清除时间 |
| clear_by | 字符串（可空） | 清除人 |
| status | 枚举 | 可选值：active / acknowledged / cleared |

- 告警日志写入不可阻塞告警产生流程
- 支持按以下条件组合查询告警日志：
  - 时间范围
  - 设备 ID
  - 告警类型
  - 严重等级
  - 状态
- 查询结果按触发时间倒序排列
- 查询响应时间不超过 3 秒（100 万条记录规模）

#### 功能 3.4.2：告警确认与清除

**User Story：**
> 作为运维人员，我需要确认告警并在问题处理后清除告警，以便区分未处理和处理中的告警状态。

**验收标准：**

- 运维人员可通过 Web UI 确认单条或批量确认告警
- 运维人员在问题解决后可标记告警为已清除，并填写清除备注
- 告警状态转换路径：active -> acknowledged -> cleared
- 告警确认和清除操作记录操作人、操作时间

### 3.5 事件记录存储与查询

#### 功能 3.5.1：系统事件记录

**User Story：**
> 作为审计人员，我需要系统完整记录所有关键操作和系统事件，以便事后审计和追踪责任。

**验收标准：**

- 系统自动记录以下类别的操作事件：

| 事件类别 | 包含内容 |
|----------|----------|
| 设备操作 | 设备投运、退役、参数修改、固件升级 |
| 控制指令 | 调度指令下发、本地控制操作、遥控操作（含指令内容、下发来源、执行结果） |
| 系统事件 | 系统启动、系统关闭、配置变更、策略切换（AI/本地/基础） |
| 通信事件 | 北向连接建立/断开、南向设备连接状态变化 |
| 安全事件 | 登录/登出、权限变更、认证失败 |

- 每条事件记录包含：

| 字段 | 类型 | 说明 |
|------|------|------|
| event_id | 整数（自增） | 事件唯一标识 |
| event_type | 枚举 | 上述五类事件之一 |
| event_time | 日期时间 | 事件发生时间 |
| source | 字符串 | 事件来源（web_ui / iec104 / mqtt / local / system） |
| operator | 字符串（可空） | 操作人（如适用） |
| description | 文本 | 事件详细描述 |
| detail | JSON | 事件详情，结构随事件类型变化 |

- 事件记录写入为异步非阻塞操作
- 支持按类型、时间范围、来源组合查询，响应时间不超过 3 秒
- 事件记录不可删除、不可修改（仅可查询）
- 事件记录作为审计依据，保留期限不低于设备退役后 2 年

### 3.6 数据生命周期管理

#### 功能 3.6.1：数据保留策略配置

**User Story：**
> 作为系统管理员，我需要配置不同类型数据的本地保留期限，以便在有限的存储空间内合理管理数据，既满足合规要求又不过度占用空间。

**验收标准：**

- 系统支持为以下数据类型分别配置保留期限：

| 数据类型 | 默认保留期限 | 配置范围 | 说明 |
|----------|-------------|----------|------|
| 电气量历史数据 | 90 天 | 30-365 天 | 高密度时序数据 |
| 电池运行数据 | 90 天 | 30-365 天 | 高密度时序数据 |
| 告警日志 | 365 天 | 90-730 天 | 合规要求 |
| 事件记录 | 730 天 | 365-1095 天 | 审计要求 |
| 故障录波数据 | 365 天 | 90-730 天 | 现有功能扩展 |
| 设备台账 | 永久 | 不可配置 | 设备退役后标记删除 |

- 保留期限在 Web UI 上可配置，配置即时生效
- 保留期限配置变更后，系统在下次自动清理时按新策略执行

#### 功能 3.6.2：自动数据清理

**User Story：**
> 作为系统管理员，我需要系统自动清理超出保留期限的历史数据，以释放存储空间，无需人工干预。

**验收标准：**

- 系统每日凌晨 2:00（可配置）执行自动数据清理任务
- 清理任务按数据类型分别执行，删除超出保留期限的数据记录
- 清理任务执行前检查可用存储空间：
  - 存储空间剩余 < 10% 时：触发告警"存储空间不足（critical）"
  - 存储空间剩余 < 5% 时：触发告警"存储空间即将耗尽（critical）"，同时缩短保留期限至默认值的 50%
- 清理过程记录日志：清理数据类型、删除记录数、清理耗时、释放空间大小
- 清理任务执行超时上限为 30 分钟，超时自动终止并记录告警
- 清理任务可手动触发

### 3.7 数据导出功能

#### 功能 3.7.1：历史数据导出

**User Story：**
> 作为本地运维人员，我需要将查询到的历史数据、告警日志、事件记录导出为通用格式文件，以便离线分析和提交报告。

**验收标准：**

- 支持将查询结果导出为 CSV 格式
- 导出数据包含查询范围内的全部匹配记录
- 单次导出上限为 10 万条记录，超出时提示用户缩小查询范围
- 导出文件生成在本地存储的 `/var/mupc/export/` 目录下
- 导出文件名格式：`{数据类型}_{起始日期}_{结束日期}_{时间戳}.csv`
- 导出过程在异步任务中执行，不阻塞 Web UI 操作
- 导出完成后通过 Web UI 通知用户并提供文件下载链接
- 导出文件保留 7 天后自动清理

#### 功能 3.7.2：设备台账导出

**User Story：**
> 作为本地运维人员，我需要将设备台账导出为结构化文件，以便导入到上级资产管理系统或进行离线资产生命周期分析。

**验收标准：**

- 支持将设备台账（含资产信息、铭牌参数、投运日期）导出为 CSV 格式
- 支持将维护记录导出为 CSV 格式
- 导出文件包含完整的字段定义
- 单次导出可包含全部设备（不受 10 万条限制）

## 4. 非功能性需求

### 4.1 存储容量规划

| 数据类型 | 单条数据大小（估算） | 记录频率 | 日增量（100 台设备） | 年增量 |
|----------|---------------------|----------|---------------------|--------|
| 电气量数据 | ~200 字节 | 每 1 分钟 1 条/设备 | ~28.8 MB | ~10.5 GB |
| 电池数据 | ~150 字节 | 每 1 分钟 1 条/设备 | ~21.6 MB | ~7.9 GB |
| 告警日志 | ~500 字节 | 按需（估算日均 50 条） | ~25 KB | ~9 MB |
| 事件记录 | ~1 KB | 按需（估算日均 200 条） | ~200 KB | ~73 MB |
| 故障录波 | 1-10 MB/次 | 按需（估算日均 5 次） | ~50 MB | ~18 GB |

- 默认 64GB eMMC 存储分配：系统分区 20GB，数据分区 44GB
- 数据分区 44GB 可支撑约 1.5-2 年历史数据存储（按默认保留策略）
- 预留 TF 卡扩展槽，插入后自动扩展数据存储分区

### 4.2 查询性能

| 查询场景 | 数据规模 | 最大响应时间 |
|----------|----------|-------------|
| 单设备 24 小时电气量数据 | ~1,440 条 | 3 秒 |
| 单设备 7 天电气量数据 | ~10,080 条 | 5 秒 |
| 告警日志按时间范围查询 | 100 万条以内 | 3 秒 |
| 事件记录按时间范围查询 | 100 万条以内 | 3 秒 |
| 设备台账单设备查询 | 1000 台设备 | 500ms |
| 设备台账全量查询 | 1000 台设备 | 2 秒 |
| 单设备维护记录查询 | 100 条以内 | 300ms |

### 4.3 数据可靠性

- 单条数据写入失败不影响后续数据写入
- 写入失败时记录错误日志，不上报告警（避免告警风暴）
- 数据库文件损坏时，系统自动检测并通过内置恢复机制尝试修复
- 恢复失败时，系统进入降级模式：停止历史数据写入、设备台账只读、告警和事件仅内存缓存
- 降级模式下通过告警通知运维人员，要求人工介入
- 降级模式下内存缓存的数据在系统重启后丢失，但系统功能不中断

### 4.4 并发与吞吐

- 支持同时处理 200 台南向设备的数据写入
- 数据写入吞吐量不低于 1000 条/秒
- 支持最多 10 个并发查询请求
- 写入操作不受查询操作影响（读写分离）

## 5. 边界条件与异常处理

### 5.1 磁盘空间不足

| 条件 | 系统行为 |
|------|----------|
| 磁盘使用率 >= 85% | 记录 WARN 级别日志 |
| 磁盘使用率 >= 90% | 触发 minor 级别告警"磁盘空间即将不足"，通知运维人员 |
| 磁盘使用率 >= 95% | 触发 critical 级别告警，立即执行紧急清理（删除超出最短保留期限 30 天的数据），停止历史数据写入 |
| 磁盘使用率 >= 98% | 停止所有数据写入（含告警和事件），仅维持只读查询功能，触发 critical 告警 |

### 5.2 数据写入失败

| 场景 | 处理方式 |
|------|----------|
| 单次写入超时（> 5 秒） | 放弃本次写入，记录错误日志，继续处理下一条 |
| 连续 10 次写入失败 | 触发告警"数据库写入异常"，每 5 分钟重试一次 |
| 数据库文件损坏 | 切换到降级模式，尝试修复，通知运维人员 |
| 数据库连接断开 | 自动重连，最多重试 5 次（间隔 1s、2s、4s、8s、16s），失败后触发告警 |

### 5.3 数据损坏恢复

- 系统启动时自动检测数据库文件的完整性
- 检测发现损坏时自动尝试修复（内置恢复机制）
- 修复成功：记录日志，恢复正常运行
- 修复失败：触发告警，进入降级模式
- 数据恢复工具应独立于主系统，可在系统离线时由运维人员手动运行

### 5.4 系统意外断电

- 数据写入采用事务保证单条写入的原子性
- 断电恢复后，未完成的事务自动回滚，不产生脏数据
- 系统启动时自动检查数据完整性

### 5.5 时间同步异常

- 所有数据记录的时间戳以系统时间为准
- 系统支持 NTP 时间同步
- 时间发生跳变（如 NTP 同步校正）时，不产生重复数据或数据空洞

## 6. 与现有系统的集成点

### 6.1 data-processing 模块

| 集成点 | 说明 | 方向 |
|--------|------|------|
| 电气量数据存储 | data-processing 的 DataCollector 采集到数据后，将周期性数据写入数据库 | data-processing -> 存储模块 |
| 告警日志存储 | data-processing 产生告警条件时，告警日志记录由存储模块接管 | data-processing -> 存储模块 |
| 故障录波扩展 | 现有 FaultRecorderImpl 的 SQLite 存储保留，存储模块提供统一的告警日志和事件记录接口 | 存储模块独立 |
| 数据生命周期 | 存储模块的数据清理策略独立运行，不影响 data-processing 的数据采集流程 | 存储模块独立 |

### 6.2 gateway 模块

| 集成点 | 说明 | 方向 |
|--------|------|------|
| 设备台账上送 | gateway 模块接收主站的召唤指令或定时触发，从存储模块读取台账数据并编码为 IEC 104/MQTT 报文发送 | 存储模块 -> gateway |
| 历史数据上送 | gateway 模块根据主站需求查询历史数据并上送（可选） | 存储模块 -> gateway |
| 事件主动上报 | gateway 模块将存储模块记录的告警和事件通过 IEC 104 的 SOE 报文主动上报 | 存储模块 -> gateway |

### 6.3 web-api 模块

| 集成点 | 说明 | 方向 |
|--------|------|------|
| 设备台账 REST API | web-api 新增 `/api/v1/devices` 路由，提供设备台账 CRUD 操作接口 | web-api <-> 存储模块 |
| 历史数据查询 REST API | web-api 新增 `/api/v1/history` 路由，提供电气量和电池数据查询接口 | web-api -> 存储模块 |
| 告警日志 REST API | web-api 新增 `/api/v1/alarms` 路由，提供告警日志查询、确认、清除接口 | web-api <-> 存储模块 |
| 事件记录 REST API | web-api 新增 `/api/v1/events` 路由，提供事件记录查询接口 | web-api -> 存储模块 |
| 数据导出 REST API | web-api 新增 `/api/v1/export` 路由，提供数据导出触发和文件下载接口 | web-api -> 存储模块 |
| 存储状态 REST API | web-api 新增 `/api/v1/storage` 路由，提供存储空间使用情况和数据保留策略配置接口 | web-api <-> 存储模块 |
| 设备名册查询 | web-api 现有 `/api/v1/status` 路由扩展，返回设备列表时附带运行状态和在线状态 | web-api -> 存储模块 |

### 6.4 device-trait 模块

| 集成点 | 说明 | 方向 |
|--------|------|------|
| 设备类型扩展 | device-trait 现有 DeviceType 枚举新增 battery / grid_connection 类型 | 存储模块使用 device-trait 定义 |
| 设备标识一致性 | 台账管理中的 device_id 与 SouthDevice/Device trait 中的 device_id 保持一致 | 存储模块引用同一标识 |

### 6.5 插件系统

| 集成点 | 说明 | 方向 |
|--------|------|------|
| 协议插件注册设备 | rs485-plugin / hplc-plugin 加载南向设备时，在启动流程中将设备自动注册到台账系统 | 插件 -> 存储模块 |
| 设备自动发现 | 插件初始化时自动填写设备的基础信息（device_id、device_type、manufacturer、model） | 插件 -> 存储模块 |
