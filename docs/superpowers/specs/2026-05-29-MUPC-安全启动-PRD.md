## 1. 产品概述

### 1.1 背景

MUPC 微电网特种调控装置作为电力调度与配电自动化的核心边缘设备，运行于关键基础设施环境中。根据《电力监控系统安全防护规定》（发改委14号令）及国家能源局相关标准要求，电力二次系统必须从硬件层确保固件和操作系统的完整性。

安全启动（Secure Boot）是 MUPC 安全防御体系的第一道防线。它通过逐级签名验证机制，确保设备从 BootROM 到应用程序的每一级代码均经过可信签名，防止因固件篡改、恶意植入或非授权升级导致的系统被控风险。

### 1.2 核心价值

| 价值 | 说明 |
|------|------|
| **防篡改** | 杜绝系统镜像被篡改后运行的攻击路径 |
| **供应链安全** | 确保只有经过厂商签名的固件才能在设备上执行 |
| **合规达标** | 满足电力二次系统安全防护规定的固件完整性要求 |
| **防御纵深** | 为 OTA 升级提供可信执行环境，防止恶意固件从升级通道侵入 |

### 1.3 目标平台

| 项目 | 要求 |
|------|------|
| 硬件 | Rockchip RK3588（ARMv8.2-A，含 OTP fuses、eFuse） |
| 操作系统 | openEuler 22.03+（Linux LTS 内核，ARM64） |
| 启动引导 | U-Boot 2023.07+（支持 verified boot / FIT 镜像验签） |
| 文件系统完整性 | dm-verity（内核模块） |
| 板级支持包 | Rockchip BSP（含 BootROM Secure Boot 使能） |

### 1.4 范围与限制

**包含范围：**
- BootROM 级别安全启动使能
- U-Boot 引导加载程序的签名与验证
- Linux 内核与设备树（DTB）验签
- 根文件系统完整性保护（dm-verity）
- 启动链密钥体系管理（密钥生成、存储、更新）
- 签名工具链与生产签名流程
- 启动失败检测与恢复机制
- 安全启动状态监控与告警上报

**不包含范围：**
- 应用程序级别的代码签名（不属于安全启动链，由 OTA 更新模块的签名验证覆盖）
- 运行时内存完整性保护（属于后续 Phase 安全增强）
- TPM 2.0 硬件信任根（RK3588 不具备板载 TPM，使用 OTP fuses 替代）
- 安全启动与 UEFI Secure Boot 的兼容（ARM64 平台使用 FIT 镜像而非 UEFI）

## 3. 核心功能列表

### 3.1 安全启动链验证

#### 功能 3.1.1：BootROM 级验签

**User Story：**
> 作为安全管理员，我需要 RK3588 BootROM 在芯片上电后验证第一阶段引导程序（U-Boot SPL/BL31）的签名，以确保从芯片最底层开始建立信任链。

**验收标准：**
- 设备上电后，BootROM 读取 OTP 中烧录的根公钥哈希
- BootROM 使用 RSA-4096（或国密 SM2）验证 U-Boot SPL 的签名
- 签名验证失败时，BootROM 中止启动流程，进入安全错误状态
- U-Boot SPL 镜像必须包含 PKCS#1 v1.5 或 SM2 签名附加段
- OTP 中的根公钥哈希仅支持在设备生产阶段烧录，运行时不可被软件修改或擦除
- 验证耗时 ≤ 500ms（从芯片上电到 BootROM 完成签名验证）
- 错误状态通过板载指示灯和 UART 错误码输出，错误码格式固定为 `SEC_BOOT_ERR_0x<16进制码>`

#### 功能 3.1.2：U-Boot 级验签

**User Story：**
> 作为固件发布工程师，我需要 U-Boot 在加载 Linux 内核之前验证 FIT 镜像签名，以防止未经签名的内核或设备树被启动。

**验收标准：**
- U-Boot 使用 verified boot 机制加载 FIT（Flattened Image Tree）镜像
- FIT 镜像包含内核（kernel）、设备树（DTB）、initramfs（可选）以及对应的签名
- U-Boot 在加载 FIT 镜像前，使用内置公钥验证每个组件的哈希值和签名
- FIT 镜像签名算法支持 RSA-4096 或 SM2（由安全管理员配置决定）
- U-Boot 公钥通过编译时嵌入或持久存储于引导分区
- 签名验证失败时，U-Boot 输出错误信息并中止启动，不加载任何未经验证的组件
- FIT 镜像验签耗时 ≤ 2 秒（含内核和 DTB 的签名验证）
- 支持 FIT 镜像中配置多个签名（密钥轮换场景），任一签名通过即可

#### 功能 3.1.3：内核级完整性验证

**User Story：**
> 作为安全管理员，我需要 Linux 内核在挂载根文件系统前，通过 dm-verity 验证根文件系统的完整性，防止文件系统层面被篡改。

**验收标准：**
- 根文件系统分区启用 dm-verity 内核模块保护
- dm-verity 哈希树存储在独立分区或元数据区域，与根文件系统物理隔离
- dm-verity 根哈希由内核启动参数传递，并与签名明文一同内嵌于 FIT 镜像
- dm-verity 验证模式设置为 `restart_on_corruption`（检测到篡改时自动重启）
- 哈希树算法使用 SHA-256（或国密 SM3，由安全管理员配置决定）
- 每次读取数据块时进行实时哈希比对，检测到不一致时按配置策略处理
- dm-verity 对正常 I/O 的性能影响 ≤ 5%（实测 IOPS 对比基线）
- /etc、/usr、/lib 等关键系统目录必须纳入 dm-verity 保护范围
- 运行时配置目录（/var、/etc/mupc/conf.d）不纳入 dm-verity，采用运行时完整性监控

#### 功能 3.1.4：分区完整性校验

**User Story：**
> 作为安全管理员，我需要系统在挂载非根分区前验证其哈希值，防止固件存储区中的其他分区被篡改。

**验收标准：**
- 启动分区（boot）、恢复分区（recovery）在挂载前进行完整哈希校验
- 校验算法使用 SHA-256 或 SM3
- 分区哈希值存储在已验证的 FIT 镜像内或签名元数据区
- 校验失败时，拒绝挂载该分区并记录告警日志
- 校验过程在 U-Boot 阶段执行，不延迟内核启动流程

### 3.2 系统镜像完整性校验

#### 功能 3.2.1：运行时完整性度量

**User Story：**
> 作为安全管理员，我需要系统在运行过程中周期性地检查关键文件与分区的完整性，及时发现运行时篡改。

**验收标准：**
- 系统启动完成后，周期性（默认每 60 秒，可配置）校验 dm-verity 保护区域外的关键文件
- 校验文件清单包含：/etc/shadow、关键二进制文件、安全策略配置文件
- 校验算法：SM3 或 SHA-256
- 检测到完整性违反时，立即输出告警日志并通过安全监控通道上报
- 校验结果记录到安全审计日志，格式包含：文件名、预期哈希值、实际哈希值、时间戳
- 校验过程 CPU 占用率 ≤ 2%（在 RK3588 A76 核心上评测）

#### 功能 3.2.2：系统更新后的完整性自检

**User Story：**
> 作为固件发布工程师，我需要 OTA 更新后系统自动执行完整性自检，确保更新后的系统处于完整状态。

**验收标准：**
- 每次固件更新（系统固件、内核、rootfs）完成后，设备在启动阶段自动执行完整性全检
- 全检范围：BootROM 签名验证状态、U-Boot FIT 验签状态、dm-verity 哈希树一致性
- 全检结果记录到安全启动日志
- 全检失败时，设备自动触发回滚机制恢复至更新前版本
- 全检结果通过 web-api 状态接口上报

### 3.3 启动密钥管理

#### 功能 3.3.1：密钥生成

**User Story：**
> 作为安全管理员，我需要一个标准化的密钥生成流程，生成安全启动链所需的各级密钥对，确保密钥强度满足安全要求。

**验收标准：**
- 支持生成 RSA-4096 或 SM2 密钥对（由安全策略配置决定）
- 密钥生成必须使用硬件真随机数发生器（RK3588 TRNG）
- 密钥生成流程输出：
  - 私钥（PEM 格式，加密存储，使用 AES-256-GCM 加密保护）
  - 公钥（DER 或 PEM 格式，用于嵌入镜像和烧录 OTP）
  - 公钥哈希值（SHA-256，用于烧录 RK3588 OTP fuses）
- 密钥生成工具必须输出一份密钥清单文件，包含密钥用途、算法、生成时间、指纹
- 私钥密码强度要求：不少于 16 位，含大小写字母、数字、特殊字符

#### 功能 3.3.2：密钥存储

**User Story：**
> 作为安全管理员，我需要安全启动密钥的私钥在安全环境中加密存储，防止私钥泄露导致信任链失效。

**验收标准：**
- 私钥以加密形式存储：
  - 生产环境私钥：存储于离线 HSM 或硬件加密的离线存储设备中
  - 开发测试私钥：AES-256-GCM 加密，密码由密钥管理系统管理
- OTP 中公钥哈希一经烧录后，不应被软件读取或篡改
- 设备不存储任何私钥
- 密钥文件访问权限严格限制：仅授权管理员可访问

#### 功能 3.3.3：密钥轮换

**User Story：**
> 作为安全管理员，我需要在现有公钥存在泄露风险或安全策略变更时，支持安全地轮换启动链公钥。

**验收标准：**
- 密钥轮换支持两种模式：
  - **模式 A（物理更换）**：仅支持出厂前或返厂时重新烧录 OTP，旧密钥作废
  - **模式 B（代码内多密钥支持）**：U-Boot 和 FIT 镜像中嵌入新旧两个公钥，过渡期内两个密钥均受信任
- 密钥轮换流程：
  1. 安全管理员生成新密钥对
  2. 使用新私钥重新签名固件
  3. 发布包含新公钥的固件
  4. 过渡期后（确认所有设备已更新），吊销旧公钥
- 密钥轮换记录完整写入安全审计日志
- 每年至少进行一次计划性密钥轮换
- 密钥轮换期间，设备不应出现非计划停机

#### 功能 3.3.4：密钥吊销

**User Story：**
> 作为安全管理员，我需要在发现私钥泄露或安全事件后，能够吊销受影响的公钥，阻止使用已泄露密钥签名的固件运行。

**验收标准：**
- 通过固件更新方式颁发密钥吊销清单（Revocation List）
- 吊销清单由当前有效私钥签名，固件中包含已吊销的公钥指纹列表
- U-Boot 验签时，检查签名公钥指纹是否在吊销清单中
- 被吊销的公钥签名的固件将被拒绝启动
- 吊销清单在每次安全启动验签时被检查
- 吊销操作不可逆（一经吊销的公钥不能重新激活）

### 3.4 签名与验签流程

#### 功能 3.4.1：固件签名工具链

**User Story：**
> 作为固件发布工程师，我需要一套标准化的签名工具，在固件构建流水线中对各级镜像进行签名。

**验收标准：**
- 签名工具支持以下镜像类型：
  - U-Boot SPL 镜像（BootROM 阶段）
  - U-Boot ITB 镜像（U-Boot 自身）
  - FIT 镜像（kernel + DTB + initramfs + dm-verity root hash）
  - 根文件系统镜像（用于生成 dm-verity 哈希树）
- 签名算法支持：RSA-4096 或 SM2（由安全策略配置）
- 哈希算法支持：SHA-256 或 SM3（由安全策略配置）
- 签名工具集成于 CI/CD 构建流水线，支持 Jenkins/GitLab CI 调用
- 签名过程记录日志：签名镜像文件名、签名时间、密钥指纹、签名人身份
- 签名工具输出验证报告：签名是否成功、验签是否通过、签名算法参数

#### 功能 3.4.2：验签流程

**User Story：**
> 作为设备，我需要每次启动时按信任链顺序逐级验签，任何一级验签失败均中止启动。

**验收标准：**
- 验签顺序严格执行：BootROM → U-Boot SPL → U-Boot → FIT (kernel/DTB) → dm-verity root hash
- 每一级验签通过后方可释放下一级执行权
- 任何一级验签失败：
  - 立即中止该阶段启动流程
  - 输出固定格式错误码到串口和板载指示灯
  - 不执行任何未经验签的代码
- 验签过程中不依赖网络连接（离线本地验证）
- 验签性能满足整体安全启动时间 ≤ 15 秒（自芯片上电至系统就绪）

### 3.5 启动失败处理与恢复机制

#### 功能 3.5.1：安全错误状态

**User Story：**
> 作为设备运维人员，我需要当安全启动验签失败时，设备进入明确的安全错误状态，并输出可识别的错误信息以辅助排查。

**验收标准：**
- 安全启动验签失败后，设备进入 SECURE_BOOT_FAILURE 状态
- 错误状态指示：
  - 板载指示灯按预设模式闪烁（如 1Hz 双闪）
  - UART 串口输出错误码（格式：`SECURE_BOOT_FAIL: <stage>: <error_code>`）
  - 错误码明确标识失败阶段（BootROM/SPL/U-Boot/FIT/dm-verity）和原因
- 安全错误状态下，设备不加载或执行任何未经签名的代码
- 错误状态数据持久化至错误记录区域（eMMC 的专用分区）
- U-Boot 阶段失败时，可降级至恢复控制台（需物理触发，如 GPIO 跳线），恢复控制台不提供加载未签名固件的能力

#### 功能 3.5.2：恢复模式

**User Story：**
> 作为设备运维人员，我需要一种安全的恢复方式，在安全启动验签失败后通过物理授权操作恢复设备。

**验收标准：**
- 恢复模式触发条件：物理操作（如按下专用恢复按钮）同时检测到安全启动失败
- 恢复模式从受保护的恢复分区启动，该分区也经过独立签名验证
- 恢复分区镜像签名密钥与主系统不同（使用恢复专用密钥对）
- 恢复模式的功能：
  - 从安全的 OTA 通道下载带签名的修复固件
  - 验证修复固件的签名完整性
  - 将修复固件写入主固件分区
  - 修复完成后自动重新启动并重新进行全链验签
- 恢复模式不提供 shell 访问或加载任意代码的能力
- 恢复模式的串口输出仅限于状态信息，不提供交互式命令行
- 恢复操作全过程记录到安全审计日志

#### 功能 3.5.3：安全回滚保护

**User Story：**
> 作为安全管理员，我需要系统具备防回滚攻击能力，防止攻击者将设备降级到存在已知漏洞的旧版本固件。

**验收标准：**
- 每次固件更新时，新固件版本号（包含防回滚计数器值）写入 OTP 或防回滚存储区域
- U-Boot 在加载 FIT 镜像前，检查镜像内嵌的防回滚计数器值
- 防回滚计数器值低于 OTP 中记录值时，拒绝启动该固件
- 防回滚计数器值单调递增，不可重置或递减
- 固件更新失败时，防回滚计数器不受影响（允许回退至前一版本）
- 支持手动设置防回滚计数器（仅在安全管理员物理接触设备时，通过授权工具操作）
- 防回滚计数器溢出（达到最大值）时，设备需返厂更换硬件

### 3.6 安全启动状态监控与告警

#### 功能 3.6.1：安全启动状态查询

**User Story：**
> 作为设备运维人员，我需要在 Web 管理界面和北向通道中查看当前设备的安全启动状态。

**验收标准：**
- 安全启动状态通过 web-api 接口提供查询：
  - 端点：`GET /api/security/boot-status`
  - 响应格式 JSON，包含字段：
    - `secure_boot_enabled`：是否启用安全启动（true/false）
    - `boot_chain_status`：各级验签结果（BootROM/SPL/U-Boot/FIT/dm-verity）
    - `root_key_fingerprint`：当前启用根密钥的指纹（SHA-256 十六进制字符串）
    - `anti_rollback_counter`：当前防回滚计数器值
    - `last_boot_verification`：最近一次启动验签时间戳
    - `overall_status`：整体状态（PASS / FAIL / DEGRADED / RECOVERY）
  - 接口响应时间 ≤ 200ms
- 北向通道支持安全启动状态主动上报：
  - 安全启动状态变化时主动上报
  - 上报协议支持 IEC 104 和 MQTT
  - MQTT 上报格式使用 JSON

#### 功能 3.6.2：安全启动告警

**User Story：**
> 作为安全管理员，我需要当安全启动异常发生时，系统立即产生告警通知，以便及时响应安全事件。

**验收标准：**
- 告警触发条件：
  - 任何一级验签失败
  - 防回滚计数器异常
  - dm-verity 检测到文件系统篡改
  - OTP 熔丝状态异常
  - 恢复模式被触发
- 告警等级分类：
  - **CRITICAL**：验签失败或检测到篡改
  - **WARNING**：防回滚计数器接近上限（≥80%）、OTP 状态异常
  - **INFO**：安全启动状态变更、恢复模式触发
- 告警上报通道：
  - 实时日志（tracing ERROR 级别）
  - 北向通道主动上报（IEC 104 告警遥信 / MQTT 告警消息）
  - Web UI 告警列表展示
- 告警内容包含：告警类型、安全启动阶段、错误码、时间戳、建议处理措施

#### 功能 3.6.3：安全启动健康检查

**User Story：**
> 作为安全管理员，我需要系统定期执行安全启动健康检查，确保安全启动功能的持续有效性。

**验收标准：**
- 健康检查周期：默认每 24 小时执行一次（可配置）
- 健康检查内容：
  - 验证 dm-verity 哈希树的完整性
  - 确认 OTP 熔丝状态未发生异常变化
  - 检查防回滚计数器存储区域的可写性
  - 确认安全启动状态文件未被篡改
- 健康检查结果记录到安全日志
- 健康检查发现异常时，按 3.6.2 告警规则触发告警

### 3.7 安全启动日志审计

#### 功能 3.7.1：安全启动事件日志

**User Story：**
> 作为监管审计人员，我需要完整记录每次安全启动的全部事件，以满足电力系统安全审计要求。

**验收标准：**
- 安全启动日志记录以下事件：
  - 每次启动的验签结果（各阶段分别记录）
  - 密钥轮换操作记录（旧密钥指纹、新密钥指纹、操作人、时间戳）
  - 密钥吊销清单更新记录
  - OTP 熔丝烧录记录（生产阶段）
  - 防回滚计数器值变更记录
  - 恢复模式进入与退出记录
  - 安全启动策略配置变更记录
- 日志格式：
  - 每条日志包含：事件 ID、时间戳（UTC，毫秒级）、事件类型、事件等级、详情描述、操作人身份（如适用）
  - 日志存储格式：JSON 或结构化文本
- 日志存储：
  - 存储于独立只读分区（通过 dm-verity 保护）
  - 日志文件采用追加写入方式，不支持删除或修改历史记录
  - 日志保留期限：≥ 12 个月
  - 日志文件最大大小：单文件 100MB，超过后滚动
- 日志记录不可被普通用户删除或修改

#### 功能 3.7.2：审计查询接口

**User Story：**
> 作为监管审计人员，我需要通过 Web UI 查询安全启动历史日志，以便定期审查设备安全状态。

**验收标准：**
- Web UI 提供安全启动日志查询页面
- 查询条件支持：
  - 时间范围（开始时间、结束时间）
  - 事件类型过滤（启动验签、密钥轮换、策略变更等）
  - 事件等级过滤（ERROR、WARN、INFO）
- 查询结果支持分页展示，每页默认 20 条
- 查询结果支持导出为 CSV 文件
- 单次查询时间范围上限：3 个月
- 查询响应时间：≤ 3 秒（3 个月数据范围内）

## 5. 边界条件与异常处理

### 5.1 签名验证失败

| 场景 | 行为 | 恢复方式 |
|------|------|----------|
| BootROM 验签 U-Boot SPL 失败 | 中止启动，输出错误码 ERR_BOOTROM_SIG_FAIL | 仅能通过恢复模式刷写正确签名的固件 |
| U-Boot 验签 FIT 镜像失败 | 中止启动，输出错误码 ERR_UBOOT_FIT_SIG_FAIL | 可通过恢复模式刷写正确签名的固件 |
| FIT 镜像中内核签名存在但 DTB 签名缺失 | 拒绝加载 DTB，中止启动 | 重新构建并签名完整的 FIT 镜像 |
| dm-verity 根哈希与内核参数不匹配 | 内核无法挂载根文件系统，触发 Kernel Panic | 恢复模式刷写正确的根文件系统 |

### 5.2 密钥泄露场景

| 泄露范围 | 影响 | 处置措施 |
|----------|------|----------|
| 生产环境签名私钥泄露 | 攻击者可签名恶意固件 | 立即吊销泄露公钥，生产环境中更换密钥对并重新签名所有固件，所有设备通过 OTA 更新吊销清单 |
| 开发测试签名私钥泄露 | 开发环境固件可被伪造 | 吊销测试密钥，重新生成开发密钥对 |
| 恢复模式私钥泄露 | 攻击者可制作恶意恢复固件 | 启用紧急处理流程，设备返厂更新恢复密钥（恢复密钥写入 OTP） |

### 5.3 固件回滚攻击防护

| 攻击方式 | 防护机制 | 说明 |
|----------|----------|------|
| 直接烧录旧版本固件 | 防回滚计数器 | OTP 中的计数器值高于固件内嵌值时，拒绝启动 |
| 绕过签名直接写入 Flash | BootROM 验签 + 分区完整性校验 | 未签名的 Flash 内容无法通过 BootROM 验签 |
| 修改防回滚计数器 | OTP 一次性编程特性 | OTP 计数器仅可增加不可减少，软件无法篡改 |
| 替换 dm-verity 哈希树 | 哈希表签名验证 | 哈希树根哈希由 FIT 镜像签名保护 |

### 5.4 设备生命周期变更

| 场景 | 安全启动行为 | 要求 |
|------|-------------|------|
| 新设备出厂 | OTP 已烧录根公钥哈希，首次启动即进行全链安全验证 | 出厂前 100% 进行安全启动功能测试 |
| 设备返厂维修 | 维修后需重新验证安全启动状态 | 维修报告需包含安全启动验签结果 |
| 设备退役报废 | OTP 熔丝不可擦除，需物理销毁 | 退役前清除所有存储数据，OTP 随芯片物理销毁 |
| 设备固件升级 | 新固件必须签名，防回滚计数器同步更新 | 升级前验证签名，升级后执行完整性自检 |

## 6. 与现有系统的集成点

### 6.1 OTA 更新模块集成

| 集成点 | 说明 | 交互方式 |
|--------|------|----------|
| 固件更新签名 | OTA 模块下载的系统固件更新包必须携带有效的安全启动签名 | OTA 下载完成后，调用签名验证接口确认签名有效性 |
| 防回滚计数器 | OTA 模块在应用固件更新前，检查新固件的防回滚计数器值 | OTA 模块通过专用接口读取当前防回滚计数器和固件内嵌计数器 |
| 恢复模式触发 | OTA 更新失败导致设备无法正常启动时，自动进入恢复模式 | 恢复模式从恢复分区启动，通过 OTA 通道下载修复固件 |
| 完整性自检 | OTA 更新完成后，设备首次启动执行完整的安全启动链验签 | 启动验签结果由安全启动模块记录并上报 |

### 6.2 安全模块（SM2/SM4）集成

| 集成点 | 说明 | 交互方式 |
|--------|------|----------|
| SM2 签名验证 | 当安全策略配置为国密模式时，U-Boot FIT 验签使用 SM2 算法 | 安全模块的 SM2 验签接口供签名工具链使用（不是运行时，是构建时） |
| SM3 哈希计算 | dm-verity 哈希树和运行时校验的哈希算法使用 SM3 | dm-verity 内核模块配合哈希算法参数配置为 SM3 |
| 私钥加密存储 | 开发测试私钥使用 SM4 加密存储 | 密钥管理工具调用 security::sm4 接口进行私钥加解密 |

**运行时无直接依赖：** 安全启动验签发生在 U-Boot 和内核阶段，此时 Rust 运行时和 `mupc-security` 模块尚未加载。SM2/SM3/SM4 算法的使用场景限于构建时的签名工具链和密钥管理工具。U-Boot 内置的验签逻辑使用 U-Boot 自带的加密库实现（支持 RSA 和 SM2）。

### 6.3 web-api 状态上报

| 集成点 | 说明 | 接口要求 |
|--------|------|----------|
| 安全启动状态查询 | web-api 提供 REST 接口供 Web UI 和北向通道查询安全启动状态 | `GET /api/security/boot-status` 返回 JSON 格式状态 |
| 安全日志查询 | web-api 提供安全启动日志查询接口 | `GET /api/security/boot-log?from=...&to=...&type=...` |
| 告警上报 | web-api 接收安全启动模块的告警事件并转发到告警通道 | 通过内部消息总线发布告警事件 |

### 6.4 密钥管理工具

| 功能 | 说明 | 类型 |
|------|------|------|
| 密钥生成工具 | 在安全管理员工作站上运行的离线工具，生成 RSA/SM2 密钥对 | 独立命令行工具 |
| 签名工具 | 集成到 CI/CD 流水线的命令行工具，对各级固件镜像进行签名 | 命令行工具，集成到构建流水线 |
| OTP 烧录工具 | 在设备生产阶段烧录根公钥哈希到 OTP 熔丝 | 生产测试专用工具 |
| 防回滚计数器管理工具 | 设置和查询防回滚计数器值 | 命令行工具，需要物理访问权限 |

## 8. 风险与对策

| 风险 | 等级 | 概率 | 影响 | 对策 |
|------|------|------|------|------|
| RK3588 OTP 容量不足 | 中 | 低 | 无法存储所需密钥信息 | 启动前确认 OTP 可用容量；如不足，使用多级派生方案压缩密钥存储 |
| U-Boot SM2 验签性能瓶颈 | 中 | 中 | 启动时间 > 15 秒 | 优化 FIT 镜像签名粒度（仅签名哈希值而非整个镜像）；若仍不满足，使用 RSA-4096 作为备选 |
| OTP 烧录失误导致设备报废 | 高 | 低 | 设备需返厂更换芯片 | 生产测试流程增加 OTP 烧录前验证步骤；先烧录测试密钥验证通过后再烧录生产密钥 |
| dm-verity 与 openEuler 内核兼容性 | 中 | 中 | 内核不支持 dm-verity 或 SM3 哈希 | 在 openEuler 内核配置中确认 CONFIG_DM_VERITY 和 CONFIG_DM_VERITY_SM3 使能；若不支持则使用 SHA-256 |
| 私钥管理流程疏漏导致泄露 | 高 | 低 | 攻击者可签名恶意固件 | HSM 硬件保护密钥；建立密钥访问审批流程；定期审计密钥使用记录 |
| 恢复模式本身被攻击 | 中 | 低 | 攻击者通过恢复模式植入恶意固件 | 恢复分区使用独立密钥签名；恢复模式功能严格受限，不支持任意代码执行 |

## 9. 术语表

| 术语 | 说明 |
|------|------|
| BootROM | RK3588 芯片内固化的一级引导程序，不可修改，上电后最先执行 |
| OTP (One-Time Programmable) | 一次性可编程熔丝，用于存储根公钥哈希等不可篡改信息 |
| eFuse | Rockchip 对 OTP 的实现名称 |
| SPL (Secondary Program Loader) | 二级引导程序，由 BootROM 加载，负责初始化 DDR 并加载 U-Boot |
| U-Boot | 开源引导加载程序，用于加载 Linux 内核和设备树 |
| FIT (Flattened Image Tree) | U-Boot 使用的镜像打包格式，支持包含内核、DTB、initramfs 及签名 |
| dm-verity | Linux 内核的 device-mapper 目标，提供块设备级别的完整性验证 |
| Verified Boot | U-Boot 的安全启动机制，通过公钥验签确保镜像完整性 |
| Anti-Rollback Counter | 单调递增计数器，防止设备运行旧版本固件 |
| HSM (Hardware Security Module) | 硬件安全模块，用于安全存储私钥和执行密码学操作 |
| Revocation List | 吊销清单，列出不再被信任的公钥指纹 |
