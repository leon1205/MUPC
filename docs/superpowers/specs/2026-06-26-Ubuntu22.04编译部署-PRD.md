## 1. 文档综述

### 1.1 背景与动机

MUPC 微电网特种调控装置当前仅能在 Windows 10 (MSVC) 开发环境中完成 `cargo check`，无法编译生成目标硬件（RK3588, ARM64）的可执行程序。具体阻塞项：

- 无 Linux 交叉编译工具链
- 无 RKNN SDK（librknnrt.so）Linux 版本
- 无 CI/CD pipeline
- 无二进制入口点（workspace 全部为 library crate，缺少 `fn main()`）

本 PRD 定义将 MUPC 从"Windows 开发验证"到"Ubuntu 22.04 ARM64 生产可执行"的完整编译部署方案。

### 1.2 术语表

| 术语 | 说明 |
|------|------|
| RKNN Runtime | Rockchip NPU 推理运行时，提供 `librknnrt.so`（Linux）/ `rknnrt.lib`（Windows）|
| Toolchain | Rust 编译目标工具链 `aarch64-unknown-linux-gnu` |
| sysroot | 交叉编译所需的 ARM64 Linux 根文件系统（glibc、libgcc 等） |
| Feature gate | 通过 Cargo `[features]` 条件编译的代码路径 |
| Binary crate | 含 `main.rs` 的可执行 crate，产出 ELF 可执行文件 |

### 1.3 参考文档

- Rust 交叉编译指南：https://rust-lang.github.io/rustup/cross-compilation.html
- Rockchip RKNN Toolkit2：https://github.com/airockchip/rknn-toolkit2
- Cross (Rust 交叉编译工具)：https://github.com/cross-rs/cross
- 本项目 CLAUDE.md v2.0

## 3. 当前状态分析

### 3.1 项目现状

| 维度 | 当前状态 |

### 3.2 阻塞项详析

#### 3.2.1 无二进制入口

当前 workspace 所有 crate 均定义 `[lib]` 目标，缺少 `[[bin]]` target。MUPC 运行时需要一个主控进程负责：

1. 解析命令行参数 / 配置文件路径
2. 初始化 tracing 日志系统
3. 启动 core::ServiceCoordinator（服务协调器）
4. 按依赖顺序拉起各子系统（gateway、intercore、data-processing、strategy-engine、ai-engine…）
5. 监听 SIGTERM / SIGINT 优雅退出

**方案**：新建 `crates/mupc-core-bin/` 二进制 crate。

#### 3.2.2 RKNN SDK 缺失 Linux 版本

`ai-engine/src/rknn_runtime_sys.rs` 中：

```rust
#[link(name = "rknnrt")]
extern "C" { ... }
```

Windows 上 `cargo test` 因找不到 `rknnrt.lib` 而链接失败。Linux 构建需要 `librknnrt.so`。

获取途径：
- GitHub Release：https://github.com/airockchip/rknn-toolkit2/releases
- Rockchip 官方 SDK：RKNN API 1.6.0+，提供 `librknnrt.so` (ARM64 Linux, glibc)

#### 3.2.3 交叉编译工具链未配置

Rust 交叉编译需要：
- `rustup target add aarch64-unknown-linux-gnu`（ARM64 Linux glibc toolchain）
- ARM64 sysroot（含 glibc 2.35+、libgcc_s 等）或使用 `cross` 工具自动处理

Ubuntu 22.04 附带 glibc 2.35，需确保 sysroot 版本匹配。

#### 3.2.4 平台 API 依赖

`rs485-plugin` 依赖 `libc`（仅 `cfg(unix)`），序列化端口操作使用 POSIX API：
- `open()` / `close()` / `read()` / `write()` / `ioctl()`（设置波特率等）
- DE/RE GPIO 控制（RS485 半双工切换）

这些在 Linux ARM64 上天然可用，无需额外适配。但需要**在 CI 中编译验证**，确保 `cfg(unix)` 路径正确激活。

## 4. 方案设计

### 4.1 总体架构

```
                     GitHub Actions Runner (ubuntu-22.04-arm64)
                              │
              ┌───────────────┼───────────────┐
              ▼                               ▼
      native build                    cross-compilation
   (自托管 ARM64 runner)           (x86_64 host + cross)
              │                               │
              └───────────────┬───────────────┘
                              ▼
                    Artifacts 产出
              ┌────────┼────────┐
              ▼        ▼        ▼
           mupcd      *.so    config/
           (ELF)      (动态库)  (yaml + models)
```

**构建策略选择**：

| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| A. GitHub Actions 自托管 ARM64 runner 原生编译 | 无需交叉编译，最简单 | 需维护 ARM64 物理机/VM | 长期 |
| B. GitHub Actions `cross` 交叉编译 | 在 x86_64 runner 上完成，依托 Docker | 交叉编译复杂度 | 短期 MVP |
| C. 本地 Docker + `cross` | 离线可用，开发阶段验证 | 手动触发 | 开发备用 |

**推荐路径**：短期先走 B + C，中期迁移到 A（当 ARM64 硬件就绪后）。

### 4.2 二进制入口点设计 (R1)

#### 4.2.1 插件 crate 编译为动态库 (.so)

4 个插件 crate 需产出 `.so` 动态库，供 plugin-loader 在运行时通过 `libloading` 加载。每个插件的 `Cargo.toml` 需添加 `crate-type`：

| 插件 crate | 产出文件 |
|-----------|---------|
| `rs485-plugin` | `librs485_plugin.so` |
| `hplc-plugin` | `libhplc_plugin.so` |
| `mqtt-plugin` | `libmqtt_plugin.so` |
| `iec61850-plugin` | `libiec61850_plugin.so` |

**Cargo.toml 示例**（以 `rs485-plugin` 为例）：

```toml
[lib]
crate-type = ["cdylib"]
name = "rs485_plugin"
```

其余 3 个插件 crate 同理。注意 `mqtt-plugin` 的 Cargo.toml name 为 `mupc-mqtt-plugin`，`lib.name` 应设为 `mqtt_plugin`（与 `crate-type = ["cdylib"]` 配合，产出 `libmqtt_plugin.so`）。

**编译命令**：

```bash
cargo build --release --target aarch64-unknown-linux-gnu
# 产物输出至 target/aarch64-unknown-linux-gnu/release/*.so
```

plugin-loader 通过 `libloading::Library::new("librs485_plugin.so")` 加载，搜索路径由 `LD_LIBRARY_PATH` 或部署目录 `/opt/mupc/lib/plugins/` 指定。

### 4.3 RKNN SDK Linux 适配 (R2)

#### 4.3.1 获取 librknnrt.so

Rockchip 官方 RKNN API 发布在：
- GitHub：https://github.com/airockchip/rknn-toolkit2
- 其中包含 `librknn_api/` 子目录，内含 `librknnrt.so`

**推荐版本**：RKNN API 1.6.0+（搭配 RK3588 NPU 驱动）

**存放路径**：`vendor/rknn/`（纳入版本管理或构建 pipeline 自动下载）

#### 4.3.2 链接方式

Rust FFI 中 `#[link(name = "rknnrt")]` 在 Linux 上会搜索 `librknnrt.so`。需配置：

1. **构建时**：通过 `cargo:rustc-link-search=native=<path>` 在 `build.rs` 中指向 vendor 目录（见 4.3.4）
2. **运行时**：`LD_LIBRARY_PATH` 包含 `.so` 路径，或将 `.so` 安装到 `/usr/lib/aarch64-linux-gnu/`

**交叉链接可行性验证**：`librknnrt.so` 本身是 ARM64 ELF，`cross` 工具在 Docker 容器内使用 `aarch64-linux-gnu-gcc` 作为 linker，只要 `build.rs` 正确指定 `rustc-link-search`，链接器就能找到并链接该 `.so`。验证方法：

```bash
# 确认 librknnrt.so 为 ARM64 ELF
file vendor/rknn/librknnrt.so
# 预期输出: ELF 64-bit LSB shared object, ARM aarch64, ...

# 确认交叉 linker 可用
aarch64-linux-gnu-gcc --version

# 在 cross 容器中测试链接
cross build --release --target aarch64-unknown-linux-gnu --features npu
```

**librknnrt.so 完整性校验**：从 Rockchip GitHub Release 或其他渠道获取 `.so` 后，应记录 SHA256 校验和，纳入版本管理：

```bash
# 计算 SHA256
sha256sum vendor/rknn/librknnrt.so > vendor/rknn/librknnrt.so.sha256
```

`build.rs` 或 CI pipeline 在构建前应对比校验和，防止文件损坏或篡改。校验逻辑内置在 `build.rs` 中：

```rust
// build.rs 中增加 SHA256 校验（伪代码）
let expected_hash = include_str!("../vendor/rknn/librknnrt.so.sha256");
let actual_hash = sha256_of_file("vendor/rknn/librknnrt.so");
assert_eq!(expected_hash.trim(), actual_hash, "librknnrt.so checksum mismatch!");
```

#### 4.3.3 条件编译 Feature Gate

为 ai-engine 添加 `npu` feature：

```toml
# ai-engine/Cargo.toml
[features]
default = []
npu = []  # 启用 RKNN Runtime 推理
```

在 `rknn_runtime.rs` / `rknn_runtime_sys.rs` 中用 `#[cfg(feature = "npu")]` 包裹全部 RKNN 代码。Windows 开发时默认不启用 `npu`，Linux 构建时启用：

```bash
cargo build --release --features npu
```

#### 4.3.4 build.rs 生成链接指令

新建 `crates/ai-engine/build.rs`（**唯一推荐方案**，替代 `.cargo/config.toml` 中的 `[env]` 方式以保持配置集中）：

```rust
use std::path::Path;

fn main() {
    // ── RKNN Vendor 目录 ──
    // 优先级：环境变量 RKNN_VENDOR_DIR > 默认 vendor/rknn
    let vendor_dir = std::env::var("RKNN_VENDOR_DIR")
        .unwrap_or_else(|_| "vendor/rknn".to_string());
    println!("cargo:rustc-link-search=native={}", vendor_dir);
    println!("cargo:rustc-link-lib=dylib=stdc++");

    // ── SHA256 完整性校验 ──
    let so_path = Path::new(&vendor_dir).join("librknnrt.so");
    if so_path.exists() {
        let hash_file = Path::new(&vendor_dir).join("librknnrt.so.sha256");
        if hash_file.exists() {
            let expected = std::fs::read_to_string(&hash_file)
                .expect("Failed to read SHA256 file");
            let expected = expected.split_whitespace().next()
                .expect("Invalid SHA256 file format");
            let actual = compute_sha256(&std::fs::read(&so_path)
                .expect("Failed to read librknnrt.so"));
            assert_eq!(expected, actual,
                "librknnrt.so SHA256 mismatch! Expected: {}, Got: {}", expected, actual);
        } else {
            // 首次导入：自动生成 .sha256 文件
            let actual = compute_sha256(&std::fs::read(&so_path)
                .expect("Failed to read librknnrt.so"));
            std::fs::write(&hash_file, format!("{}  librknnrt.so\n", actual))
                .expect("Failed to write SHA256 file");
        }
    }
}

fn compute_sha256(data: &[u8]) -> String {
    use std::fmt::Write;
    // 使用 sha2 crate（已在 ai-engine 依赖中）
    let hash = sha2::Sha256::digest(data);
    let mut s = String::with_capacity(64);
    for byte in hash.iter() {
        write!(&mut s, "{:02x}", byte).unwrap();
    }
    s
}
```

### 4.4 交叉编译工具链 (R3)

#### 4.4.1 Rust Target

```bash
rustup target add aarch64-unknown-linux-gnu
```

#### 4.4.2 sysroot 获取

**方案 A（推荐）**：使用 `cross` 工具

```bash
cargo install cross
cross build --release --target aarch64-unknown-linux-gnu --features npu
```

`cross` 自动拉取预构建 Docker 镜像（含 Ubuntu 22.04 sysroot + glibc 2.35），无需手动配置。

**方案 B**：手动构建 sysroot

```bash
# 从 Ubuntu 22.04 ARM64 镜像提取
sudo apt install qemu-user-static
docker run --rm -v $PWD:/mnt arm64v8/ubuntu:22.04 bash -c "
    apt update && apt install -y libssl-dev libsqlite3-dev
    cp -r /usr/lib/aarch64-linux-gnu/* /mnt/sysroot/usr/lib/
    cp -r /usr/include/* /mnt/sysroot/usr/include/
"
```

在 `.cargo/config.toml` 中配置：

```toml
[target.aarch64-unknown-linux-gnu]
linker = "aarch64-linux-gnu-gcc"   # 需安装 gcc-aarch64-linux-gnu
rustflags = ["-C", "link-arg=--sysroot=./sysroot"]
```

**推荐**：开发阶段用方案 B（可完全离线），CI 用方案 A（免维护）。

### 4.5 CI/CD Pipeline (R4)

#### 4.5.1 GitHub Actions Workflow

文件位置：`.github/workflows/build-ubuntu.yml`

```yaml
name: Build Ubuntu 22.04 ARM64

on:
  push:
    branches: [master]
    tags: ['v*']
  pull_request:
    branches: [master]

jobs:
  build:
    runs-on: ubuntu-22.04  # x86_64，通过 cross 交叉编译
    steps:
      - uses: actions/checkout@v4

      - name: Install cross
        run: cargo install cross --git https://github.com/cross-rs/cross

      - name: Fetch RKNN SDK
        run: |
          mkdir -p vendor/rknn
          # 从内部制品库拉取 librknnrt.so（因需授权，从 GitHub Release 手动下载并缓存）
          # 路径：vendor/rknn/librknnrt.so

      - name: Build
        run: cross build --release --target aarch64-unknown-linux-gnu --features npu

      - name: Run unit tests (no RKNN)
        run: cross test --target aarch64-unknown-linux-gnu --workspace

      - name: Strip binaries
        run: aarch64-linux-gnu-strip target/aarch64-unknown-linux-gnu/release/mupcd

      - name: Upload artifacts
        uses: actions/upload-artifact@v4
        with:
          name: mupc-ubuntu2204-arm64
          path: |
            target/aarch64-unknown-linux-gnu/release/mupcd
            target/aarch64-unknown-linux-gnu/release/*.so
            config/
            deploy/
```

#### 4.5.3 测试排除策略说明

`mupc-ai-engine` 的 `npu` feature 启用时会触发 `#[link(name = "rknnrt")]` FFI 链接。`mupc-strategy-engine` 直接依赖 `mupc-ai-engine`，因此即使 `--exclude mupc-ai-engine` 跳过其自身测试，`mupc-ai-engine` 作为库仍会被编译（触发链接失败）。

**正确策略**：运行 `cross test` 时**不传 `--features npu`**。已在 4.3.3 中定义 `npu` feature gate，所有 RKNN FFI 代码由 `#[cfg(feature = "npu")]` 包裹。不启用该 feature 时，`rknn_runtime_sys.rs` 中的 `#[link]` 不会被编译，`strategy-engine` 的测试可安全执行。

```yaml
      - name: Run unit tests (no RKNN)
        run: cross test --target aarch64-unknown-linux-gnu --workspace
```

**验证**：本地 Windows 开发环境下 `cargo test` 不启用 `npu` feature 即可通过，与 CI 行为一致。

### 4.8 平台适配 (R7)

| crate | 平台特定依赖 | 适配方案 |
|-------|-------------|---------|
| `rs485-plugin` | `libc` (cfg(unix)) | 已有 cfg 适配，CI 编译验证即可 |
| `hplc-plugin` | 纯 Rust（默认）；`ffi` feature 预留 | 已审计通过 —— 无平台依赖。默认依赖均为纯 Rust crate（`device-trait`、`tokio`、`serde`、`thiserror`、`tracing`），无 `libc` / FFI 绑定。`[features] ffi = []` 为预留 feature，当前无实际代码路径，交叉编译无阻塞 |
| `ai-engine` | `#[link(name = "rknnrt")]` | feature gate `npu` |
| `iec61850-plugin` | `libIEC61850` FFI | 已有 optional feature `real_iec61850`，默认 `fake_iec61850`，暂不启用 FFI |
| `wireless` | p256/hkdf/sha2 | 纯 Rust，无平台适配负担 |
| `security` | SM2/SM4 | gmsm 为纯 Rust，无平台依赖 |
| `system-monitor` | 无 | 已审计通过 —— 纯 Rust。依赖 `tokio`、`tracing`、`sqlx`、`serde`，无 `libc` / 平台特定 crate。CPU/内存采集通过 `/proc` 文件系统读取（Linux 原生接口），无需 FFI |
| `mqtt-bridge` | 纯 Rust | 已审计 —— 依赖 `rumqttc`、`rustls`，均为跨平台纯 Rust |

## 7. 风险评估

| 编号 | 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|------|---------|
| RK-01 | RKNN SDK 版本与 NPU 驱动不匹配 | 中 | 高：AI 推理不可用 | 构建时记录 RKNN API 版本号；启动时校验 `rknn_query` 返回的 API/Driver 版本一致性 |

| RK-03 | 交叉编译 glibc 版本不兼容 | 低 | 中：运行时符号解析失败 | 用 Ubuntu 22.04 官方 Docker 镜像的 sysroot；`cross` 工具自带正确版本 |
| RK-04 | hplc-plugin / iec61850-plugin 存在未发现的 FFI 依赖 | 中 | 中：编译报错 | S1 阶段全 crate 审计平台依赖 |
| RK-05 | 自托管 ARM64 runner 不可用 | 高 | 低：替代方案存在 | 使用 cross（x86_64 + Docker）交叉编译，结果等价 |
| RK-06 | 编译产物过大（>50MB）| 低 | 低：部署带宽 | LTO + strip 已启用；必要时启用 `panic=abort` + `opt-level=s` |
| RK-07 | 第三方 crate 不支持 ARM64 Linux | 低 | 中：编译失败 | 预检所有依赖的 target 支持情况：`cargo tree --target aarch64-unknown-linux-gnu` |
| RK-08 | librknnrt.so 间接依赖的 C++ 库版本冲突 | 中 | 中：运行时 dlopen 失败 | 静态分析 .so 依赖：`readelf -d librknnrt.so`；将依赖的 libstdc++.so.6 与部署包一同分发 |
