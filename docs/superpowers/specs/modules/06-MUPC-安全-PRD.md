## 1. 产品概述

### 1.1 背景与定位

MUPC 微电网特种调控装置作为电力调度与配电自动化的核心边缘设备，运行于关键基础设施环境中。安全模块是 MUPC 安全防御体系的核心支撑，覆盖国密算法、安全启动、电力合规三大安全领域。

**安全防御三大防线：**

| 防线 | 领域 | 覆盖 PRD |
|------|------|----------|
| 第一防线 | SM2/SM4/SM3 国密算法实现 — 密码学基础设施 | SM2/SM4 国密设计文档 |
| 第二防线 | 安全启动（Secure Boot）— BootROM→U-Boot→Kernel→RootFS 信任链 | 安全启动 PRD |
| 第三防线 | 电力安全合规增强 — 纵向加密认证、证书管理、全链路加密审计 | 电力合规 PRD |

### 1.2 核心价值

| 维度 | 价值 |
|------|------|
| **密码学合规** | 使用符合国家密码管理局标准的 SM2/SM3/SM4 算法替代模拟实现 |
| **防篡改** | 安全启动确保从 BootROM 到应用程序的每一级代码均经过可信签名 |
| **供应链安全** | 仅经过厂商签名的固件才能在设备上执行 |
| **电力合规** | 满足国家发改委 2014 年第 14 号令、GB/T 36572-2018 等法规的纵向加密认证要求 |
| **防御纵深** | 为 OTA 升级提供可信执行环境，防止恶意固件从升级通道侵入 |
| **可审计性** | 所有加密操作和控制指令全链路可追溯，满足等保 2.0 三级要求 |

### 1.3 目标平台

| 项目 | 要求 |
|------|------|
| 操作系统 | Linux (openEuler 22.03+) |
| 硬件 | Rockchip RK3588（ARMv8.2-A，含 OTP fuses、eFuse） |
| 编程语言 | Rust |
| 异步运行时 | Tokio |
| 引导加载程序 | U-Boot 2023.07+（支持 verified boot / FIT 镜像验签） |
| 文件系统完整性 | dm-verity（内核模块） |
| 板级支持包 | Rockchip BSP（含 BootROM Secure Boot 使能） |

### 1.4 适用范围

| 项目 | 说明 |
|------|------|
| 通信协议 | IEC 60870-5-104、IEC 61850 MMS、MQTT over TLS |
| 安全标准 | GM/T 0002-2012/SM4、GM/T 0003-2012/SM2、GM/T 0004-2012/SM3、RFC 8998 |
| 行业标准 | 发改委 2014 年第 14 号令、GB/T 36572-2018、等保 2.0 三级 |

### 1.5 术语定义

| 术语 | 定义 |
|------|------|
| 国密算法 | 国家密码管理局发布的商用密码算法标准，包括 SM2（公钥密码）、SM3（密码杂凑）、SM4（分组密码） |
| 安全启动 (Secure Boot) | 通过逐级签名验证机制，确保设备从 BootROM 到应用程序的每一级代码均经过可信签名 |
| 纵向加密认证 | 电力调度数据网中上下级系统之间的身份认证、数据加密和完整性保护机制 |
| OTP (One-Time Programmable) | 一次性可编程熔丝，用于存储根公钥哈希等不可篡改信息 |
| dm-verity | Linux 内核的 device-mapper 目标，提供块设备级别的完整性验证 |
| FIT (Flattened Image Tree) | U-Boot 使用的镜像打包格式，支持包含内核、DTB、initramfs 及签名 |
| 防回滚计数器 | 单调递增计数器，防止设备运行旧版本固件 |
| 全链路加密审计 | 从调度主站下发控制指令、经 MUPC 转发到实时控制模块的完整链条中，每个环节的加密操作均有日志记录 |
| SM2 TLS 握手 | 使用 SM2 证书和 SM2 签名算法进行 TLS 1.2/1.3 握手（RFC 8998） |
| CRL (Certificate Revocation List) | 证书吊销列表 |

| **生产测试人员** | 负责设备出厂时的安全启动功能测试 | OTP 烧录验证、首次启动签名校验 | 中 |

- 安全管理员和合规审计人员必须为不同人员担任
- 安全管理员的操作必须被合规审计人员可追溯
- 任何安全策略变更必须记录审计日志

## 3. SM2/SM4/SM3 国密算法

### 3.1 概述

当前 `security` 模块中的 SM2/SM4 实现使用 `ring` 库的 P-256/AES-256-GCM 曲线进行模拟，不符合国家密码管理局发布的国密标准。本功能使用纯 Rust 国密库 **gmsm** 替换现有模拟实现，提供真正的 SM2/SM3/SM4 国密算法支持。

### 3.2 技术选型

| 特性 | 说明 |
|------|------|
| 库 | gmsm 0.14（纯 Rust，无外部依赖） |
| 标准 | 完全符合国密局 SM2/SM3/SM4 标准 |
| 平台 | 支持 Linux/RK3588、Windows、macOS |
| 许可 | Apache-2.0 / MIT |
| Cargo Feature | `default = ["real_gmsm"]`，通过 `fake_gmsm` feature 支持 CI 测试（使用 ring 模拟） |

### 3.3 SM2 签名与验签

#### 功能 3.3.1：SM2 签名/验签（[REVIEWED: PASS]）

**User Story：**
> 作为安全管理员，我需要使用符合国密标准的 SM2 算法对数据进行签名和验签，以满足电力行业对数据完整性和不可否认性的合规要求。

**验收标准：**
- GM-01：SM2 签名符合国密标准（GM/T 0003-2012），使用国家密码管理局测试向量验证
- GM-02：SM2 验签符合国密标准，使用国家密码管理局测试向量验证
- SM2 曲线参数为国密局指定的 `sm2p256v1` 曲线
- 密钥生成必须使用硬件真随机数发生器（RK3588 TRNG）

**接口设计：**

```rust
// 保持现有接口兼容
pub fn sm2_sign(data: &[u8], private_key: &str) -> Result<Vec<u8>>;
pub fn sm2_verify(data: &[u8], signature: &[u8], public_key: &str) -> Result<bool>;

// 新增接口
pub fn sm2_key_generate() -> Result<Sm2KeyPair>;
pub fn sm2_derive_shared_key(key_pair: &Sm2KeyPair, peer_public_key: &[u8]) -> Result<Vec<u8>>;
```

### 3.4 SM4 对称加密

#### 功能 3.4.1：SM4 加密/解密（[REVIEWED: PASS]）

**User Story：**
> 作为安全管理员，我需要使用符合国密标准的 SM4 算法对通信数据进行加密传输，确保数据机密性。

**验收标准：**
- GM-03：SM4 加密符合国密标准（GM/T 0002-2012），使用 KAT 测试向量验证
- GM-04：SM4 解密符合国密标准，使用 KAT 测试向量验证
- 密钥长度：16 字节（128 位）
- GCM 模式下 IV 严禁重用，每次加密使用不同的 12 字节随机 IV

**接口设计：**

```rust
// 保持现有接口兼容
pub fn sm4_gcm_encrypt(data: &[u8], key: &[u8], iv: &[u8]) -> Result<Vec<u8>>;
pub fn sm4_gcm_decrypt(data: &[u8], key: &[u8], iv: &[u8]) -> Result<Vec<u8>>;

// 新增接口（CBC 模式）
pub fn sm4_cbc_encrypt(data: &[u8], key: &[u8], iv: &[u8]) -> Result<Vec<u8>>;
pub fn sm4_cbc_decrypt(data: &[u8], key: &[u8], iv: &[u8]) -> Result<Vec<u8>>;
```

**接口设计：**

```rust
pub fn load_sm2_certificate(path: &str) -> Result<Certificate>;
```

### 3.7 Feature Flag 与兼容性

- 保留现有接口签名，仅替换底层实现
- `default = ["real_gmsm"]` 使用 gmsm 实现
- `fake_gmsm`：通过条件编译实现，使用 ring 模拟，用于 CI 测试和开发环境
- **生产环境必须启用 `real_gmsm`**

### 3.8 IV 重用防护

> **安全警告**：GCM 模式 IV 重用会导致密文可被攻击者解密！

**对策：**
- 每次加密使用 12 字节随机 IV
- 使用单调递增计数器（适用于流式加密）
- 实现 IV 管理机制，防止重放

### 3.9 敏感数据清除

建议使用 `zeroize` crate 安全清除敏感数据：

```rust
use zeroize::Zeroizing;
let key = Zeroizing::new(sensitive_data);
// 使用后自动清零
```

## 4. 双向证书认证与 SM2 TLS

### 4.1 SM2 证书格式兼容性（[REVIEWED: PASS]）

#### 功能 4.1.1：SM2 证书格式验证（LEA-20 ~ LEA-24）

**User Story：**
> 作为安全管理员，我需要确保系统使用的 SM2 证书符合 X.509 v3 标准，并在 TLS 握手过程中被正确识别和验证。

**验收标准：**

| ID | 验收内容 | 验证方法 |
|----|----------|----------|
| LEA-20 | SM2 证书必须使用 SM2-with-SM3 签名算法（OID 1.2.156.10197.1.501） | 使用 `openssl` 解析证书，验证签名算法 OID |
| LEA-21 | SM2 证书公钥算法为 id-ecPublicKey（OID 1.2.840.10045.2.1）且曲线为 sm2p256v1（OID 1.2.156.10197.1.301） | 使用 `openssl` 解析证书，验证公钥算法 OID 和曲线 OID |
| LEA-22 | TLS 1.3 握手中 SM2 证书被用于支持 sig_sm2_sign_sm3 签名算法（RFC 8998 Section 2.2） | 抓包验证 TLS 1.3 CertificateVerify 消息中使用 sm2sig_sm3 算法标识 |
| LEA-23 | MUPC 加载 SM2 证书时报错信息明确区分：证书格式错误、签名算法不匹配、证书已过期、证书链不完整 | 分别构造上述四种错误场景，验证错误信息内容 |
| LEA-24 | MUPC 支持同时管理至少 3 张 SM2 证书（TLS 服务器证书、TLS 客户端证书、IPSec 证书） | 加载 3 张证书并分别配置到三个通道，验证各通道正常工作 |

### 4.2 SM2 TLS 握手（[REVIEWED: PASS]）

#### 功能 4.2.1：SM2 TLS 握手流程（LEA-25 ~ LEA-29）

**User Story：**

**验收标准：**

| ID | 验收内容 | 验证方法 |
|----|----------|----------|
| LEA-25 | TLS 1.2 握手支持 SM2-SM4-SM3 密码套件：`TLS_ECDHE_SM2_WITH_SM4_GCM_SM3`（0x00,0xC6）（RFC 8998） | 配置 TLS 1.2 国密套件，验证握手协商结果 |
| LEA-26 | TLS 1.3 握手支持 SM2 签名算法和 SM4-GCM 记录加密 | 抓包验证 TLS 1.3 握手和记录层加密 |
| LEA-27 | MUPC 作为 TLS 客户端和服务端均可使用 SM2 证书完成双向认证 | 分别在客户端和服务端模式下测试双向认证 |
| LEA-28 | SM2 TLS 完整握手性能 ≤ 100ms（RK3588 平台），会话恢复握手 ≤ 10ms | 连续执行 1000 次握手，取 P99 延迟 |
| LEA-29 | 与 GmSSL 3.x、铜锁(Tongsuo) 8.x、OpenSSL 3.x + SM2 patch 互操作测试通过 | 分别进行 TLS 握手连通性测试 |

## 5. 纵向加密认证（电力合规）

### 5.1 纵向加密认证合规（[REVIEWED: PASS]）

#### 功能 5.1.1：纵向加密认证策略管理与合规（LEA-01 ~ LEA-05）

**User Story：**
> 作为安全管理员，我需要确保 MUPC 与调度主站之间的所有通信都经过纵向加密认证，满足国家发改委 2014 年第 14 号令第十四条和 GB/T 36572-2018 第 6.3 节的要求。

**验收标准：**

| ID | 验收内容 | 验证方法 |
|----|----------|----------|
| LEA-01 | MUPC 与调度主站（IEC 104）之间的通信通道支持在应用层进行 SM2 签名和 SM4 加密 | 抓包验证 IEC 104 应用层报文包含 SM2 签名字段和 SM4 加密载荷 |
| LEA-02 | 每一条从调度主站下发的控制指令必须通过 SM2 签名验证，验签失败时指令被拒绝执行 | 构造无效签名指令发送至 MUPC，验证指令被拒绝并产生告警 |
| LEA-03 | MUPC 返回的遥测、遥信数据必须附带 SM2 数字签名，接收方可验证数据完整性 | 截获 MUPC 上行的 IEC 104 报文，验证 SM2 签名字段存在且有效 |
| LEA-04 | 支持对 IEC 104 APDU 整体进行国密加密，满足 GB/T 36572-2018 第 6.3.2 条要求 | 配置加密启用后，抓取报文验证 APDU 载荷为 SM4 密文 |
| LEA-05 | 支持按通道粒度配置加密策略（开启/关闭加密、选择签名/加密算法） | 通过 web API 修改通道加密策略，验证通信行为符合配置 |

**User Story：**

**验收标准：**

| ID | 验收内容 | 验证方法 |
|----|----------|----------|
| LEA-06 | MUPC 启动时自动执行安全合规自检：国密算法可用性、加密策略完整性、证书有效性 | 查看启动日志，每项检查有通过/失败状态 |

### 5.2 纵向加密认证装置对接（[REVIEWED: PASS]）

| LEA-13 | 支持 IKEv2 协议中定义的分支地址、NAT 穿透、DDoS 防御机制 | 测试 NAT 场景下隧道建立和报文转发 |
| LEA-14 | 加密隧道建立超时默认 30 秒，可配置（10~120 秒） | 配置超时 10 秒，验证超时后重连 |
| LEA-15 | 加密隧道断开后自动重连，重连间隔指数退避（1s、2s、4s...最大 60s） | 手动断开隧道，验证自动重连和退避时间 |
| LEA-16 | 支持同时维护至少 2 条独立加密隧道（不同调度主站或不同安全分区） | 配置两个加密装置地址，验证两条隧道同时建立 |

#### 功能 5.2.2：加密装置状态监控（LEA-17 ~ LEA-19）

**验收标准：**

| ID | 验收内容 | 验证方法 |
|----|----------|----------|
| LEA-17 | 加密隧道状态查询接口返回每条隧道的：连接状态、协商算法、已运行时间、收发字节数 | 调用查询接口，验证返回信息完整性 |
| LEA-18 | 加密隧道状态变化（建立/断开/重连）产生 syslog 告警 | 模拟隧道断开，验证 syslog 记录 |
| LEA-19 | 加密隧道持续断开超过配置阈值（默认 5 分钟）触发运行告警（蜂鸣器或 LED） | 保持隧道断开 5 分钟以上，验证告警触发 |

### 5.3 纵向加密认证降级策略

**核心原则：加密强度只可升级不可降级。**

| 场景 | 降级行为 | 安全约束 |
|------|----------|----------|
| SM2 TLS 握手失败（服务端不支持国密） | 不允许降级至 RSA TLS | 必须双向证书认证；加密强度不低于 AES-128-GCM |
| 双向认证失败（客户端证书无效） | 连接被拒绝 | 无降级路径 |
| 协议版本协商失败（仅支持 TLS 1.1 及以下） | 连接被拒绝 | 必须 TLS 1.2+ |
| 证书链验证失败 | 连接被拒绝 | 无降级路径 |

## 6. 安全启动（Secure Boot）

### 6.1 安全启动链验证（[REVIEWED: PASS]）

#### 功能 6.1.1：BootROM 级验签（SB-01）

**User Story：**
> 作为安全管理员，我需要 RK3588 BootROM 在芯片上电后验证第一阶段引导程序的签名，以确保从芯片最底层开始建立信任链。

**验收标准：**
- 设备上电后，BootROM 读取 OTP 中烧录的根公钥哈希
- BootROM 使用 RSA-4096（或国密 SM2）验证 U-Boot SPL 的签名
- 签名验证失败时，BootROM 中止启动流程，进入安全错误状态
- U-Boot SPL 镜像必须包含 PKCS#1 v1.5 或 SM2 签名附加段
- OTP 中的根公钥哈希仅支持在设备生产阶段烧录，运行时不可被软件修改或擦除
- 验证耗时 ≤ 500ms（从芯片上电到 BootROM 完成签名验证）
- 错误状态通过板载指示灯和 UART 错误码输出，格式：`SEC_BOOT_ERR_0x<16进制码>`

#### 功能 6.1.2：U-Boot 级验签（SB-02）

**User Story：**
> 作为固件发布工程师，我需要 U-Boot 在加载 Linux 内核之前验证 FIT 镜像签名，以防止未经签名的内核或设备树被启动。

**验收标准：**
- U-Boot 使用 verified boot 机制加载 FIT 镜像
- FIT 镜像包含内核（kernel）、设备树（DTB）、initramfs（可选）及对应签名
- U-Boot 在加载 FIT 镜像前，使用内置公钥验证每个组件的哈希值和签名
- FIT 镜像签名算法支持 RSA-4096 或 SM2（由安全策略配置）
- U-Boot 公钥通过编译时嵌入或持久存储于引导分区
- 签名验证失败时中止启动，不加载任何未经验证的组件
- FIT 镜像验签耗时 ≤ 2 秒
- 支持 FIT 镜像中配置多个签名（密钥轮换场景），任一签名通过即可

#### 功能 6.1.3：内核级完整性验证（SB-03）

**User Story：**
> 作为安全管理员，我需要 Linux 内核在挂载根文件系统前，通过 dm-verity 验证根文件系统的完整性。

**验收标准：**
- 根文件系统分区启用 dm-verity 内核模块保护
- dm-verity 哈希树存储在独立分区或元数据区域，与根文件系统物理隔离
- dm-verity 根哈希由内核启动参数传递，与签名明文一同内嵌于 FIT 镜像
- dm-verity 验证模式设置为 `restart_on_corruption`（检测到篡改时自动重启）
- 哈希树算法使用 SHA-256 或 SM3（由安全策略配置）
- 每次读取数据块时进行实时哈希比对，检测到不一致时按配置策略处理
- dm-verity 对正常 I/O 的性能影响 ≤ 5%
- /etc、/usr、/lib 等关键系统目录必须纳入 dm-verity 保护范围
- /var、/etc/mupc/conf.d 不纳入 dm-verity，采用运行时完整性监控

#### 功能 6.1.4：分区完整性校验（SB-04）

**验收标准：**
- 启动分区（boot）、恢复分区（recovery）在挂载前进行完整哈希校验
- 校验算法使用 SHA-256 或 SM3
- 分区哈希值存储在已验证的 FIT 镜像内或签名元数据区
- 校验失败时拒绝挂载并记录告警日志

### 6.2 系统镜像完整性校验（[REVIEWED: PASS]）

#### 功能 6.2.1：运行时完整性度量（SB-13）

**User Story：**
> 作为安全管理员，我需要系统在运行过程中周期性地检查关键文件与分区的完整性。

**验收标准：**
- 系统启动完成后，周期性（默认每 60 秒，可配置）校验 dm-verity 保护区域外的关键文件
- 校验文件清单包含：/etc/shadow、关键二进制文件、安全策略配置文件
- 校验算法：SM3 或 SHA-256
- 检测到完整性违反时立即输出告警日志并通过安全监控通道上报
- 校验结果记录到安全审计日志
- 校验过程 CPU 占用率 ≤ 2%（RK3588 A76 核心）

#### 功能 6.2.2：系统更新后的完整性自检

**验收标准：**
- 每次固件更新完成后，设备在启动阶段自动执行完整性全检
- 全检范围：BootROM 签名验证状态、U-Boot FIT 验签状态、dm-verity 哈希树一致性
- 全检失败时自动触发回滚机制恢复至更新前版本
- 全检结果通过 web-api 状态接口上报

### 6.3 启动密钥管理（[REVIEWED: PASS]）

#### 功能 6.3.1：密钥生成（SB-05）

**验收标准：**
- 支持生成 RSA-4096 或 SM2 密钥对
- 密钥生成必须使用 RK3588 TRNG
- 输出：私钥（PEM 加密存储，AES-256-GCM）、公钥（DER/PEM）、公钥哈希（SHA-256 用于 OTP）
- 输出密钥清单文件，包含密钥用途、算法、生成时间、指纹
- 私钥密码强度：不少于 16 位，含大小写字母、数字、特殊字符

#### 功能 6.3.2：密钥存储

**验收标准：**
- 私钥以加密形式存储，生产环境私钥存储于离线 HSM
- 开发测试私钥：AES-256-GCM 加密，密码由密钥管理系统管理
- OTP 中公钥哈希一经烧录后不可被软件读取或篡改（SB-06）
- 设备不存储任何私钥
- 密钥文件访问权限严格限制

#### 功能 6.3.3：密钥轮换（SB-07）

**验收标准：**
- 密钥轮换支持两种模式：
  - 模式 A（物理更换）：出厂前或返厂时重新烧录 OTP
  - 模式 B（代码内多密钥）：U-Boot 和 FIT 镜像中嵌入新旧两个公钥，过渡期内均受信任
- 密钥轮换流程：生成新密钥对 → 重新签名固件 → 发布含新公钥固件 → 过渡期后吊销旧公钥
- 密钥轮换记录完整写入安全审计日志
- 每年至少进行一次计划性密钥轮换
- 轮换期间设备不应出现非计划停机

#### 功能 6.3.4：密钥吊销（SB-15）

**验收标准：**
- 通过固件更新方式颁发密钥吊销清单（Revocation List）
- 吊销清单由当前有效私钥签名
- U-Boot 验签时检查签名公钥指纹是否在吊销清单中
- 被吊销公钥签名的固件将被拒绝启动
- 吊销操作不可逆

### 6.4 签名与验签流程（[REVIEWED: PASS]）

#### 功能 6.4.1：固件签名工具链（SB-14）

**验收标准：**
- 签名工具支持镜像类型：U-Boot SPL、U-Boot ITB、FIT（kernel+DTB+initramfs+dm-verity root hash）、根文件系统
- 签名算法：RSA-4096 或 SM2
- 哈希算法：SHA-256 或 SM3
- 集成于 CI/CD 构建流水线（Jenkins/GitLab CI）
- 签名过程记录日志：签名镜像文件名、签名时间、密钥指纹、签名人身份

#### 功能 6.4.2：验签流程（SB-04）

**验收标准：**
- 验签顺序：BootROM → U-Boot SPL → U-Boot → FIT (kernel/DTB) → dm-verity root hash
- 每一级验签通过后方可释放下一级执行权
- 任何一级验签失败：中止启动、输出错误码、不执行未经验签代码
- 验签过程不依赖网络连接
- 整体安全启动时间 ≤ 15 秒（从上电到系统就绪）

### 6.5 启动失败处理与恢复机制（[REVIEWED: PASS]）

#### 功能 6.5.1：安全错误状态

**验收标准：**
- 验签失败后进入 SECURE_BOOT_FAILURE 状态
- 错误状态指示：板载指示灯 1Hz 双闪、UART 输出 `SECURE_BOOT_FAIL: <stage>: <error_code>`
- 错误码明确标识失败阶段和原因
- 错误数据持久化至 eMMC 专用分区
- U-Boot 阶段失败时可降级至恢复控制台（需物理触发，不提供加载未签名固件能力）

#### 功能 6.5.2：恢复模式（SB-09）

**验收标准：**
- 恢复模式触发条件：物理操作（专用恢复按钮）+ 安全启动失败
- 恢复分区经过独立签名验证（使用恢复专用密钥）
- 恢复模式功能：从安全 OTA 下载带签名修复固件 → 验签 → 写入主分区 → 重启全链验签
- 恢复模式不提供 shell 访问或加载任意代码的能力
- 恢复操作全过程记录到安全审计日志

#### 功能 6.5.3：安全回滚保护（SB-08）

**验收标准：**
- 每次固件更新时，新固件版本号（含防回滚计数器值）写入 OTP
- U-Boot 检查镜像内嵌的防回滚计数器值
- 计数器值低于 OTP 记录值时拒绝启动
- 计数器单调递增，不可重置或递减
- 固件更新失败时计数器不受影响（允许回退至前一版本）
- 支持手动设置防回滚计数器（需物理接触 + 授权工具）
- 计数器溢出时设备需返厂更换硬件

## 12. 边界条件与异常处理

### 12.1 签名验证失败

| 场景 | 行为 | 恢复方式 |
|------|------|----------|
| BootROM 验签 U-Boot SPL 失败 | 中止启动，ERR_BOOTROM_SIG_FAIL | 恢复模式刷写正确签名固件 |
| U-Boot 验签 FIT 镜像失败 | 中止启动，ERR_UBOOT_FIT_SIG_FAIL | 恢复模式刷写正确签名固件 |
| FIT 中内核签名存在但 DTB 签名缺失 | 拒绝加载 DTB，中止启动 | 重新构建并签名完整 FIT |
| dm-verity 根哈希与内核参数不匹配 | Kernel Panic | 恢复模式刷写正确根文件系统 |

### 12.2 加密装置故障

| 场景 | 行为 | 恢复策略 |
|------|------|----------|
| 加密装置完全不可用 | 切断加密通道，10 秒内 CRITICAL 告警 | 尝试备用加密装置，每 30 秒重试 |
| 隧道间歇性断开 | WARNING 告警，自动重连 | 指数退避重连，最大 60 秒 |
| 加密装置性能不足 | WARNING 告警（延迟超 2 倍基线） | 仅告警通知 |
| 配置不匹配 | ERROR 告警，记录协商失败原因 | 管理员修复后手动重试 |

### 12.3 证书异常

| 场景 | 行为 | 恢复策略 |
|------|------|----------|
| 证书已过期 | 拒绝新连接，CRITICAL 告警 | 导入新证书后自动生效 |
| 证书链不完整 | 加载失败，ERROR 告警 | 导入完整证书链 |
| 私钥与证书不匹配 | 加载失败，CRITICAL 告警 | 导入匹配的正确私钥 |
| CRL 查询失败 | 允许继续连接，WARNING 告警 | 重新获取 CRL |
| 私钥文件权限错误 | 加载失败，ERROR 告警 | 修正权限（600）后自动加载 |

### 12.4 密钥泄露场景

| 泄露范围 | 影响 | 处置措施 |
|----------|------|----------|
| 生产签名私钥泄露 | 攻击者可签名恶意固件 | 立即吊销公钥，更换密钥对，OTA 更新吊销清单 |
| 开发测试私钥泄露 | 开发环境固件可被伪造 | 吊销测试密钥，重新生成 |
| 恢复模式私钥泄露 | 攻击者可制作恶意恢复固件 | 设备返厂更新恢复密钥 |

### 12.5 回滚攻击防护

| 攻击方式 | 防护机制 |
|----------|----------|
| 直接烧录旧版本固件 | 防回滚计数器 |
| 绕过签名直接写入 Flash | BootROM 验签 + 分区完整性校验 |
| 修改防回滚计数器 | OTP 一次性编程特性，仅可增加不可减少 |
| 替换 dm-verity 哈希树 | 哈希表根哈希由 FIT 镜像签名保护 |

### 12.6 其他边界条件

| 场景 | 行为 |
|------|------|
| 磁盘空间不足导致审计日志无法写入 | 保留最后 100MB 日志，删除最旧日志，CRITICAL 告警 |
| 系统时间错误导致证书验证异常 | 记录系统时间，偏差超 24 小时触发 WARNING 告警 |
| 加密引擎初始化失败 | 系统启动失败，CRITICAL 告警，禁止以无加密模式运行 |
