## 1. 产品概述

### 1.1 产品定位

MUPC 微电网特种调控装置通信管理模块是"异构双核心模块主控架构"中的**非实时处理核心**（大脑），与"实时控制核心模块"（小脑）协同工作。

数据处理与存储模块（data-processing）作为"大脑"的核心数据处理组件，**承担以下职责**：

- **数据采集**：从 intercore 模块接收实时控制模块的高频采样数据，汇聚为统一数据源
- **遥测上送**：以 >= 1Hz 频率将遥测数据通过消息总线分发给消费者（gateway、strategy-engine 等）
- **故障录波**：检测故障条件时录制故障前后波形，支持波形数据的存储、查询、导出和北向上报
- **历史数据存储**：持久化存储周期性电气量数据、电池运行数据、告警日志和系统事件记录
- **设备台账管理**：管理管辖范围内所有设备的资产信息、铭牌参数、维护记录，支持北向上送
- **数据生命周期管理**：按配置策略自动清理过期数据，保障存储空间合理使用

### 1.2 目标平台

| 项目 | 要求 |
|------|------|
| 操作系统 | Linux (openEuler 22.03+) |
| 硬件 | RK3588，存储介质：eMMC（默认 64GB）+ TF 卡扩展槽 |
| 编程语言 | Rust 1.75+ |
| 异步运行时 | Tokio 1.x |
| 数据库 | SQLite (rusqlite) |
| 消息总线 | tokio::sync::mpsc |

### 1.3 与上下游模块的关系

```
实时控制模块
     │
     ▼ (TCP/RJ45 高频数据帧)
intercore
     │
     ▼ (DataCollector 接收)
data-processing
     ├── HighFrequencyTelemetry ──→ 消息总线(telemetry.high_freq) ──→ gateway(北向上送)
     │                                                               └── strategy-engine(策略决策)
     ├── FaultRecorder ──→ 消息总线(telemetry.fault) ──→ gateway(北向上送)
     │                    ├── 波形文件(.wave) → 文件系统
     │                    └── 故障元数据 → SQLite
     ├── 历史数据存储 ──→ SQLite（电气量、电池数据、告警日志、事件记录）
     └── 设备台账管理 ──→ SQLite（资产信息、铭牌参数、维护记录）
```

| 上游模块 | 数据流向 | 说明 |
|----------|----------|------|
| intercore | → data-processing | TCP/RJ45 高频采样数据（10ms 间隔瞬时值帧） |
| rs485-plugin / hplc-plugin | → data-processing | 南向设备数据采集（Phase 2+ 预留） |

| 下游模块 | 数据流向 | 说明 |
|----------|----------|------|
| data-processing → gateway | 遥测、故障、台账上送 | 通过消息总线 + 直接调用 |
| data-processing → strategy-engine | 遥测数据 | 通过消息总线 |
| data-processing → web-api | 历史数据、台账、告警查询 | REST API 查询接口 |

### 1.4 模块依赖

```
data-processing
  ├── core (message_bus)
  ├── intercore (数据来源)
  └── device-trait (设备抽象)
```

## 2. 遥测数据采集与上送（≥1Hz）

### 2.1 DataCollector — 数据采集

**职责**：从 intercore 模块接收实时控制模块的数据，汇聚为统一数据源。

**接口定义**：

```rust
pub trait DataCollector {
    async fn start(&mut self) -> Result<(), DataProcessingError>;
    async fn stop(&mut self) -> Result<(), DataProcessingError>;
    fn get_latest_data(&self) -> Option<TelemetryData>;
}
```

**数据来源**：intercore 模块（TCP/RJ45）

**采集数据类型**：

| 数据类型 | 说明 | 单位 |
|----------|------|------|
| battery_soc | 电池荷电状态 | % |
| battery_power | 电池充放电功率 | kW |
| pv_output | 光伏出力 | kW |
| load_power | 负荷功率 | kW |
| grid_power | 电网功率（有功） | kW |
| transformer_load | 变压器负载率 | % |

**数据包内容**：电气量、电池数据、设备状态、UTC 时间戳

**验收标准 [DP-DC]**：

| ID | 验收条件 | 验证方法 |
|----|----------|----------|
| DP-DC-01 | DataCollector 能从 intercore 接收数据 | 单元测试 |
| DP-DC-02 | get_latest_data() 返回最新的有效数据，无数据时返回 None | 单元测试 |
| DP-DC-03 | start()/stop() 可多次调用，不产生重复资源分配 | 单元测试 |

### 2.2 HighFrequencyTelemetry — 高频遥测

**职责**：以 >= 1Hz 频率上报遥测数据到消息总线。

**接口定义**：

```rust
pub trait HighFrequencyTelemetry {
    async fn start(&mut self) -> Result<(), DataProcessingError>;
    async fn stop(&mut self) -> Result<(), DataProcessingError>;
    fn get_current_value(&self, point: &str) -> Option<f64>;
}
```

**上报频率**：1Hz（可配置，动态调整采集周期）

**内存缓冲**：保留最近 1 分钟数据（60 条记录）

**消息主题**：

| 主题 | 内容 |
|------|------|
| `telemetry.high_freq` | 高频遥测数据 |
| `strategy.decision` | 策略决策结果 |

**验收标准 [DP-HF]**：

| ID | 验收条件 | 验证方法 |
|----|----------|----------|
| DP-HF-01 | HighFrequencyTelemetry 以 1Hz 上报数据 | 单元测试 |
| DP-HF-02 | 数据在内存中缓冲 60 条 | 单元测试 |
| DP-HF-03 | 支持动态调整采集周期 | 单元测试 |

### 2.3 DataReporter — 数据上报

**职责**：通过消息总线将处理后的数据发送给消费者（gateway、strategy-engine 等）。

**接口定义**：

```rust
pub trait DataReporter {
    async fn report(&self, data: TelemetryData) -> Result<(), DataProcessingError>;
    fn subscribe(&mut self, topic: &str) -> Result<(), DataProcessingError>;
}
```

**消息主题**：

| 主题 | 生产者 | 消费者 | 说明 |
|------|--------|--------|------|
| `telemetry.high_freq` | DataCollector | strategy-engine, gateway | 高频遥测数据 |
| `telemetry.fault` | FaultRecorder | gateway | 故障事件 |
| `strategy.command` | strategy-engine | intercore | 控制指令 |

**验收标准 [DP-DR]**：

| ID | 验收条件 | 验证方法 |
|----|----------|----------|
| DP-DR-01 | DataReporter 通过消息总线发送数据 | 单元测试 |
| DP-DR-02 | 支持订阅指定主题，收到消息时触发回调 | 单元测试 |

## 3. 故障录波（波形采样、触发条件、COMTRADE导出、上报）

**[REVIEWED: PASS]**

### 3.1 产品背景与核心价值

MUPC Phase 3A 已实现 `FaultRecorder` 接口和 `FaultRecorderImpl` 的 SQLite 故障事件记录功能，但该实现仅记录故障事件的**元数据**（故障类型、触发条件阈值），未记录故障前后的**波形数据**（高频率采样的电气量时序数据）。

**解决的核心问题**：

| 问题 | 影响 | 解决方案 |
|------|------|----------|
| 故障时仅有事件记录，无波形数据可分析 | 运维人员无法定位故障根因 | 实现故障前后波形采样与存储 |
| 波形数据离线存储，不支持远程获取 | 故障分析依赖现场取数 | 实现波形数据北向上报（IEC 104 / MQTT） |
| 录波参数不可配置 | 无法适应不同工况场景 | 实现可配置的触发条件和采样参数 |
| 波形数据格式封闭 | 无法导入第三方分析工具 | 支持 COMTRADE / CSV 格式导出 |

**核心价值**：

- **故障根因分析**：通过故障前后的波形数据，准确定位过压、欠压、谐波畸变、短路等故障的起止时刻和演变过程
- **电能质量追溯**：为电压暂降、暂升、中断等电能质量事件提供波形证据
- **设备状态评估**：通过波形趋势分析断路器、变压器等设备的运行健康状况
- **事故调查取证**：满足电力系统事故调查对录波数据的合规性要求（保存期限 >= 30 天）

### 3.2 故障触发条件配置

#### 3.2.1 功能描述

支持以下触发条件的独立配置，每个条件包含启用开关、阈值和回差（滞回区间）。

| 触发条件 | 参数 | 默认值 | 单位 | 说明 |
|----------|------|--------|------|------|
| 过压触发 | 电压越上限阈值 | 420.0 | V | 相电压有效值超过阈值触发 |
| 过压触发 | 回差 | 10.0 | V | 电压回落到 阈值-回差 以下才解除触发 |
| 欠压触发 | 电压越下限阈值 | 200.0 | V | 相电压有效值低于阈值触发 |
| 欠压触发 | 回差 | 10.0 | V | 电压回升到 阈值+回差 以上才解除触发 |
| 过流触发 | 电流越上限阈值 | 150.0 | A | 相电流有效值超过阈值触发 |
| 过流触发 | 回差 | 5.0 | A | 电流回落到 阈值-回差 以下才解除触发 |
| 短路触发 | 电流突变量阈值 | 500.0 | A | 电流瞬时值超过阈值触发（不判有效值） |
| 频率越限触发 | 频率上限 | 50.5 | Hz | 频率超过上限触发 |
| 频率越限触发 | 频率下限 | 49.5 | Hz | 频率低于下限触发 |
| 频率越限触发 | 回差 | 0.1 | Hz | 频率回到范围内才解除触发 |
| 零序过流触发 | 零序电流阈值 | 20.0 | A | 零序电流超过阈值触发（接地检测） |

#### 3.2.2 验收标准 [TRG]

| ID | 验收条件 | 验证方法 |
|----|----------|----------|
| TRG-01 | 所有 6 种触发条件可独立启用/禁用 | 单元测试：逐个设置启用/禁用状态，确认触发逻辑生效/失效 |
| TRG-02 | 所有阈值参数可配置，配置即时生效 | 单元测试：修改阈值后，输入低于新阈值的信号不应触发，输入高于新阈值的信号应触发 |
| TRG-03 | 回差机制正确：触发后需信号回到阈值 +/- 回差范围内才解除 | 单元测试：设置回差后，触发信号短暂回落到阈值和阈值 +/- 回差之间，确认不解除触发 |
| TRG-04 | 多个触发条件同时满足时，每个故障事件记录所有触发条件 | 集成测试：输入同时触发过压和过频的信号，故障记录中两个条件均有标记 |

### 3.3 故障前后波形采样

#### 3.3.1 功能描述

故障触发时，录制触发点前后特定时间窗口内的高频采样数据。

**采样参数配置**：

| 参数 | 取值范围 | 默认值 | 说明 |
|------|----------|--------|------|
| 采样率 | 1kHz, 2kHz, 4kHz, 8kHz, 16kHz | 4kHz | 每通道每秒采样点数 |
| 故障前记录时长 | 40ms ~ 1000ms | 200ms | 触发时刻之前的采样记录长度 |
| 故障后记录时长 | 40ms ~ 5000ms | 1000ms | 触发时刻之后的采样记录长度 |
| 总记录时长 | 故障前 + 故障后 | 1200ms | 一次录波的总时长 |

**采样通道**：

| 通道组 | 通道数 | 内容 |
|--------|--------|------|
| 三相电压 | 3 | Ua, Ub, Uc 瞬时值 (V) |
| 三相电流 | 3 | Ia, Ib, Ic 瞬时值 (A) |
| 零序电压 | 1 | U0 瞬时值 (V) |
| 零序电流 | 1 | I0 瞬时值 (A) |
| 有功功率 | 1 | P 瞬时值 (kW) |
| 无功功率 | 1 | Q 瞬时值 (kVar) |
| 频率 | 1 | f 瞬时值 (Hz) |

**可配置通道选择**：用户可选择启用/禁用一个或多个通道组，节省存储空间。

**循环录波缓冲**：
- 设备启动后持续将高频采样数据写入环形缓冲区
- 缓冲区长度 = 故障前记录时长对应的采样点数（如 4kHz x 200ms = 800 点）
- 故障触发时，将缓冲区数据 + 持续写入的故障后数据打包为一次完整的波形记录

**双缓冲区机制**：
- 一次录波完成后立即切换到第二个缓冲区，保证连续故障不丢失波形数据
- 第一个缓冲区的数据在保存完成前不被覆盖

#### 3.3.2 验收标准 [SMP]

| ID | 验收条件 | 验证方法 |
|----|----------|----------|
| SMP-01 | 采样率可在 1kHz ~ 16kHz 范围内按指定档位配置 | 单元测试：设置不同采样率，确认采集的波形数据点间隔符合设定值 |
| SMP-02 | 故障前记录时长可在 40ms ~ 1000ms 范围内配置 | 单元测试：设置故障前时长，触发后确认缓冲区数据点数 = 采样率 x 时长 |
| SMP-03 | 故障后记录时长可在 40ms ~ 5000ms 范围内配置 | 单元测试：设置故障后时长，触发后确认录波数据总点数 = 采样率 x (前+后时长) |
| SMP-04 | 所有 10 个通道的数据同步录波 | 集成测试：输入已知波形信号，触发后确认 10 个通道各有完整数据 |
| SMP-05 | 环形缓冲区在稳态时不间断更新，不阻塞采数流程 | 集成测试：连续运行 24 小时，录波触发时数据完整无缺口 |
| SMP-06 | 双缓冲区机制在连续触发故障时，两次录波数据均完整保存 | 集成测试：在 500ms 内连续触发两次故障，确认两次录波数据均正确 |
| SMP-07 | 录波启动延迟 <= 1 个采样周期 | 单元测试：从故障条件满足到第一个采样点写入波形记录的时间差 <= 1/采样率 |

### 3.4 波形数据存储

#### 3.4.1 功能描述

**存储结构**：

波形数据与故障事件元数据分开存储：

| 存储类型 | 存储内容 | 存储引擎 | 说明 |
|----------|----------|----------|------|
| 元数据 | 故障事件记录（类型、时间、触发条件值） | SQLite | 已有 Phase 3A 实现，需扩展字段 |
| 波形数据 | 二进制格式的采样数据 | 文件系统 | 新增，按故障事件 ID 命名文件 |

**SQLite 扩展字段**（在现有 `fault_records` 表基础上增加）：

| 字段 | 类型 | 说明 |
|------|------|------|
| waveform_path | TEXT | 波形数据文件的路径（相对路径，相对于录波数据目录） |
| sample_rate | INTEGER | 本次录波的采样率（Hz） |
| pre_trigger_ms | INTEGER | 故障前记录时长（ms） |
| post_trigger_ms | INTEGER | 故障后记录时长（ms） |
| channel_mask | INTEGER | 录波通道的位掩码，标识启用的通道 |
| waveform_size | INTEGER | 波形数据文件大小（字节） |

**波形文件格式**（二进制紧凑格式）：

```
+------------------------------+
|  Header (64 bytes)           |
+------------------------------+
|  Channel 0 samples (N x f64) |
|  Channel 1 samples (N x f64) |
|  ...                         |
|  Channel M samples (N x f64) |
+------------------------------+
|  Footer (8 bytes): checksum  |
+------------------------------+
```

Header 格式：

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 4B | magic | 魔数 `WAVE` (0x57415645) |
| 4 | 2B | version | 文件格式版本号 (v1 = 0x0001) |
| 6 | 2B | channel_count | 录波通道数 (<=10) |
| 8 | 8B | sample_count | 每通道样本数 |
| 16 | 8B | sample_rate | 采样率 (Hz) |
| 24 | 8B | trigger_timestamp | 触发时刻的 unix 时间戳 (ms) |
| 32 | 8B | trigger_offset | 触发点在样本序列中的偏移量（第几个样本） |
| 40 | 8B | pre_trigger_nsamples | 故障前样本数 |
| 48 | 8B | post_trigger_nsamples | 故障后样本数 |
| 56 | 4B | channel_mask | 通道启用位掩码 |
| 60 | 4B | reserved | 保留 |

**数据目录布局**：

```
/data/mupc/waveforms/
+-- index/
|   +-- fault_records.db
+-- recordings/
    +-- 2026/
        +-- 05/
            +-- 20260529_143022_001.wave
            +-- 20260529_143022_002.wave
```

文件名格式：`YYYYMMDD_HHMMSS_seq.wave`

#### 3.4.2 存储容量管理

**循环覆盖策略**：

| 策略参数 | 默认值 | 说明 |
|----------|--------|------|
| 单次录波存储上限 | 10 MB | 单个波形文件大小上限。超过上限时截断 |
| 总存储空间上限 | 2 GB | 波形数据目录占用磁盘空间上限 |
| 保留期限 | 30 天 | 超过此期限的波形文件可被自动删除 |
| 空余空间阈值 | 500 MB | 磁盘空余空间低于此值时，优先删除最旧的波形文件 |
| 单日录波次数上限 | 1000 次 | 每自然日录波次数超过此值时停止录波 |

**覆盖执行顺序**：
1. 先删除超过 30 天保留期限的波形文件
2. 若仍超出总存储空间上限，继续删除最旧的波形文件（无论是否过期）
3. 若磁盘空余空间仍低于 500MB，继续删除最旧波形文件
4. 每次覆盖操作删除的波形文件同时删除对应的故障事件记录中的 `waveform_path` 引用

#### 3.4.3 验收标准 [STO]

| ID | 验收条件 | 验证方法 |
|----|----------|----------|
| STO-01 | 故障事件元数据写入 SQLite，波形数据写入文件系统 | 集成测试：触发故障后确认 SQLite 有记录且文件存在 |
| STO-02 | 波形文件格式符合上述二进制格式定义 | 单元测试：读取写入的波形文件，解析 header 各字段与写入值一致 |
| STO-03 | 波形文件校验和验证：读取时校验 footer checksum | 单元测试：手动修改波形文件一个字节，读取时报告校验失败 |
| STO-04 | 单次录波超过 10MB 时自动截断 | 集成测试：配置长时间录波（5000ms + 16kHz），确认文件 <= 10MB |
| STO-05 | 超过保留期限（30天）的波形文件被自动清理 | 集成测试：创建过期的录波文件，触发清理后确认被删除 |

### 3.8 多通道同步录波

#### 3.8.1 功能描述

- 所有采样通道使用同一个采样时钟，确保各通道数据在时间上严格对齐
- 单次录波的数据结构中，所有通道的采样点数量相同（均为 `sample_count`）
- 第 i 个采样时刻的数据在内存中表示为 `[ch0[i], ch1[i], ..., chN[i]]`

**通道间同步要求**：

| 要求 | 指标 |
|------|------|
| 通道间时延 | <= 1 个采样周期（如 4kHz 下 <= 250us） |
| 时间戳标定 | 每个采样点的时间戳精度 <= 100us |
| 各通道采样点数 | 严格相等，偏差 = 0 |

**周期性同步校验**：
- 每秒执行一次通道同步性校验
- 校验方法：向所有通道注入同一已知信号（如 50Hz 正弦波），确认各通道数据的相位差 <= 1 度

#### 3.8.2 验收标准 [CHN]

| ID | 验收条件 | 验证方法 |
|----|----------|----------|
| CHN-01 | 所有通道的采样点数严格相同 | 单元测试：触发录波后，检查 WaveformData 中各 channel 的 Vec 长度一致 |
| CHN-02 | 通道间相位差 <= 1 度（在 50Hz 信号下） | 集成测试：输入相同的 50Hz 正弦波到所有通道，计算各通道间相位差 |
| CHN-03 | 可选择启用/禁用一个或多个通道组 | 单元测试：设置 channel_mask 只包含三相电压，确认波形数据只包含 3 个通道 |
| CHN-04 | 通道间时延 <= 1 个采样周期 | 单元测试：同一时刻采集所有通道的值，记录时间戳偏差 |

### 3.10 故障录波边界条件与异常处理

#### 3.10.1 存储空间不足

| 场景 | 行为 | 告警级别 |
|------|------|----------|
| 磁盘空余空间 < 500MB | 删除最旧波形文件直到空余空间 > 500MB，停止新录波 | 重要告警 |
| 磁盘空余空间 < 200MB | 紧急停止所有录波功能，保留核心功能运行 | 紧急告警 |
| 单次录波写入失败 | 将波形数据保留在内存缓冲区，30 秒后重试，重试 3 次放弃 | 告警 |
| 元数据写入失败（SQLite） | 当前录波整体失败，记录日志，不影响下一次录波 | 告警 |

#### 3.10.2 多故障并发

| 场景 | 行为 |
|------|------|
| 录波进行中（故障后时段）发生第二个故障 | 不中断当前录波，在第二个缓冲区启动第二次录波 |
| 两个缓冲器均满时发生第三个故障 | 丢弃当前录波中最旧的一次，释放一个缓冲区用于新的录波 |
| 同一秒内触发多次同类型故障 | 合并为一次故障事件，记录首次触发时间，后续触发更新事件状态 |
| 不同类型的故障在 100ms 内先后发生 | 作为独立事件分别录波，共享故障前重叠时段的波形数据 |

#### 3.10.3 采样数据丢失

| 场景 | 行为 |
|------|------|
| 单个采样点丢失 | 数据文件中用 `NaN` 填充缺失位置，在波形文件中标记 `data_quality=gap_detected` |
| 连续 10 个以上采样点丢失 | 中断当前录波，已录数据保留，标记 `data_quality=major_gap` |
| 所有通道同时数据丢失 | 可能为 intercore 通信中断，停止录波，发起通信重连 |
| 单个通道数据丢失 | 其他通道继续录波，缺失通道用 `NaN` 填充 |

#### 3.10.4 触发抖动处理

| 场景 | 行为 |
|------|------|
| 触发条件在临界值附近震荡 | 使用回差机制防止反复触发 |
| 同一故障条件在 1 秒内反复满足/解除 | 合并为一次故障事件，记录首次触发和最终解除时间 |
| 瞬态尖峰（< 1ms）误触发 | 触发条件判定引入 3 个连续采样点的确认窗口（防抖滤波） |

#### 3.10.5 配置异常

| 场景 | 行为 |
|------|------|
| 故障前记录时长 > 故障后记录时长 3 倍 | 拒绝配置，返回配置错误 |
| 采样率设置为不支持的值 | 四舍五入到最近的可用档位，记录日志提示 |
| 所有通道均禁用 | 拒绝配置，要求至少启用一个通道组 |
| 总记录时长 < 80ms | 拒绝配置（至少 40ms 前 + 40ms 后） |

  - 存储空间剩余 < 5% 时：触发告警"存储空间即将耗尽（critical）"，同时缩短保留期限至默认值的 50%
- 清理过程记录日志：清理数据类型、删除记录数、清理耗时、释放空间大小
- 清理任务执行超时上限为 30 分钟，超时自动终止并记录告警
- 清理任务可手动触发

### 6.3 数据导出

#### 6.3.1 功能描述

**历史数据导出**：
- 支持将查询结果导出为 CSV 格式
- 导出数据包含查询范围内的全部匹配记录
- 单次导出上限为 10 万条记录，超出时提示用户缩小查询范围

- 导出文件包含完整的字段定义
- 单次导出可包含全部设备（不受 10 万条限制）

| 需求 | 说明 |
|------|------|

## 8. 边界条件与异常处理

### 8.1 磁盘空间不足（通用）

| 磁盘使用率 | 系统行为 |
|------------|----------|
| >= 85% | 记录 WARN 级别日志 |
| >= 90% | 触发 minor 级别告警"磁盘空间即将不足" |
| >= 95% | 触发 critical 级别告警，立即执行紧急清理，停止历史数据写入 |
| >= 98% | 停止所有数据写入（含告警和事件），仅维持只读查询功能 |

### 8.2 数据写入失败（通用）

| 场景 | 处理方式 |
|------|----------|
| 单次写入超时（> 5 秒） | 放弃本次写入，记录错误日志，继续处理下一条 |
| 连续 10 次写入失败 | 触发告警"数据库写入异常"，每 5 分钟重试一次 |
| 数据库文件损坏 | 切换到降级模式，尝试修复，通知运维人员 |
| 数据库连接断开 | 自动重连，最多重试 5 次（间隔 1s、2s、4s、8s、16s），失败后触发告警 |

### 8.3 系统意外断电

- 数据写入采用事务保证单条写入的原子性
- 断电恢复后，未完成的事务自动回滚，不产生脏数据
- 系统启动时自动检查数据完整性
- 内存缓冲的数据在系统重启后丢失，但系统功能不中断

### 8.4 时间同步异常

- 所有数据记录的时间戳以系统时间为准
- 系统支持 NTP 时间同步
- 时间发生跳变（如 NTP 同步校正）时，不产生重复数据或数据空洞
- 未同步时数据标记 `time_quality=unsynchronized`
