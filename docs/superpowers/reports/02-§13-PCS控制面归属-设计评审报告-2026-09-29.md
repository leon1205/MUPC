## 4. 问题清单

> 归属分类口径：**设计缺陷** = §13 作为合同自身不完整/不自洽/依据不实；**实现未兑现设计** = 设计已给可达落点与判据，实现没做；**可接受的登记项** = 已进台账且处置路径明确、不阻塞本合同成立。

### P-1（阻断）写审计"须新增的落地项"在 §13 内**无任何可达落点**，且 §13.5.3 与 §13.9 直接矛盾 —— 设计缺陷（兼实现未兑现设计）

**条款**：§13.5.3 末句（设计文档第 3417 行）
> 「**须新增的落地项**：每次写序列投一条 `events`（调用方 token / 时刻 / 寄存器+值 / **回读值**），复用既有 `storage.events` + `AlertFeed`；回读失败 ⇒ 事件标记"未确认"（不阻断控制）。」

**§13.9 同时冻结了唯一出口**（设计文档第 3475 行）：
> 「| `StationSink`（4 方法） | **无**（`PcsHandle` 只是多一个调用方） |」

**双证据（代码）**：

1. `PcsHandle` 在进程内的**唯一出口**就是 `StationSink`，而该 trait 恰为 4 方法且**无任何事件/审计方法**：
   - `mupc-southd/src/scheduler.rs:49-76`：`on_grid_package` / `on_station_telemetry` / `on_battery_soc` / `on_station_offline`（4 条，无第 5 条）；
   - `PcsHandle::new(cfg, bus, sink)` 的 sink 即 `Arc<dyn StationSink>`；`tick_once` 只投 `on_station_telemetry` / `on_station_offline`（`collect.rs:245-275`），与 PRD N-1/N-2（不投 `on_battery_soc`/`on_grid_package`）一致。
2. §13.5.3 要求"复用 `AlertFeed`"，而 `AlertFeed` **定义在 `mupc-core-bin`**（`crates/mupc-core-bin/src/alert_feed.rs:70`），`mupc-southd` 的 `Cargo.toml [dependencies]` **不依赖 `mupc-core-bin`**（依赖只有 serde/tokio/tracing/thiserror/async-trait/chrono/rs485-plugin/mupc-data-processing）—— 且该依赖方向**不可能成立**（`mupc-core-bin` 依赖 `mupc-southd`，反向即成环）。⇒ 「复用 `AlertFeed`」在写入代码所在的 crate 内**结构性不可达**。
3. 实现侧确认为零落地：`grep -rn "audit\|Audit" mupc/crates/mupc-southd/src/` 与 `grep -rn "record_event\|AlertFeed" mupc/crates/mupc-southd/src/` **均为空**。

**归属判定**（本任务的指定问题）：
- **设计缺陷（主）**：合同声明"须新增"却把落点指向一个按本合同又**必须零改动**的 4 方法 trait，并且指向一个**依赖方向上不可达**的类型 ⇒ 该"落地项"按 §13 原文**不可能被实施**。合同自相矛盾。
- **实现未兑现设计（次）**：即便按最宽松读法（把审计事件搭 `on_station_telemetry` 的 `is_event=true` 点发出），实现也未做；且 `(metric: String, value: f64, is_event: bool)` 三元组承载不了"调用方 token + 寄存器 + 值 + 回读值"这四要素。
- **这不是"可接受的登记项"**：`docs/technical-debt.md` §6.13 U-75（P1）如实登记了"未落地"，但**登记的是"实现缺口"，未指出"落点不可达"这一设计问题**；PRD N-4（v1.14）同样只写"尚未落地，登记为待办"。⇒ 台账与 PRD 都把一个**设计层矛盾**记成了**实现层待办**。

**依据**：本设计合同自列条款（§13.5.3）与自身冻结条款（§13.9 `StationSink` 行）互斥；PRD §9.6.2 N-4 的"独占由单一所有者 + 4 条受限写入口保证"在缺审计时**不可验证**（"谁/何时/写了什么/回读值"无落库面）；`design_reviewer` 审查清单「完整性」与「安全性」项。

### P-2（阻断）该"须新增的落地项"未进入 §13.10 的任一分期，且无验收判据 —— 设计缺陷

**条款**：§13.10 迁移分期只列 **T1–T4**（设计文档第 3500-3507 行），四条**均未提及写审计**：

| 阶段 | 是否含写审计 |
|---|---|
| T1（rs485-plugin R-1/R-2/R-3 + `StationBus::write_single`） | 否 |
| T2（`southd` pcs/ + 配置） | 否 |
| T3（core-bin 原子换型 + 校验规则） | 否 |
| T4（删 intercore PCS 面 + 跨文档回写） | 否 |

**同时**：§13.5.3 未给判据 —— 无事件字段定义（"调用方 token"的**来源与取值域**未定义：是 `enum`？是字符串？是谁赋值？）、无事件名/表列映射、无测试或验收条目。对照 §13 对**其他**项的一贯要求（如 §13.4 的"判离线复位"给了 fail-open 后果论证、§13.6 R-2 给了"停机写 500=0 是安全动作，必须校验回显"的理由），本项是 §13 内**唯一一条既无判据又未分期**的"须新增"。

### P-3（须改）§13.8 规则表与实现不同步且不自洽 —— 设计缺陷（合同准确性）

**双证据**：

1. **P-1 的判据对象已不存在**。§13.8（设计文档第 3464 行）：「`south_pcs.enabled` ⇒ **禁止** `intercore.transport == "modbus_rtu"`」。但 `intercore.transport` 是 `String` 且全仓**已无 `modbus_rtu` 档**（`core_config.rs:249-253`；部署 YAML 只允许 `tcp`），真实拦截点是 `startup.rs:1396-1410` 的 `match config.intercore.transport.as_str() { "tcp" => …, other => Err(...) }` —— **无条件拦截、与 `south_pcs.enabled` 无关**，且落点**不在 `core_config.rs`**（§13.8 表头声称"落 `core_config.rs`"）。

**依据**：`core_config.rs:249-253,740,1112-1145`；`startup.rs:1396-1410`；`config.rs:307,334,426`；`design_reviewer` 审查清单「规范性」。
