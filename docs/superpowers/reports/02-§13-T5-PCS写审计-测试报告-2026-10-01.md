## 3. F2 缺口：复现、判断与处置

### 3.1 复现（取证）

**改坏点**：`mupc/crates/mupc-core-bin/src/startup.rs:285` 的 IEC104 `p_set` 生产调用点，首参 `WriteToken::Iec104` → `WriteToken::Strategy`。

**结果**：`cargo test -p mupc-core-bin -p mupc-southd -p mupc-strategy-engine -j 2` ⇒ **0 failed**（433 + 253 + 8 + … 全绿）。⇒ 缺口**证实存在**。

**还原取证**：`cp` 备份还原后 `sha256sum` = `5a730cf77ca0634d8e937330c9aa9b6193e293fde525c942b2da2dbf736c8a9d`（与改坏前逐字一致）；`diff` 为空；`git diff --stat` 无输出。（全程**未**使用 `git checkout --` / `git restore`。）

### 3.2 判断

**缺口性质**：既有 token 用例（`t5_audit_exactly_one_event_per_entry_with_token`）把 token **作为入参**传给 `PcsHandle` 再断言原样返回 —— 它只证明 **`PcsHandle` 的转发无损**，对「调用方是否如实传」**零判别力**。而 §13.5.3 明写 token 取值「由**调用点**传入；**不得**从调用栈 / 全局态推断」—— 该条款此前**无真判据**，属本项目反复中招的「零判别力断言」形态。**结论：补，且必须补。**

### 3.3 处置：新增 3 条调用点 token 判据（覆盖 4 个生产调用点中的 3 个）

| 生产调用点 | 应有 token | 新增用例 | 判据手法 |
|---|---|---|---|
| `startup.rs` IEC104 `p_set` | `Iec104` | **`t5_iec104_p_set_is_audited_with_iec104_token`**（mupc-core-bin） | 构造真 `StrategyCommandHandler` → `handle_command(PowerRegulation, p_set)` → sink 边界断言 token |
| `interlock.rs` `impl InterlockPort for Arc<PcsHandle>` | `Interlock` | **`t5_interlock_stop_adapter_uses_interlock_token`**（mupc-core-bin） | 走真适配器 `<Arc<PcsHandle> as InterlockPort>::stop()` → sink 边界断言 token |
| `ai_integration.rs` `dispatch_phase_pq`（台区储能 = 唯一默认下发引擎） | `Strategy` | **`t5_tai_storage_dispatch_is_audited_with_strategy_token`**（mupc-strategy-engine） | `run_fallback_strategies`（fresh 数据）→ 真生产路径 → sink 边界断言 token |
| `ai_integration.rs` `dispatch_ai_decision` / `dispatch_robust_action` | `Ai` | **未补（不可测，如实登记）** | 该两处仅由 `dispatch_ai_decision` 调用，AI 停用期模型不加载 ⇒ 恒 `Err(ModelNotLoaded)`，**当前不可达**（§13.5.3 自认"停用期不可达但代码真实存在"）。无判据可设 |

每条新增用例均已做「改坏 ⇒ 红 ⇒ 还原 ⇒ 绿」的逐点验证（见 §4-D）。

**F2 残余（登记，不阻塞）**：`tests/pcs_e2e.rs`、`pcs/collect.rs`、`scheduler.rs` 三处测试 sink 仍**写而不读** `audits` 字段（`5233289` 已删其访问器，字段与捕获链保留，rustc/clippy 不报）。属**测试代码冗余**，非产品缺陷；未在本笔清理（改动面与 QA 职责无关，且清理会扩大 diff 面）。
