## 3. 两项指定分歧的裁定

### 3.1 分歧 (1)：原 P-1 的定性「维持 / 采纳」→ **采纳提交方的修正**（即原定性不成立）

**裁定：采纳。** 原报告 P-1 的核心定性（"在 §13 内**无任何可达落点**"、"**结构性不可实施**"）**经本次实测不能成立**，理由逐条：

1. **通道确为可达**：`PcsHandle` 持有 `Arc<dyn StationSink>`，而**该 trait 的第 2 方法就是事件方法** —— `on_station_telemetry` 的 `is_event == true` 分支在 `core-bin` 侧落 `record_event`，后者**同时** `events.insert(&ev)` 与 `alert_feed.push_system_alert(level, message)`（`startup.rs:826-840`、`:947-962`）。⇒ §13.5.3 原文的"投一条 `events`…复用既有 `storage.events` + `AlertFeed`"**在本章既有通道上可读通**，且**不需要** `mupc-southd` 反向依赖 `mupc-core-bin`（依赖成环问题不存在）。
2. **"三元组承载不了四要素"是过度断言**：`points: Vec<(String, f64, bool)>` 是**可变长**容器，可承载 N 条记录（token / 寄存器可编码进 `metric` 字符串）。原报告以"三元组"否定承载能力，**论据不成立**（真正缺的只是"回读值"没有自然槽位 —— 这恰支持"另立第 5 方法"这一更保守的形态，而非"不可达"）。
3. **"§13.5.3 与 §13.9 直接矛盾"是条件性的**：若审计搭 `on_station_telemetry` 的事件分支走，则 §13.9 的"`StationSink`（4 方法）**无**变化"**并不矛盾**；只有"必须新开方法"的读法才构成矛盾。⇒ 原报告把**读法歧义**升级成了"合同自相矛盾"。

**因此原 P-1 应降级为"合同**欠定义**"（须改级，非阻断级）**：通道可达、但原文缺"编码方式 / token 来源与取值域 / 事件名与字段映射 / 验收判据"。提交方按"补规格"处置（且选了"新增第 5 方法"这一更保守形态）**方向正确**。

**同时须更正原报告的两处措辞**（避免下游误引）：① 原报告"`mupc-southd/src` 内 audit/AlertFeed 零命中"**字面为真但结论误导** —— 该 grep 的零命中**不能**证明"通道不可达"，因为通道的实现方在 `mupc-core-bin`（`SouthSink`）而非 `southd`；② 原报告"P-1 属设计缺陷（主）"的定性应改为"欠定义（主）"。

> ⚠️ 本项裁定**不改变本次复审的结论**：订正文本自身存在新缺陷（§5），见 N-1 / N-2。

### 3.2 分歧 (2)：`hw/_ref_pcs60_proto.txt:1270/1277` 的引用 → **采纳异议（非阻断）**

**裁定：异议成立，判非阻断。** 实测：`:1270` / `:1277` **确为** `1001` / `1002` 的**点号行**（即"条目锚点"），`:1275` / `:1282` 是其**量程行**（`-100~100`）。⇒ 原报告"差 5 行"的定性宜改为"**锚点行与所引字面不在同一行**"，**不构成错误**，提交方"未改"**可接受**。

**保留一句提醒（不要求改）**：该句正文引的是**字面**「逐行明写 `*1Kw` / `*1kvar`、`-100~100`」，这四个字面分别在 `:1274` / `:1281`（`*1Kw`/`*1kvar`）与 `:1275` / `:1282`（`-100~100`）。若希望"读引文即得字面"，可加半句"（字面见 1274/1275、1281/1282）"；**不加也可判通过**，本条**不进阻断清单**。

## 5. 新引入问题的核查（本次判 REJECTED 的直接依据）

### N-1（**阻断**）§13.5.3「回读值来源」行引用了**两个不存在的返回类型**，并据此把影响面写成了"零成本"

**条款**（设计文档第 3446 行）：

> \| **回读值来源** \| **上抛 R-2 已在链路上取得的回显**（`write_single_register_from` → `Result<u16, _>`；`StationBus::write_single` → `Result<u16, BusError>`）⇒ **零额外总线往返**。…

**双证据（实测）**：

- `mupc/crates/rs485-plugin/src/device.rs:1070-1075`：`pub fn write_single_register_from(&self, slave: u8, addr: u16, value: u16) -> Result<(), Rs485Error>` —— **回显被校验后即被丢弃**（函数体的四项逐字比对失败即 `Err`），**从不作为返回值**；全 crate **无任何**返回 `u16` 的写 API（`write_single_register :1060` 亦 `Result<(), _>`）。
- `mupc/crates/mupc-southd/src/port_runtime.rs:92`：`async fn write_single(&self, slave: u8, addr: u16, value: u16) -> Result<(), BusError>`；实现方 `:263`、`:584` 同。

**为什么这是阻断级（而非又一条 P-4b 式的"须改"）**：

1. **它不是"行号漂移"，是"接口事实写反"**：原报告 P-4b 的行号失误不改变"要建什么"；本条把"值**已经**返回 ⇒ 只需上抛（**零改动契约**）"写成前提，而真相是"值**被丢弃** ⇒ 必须改**三层签名**"。照原文实施者会去找一个不存在的 `Result<u16, _>`。
2. **它使 R1 的必需要素失真**：R1 要求"给出可达落点 + 字段定义 + 判据"。判据（第 3450 行 ①/②）与 T5 的"独立可编译 / 独立可回退"**全部建立在这条错误前提上**。
3. **真实影响面被系统性漏报**（这是本次复审题目点名要核的项）。原文只说"上抛两个方法的返回值"，实测"上抛"至少穿过**四层**、影响**至少 9 个实现体**：
   - `rs485_plugin::Rs485Device::write_single_register_from`（公共 API，**改返回类型会连带 `write_single_register` :1060 与全部 `?` 调用点**）；
   - 进而 `Rs485Device` 的响应解析路径（`write_single_register_from` 的校验分支 `device.rs:1075` 起）也要把回显**带出**；
   - `mupc_southd::port_runtime::StationBus::write_single`（trait）+ **全部 4 个实现方**：`Rs485PortBus`（`:263`）、`MockBus`（`:584`）、`LatchOnReadBus`（`pcs/mod.rs:543`）、`SeamBus`（`tests/pcs_e2e.rs:134`）；
   - `mupc_southd::pcs::PcsHandle::write_reg`（`pcs/mod.rs:350-357`，**4 个入口的唯一写漏斗**，返 `Result<(), PcsError>`）—— **§13.5.3 与 §13.10 的 T5 行都未点名**；
   - 才轮到 §13.9 已点名的 `StationSink`。

### N-3（须改）§13.5.3 的验收判据 ①/③ 与**同一笔新增的 O-4 注**及 §13.5.1 的写序**互不自洽**

### N-4（须改）审计投递与 `PcsHandle` 总线锁的**纪律未规定**，与既有不变式冲突

`pcs/mod.rs` 的 4 个入口**全程持锁**（`let _g = self.inner.lock.lock().await;`，如 `:278`、`:320`）；而 `collect.rs:243` 明写既有不变式：

新规格要求"每次写序列一条事件"经 `StationSink` → `record_event`（**落 SQLite + 投递**）。若按最自然的写法在入口内投递，则**在持锁区内做 SQLite I/O**，直接违背上述不变式，且会拖慢联锁 `stop()` 取锁 —— 与本章"安全链优先"的立意相反。规格**未规定**投递时机/位置。

**最小要求**：在 §13.5.3 的规格表加一行"**投递必须在出锁后**：写序列的结果先在栈上累积为 `Vec<PcsWriteRecord>`，释放 `inner.lock` 后一次性 `on_pcs_write_audit(...)`；不得在持锁区 `.await` sink"，并把这句纳入 T5 的判据。
