## 2. 逐项决议

### X-01（中）：ControlCommand 字段命名不一致

**问题描述**：
- 模块 01（通信网关）设计文档定义 `ControlCommand` 使用 `p_set`、`q_set`、`switch_state` 三个字段（定义于 `gateway/src/command.rs`）
- 模块 04（策略引擎）设计文档使用更丰富的字段集：`p_batt_set`、`q_batt_set`、`start_stop`、`phase_compensation`、`pv_limit`、`load_shedding`

**决议**：
以模块 04（策略引擎）的完整 `ControlCommand` 定义为**权威标准**。模块 04 作为本地决策核心，其字段定义覆盖了削峰填谷、需量控制、防逆流三大策略的全部控制维度，语义更精确（`p_batt_set` 明确指向电池有功设定、`pv_limit` 明确指向光伏限制）。模块 01（网关）接收北向调度指令（IEC 104 ASDU 类型 45/46/47）后，需在 `gateway/src/command.rs` 或新增 `gateway/src/command_mapping.rs` 中实现**字段映射转换层**，将调度协议中的通用 `p_set`/`q_set`/`switch_state` 映射为策略引擎的规范字段名。该转换层同时负责遥控选择→遥控执行的时序管理和调度指令优先级校验（本地运维 > 调度主站）。

**影响的模块和文件**：
| 模块 | 文件 | 变更类型 |
|------|------|----------|
| 01-通信网关 | `gateway/src/command.rs` | 新增映射转换函数 |
| 01-通信网关 | `gateway/src/command_mapping.rs`（新建） | IEC 104 ASDU → ControlCommand 映射 |
| 04-策略引擎 | `strategy-engine/src/strategies.rs` | 作为权威定义，不做变更 |
| 01-通信网关 | `docs/superpowers/plans/modules/01-MUPC-通信网关-设计文档.md` | 补充映射说明 |
| device-trait | `device-trait/src/types.rs` | 统一 ControlCommand 结构体定义 |

**实施优先级**：P1（开发过程中解决，非阻塞性）

### X-02（低）：DeviceRegistry 引用 Device vs SouthDevice trait

**问题描述**：
- 模块 01（通信网关）设计文档中 `DeviceRegistry` trait 引用 `Device` trait（`device-trait/src/device.rs`）
- 模块 02（南向通信）设计文档使用 `SouthDevice` trait（`device-trait/src/south_device.rs`）
- 两份设计文档对设备注册表应管理哪种类型的设备抽象存在分歧

**决议**：
统一使用 `SouthDevice` trait 作为 `DeviceRegistry` 的注册单元。`SouthDevice` 是南向设备的统一抽象接口（含 `device_id()`、`device_type()`、`status()`、`connect()`、`disconnect()`、`read()`、`read_batch()`、`write()` 等方法），语义更精确，覆盖 RS485 和 HPLC 两类南向物理通道。`Device` trait（定义于 `device-trait/src/device.rs`）是早期通用性较高的抽象，标记为 `#[deprecated]`，在其 doc comment 中注明迁移指引："请使用 `SouthDevice` trait，详见 `south_device.rs`"。

`DeviceRegistry` 的注册方法签名统一为：
```rust
fn register(&self, device: Arc<dyn SouthDevice>) -> Result<(), RegistryError>;
fn get(&self, device_id: &str) -> Option<Arc<dyn SouthDevice>>;
```

**影响的模块和文件**：
| 模块 | 文件 | 变更类型 |
|------|------|----------|
| 01-通信网关 | `docs/superpowers/plans/modules/01-MUPC-通信网关-设计文档.md` | DeviceRegistry 签名修正 |
| device-trait | `device-trait/src/device.rs` | 标记 deprecated |
| device-trait | `device-trait/src/registry.rs` | 签名修正为 SouthDevice |
| device-trait | `device-trait/src/south_device.rs` | 作为权威定义，不做变更 |

**实施优先级**：P1（开发过程中解决，非阻塞性）

### X-03（低）：FaultRecorder 方法名不一致

**问题描述**：
- PRD（`2026-05-29-MUPC-故障录波完整实现-PRD.md`）设计接口使用 `get_waveform(event_id)` 命名
- 设计文档（`2026-05-29-MUPC-故障录波完整实现-设计文档.md`）中新增扩展方法命名为 `get_waveform_by_id(event_id)`，与 PRD 不一致

**决议**：
统一为 `get_waveform(event_id: i64) -> Result<WaveformData, FaultRecorderError>`。该方法接收 `event_id` 参数，语义自明，无需在方法名中冗余 `by_id`。`FaultRecorder` trait（位于 `data-processing/src/recorder.rs`）中已有的无参 `get_waveform(&self) -> Result<WaveformData, MupcError>` 是 Phase 3A 遗留的占位方法（返回空数据结构），统一后改为带参数版本，同时移除占位方法。

**影响的模块和文件**：

| 03-数据处理 | `data-processing/src/recorder.rs` | FaultRecorder trait 方法名修正 |
| 03-数据处理 | `data-processing/src/fault_recorder_impl.rs` | 实现方法名同步修正 |
| 03-数据处理 | `data-processing/src/waveform/` | 内部调用统一 |
| 03-数据处理 | `docs/superpowers/plans/2026-05-29-MUPC-故障录波完整实现-设计文档.md` | 设计文档方法名修正 |

### X-04（低）：DataReporter 独立 trait vs MessageBus

**问题描述**：
- 模块 01（通信网关）设计中将 `DataReporter` 视为 `MessageBus` 之上的一个概念层，通过 `MessageBus::publish()` 实现数据上报
- 模块 03（数据处理）设计中定义了独立的 `DataReporter` trait（含 `report()` 和 `subscribe()` 方法），与 `MessageBus` trait 并行存在

**决议**：
`DataReporter` **不作为独立 trait 存在**，而是作为 `MessageBus` trait 的上层封装模块。具体方案：`DataReporter` 实现为一个具体的结构体 `DataReporterImpl`，内部持有 `Arc<dyn MessageBus>`，其 `report()` 方法封装 `MessageBus::publish()` 调用并附加遥测数据的 Topic 路由逻辑。模块 03 设计文档中的独立 `DataReporter` trait 定义应予移除，改为描述 `DataReporterImpl` 与 `MessageBus` 的依赖关系。

```rust
// mupc/crates/data-processing/src/reporter.rs
pub struct DataReporterImpl {
    bus: Arc<dyn MessageBus>,
}

impl DataReporterImpl {
    pub fn new(bus: Arc<dyn MessageBus>) -> Self { ... }
    pub async fn report(&self, data: TelemetryData) -> Result<(), DataProcessingError> { ... }
}
```

**影响的模块和文件**：
| 模块 | 文件 | 变更类型 |
|------|------|----------|
| 03-数据处理 | `data-processing/src/reporter.rs` | trait 改为 struct impl |
| 03-数据处理 | `docs/superpowers/plans/modules/03-MUPC-数据处理与存储-设计文档.md` | 移除独立 trait 定义 |
| device-trait | `device-trait/src/message_bus.rs` | MessageBus 作为唯一消息总线 trait |

**实施优先级**：P1（开发过程中解决，非阻塞性）

### X-05（中）：调度指令端到端流转路径未集中描述

**问题描述**：
调度指令从北向网关接收 → 安全校验 → 策略引擎仲裁 → 核间通信下发的完整端到端流转路径，分布在模块 01、04、10 三份设计文档中，没有一份集中文档描述全链路的数据格式转换、校验节点和异常处理流程。

**决议**：
在模块 04（策略引擎）设计文档 `docs/superpowers/plans/modules/04-MUPC-策略引擎-设计文档.md` 的第 1 节"模块架构"中新增 **"1.7 调度指令端到端数据流"** 小节。策略引擎是指令汇聚和仲裁的中心节点，最适合作为全链路描述的锚点文档。模块 01 和模块 10 设计文档中交叉引用此节即可。

该小节至少包含：
1. **端到端时序图**：调度主站(TCP/IEC 104) → gateway 帧解析 → 合规校验(security/policy.rs) → MessageBus → strategy-engine 仲裁 → ControlCommand 构造 → intercore(TCP) → 实时控制模块
2. **各节点的数据格式变化**：IEC 104 ASDU → ControlCommand → intercore JSON payload
3. **异常分支**：校验失败（拒绝并审计）、策略冲突（本地优先）、AI 降级（兜底策略接管）、核间通信不通（重试/告警）
4. **端到端延迟预算**：每段预估延迟和总预算不超过 200ms（含策略决策 <100ms）

**影响的模块和文件**：
| 模块 | 文件 | 变更类型 |
|------|------|----------|
| 04-策略引擎 | `docs/superpowers/plans/modules/04-MUPC-策略引擎-设计文档.md` | 新增 1.7 节 |
| 01-通信网关 | `docs/superpowers/plans/modules/01-MUPC-通信网关-设计文档.md` | 交叉引用 |

### X-06（高）：审计日志存储路径不一致

**问题描述**：
三个模块定义了三种不同的审计日志存储方案：
| 模块 | 方案 | 存储位置 | 格式 |
|------|------|---------|------|
| 06-安全 | JSONL + SM3 哈希完整性链 | `/var/log/mupc/audit/` 目录 | 滚动 JSONL 文件（100MB/个） |
| 08-Web | 独立 SQLite 数据库 | `/var/log/mupc/audit.db` | SQLite 表（仅追加） |
| 09-无线 | 单文件追加 | `/var/log/mupc/audit.log` | 单行 JSON |

**决议**：
统一使用**模块 06（安全）的方案作为权威审计存储架构**：

1. **主存储**：所有模块的审计事件统一写入 `/var/log/mupc/audit/audit_NNNNNN.jsonl`（JSONL 格式，每行一条事件），由 `security::audit::AuditLogger` 统一管理。
2. **完整性保护**：每 5 分钟对当前 JSONL 文件计算 SM3 哈希，追加到鉴证链文件 `audit_chain.json`，确保日志不可篡改。
3. **滚动策略**：单文件上限 100MB，超过则滚动到下一个序号。磁盘低于 200MB 时自动 gzip 归档到 `/var/log/mupc/audit/archive/`。
4. **模块 08（Web）的 SQLite**：改为只读查询索引。`web-api` 启动时或定期（每小时）从 JSONL 目录同步到 `audit.db`（SQLite），仅用于 Web UI 的快速查询和过滤，不作为主存储。由 `web-api/src/audit_index.rs` 实现同步逻辑。
5. **模块 09（无线）的单文件追加**：废弃 `audit.log` 单文件方案，无线运维操作审计通过 `security::AuditLogger` 的公共 API 写入统一 JSONL 存储。同时保留无线通道的独立操作日志（`/var/log/mupc/wireless_operations.log`）用于无线协议调试，但此为运维日志而非安全审计日志。
6. **统一审计 API**：`security::AuditLogger` 暴露 `pub fn log_event(&self, entry: AuditLogEntry) -> Result<(), AuditError>` 供所有模块调用。

**影响的模块和文件**：
| 模块 | 文件 | 变更类型 |
|------|------|----------|
| 06-安全 | `security/src/audit.rs` | 作为权威实现，确认接口不变 |
| 06-安全 | `docs/superpowers/plans/modules/06-MUPC-安全-设计文档.md` | 补充多模块消费说明 |
| 08-Web | `web-api/src/audit_index.rs`（新建） | SQLite 读副本同步逻辑 |
| 08-Web | `docs/superpowers/plans/modules/08-MUPC-Web管理与AI可视化-设计文档.md` | 修改审计存储方案描述 |
| 09-无线 | `wireless/src/` | 移除 audit.log 写入，调用 security::AuditLogger |
| 09-无线 | `docs/superpowers/plans/modules/09-MUPC-本地运维通信-设计文档.md` | 修改审计存储描述 |

**实施优先级**：P0（开发启动前必须解决，阻塞性）

### X-07（高）：核间策略模式信号传输协议不一致

**问题描述**：
- OTA 模块（07）设计中使用独立的 JSON 帧 `{"cmd":"set_strategy_mode","mode":"basic"}` 切换策略模式
- 核间通信模块（10）设计中将 `strategy_mode` 和 `ai_ready` 嵌入 `ControlCmd` 帧（类型编码 `0x0010`）的 payload 中，作为控制指令的上下文字段

**决议**：
策略模式切换**统一通过模块 10（核间通信）的 ControlCmd 帧（类型编码 `0x0010`）**实现。具体方案如下：

1. **帧定义**：ControlCmd 帧 payload（JSON 编码）的顶级字段包含：
   ```json
   {
       "cmd_type": "strategy_mode_switch",
       "strategy_mode": "basic",
       "ai_ready": false,
       "value": null,
       "unit": null,
       "timestamp": 1712345678,
       "seq_no": 42
   }
   ```

2. **cmd_type 枚举扩展**：在现有 `"P_batt_set"` 等指令类型之外，增加 `"strategy_mode_switch"` 类型，用于专用模式切换指令。

3. **OTA 模块适配**：模块 07（OTA）的固件升级前模式切换、升级后恢复，均通过调用 intercore 的 `send_command(ControlCommand { cmd_type: "strategy_mode_switch", ... })` 方法发送 ControlCmd 帧，废弃独立的 `{"cmd":"set_strategy_mode"}` 帧格式。

4. **ai_ready 信号**：`ai_ready` 字段作为 ControlCmd payload 的可选顶级字段（`Option<bool>`），在 `strategy_mode_switch` 指令中必须设置。

5. **StatusReport 帧（`0x0020`）** 中的 `ai_ready` 和 `strategy_mode` 字段保持不变 —— 它们是实时控制模块的定期状态回执，反映实际运行状态，与 ControlCmd 控制信道不冲突。

**影响的模块和文件**：
| 模块 | 文件 | 变更类型 |
|------|------|----------|
| 07-OTA | `ota-update/src/` | 废弃独立模式切换帧，改用 intercore ControlCmd |
| 07-OTA | `docs/superpowers/plans/modules/07-MUPC-OTA与系统可靠性-设计文档.md` | 修改第 8 节核间协同描述 |
| 10-核间通信 | `intercore/src/commands.rs` | cmd_type 枚举增加 `strategy_mode_switch` |
| 10-核间通信 | `intercore/src/frame.rs` | ControlCmd payload 增加 ai_ready 可选字段 |
| 10-核间通信 | `docs/superpowers/plans/modules/10-MUPC-核间通信-设计文档.md` | 确认 ControlCmd 作为唯一模式信号载体 |

**实施优先级**：P0（开发启动前必须解决，阻塞性）

### X-08（中）：Web API 路由版本前缀不统一

**问题描述**：
| 模块 | 当前前缀 | 示例 |
|------|---------|------|
| 06-安全（合规增强） | `/api/v1/` | `/api/v1/security/compliance` |
| 06-安全（安全启动） | `/api/` | `/api/security/boot-status` |
| 07-OTA | `/api/v1/` | `/api/v1/ota/firmware/status` |
| 08-Web | `/api/` | `/api/ai/decision`、`/api/auth/login` |
| 09-无线 | `/api/v1/` | `/api/v1/wireless/status` |

**决议**：
统一使用 `/api/v1/` 前缀。具体方案：

1. **路由中间件统一添加前缀**：`web-api/src/router.rs` 中，所有子路由模块注册时**不带版本前缀**（内部路由用 `/security/`、`/ai/`、`/ota/`、`/wireless/` 等），由 Axum Router 的 `.nest("/api/v1", ...)` 统一包裹。这确保所有 API 端点自动获得一致的版本前缀。

2. **当前例外处理**：
   - `/ws/logs`（WebSocket 日志流）不使用 `/api/v1/`，保持 `/ws/logs` 路径（WebSocket 升级协议与 REST 不同，版本在握手消息中协商）。
   - 安全启动 API 从 `/api/security/boot-status`、`/api/security/boot-log`、`/api/security/health`、`/api/security/integrity-check` 统一迁移至 `/api/v1/security/boot/status`、`/api/v1/security/boot/log`、`/api/v1/security/boot/health`、`/api/v1/security/boot/integrity-check`。

3. **安全模块内部的 `/api/` vs `/api/v1/` 分裂**：安全模块 06 设计文档中安全启动 API 使用 `/api/` 前缀而合规增强 API 使用 `/api/v1/` 前缀，需全部统一为 `/api/v1/`。

### X-09（中）：AiIntegrator 门面多模块依赖粒度

**问题描述**：
- 模块 06（安全）、模块 07（OTA）、模块 08（Web）均依赖 `AiIntegrator`，但调用的方法集合和粒度不一致
- 模块 08（Web）设计文档中列举了 `get_prediction()`、`get_decision()`、`get_reward_history()`、`apply_weight_changes()`、`apply_mode_switch()`、`resume_auto_mode()`、`get_model_versions()` 等 7+ 个方法
- 模块 04（策略引擎）设计文档中 `AiIntegrator` 仅有 4 个核心方法：`new()`、`initialize()`、`get_decision()`、`is_ready()`、`status()`
- 模块 07（OTA）设计文档中未显式引用 AiIntegrator 但需要模式切换能力

**决议**：
`AiIntegrator` 定义在 `strategy-engine/src/ai_integration.rs` 中，对外暴露 **5 个公共方法**作为稳定 API，所有依赖模块统一通过这 5 个方法交互：

| 序号 | 方法签名 | 用途 | 调用方 |
|------|---------|------|--------|
| 1 | `async fn get_decision(&self, state: &SystemState) -> Result<ActionOutput, StrategyError>` | 获取 AI 决策结果 | 策略引擎内部、Web 可视化 |
| 2 | `async fn get_status(&self) -> Result<AiStatusResponse, StrategyError>` | 查询 AI 引擎状态（含场景模式、模型版本、预测曲线摘要、最近奖励值） | Web 可视化、安全合规自检 |
| 3 | `async fn force_mode_switch(&self, target: StrategyMode, reason: &str) -> Result<(), StrategyError>` | 强制切换策略模式（OTA 升级前切 basic、Web 人工干预等） | OTA、Web 专家干预、安全 |
| 4 | `async fn get_model_info(&self) -> Result<ModelInfoSnapshot, StrategyError>` | 获取模型版本清单、A/B 实验状态、模型刷新历史 | Web 模型管理、OTA 模型更新验证 |
| 5 | `async fn register_callback(&self, cb: Arc<dyn AiStatusCallback>) -> Result<(), StrategyError>` | 注册 AI 状态变更回调（用于告警联动、审计记录） | 安全告警、审计日志 |

**边界约束**：

1. **不在 AiIntegrator 公开 API 中的操作由策略引擎内部完成**：
   - `initialize(config)` → 仅在策略引擎启动时调用，不对外暴露
   - `apply_weight_changes()` → 合并入 `force_mode_switch()` 的扩展参数（可选权重覆盖）
   - `get_reward_history()` → 合并入 `get_status()` 返回值中的 `recent_rewards` 字段
   - `get_model_versions()` → 合并入 `get_model_info()`

2. **模块 08（Web）的适配**：Web 后端不再直接调用 `ai-engine::ModelManager` 的任何方法，所有 AI 交互均通过 `AiIntegrator` 的 5 个公共方法完成。Web 模块对 AI 引擎的依赖应声明为 `strategy-engine` 而不是 `ai-engine`。

3. **模块 07（OTA）的适配**：OTA 模块升级前通过 `AiIntegrator::force_mode_switch(StrategyMode::Basic, "firmware_ota")` 触发模式切换，升级后通过 `AiIntegrator::get_status()` 验证 AI 引擎恢复状态。

4. **模块 06（安全）的适配**：安全模块通过 `AiIntegrator::register_callback()` 注册审计回调，记录所有模式切换事件；合规自检通过 `get_status()` 获取 AI 引擎健康状态。

**影响的模块和文件**：
| 模块 | 文件 | 变更类型 |
|------|------|----------|
| 04-策略引擎 | `strategy-engine/src/ai_integration.rs` | 精简公开 API 为 5 个方法 |
| 04-策略引擎 | `docs/superpowers/plans/modules/04-MUPC-策略引擎-设计文档.md` | 更新 AiIntegrator API 定义 |
| 08-Web | `web-api/src/routes/ai/` | 调用路径改为仅通过 AiIntegrator |
| 08-Web | `docs/superpowers/plans/modules/08-MUPC-Web管理与AI可视化-设计文档.md` | 修正 AiIntegrator 调用方设计 |
| 07-OTA | `docs/superpowers/plans/modules/07-MUPC-OTA与系统可靠性-设计文档.md` | 补充 AiIntegrator 集成描述 |
| 06-安全 | `docs/superpowers/plans/modules/06-MUPC-安全-设计文档.md` | 补充回调注册设计 |

**实施优先级**：P1（开发过程中解决，非阻塞性）
