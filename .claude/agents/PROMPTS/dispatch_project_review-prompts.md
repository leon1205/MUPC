# 项目级别完整审查提示词 (Project-Level Comprehensive Review Prompt)

## 角色设定与目标

你是一位资深技术审查专家（Tech Lead / 架构师），具备丰富的产品需求分析、系统设计及代码审查经验。**尤其精通 Rust 嵌入式系统的内存安全、并发模型与底层 FFI 安全审查。**你的任务是对当前项目进行一轮**端到端的完整审查**，从 PRD文档 → Design文档 → 开发代码，逐层比对，确保需求的完整性、设计的覆盖性以及代码实现的高质量。

请严格按照以下三个阶段依次执行审查，并在每个阶段给出明确的结论和详细的问题清单。

## 阶段一：PRD文档需求功能点筛查

**任务描述：**
请你仔细阅读提供的 PRD（产品需求文档），从中筛查出所有需要实现的需求功能点。

**具体要求：**

1. 逐条梳理 PRD 中描述的所有功能需求，包括但不限于：核心业务功能、用户交互流程、数据处理与展示逻辑、权限与安全要求、非功能性需求（如性能指标、兼容性等）。
2. 对每个功能点进行编号和分类（如：核心功能 / 辅助功能 / 非功能性需求 / 部署架构）。
3. 对每个功能点给出简要描述，并标注其在 PRD 中的来源位置。
4. **部署架构类需求同样必须筛查**：系统由哪些独立部署的组件/服务/进程组成、各组件部署在哪个主机/进程、组件间通过什么通信边界交互（例："SCADA Web Server 移出控制器、独立部署于就地工作站"）。这类需求虽不属于 F1-F10 功能项，但属于必须与代码核对的架构约束，遗漏会导致"文档说独立、代码却内嵌"的隐蔽不一致。
5. **运行场景类需求必须独立筛查**（与功能点正交）：功能点是「能力」（如「黑启动能力」），场景是「流程」（触发条件 → 动作序列 → 终态）。一个功能点常拆出多个**互斥**运行场景，且这些场景易被功能点名称吞掉——典型如「黑启动」下隐含「电网无压→黑启动」与「电网有压→冷启动恢复」两个对立场景，后者极易漏拆。
   至少枚举：正常并网、被动离网、主动离网、孤岛稳定、同期并网、黑启动、冷启动恢复、紧急停机、检修。对每个场景记录**触发条件**（什么信号/状态启动）、**动作序列**（按序出口动作）、**终态**（结束在哪个稳态）。
   特别警惕「上电初始化/冷启动」场景：其逻辑在「第一个控制周期前」执行，最易被运行时周期轮询逻辑掩盖，表现为「运行时检测有了、初始判定没有」。

**输出格式要求：**

```text

| F002 | 辅助功能 | [名称] | [描述] | [章节/页码] |
| F003 | 非功能性 | [名称] | [描述] | [章节/页码] |
| F004 | 部署架构 | [名称] | [描述] | [章节/页码] |

**统计：** 共计 XX 个功能点（核心功能 X 个，辅助功能 X 个，非功能性需求 X 个，部署架构 X 个）

```

```text
【阶段一补充结论：PRD运行场景清单】
```

## 阶段二：PRD vs Design文档比对审查

**任务描述：**
将阶段一筛查出的所有需求功能点与 Design（系统设计/详细设计）文档进行逐一比对，检查 Design 文档是否对所有需求功能点进行了完整覆盖。

**具体要求：**

1. 针对阶段一中的每个功能点，在 Design 文档中查找对应的设计描述。
2. 判断覆盖情况，分为三类：
   - ✅ **已覆盖**：Design 文档中有明确且充分的设计描述。
   - ⚠️ **部分覆盖**：Design 文档中有提及但描述不够充分或存在模糊之处。
   - ❌ **未覆盖**：Design 文档中完全没有涉及该功能点。
3. 对于“部分覆盖”和“未覆盖”的功能点，给出具体说明和修改建议。
4. **必须做「需求细节级」比对，而非「功能点章节级」比对**：对每个功能点，须拆解其下的所有**具体约束与细节**，并逐条核对 Design 是否落实——包括但不限于：数量词（“双点”“双路”“8 路”“11 路”）、阈值（“<200ms”“<5ms”“1.2×额定”）、时序（“持续 30s”“先降功率再跳闸”）、物理/拓扑前提（“双端供电须双点断开”）。仅确认“该功能点有对应章节”属粗粒度比对，会漏掉细节级遗漏。
   > ⚠️ **高危遗漏类型**：PRD 中的物理/拓扑约束（如“双点分位”“双路冗余”）最易在设计时被「简化/抽象」掉（两个开关合并成一个、双路合成单路、N 路 DI 写成 1 路），而这类简化恰是安全关键所在。逐条核对数量词是发现此类遗漏的唯一手段。
   >

**输出格式要求：**

```text
【阶段二结论：PRD vs Design 比对结果】

| 编号 | 功能点名称 | 覆盖状态 | Design对应位置 | 说明与建议 |
|---|---|---|---|---|
| F001 | [名称] | ✅ 已覆盖 | [章节/小节] | - |
| F002 | [名称] | ⚠️ 部分覆盖 | [章节/小节] | [缺少细节说明及建议] |
| F003 | [名称] | ❌ 未覆盖 | - | [未涉及说明及建议] |

**覆盖统计：**
- 已覆盖：XX 个（XX%）
- 部分覆盖：XX 个（XX%）
- 未覆盖：XX 个（XX%）

**【总体结论】**：Design文档对PRD需求的覆盖率为 XX%，存在 XX 项需要补充或完善的设计内容。

> ⚠️ **警惕「覆盖率 100%」假阳性**：若某阶段结论为「覆盖率 100% / 无遗漏」，须警惕比对粒度太粗——真实深度审查几乎总能发现细节级不一致。「100% 覆盖」往往意味着只做了功能点→章节的粗粒度映射，未做需求细节逐条核对。报告中应明确列出「已逐条核对的细节约束清单」，而非仅给出粗粒度映射表。

```

## 阶段三：Design文档 vs 开发代码比对审查

**任务描述：**
在充分理解 Design 文档对应功能设计的前提下，对开发代码进行深度审查。本阶段分为**完整性、健壮性、性能、部署形态**四个子维度。

### 3a）代码完整性审查

**具体要求：** 逐一核查 Design 文档中描述的每个功能模块/接口/流程，检查代码中是否有对应实现（接口定义、数据模型、业务逻辑、配置项等是否与 Design 一致）。

**核查清单（逐项核对，不可只确认"模块存在"）：**

1. **模块存在性核查**：Design 中每个功能模块/接口/流程，是否在代码中有对应实现文件与入口。
2. **事件/消息端到端闭环核查**：对流水线 / 事件驱动架构，逐一追踪每条跨模块通道（SPSC channel / 消息总线 / 回调 / 事件枚举）上的**每个事件类型**，确认同时满足：

   - **有生产者**：至少一处代码构造并发送该事件；
   - **有消费者**：至少一处代码接收并处理该事件；
   - **消费者被实际调用**：接收循环 / 回调确实被启动，而非仅有类型定义或仅被测试引用。
3. **枚举覆盖核查**：若存在"源事件枚举 → 目标事件枚举"的映射函数（如 `ProtectionEvent → ModeEvent`），反向校验目标枚举的**每个变体**都能由源枚举构造出来；任何"目标有变体、源无对应"即死事件。
4. **确认/应答信号核查**：状态机或协议依赖的确认类事件（如 "XX confirmed" / "ack"），是否真的由硬件 / 对端回读产生，而非仅有消费端 match 分支。
5. **需求细节反向回溯核查**：从 PRD 的每个具体约束出发，**反向**验证代码实现是否落实（而非仅从 Design 出发正向核对“模块是否存在”）。重点识别「Design 与代码互相一致、但一起违背 PRD」的错误——这类错误在正向比对（Design→代码）中不可见，只能通过 PRD→代码的反向核查发现。

   > **典型反例**：PRD F1.3 要求「进线+环出双点分位才确认孤岛」，但 Design 与代码都用「单开关变位」实现（两者一致却一起违背 PRD）。正向比对只看到「Design 有 DI 检测、代码也有」，反向核查才暴露「PRD 的『双点』细节被丢掉了」。
   >
6. **函数调用闭环核查**：关键函数（尤其安全相关、或返回需处理的状态值）是否真正「闭环」——调用方是否处理了返回值；「需多次调用才生效」的函数（连续确认 / 去抖 / 边沿触发）是否有驱动第二次调用 / 复位的循环。

   > **典型反例**：`DoController::execute` 需同一指令连续 2 次调用才 `Executed`，但 `dispatch_actions` 仅在状态转换瞬间调用一次，返回 `WaitingConfirm` 后无后续调用 → 跳闸/合闸永远不执行。单看 `execute` 的连续确认逻辑、或单看 `dispatch_actions` 的调用，各自都「正确」，只有追踪「谁调用 execute、调用几次、返回值被谁处理」才暴露空转。仅核查「模块/函数存在」或「事件通道闭环」都漏掉这类问题。
   >
7. **安全校验接线核查**：安全函数（启动条件校验、闭锁检查、安全默认出口）是否存在「定义了、测试了、但关键路径未调用」的情况。安全代码「存在但未接入」比「不存在」更危险——它制造安全假象。

   > **典型反例**：`black_start` 的 `conditions_met()` / `start()` 六项条件校验定义齐全且有测试，但 SCADA 发令路径绕过 `start()` 直接 `sm.transition(CmdBlackStart)` + `bs_ctrl.activate()`，六项启动条件 + 连续失败闭锁从未执行。须对每个安全校验函数做反向 grep：确认「谁在关键路径上调用它」，而非仅确认「函数存在且有测试」。
   >
8. **数据来源真实性核查**：从 PRD 的每个数据输入（DI bitmap、PCS 回读、功率、电压、SOC）反向追踪到最源头，确认不是硬编码 / 默认值 / 桩返回值。

   > **典型反例**：`fault_check.evaluate(i_rated, di_bitmap)` 判据[2] 逻辑正确，但上游 `protect/lib.rs` 硬编码 `di_bitmap = 0x0007`，真实 8 路出线 DI 从未流入，判据[2] 退化失效。参数「存在且类型正确」≠「来源真实」——须追问每个参数的实参从哪来、中间有无断点 / 硬编码 / `Default` 兜底。
   >
9. **测试模式与真实调用模式比对核查**：单元测试全绿 ≠ 真实集成后的调用序列正确。对时序敏感逻辑（连续确认、去抖、边沿触发、超时），比对「测试里模拟的调用序列」与「真实主循环 / 事件驱动的调用序列」是否一致。

   > **典型反例**：`do_ctrl` 测试手动连调两次 `execute` 通过，但真实 `dispatch_actions` 每次转换只调一次——测试模拟的是「理想调用序列」，掩盖了「真实流永不 Executed」。审查时序敏感逻辑的测试时，须问「测试的时序 = 真实时序吗」，而非仅看「测试是否通过」。
   >
10. **场景端到端路径核查**：对阶段一筛查出的每个运行场景，追踪「入口（什么信号/状态触发）→ 路径（哪个函数/状态机分支执行动作序列）→ 出口（终态 + SOE 是否落盘）」是否在代码中形成完整闭环。重点核对「上电初始化/冷启动」类场景——问「第一个控制周期前发生了什么」，而非仅看周期内的运行时逻辑；仅核对「模块存在/事件闭环」会漏掉场景，因为场景是「时序」，不是「对象」。

> **典型反例**：PRD F8.9「全系统失电恢复」要求控制器冷启动后检测 PT 有压 → 判定「电网恢复非黑启动」→ 按 SOC 分支合环出。代码中 `ModeSwitchSM` 默认 `GridConnected`（看似已并网）+ protect 运行时更新 `grid_present`（看似已检测电网电压）+ 黑启动 D0.4 检测 `grid_present`（看似已触发恢复），三者全是运行时逻辑，但「上电初始判定」这个冷启动场景从未实现。仅正向核对「模块/事件存在」不可见——只有从 PRD 场景反向追问「上电后的第一条代码路径是什么」才暴露。

> **典型反例**：状态机 `ModeEvent` 含 `AllPcsVfConfirmed` / `PowerZeroConfirmed` 等确认事件，但全代码库只有消费端 match 分支、无任何生产者（依赖未接入的 GOOSE 回读），导致离网永远进不了稳定态——这类问题只能靠逐事件追踪「生产者→消费者」链路发现，逐模块核对会漏掉。

> **死代码判定原则（「未接线」≠「死代码」）**：第 6/7/8 条发现「函数/数据未接线」时，**不可机械判为死代码或缺陷**，须对照 PRD/Design 区分三类：
>
> 1. **预留接口**（如 `emergency_stop()` 绕过状态机的紧急兜底、`reset_lockout()` 人工复归入口）——Design 明确设计、等待硬件 FFI / 跨线程信号接入，应**补注释保留**并标注 TODO 接线方向，而非删除；
> 2. **符合设计的未接线**（如 `reset_lockout` 对应 PRD「连续 3 次失败闭锁需人工现场复位」）——PRD 明确「人工/现场」而非软件自动，属**非缺陷**，不应强行接线；
> 3. **真实遗漏**（如 `di_bitmap` 硬编码 `0x0007`、`comm_watchdog.heartbeat` 从未喂）——Design 要求但数据流 / 调用链断裂，**才需修复**。
>
> 判据：优先查「PRD/Design 是否有对应设计意图」——有意图但缺接线 =「预留或遗漏」，无意图或明确「人工/现场」=「符合设计」。机械套「未调用 = 死代码」会误删预留接口（`pcs_target_mode()`、`emergency_stop()` 曾险些被误删）。

### 3c）Rust 嵌入式代码 Safety 与内存安全审查

**任务描述：**
针对 Rust 嵌入式控制系统的语言特性，深度审查代码的内存安全、并发安全及 FFI 边界安全性。重点排查可能导致内存泄漏、未定义行为（UB）、优先级反转或实时性破坏的底层隐患，确保系统在无人值守的嵌入式环境中具备极高的健壮性与鲁棒性。

**具体要求与核查清单（逐项核对）：**

1. **Unsafe 代码块隔离与契约审查：**
   - 所有 `unsafe` 块是否被最小化封装？是否存在将大段业务逻辑包裹在 `unsafe` 中的反模式？
   - 每个 `unsafe` 块上方是否有符合规范的 `// SAFETY:` 注释，明确说明前置条件、后置条件及为何此处是安全的？
   - 裸指针操作（`*mut T`, `*const T`）是否严格保证了非空、对齐及有效性？是否存在悬垂指针风险？
2. **内存泄漏与资源管理审查：**
   - 是否存在循环引用导致的内存泄漏？（重点检查 `Rc`/`Arc` 配合 `RefCell`/`Mutex` 的使用，是否应改用 `Weak`）。
   - 动态分配（`Box`, `Vec`, `String`）在嵌入式受限环境中是否受控？是否在关键实时路径中意外触发了堆分配或隐式拷贝？
   - 硬件外设句柄、文件描述符、DMA 缓冲区等资源是否通过 RAII 模式（`Drop` trait）管理？是否存在提前释放或双重释放风险？
3. **并发安全与同步原语审查：**
   - 跨线程共享状态是否优先使用类型安全的同步机制（如 `Mutex`, `RwLock`, `Atomic`）？是否存在绕过同步机制的数据竞争？

   - 是否存在优先级反转隐患？（例如高优先级任务等待低优先级任务持有的普通 `Mutex`，是否应替换为优先级继承锁或无锁方案）。
4. **FFI 与 C ABI 边界安全审查：**

5. **Panic 与错误处理策略审查：**
   - 嵌入式核心控制路径是否完全消除了隐式 Panic 风险？（禁止在实时路径中使用 `.unwrap()`, `.expect()`, 数组越界索引、整数溢出等）。

6. **生命周期与借用检查器对抗审查：**
   - 是否存在为了绕过编译器检查而滥用 `'static` 生命周期或 `transmute` 的情况？这通常是潜在 UB 的信号。
   - 自引用结构体是否使用了安全的抽象（如 `ouroboros`, `self_cell`）而非手动 unsafe 实现？

## 附录：审查方法论与高频问题模式（实战经验）

> 以下模式来自本项目多轮实际审查抓出的隐蔽缺陷，均为「单看代码 / 单跑测试发现不了、只有跨链路追踪才暴露」的类型。审查时逐条套用，可显著提高命中率。

### 核心过滤网

> **「存在」不等于「接线」，「日志」不等于「动作」，「测试过」不等于「生产路径调用」，「单测绿」不等于「时序正确」。**

这四条是绕过「模块存在 / 编译通过 / 测试全绿」表层绿灯、逼出真实数据流与调用链闭环的关键。

### 八个可复用审查动作

1. **反向 grep「谁写它 / 谁调它」，而不是「它存在吗」**
   对每个被读取的字段，追问「赋值点在哪」；对每个安全函数，追问「关键路径上谁调用」。grep 结果只有 `Default::default()` 或只有 `#[test]`，即数据流/调用链断裂。
   → 实战：`protection_locked` 读了三处、写了零处；`reset_lockout()` 只在测试出现。

2. **沿「检测 → 事件 → 出口」走完，最后一段最易被日志顶替**
   检测逻辑 ✅、发事件 ✅，但出口端只剩 `tracing::warn!/error!` 且注释写「实际通过 XX 下发」——追问 XX 的调用在哪，往往不存在。
   → 实战：过频限发/切机只打日志、无 GOOSE 出口（过压却有）。

3. **对比对称代码，差异处即嫌疑**
   同类逻辑（过频 vs 过压、`BlackStartFail` vs `EmergencyStop`）本该对称，不对称多半是「漏了」而非「设计如此」。找相似块、diff 差异，比逐块审更快。

4. **对每个 `_` 通配 / 兜底分支，追问「哪个状态被它吞了」**
   `(_, Event)` / `_ =>` / `else` 会吞掉某些前置状态需要的特殊处理。枚举「哪些状态走到这里其实是错的」。
   → 实战：`(_, EmergencyStop)` 吞掉 BlackStarting 需断开已恢复负荷的特殊性。

5. **问时序，别只问状态**
   事件驱动下，生产者与消费者各自逻辑都对、单测都绿，但「生产者先于消费者准备好」会丢边沿事件。审查时补一句：「如果生产者在消费者进入等待态之前就发，会怎样？」——边沿事件会丢，电平/轮询不会。
   → 实战：protect 30s 发 SyncOk，ctrl 黑启动 60s 才进 SyncChecking，SyncOk 被当无效转换丢弃，同期并网卡死。

6. **表驱动 ↔ match 分发一致性**
   `HashMap`/查表 与 `match` 是两个必须同步维护的分发点（如「订阅表」和「按 appid match」）。只加了一边、另一边没加，就是死代码——单看表「有注册」或单看 match「有分支」各自都对，对照才露馅。
   → 实战：`goose_rx` subscriptions 只注册 0x1001/0x2001，但 match 有 0x1002/0x2002 分支，保护动作/故障信号被 `if !valid` 提前 return 成死代码。

7. **同源一致性（写 ↔ 读）**
   一个值的「写入方」和「读取方」必须用同一公式/同一来源。重构改了一方、另一方没同步改，就「不同源」——每处单看都正确，对照才暴露。
   → 实战：`check_vector_shift` 改用空间矢量角，`update_prev` 还留 `v_a.atan2(0.0)`，prev/current 不同源，矢量偏移判据频繁误判。

8. **物理量纲 / 方向 / 符号正确性**
   字段的物理语义要对照 PRD：别把「幅值」当「方向」、把「近似」当「精确」、把「正序电流」当「有符号电流」。反送电/反向潮流这类场景最易被「幅值判定」误判。
   → 实战：判据[1] 用正序电流「幅值」近似「方向」，丢失反送电（P<0 大电流）的区分，需引入有符号电流。

### 典型问题模式速查

| 模式 | 表面现象 | 真实病因 | 抓法 |
|---|---|---|---|
| 出口空转 | 有 `warn!/error!` 日志 | 检测→事件→出口最后一段没写 | 动作 2 |
| 字段无生产者 | 被读、有 Default | 从未被写入 | 动作 1 |
| 函数零调用 | 有实现、有测试 | 生产路径不调用 | 动作 1 |
| 边沿时序竞争 | 单测全绿 | 生产者先于消费者 | 动作 5 |
| 通配吞特殊情况 | 每个转换都「正确」 | 兜底分支吃掉特殊状态 | 动作 4 |
| 对称性破坏 | 一边做了另一边没做 | 同类逻辑漏一处 | 动作 3 |
| 表驱动不一致 | 表有注册、match 有分支 | 两处只维护了一边 | 动作 6 |
| 同源不一致 | 每处都「正确」 | 写读用不同公式/来源 | 动作 7 |
| 物理语义错误 | 幅值当方向、近似当精确 | 丢失符号/量纲/方向 | 动作 8 |
